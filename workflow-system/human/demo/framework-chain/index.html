01 / HIERARCHY

Three layers, one implementation boundary

Project and Wave are dispatchers, not implementers. Only Task performs the assigned work; every layer receives a deliberately small context.

  1. Owns goal, checklist, preflight, priority selection, gate decisions, reinforcement, checkpoints, and human reporting.

    Must not: implement delegated output, run delegated checks, or substitute a score for evidence.

  2. Validates dependencies and disjoint ownership, dispatches up to five Tasks, checks conflicts, and aggregates item-level evidence.

    Must not: perform Task work, alter Task artifacts, or mark checklist items complete.

  3. Implements one atomic assignment, modifies only owned files, self-verifies, and returns a lean StatusReport with observable evidence.

    Must not: spawn agents, self-award a score, mark checklist items complete, or exceed ownership.

P1 · Dispatcher-not-implementer Dispatch moves Project → Wave → Task. Evidence returns Task → Wave → Project. Escalation continues upward to the human.

02 / ROUNDS

From intent to archive

The seed shapes a checklist; the sole runtime advances only through bounded, evidence-backed round decisions.

  1. 01

    Select a seed

    L0 maps user intent to registered decomposition knowledge with TemplateRegistry.load_seed(name), then loads the change-driven runtime. Seed labels remain provenance, not a schedule.

  2. 02

    Anchor the contract

    The user confirms goal.md, checklist.md, and preflight.md: assertions, P0/P1/P2 priorities, dependencies, ownership, verification recipes, and execution authorization.

  3. 03

    Select the next round

    L0 orders open work by reverted blockers → P0 → P1 → P2 → satisfied dependencies → stable checklist order. The selection is finite and recorded.

  4. 04

    Partition and dispatch Wave work

    L0 partitions the selection into no more than seven Waves. L1 validates each Wave and dispatches no more than five pairwise-disjoint Tasks.

  5. 05

    Converge inside each Task

    L2 runs a declared implement → review → fix → re-review loop within max_iterations, then stops with success, concerns, or escalation. It never continues indefinitely.

  6. 06

    Return evidence, not self-certification

    Task emits item-keyed checks and artifacts; Wave preserves exact command and metric facts, checks conflicts, and submits an evidence proposal to Project.

  7. 07

    Apply the L0 evidence gate

    Project verifies every selected item, configured checks, reinforcement closure, zero blockers, and zero unresolved ownership or interface conflicts before a round can PASS.

  8. 08

    Reinforce or checkpoint

    FAIL produces up to five severity-filtered reinforcement rules for the next bounded round. PASS creates a convergence_round_complete checkpoint and selects remaining work.

  9. 09

    Archive only a complete change

    After every checklist item is checked, evidence and preflight references validate, mergeability passes, and release-readiness is sufficient, L0 may archive the change and propose source-of-truth updates.

04 / GATE

What decides PASS

Round completion and release readiness are related decisions with different evidence obligations.

Round PASS
All selected checklist items have valid evidence and passing configured checks; reinforcement is accounted for; there are zero blockers and no unresolved ownership or interface conflicts.
Composite signal
The composite is recorded as trend context during rounds and used for release-readiness at archive. It never replaces item evidence, checks, or blocker closure.
A failed round has a ceiling. L0 carries actionable findings forward as reinforcement. When max rounds are reached or progress stagnates, execution escalates upward instead of continuing autonomously.
