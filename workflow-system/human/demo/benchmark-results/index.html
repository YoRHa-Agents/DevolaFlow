Evidence inputs

The evaluator combines an append-only ledger, deterministic fixtures, and bounded repository-local signals. Model probes are optional.

Telemetry ledger

.local/telemetry/harness.jsonl

Dispatch records supply measured token budgets, constraint tiers, rounds, changes, and model-profile references.

Deterministic fixtures

tests/fixtures/harness/

Validated fixtures make contract checks repeatable. A model probe accepts at most ten fixtures.

Repository-local signals

--repo . --base HEAD~1

Bounded local checks cover lint, formatting, tests, coverage, layout invariants, compatibility, test growth, and docstrings.

Optional bounded probe

python -m devolaflow.harness probe

An explicit provider/model pair—or a configured model table—can test model compliance. Missing credentials produce SKIPPED_NO_KEY, never invented evidence.

Evaluation pipeline

One built-in path preserves the evidence boundary from input to decision.

  1. Record Append dispatch telemetry without mutating the dispatch.
  2. Aggregate Validate and summarize ledger records and settled baseline context.
  3. Collect Run bounded local probes and preserve unavailable signals explicitly.
  4. Evaluate Score the six W-3 dimensions and calculate the weighted composite.
  5. Decide Emit READY, NOT_READY, or INSUFFICIENT with suggestions and evidence.

Run the evaluator

The command reads local evidence and writes deterministic JSON. It has no external evaluator dependency.

python -m devolaflow.harness evaluate \
  --ledger .local/telemetry/harness.jsonl \
  --repo . \
  --base HEAD~1 \
  --output .local/research/v17.0.0_harness_evaluation.json

Run an optional bounded probe

This deterministic mock example keeps the fixture, token, and timeout bounds visible. Choose an approved provider and model only when model evidence is required.

python -m devolaflow.harness probe \
  --provider mock \
  --model harness-demo \
  --cycle v17.0.0 \
  --fixtures tests/fixtures/harness \
  --max-tokens 512 \
  --timeout 30

Six W-3 dimensions

The composite is a weighted release-readiness output, not a replacement for underlying evidence.

0.20

Code quality

Code hygiene and coverage.

0.20

Architecture rationality

Layout invariants and constraint quantifiability.

0.20

Test adequacy

Test execution, coverage, and bounded test growth.

0.15

Maintainability

Formatting hygiene and docstring coverage.

0.10

Compatibility

Layout witnesses and compatibility-suite results.

0.15

Performance impact

Token-budget compliance and p95 token headroom.

Explicit outcomes

Availability and threshold checks remain visible in the machine-readable result.

READY

All required machine subcomponents are available and the configured readiness threshold is met.

NOT_READY

Evidence is available, but the composite is below the configured threshold. Iterate or escalate.

INSUFFICIENT

At least one required machine subcomponent is unavailable. Prose or estimates cannot turn this into a pass.

Historical release reference

The v17.0.0 release record reports a W-3 composite of 9.84 and READY. This is archived release evidence, not live telemetry from this page.

Approval-only proposals

Evaluation suggestions may inform a tuning proposal, but they never authorize mutation.

evaluate emits evidence and suggestions → propose creates an immutable candidate → apply requires both the proposal and an explicit approval artifact.

No approval, no change. An unapproved proposal produces byte-zero parameter changes.
