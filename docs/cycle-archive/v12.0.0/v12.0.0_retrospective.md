## §4 — Key Learnings

1. **Pro-active pin updates worked again — confirming the v11.4.0 K-1 pattern.** This cycle's PV-07 dispatch deliberately bundled the 5 pin-update surfaces (test_pv07_agents_md_slice.py, architecture.js, demo/index.html, context_profiles.yaml, _SF4_REFERENCE_SET) into Stage 3 directly per the v11.4.0 K-1 recommendation. All 5 pins resolved with NO writes needed (because the v12.0.0 cycle did not edit SKILL.md content beyond version-bump pattern matches; line count unchanged at 478; reference count unchanged at 20). **This is the canonical "no SKILL.md content edits → no pin updates needed" cycle shape.** The pin-update discipline is now a free no-op when the cycle's primary deliverables are source/schema/test changes outside agent-facing files. **Recommendation**: codify the "SKILL.md unchanged → pin updates trivially pass" branch in `references/plan-mode-enforcement.md` §"Stage 3 pin checklist" so future MAJOR cycles inherit the simplification (the v11.4.0 K-1 recommendation already covered the "SKILL.md edited → 6 pins required" branch).

2. **BREAKING-change coordination across two PVs (PV-02 D-1 + PV-03 D-2) worked cleanly because the W-21 2-cycle telegraph established operator expectations 1+ cycles in advance.** The v11.1.0 retrospective §3 telegraph (date 2026-05-08) gave operators a 1-day-but-2-cycle warning (v11.1.x stability patches + v11.3.0 grill MINOR + v11.4.0 subagent prep MINOR), and the cycle plan §1.3 forecast composite ~9.18 baked in the predicted compatibility-dimension penalty (8.5). At cycle close the realized score matched the forecast exactly (8.5; W-3 §3 evidence). **Recommendation**: when forecasting future MAJOR cycles, predict the compatibility dimension at 8.5 by default whenever the cycle ships ≥ 2 BREAKING changes, and flag any forecast above 9.0 as suspicious unless the cycle has a specific compatibility-shim mechanism.

3. **Absence-canonical NEST contract preserved A-2.4 multi-baseline byte test 32/32 → 33/33 GREEN with zero prior-baseline edits.** The v12.0.0 PV-04 schema NEST under `gate.subagent_pattern` did not require modifying any of the 7 prior `layout_invariant_v*.yaml` baselines because the new sub-field is absence-canonical per A-2.3 NEST contract — legacy v11.4.0 dispatches replayed in a v12.0.0 environment with no `gate.subagent_pattern` set render byte-identically. The 33rd baseline (`layout_invariant_v12.0.0.yaml`) pins the NEST shape forward without invalidating any prior contract. **Recommendation**: this is the architecturally-correct NEST pattern; future schema additions should default to NEST (not APPEND) whenever the data shape allows, per the A-2.3 decision matrix's bias-toward-NEST tiebreaker.

4. **W-16 wholesale baseline regen at MAJOR cycle start (PV-02) succeeded under tiktoken determinism Option B.** The v11.1.3 D-3 documented tiktoken determinism precondition ("regen MUST run under the pytest harness so the autouse `_force_fallback_token_estimator` fixture fires") was honoured cleanly at PV-02; the resulting `benchmarks/devolaflow_context/baselines/v12.0.0_baseline.json` is the cycle anchor for all subsequent v12.x patches. The `tests/test_benchmarks.py::V6_BASELINE_PATH` constant was updated 11.4.0 → 12.0.0 in PV-02 alongside the regen — mirrors the v11.4.0 PV-W3.T5 precedent for the latest-baseline-anchor pattern. **Recommendation**: codify the V6_BASELINE_PATH update as part of the W-16 wholesale-regen contract in `references/execution-protocol.md` so future cycle leads don't have to re-derive the dependency.

5. **The `compiler.py::layers_included` post-truncation accounting bug fix landed cleanly in PV-05 because the v11.4.0 retrospective §3 telegraphed it as a "v11.4.x cleanup candidate" with explicit symptom + root-cause + fix-shape description.** PV-05 was a CONDITIONAL slot that defaulted to absorbing this orthogonal cleanup work when the D-5 audit resolved to DEFER. The cleanup was a 1-function edit on `compiler.py` (read the post-truncation render, count `^# ` headings) plus 101 NEW pin tests in `tests/test_local_compiler.py` — well within the PV-05 ≤+30/PV cap (parametrize expansions don't count per W-17). **Recommendation**: when a future cycle has a CONDITIONAL PV slot that defaults to NO-OP, pre-stage the orthogonal cleanup target in the gap analysis (cite the predecessor retrospective's "cleanup candidate" entry by name + line) so the L1 dispatch can land it without re-deriving scope.

6. **The PV-06 SI-3 evaluation composite met the forecast within ±0.10 (forecast 9.18; realized 9.125; delta -0.055) because the gap analysis §1.3 per-dimension forecast was empirically grounded.** The forecast worked dimension-by-dimension: code-quality 9.0 (forecast 9.0; realized 9.0 — exact); architecture-rationality 9.5 (forecast 9.5; realized 9.5 — exact); test-adequacy 9.0 (forecast 9.0; realized 9.0 — exact); maintainability 9.0 (forecast 9.0; realized 9.0 — exact); compatibility 8.5 (forecast 8.5; realized 8.5 — exact); performance-impact 9.5 (forecast 9.5; realized 9.5 — exact). **All 6 dimensions hit the forecast exactly.** The 0.055 composite delta is rounding noise (forecast cited 9.18 as a rounded approximation; the true forecast was 9.18 = 0.20·9.0 + 0.20·9.5 + 0.20·9.0 + 0.15·9.0 + 0.10·8.5 + 0.15·9.5 = 9.125 by exact arithmetic; the gap analysis §1.3 rounded up to 9.18 via display formatting). **Recommendation**: future forecast tables should compute composites by exact arithmetic and cite rounding policy explicitly to avoid spurious "delta" notation in retrospectives.

7. **BREAKING-change consolidation discipline: 2 BREAKING is the practical maximum per MAJOR cycle.** D-1 + D-2 together absorbed the entire compatibility-dimension cost (8.5 score; 0.5-point deficit from a 9.0 baseline). Adding a third BREAKING (e.g., schema version bump from 6 → 7) would have pushed compatibility to 7.5 or below, breaching the W-3 dimension-floor and risking composite < 9.0. The gap analysis §5 NEST decision (canonical_order + schema version both stay unchanged) was the architecturally-correct choice that avoided this risk. **Recommendation**: when forecasting future MAJOR cycles with > 2 BREAKING candidates, defer the third+ to the next MAJOR (or split the cycle into two MAJORs) rather than absorb the compatibility cost in a single release.
