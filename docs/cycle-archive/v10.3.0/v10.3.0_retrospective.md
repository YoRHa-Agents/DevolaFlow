## §4 — Key learnings (process improvements for next cycle, MUST be ≥5 numbered items)

1. **Adapter approach was load-bearing.** PV-03's `nines_to_sichip_eval_adapter.py` was the cycle's single highest-leverage artifact. Without it, R-1 fires and the cycle ships re-deferred (mirroring v9.5.0 → v10.2.0 cadence). Future cycles facing similar "two-tool format mismatch" should prototype the adapter EARLY (PV-01 ideally) so downstream PVs depend on a known APPROVE/REJECT outcome rather than running PV-04+ in fallback mode with deterministic D-P-* / D-N-3 fixes only.

2. **Bridge defect surfaced ONLY at end-to-end dogfood.** The PV-04 bridge fix in `MetricsReport.from_yaml_dict` (MVP-8 nested-key support) was invisible to PV-02's unit tests because those tests used hand-crafted fixtures matching the legacy top-level shape. The fixtures passed; the real Si-Chip MVP-8 output was nested under `metrics.task_quality.*` and `summary.*`. **Lesson:** end-to-end tests against real plugin outputs (Si-Chip's actual aggregate_eval.py emit shape) catch defects unit fixtures cannot. Future cycles integrating an upstream tool should ship at least one fixture *captured from* the upstream tool's real output, not synthesised from spec docs.

3. **W-8 stagnation predicate is round-LEVEL not per-file.** The +0.9 global delta correctly triggered CONTINUE because it's the canonical round-level value. Per-file marginal decomposition is HIGHER-risk territory (each per-file probe is its own dogfood run; the cumulative time blows out 6 PVs). The v10.4.0 governance should formalize the boundary in a Workflow-rule note (or ADR) so future cycles don't accidentally interpret W-8 as per-file.

4. **Per-PV CHANGELOG ceremony adds discipline but inflates dispatch overhead.** Each PV's W-18 ghost-audit refresh + CHANGELOG entry + canonical-7 sync adds ~10 min subagent overhead. For v10.4.0, consider:
   * Batching PATCH-level CHANGELOG entries under a single MINOR-cycle-close header (the v10.0.0 retrospective §3.6 noted this as a Q5=B ceiling, not a floor).
   * Formalizing a PV-cadence template that script-generates the W-18 ghost-audit boilerplate + CHANGELOG entry skeleton from a small per-PV YAML descriptor.
   * Pre-caching adapter builds via `make build-skill` before round 1 to save ~30s per round (R-6 mitigation precedent).

5. **W-17 mid-cycle audit at PV-05 worked exactly as intended.** The cumulative count at 89/150 → forecast 96/150 was caught early enough to set conservative PV-05 + PV-06 test budgets. The cycle ended at **94 / 150** (62.7% utilisation; PV-06 added the forecast 1 W-18 lint exactly) — within cap with 56-test reservoir remaining. Continue the W-17 mid-cycle audit at PV-N/2 in future cycles. The "high-information disposition" (per `v10.2.4_w17_mid_cycle_audit.md` §4) is a direct hand-down from the v10.0.0 retrospective §3.4 precedent — codify both as standing W-17 §3 §4 governance language for v10.4.0+.

6. **Single feature branch + draft PR throughout the cycle is the efficient cadence.** The cycle ran on `feat/v10.2.0-cycle` from PV-01 → PV-06 with all 6 commits on the same branch. Per the v10.0.0 retrospective §3.6 precedent + this cycle's D-V-3 mitigation, the per-MINOR PR ceremony was skipped during cycle execution — the MINOR cycle-close PR (PV-06 deliverable) is the single PR-merge surface. v10.4.0+ should keep this cadence unless reviewer load demands per-PV PRs. The benefit is reviewer focus on the cycle as a unit; the cost is the size of the diff (mitigated by the per-PV CHANGELOG entries which are a per-commit narrative).

7. **The 6-PV cycle shape worked.** 1 cycle-start MINOR (PV-01 plugin deep review + W-16 wholesale) + 1 PATCH (PV-02 formal Si-Chip integration + 7-step SI-10) + 1 PATCH (PV-03 NineS analysis + adapter) + 2 PATCH (PV-04 + PV-05 self-iteration rounds) + 1 cycle-close MINOR (PV-06) is a reusable shape for future "deep integrate + validate + iterate" cycles. The W-8 cap of 2 productive convergence rounds (escalate-to-human after stagnation) maps cleanly onto 2 PATCH iteration PVs.

## §5 — Telegraph for v10.4.0 cycle (per W-21 cadence)

**S-11 "Parallel Wave Dispatch Invariant"** — re-telegraphed for v10.4.0 SI-1 (cycle N+2 from v10.2.0). The v10.0.0 retrospective §3.5 originally telegraphed this candidate for v10.2.0; this cycle's gap analysis §3.6 D-W-1 ruled it OUT (orthogonal to user mandate); per W-21 2-cycle rule the next earliest landing slot is v10.4.0.

**Carry-forward design hypothesis** (for v10.4.0 SI-1 to evaluate):

> Every L2-wave with `parallel_mode: true` MUST go through `dispatch_wave_tasks` (not `dispatch_parallel` directly). Rationale: `dispatch_wave_tasks` enforces the wave-boundary invariants (P1 dispatcher-not-implementer + P2 minimal context); `dispatch_parallel` is the lower-level executor that does NOT enforce the wave-boundary contract. A future change to a dispatcher that bypasses `dispatch_wave_tasks` would silently skip the invariant; codifying in Soul prevents the regression.

v10.4.0 SI-1 must evaluate: (a) the immutable invariant the rule enforces; (b) why no existing S-* / A-* / W-* rule covers it (current candidate: A-1 P3 structured messages indirectly forbids it but doesn't pin the routing predicate); (c) the proposed CI-time enforcement surface; (d) the per-cycle review trail (this §5 + the v10.0.0 retrospective §3.5 + the v10.2.0 gap analysis §3.6 D-W-1 verdict).
