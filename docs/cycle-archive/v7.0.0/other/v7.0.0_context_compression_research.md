`@trq212` is **Thariq Shihipar**, an engineer on Anthropic's Claude Code team

### Inferred topic from author + adjacent posts + user framing

The user's framing in `feedback_for_v6.3.x.md` is unambiguous: it asks for a
**deep best-practice survey on staged context compression**, motivated by
analysing `@trq212`'s post. Cross-referencing the recoverable Thariq corpus
(`[ref-1]`, `[ref-2]`, `[ref-4]`) with the user's framing, the post almost
certainly addresses one or more of the following inter-related themes:

1. **Prompt-caching layout discipline.** Static content (system instructions
   + tools) at the front of the request, dynamic content (messages) at the
   end, so the cached prefix grows monotonically across turns. Cache hit
   rate is the operational SLO, with alerts firing when it falls below
   target (`[ref-1]`).
2. **Never mutate the cached prefix mid-session.** Concretely: never swap
   models mid-session (caches are model-specific), never add or remove tools
   mid-session (the tool list is part of the cached prefix), and prefer
   sending updates as new user messages rather than editing the system
   prompt (`[ref-1]`, `[ref-2]`).
3. **Tool-output pruning / lazy tool loading.** When tool definitions or
   tool outputs would consume more than ~10% of the context window, switch
   to dynamic search / lazy load instead of front-loading them (`[ref-3]`).
4. **Hand-offs to sub-agents in lieu of model swap.** When a different
   capability tier is needed (e.g. a quick verification by a budget model),
   spawn a sub-agent with a hand-off message rather than swap the model on
   the live cached session (`[ref-2]`).
5. **Economics of caching.** A long Opus coding session costs USD 50–100
   un-cached vs. USD 10–19 with a 90 % cache hit rate, making the 5–10x
   cost differential the dominant factor in agent design (`[ref-3]`).

### Implications for DevolaFlow

The five points above land directly on DevolaFlow's **lean message schema**
(`schemas/lean-dispatch.yaml`, `schemas/lean-report.yaml`) and the layered
context profiles (`workflow-system/agent/context_profiles.yaml`):

- The lean dispatch already pins file paths, IDs, and acceptance criteria
  verbatim, which aligns with the *layout* discipline (point 1).
- The 4-layer L0→L3 hierarchy with sub-agent dispatch via the `Task` tool
  (`workflow-system/agent/SKILL.md` §"4-Layer Agent Hierarchy") aligns with
  *hand-offs to sub-agents* (point 4).
- We do **not** yet enforce point 3 (tool-output pruning) — the current
  `compressor.py` only acts on prose and natural-language drop-list
  patterns; it does not surgically trim `tool_result` content.
- We do **not** yet measure cache-hit-rate (point 1 / point 5) as a first-
  class metric in `benchmarks/devolaflow_context/` baselines.

These four observations seed the recommendations in Section J.

## Section B — Anthropic / Claude / Claude Code Best Practices

This section synthesises five primary Anthropic-published references plus
the bundled Skills system documentation and Claude Code product blog
content. All quotes are paraphrased unless wrapped in `"..."`.

### B.1 Anthropic's official "Effective context engineering" essay (Sep 29, 2025)

`[ref-5]` is the canonical Anthropic position on the discipline. Key points:

- **Definition.** "Context engineering refers to the set of strategies for
  curating and maintaining the optimal set of tokens (information) during
  LLM inference." It is the natural successor to prompt engineering as
  agents move from one-shot text-generation tasks to multi-turn loops.
- **Context rot.** Empirically, "as the number of tokens in the context
  window increases, the model's ability to accurately recall information
  from that context decreases" (`[ref-5]`, citing the Chroma needle-in-a-
  haystack study `[ref-12]`). Context is treated as a *finite* resource
  with diminishing marginal returns, not a free buffer.
- **Architectural cause.** The transformer's `n²` pairwise attention
  pattern means doubling the context quadruples the relationships
  competing for the same attention budget (`[ref-12]`).
- **System-prompt altitude.** The right altitude is a Goldilocks zone
  between "brittle if-else hardcoded prompts" and "overly general" prompts
  that "falsely assume shared context."  Anthropic recommends XML tagging
  or markdown headers and aggressively pursuing the *minimal informative*
  set rather than the *maximal* set.
- **Tool design.** Tool sets must avoid functional overlap. "If a human
  engineer can't definitively say which tool should be used in a given
  situation, an AI agent can't be expected to do better." Bloated tool
  sets are listed as one of the most common failure modes.
- **Few-shot examples.** Provide a *small* set of canonical examples
  rather than enumerating edge cases.
- **Just-in-time retrieval.** Maintain lightweight identifiers (paths,
  queries, links) and pull data into context only when needed, instead of
  pre-loading. Claude Code is cited as the reference implementation:
  `CLAUDE.md` is loaded up-front, but `glob` and `grep` are used for
  on-demand exploration.
- **Hybrid strategies.** Pure just-in-time has a runtime-exploration cost;
  hybrid (some pre-loading + on-demand expansion) is recommended for less
  dynamic content domains like legal or finance.

### B.2 Anthropic's three first-party long-horizon primitives

`[ref-5]` and the cookbook `[ref-6]` describe three primitives that ship as
first-party API features:

| Primitive | API identifier | Beta header | Trigger | Tunable knobs |
|---|---|---|---|---|
| Compaction | `compact_20260112` | `compact-2026-01-12` | server-side token threshold (min 50 K) | `trigger` (default 150 K), `instructions`, `pause_after_compaction` |
| Tool-result clearing | `clear_tool_uses_20250919` | `context-management-2025-06-27` | server-side token threshold | `trigger` (default 100 K), `keep` (default 3), `clear_at_least`, `exclude_tools`, `clear_tool_inputs` |
| Memory tool | `memory_20250818` | none (standalone) | model-driven (it's a tool call) | client-implemented `view`/`create`/`str_replace`/`insert`/`delete`/`rename` |

(Source: `[ref-6]`, "How the three APIs map to the problem" table.)

The cookbook explicitly maps the three primitives to three *classes* of
context growth:

- **Conversation accumulation** ("running commentary, follow-up
  questions") → **compaction**.
- **Tool-result accumulation** (large file reads, API responses that are
  re-fetchable) → **tool-result clearing**.
- **Cross-session knowledge persistence** ("Session 2 should not
  rediscover Session 1's findings") → **memory**.

The agent-design implication: **diagnose your bottleneck class first, then
pick the matching primitive.** Mixing them indiscriminately wastes effort
and confuses the agent.

### B.3 Compaction implementation tactics

From `[ref-5]` and `[ref-6]`:

- The compaction prompt is itself prompt-engineered. Anthropic recommends
  "carefully tuning your prompt on complex agent traces" — start by
  maximising recall, then iterate to improve precision.
- Compaction is a *whole-transcript* operation: user messages, assistant
  messages, tool calls, tool results, and even prior compaction blocks are
  flattened into the summary.
- Claude Code preserves: architectural decisions, unresolved bugs,
  implementation details. It discards: redundant tool outputs and
  intermediate messages. It keeps the *five most recently accessed files*
  alongside the compacted summary as a working-set heuristic.
- **Lightest-touch lever:** tool-result clearing. "Once a tool has been
  called deep in the message history, why would the agent need to see the
  raw result again?" The `tool_use` record stays (so the model knows the
  call happened); only the bulky `tool_result` payload is replaced with a
  short placeholder.

### B.4 Sub-agent architectures

`[ref-5]` and Anthropic's earlier "How we built our multi-agent research
system" essay describe the sub-agent pattern in operational terms:

- The main agent coordinates with a high-level plan; sub-agents perform
  deep technical work in clean context windows.
- Sub-agents may use "tens of thousands of tokens" internally but return
  only "a condensed, distilled summary of its work (often 1,000–2,000
  tokens)."
- This produces a clean separation of concerns: the lead agent synthesises
  while the detailed search context remains isolated within sub-agents.
- Reported outcome: "substantial improvement over single-agent systems on
  complex research tasks."

This is the direct lineage of DevolaFlow's L0→L3 hierarchy and the lean
dispatch / lean report message schemas.

### B.5 Anthropic Skills system

`[ref-7]` and `[ref-8]` document the Skills mechanism that ships with
Claude Code. Three-level progressive disclosure:

1. **Frontmatter metadata** is pre-loaded into the system prompt at start
   (cheap, always-on).
2. **Full SKILL.md content** loads only when Claude determines the skill
   is relevant (gated by the description field).
3. **Additional linked files** (referenced from inside SKILL.md) load on
   demand (one further level of laziness).

> "Long reference material costs almost nothing until you need it." (`[ref-7]`)

This is identical in spirit to DevolaFlow's `task_adaptive_selector.py`
section-priority allocation (critical → important → supplementary →
skip), and is the architectural precedent we should preserve when
designing v7's stage-wise compression.

### B.6 Thariq Shihipar's "Prompt Caching is Everything" lessons (`@trq212`)

`[ref-1]`, `[ref-2]`, `[ref-3]`, `[ref-4]` document the operational
lessons from running Claude Code at scale:

- **Cache layout discipline:** static (system instructions + tools) → less
  dynamic (project context) → more dynamic (session context) → most
  dynamic (messages). The cached prefix grows monotonically, so any
  invalidation forces a costly rebuild.
- **Cache-hit alerting.** Internal alerts fire when hit rate drops below a
  target threshold, treating cache-hit-rate as a production SLO.
- **Never swap model mid-session.** Caches are model-specific; switching
  Opus → Haiku mid-conversation costs *more* than staying on Opus, because
  the entire cache rebuilds.
- **Never add/remove tools mid-session.** The tool list is part of the
  cached prefix; mutating it invalidates the entire conversation cache.
  This is why Claude Code's "Plan Mode" is implemented as a tool that
  toggles internal state, not as a tool-set swap.
- **Use messages, not prompt edits, for time- and file-staleness.** Patch
  facts forward in the next user turn, never modify the system prompt.
- **Sub-agent hand-off.** When a different model tier is required, spawn
  a fresh sub-agent rather than swap on the live session.
- **Economics.** Long Opus coding sessions: ~USD 50–100 un-cached, ~USD
  10–19 at 90 % cache hit rate (`[ref-3]`).

### B.7 Synthesis of Section B

Anthropic's published stack converges on five techniques: (a) cache-aware
layout, (b) compaction, (c) tool-result clearing, (d) external memory, (e)
sub-agent isolation. All five are built around one observation: **the
attention budget is the primary constraint**, not the nominal context
window size. DevolaFlow already implements (e) explicitly and (d)
implicitly via artifacts; (a)/(b)/(c) are the gaps Section J targets.

## Section C — OpenAI / Codex / GPT Context Management

### C.1 OpenAI's Compaction API (responses platform, 2026)

`[ref-13]` and `[ref-14]` document OpenAI's two-pronged compaction:

- **Server-side compaction.** Setting `context_management.compact_threshold`
  in a Responses `create` request causes the server to auto-run compaction
  when rendered tokens cross the threshold; a `compaction` item is emitted
  in the stream and prior context is pruned before continuing.
- **Standalone `/responses/compact` endpoint.** Stateless: send a full
  context window, receive a new compacted window with an *encrypted*
  compaction item carrying forward state and reasoning in fewer tokens.

Reference example uses `model="gpt-5.3-codex"` and `compact_threshold` of
200 000 tokens (`[ref-14]`). Both server-side and explicit modes are
available; the choice mirrors the Anthropic compaction-vs-clearing
distinction from `[ref-6]`.

### C.2 Codex CLI compaction PR

The Codex CLI merged context compaction in PR #3446 in September 2025
(`[ref-15]`). Implementation:

1. Stop the model when the context window grows beyond a threshold.
2. Issue a synthetic user turn requesting a summary.
3. Build a "bridge": all previous user messages + the summary.
4. Restart sampling from that bridge with a fresh conversation buffer.

This confirms that even the *agent harness*, not just the model server,
needs to participate in compaction — the threshold-and-bridge pattern is
nearly identical to Claude Code's compaction loop.

### C.3 Codex CLI context architecture

`[ref-16]`, `[ref-17]`, `[ref-18]` describe Codex's context layering:

- Context is assembled dynamically from: repository (cloned to sandbox per
  task), AGENTS.md (auto-loaded persistent instructions), Skills (reusable
  bundles), task prompts, prior interactions (persistent memory in the
  desktop app).
- Approximate context window: 192 K tokens for default GPT-5 Codex; up to
  1 M tokens for some configurations (`[ref-16]`).
- **AGENTS.md** is the foundation, auto-loaded before every task. Should
  contain: project overview, coding standards, architectural patterns,
  testing requirements, deployment constraints.
- `config.toml` named profiles (`fast`, `careful`, `auto`) switch entire
  context-management presets — direct analogue of DevolaFlow's
  `context_profiles.yaml`.
- `/compact` slash-command for explicit context budgeting.
- `@file` references for explicit file inclusion.
- `/plan` slash-command (or PLANS.md template) for reasoning-heavy work.

### C.4 Codex container caching (Sep 2025 update)

`[ref-17]` notes: "Container caching reduced median completion time by
approximately 90 percent on cloud tasks." This is the IDE-side analogue
of Anthropic's prompt caching — keeping the *runtime sandbox* warm instead
of cold-booting.

### C.5 Synthesis of Section C

OpenAI's stack mirrors Anthropic's stack: server-side compaction, AGENTS.md
as a persistent / pre-loaded layer (analogous to CLAUDE.md), Skills as the
reusable extension format (analogous to Anthropic Skills), and slash-
commands (`/compact`, `/plan`) for explicit user-driven context control.
The convergence across vendors is striking — both have settled on
approximately the same primitive set.

## Section D — Cursor IDE Context Architecture

### D.1 Cursor's three-tier rules system

`[ref-19]`, `[ref-20]`, `[ref-21]` document the rules layering:

| Tier | Path | Activation | Cache discipline |
|---|---|---|---|
| Global | Cursor Settings → User-level rules | All projects | Always-applied, in cached prefix |
| Project | `.cursorrules` (legacy) or `.cursor/rules/*.mdc` | Repo-scoped | Always-applied or glob-gated |
| Directory / file | `.cursor/rules/*.mdc` with `globs:` | Files matching glob | Loaded when file in context |

Each `.mdc` file uses YAML frontmatter with three control fields
(`[ref-20]`):

- `description`: prose summary used by the agent to *decide* whether to
  request the rule (analogous to Anthropic Skill metadata).
- `globs`: glob pattern that auto-attaches the rule when matching files
  enter context.
- `alwaysApply: true | false`: hard always-on flag.

Two activation modes thus compose: `alwaysApply` (always in prefix) vs.
**agent-requestable** (loaded only when description match or glob match).

### D.2 Skills vs. Rules

`[ref-22]` and `[ref-19]` distinguish:

- **Rules** (`.cursor/rules/*.mdc`): always-on or glob-attached static
  context. Best for invariant constraints (coding style, anti-patterns).
- **Skills** (`.cursor/skills/*/SKILL.md`): dynamic, agent-invokable
  workflows. Best for multi-step procedures (deploy to staging, run the
  release pipeline). Loaded dynamically when the agent decides they're
  relevant — keeps the cached prefix small.

Cursor explicitly recommends: "Don't over-optimize before you understand
your patterns. Start simple. Add rules only when you notice the agent
making the same mistake repeatedly" (`[ref-22]`).

### D.3 Plan Mode

`[ref-22]`, `[ref-23]` document Plan Mode (`Shift+Tab` toggle):

- The agent **researches** the codebase, **asks clarifying questions**,
  **generates a plan** (Markdown, editable), then **waits for approval**
  before coding.
- Plans can be saved to `.cursor/plans/` for resumption and team
  documentation.
- "Sometimes the agent builds something that doesn't match what you
  wanted. Instead of trying to fix it through follow-up prompts, go back
  to the plan." (`[ref-22]`)

This is operationally identical to DevolaFlow's PLAN MODE detection
(`workflow-system/agent/SKILL.md` §"Mode Awareness"), which since v6.1.5
escalates `agent_hierarchy`, `decomposition_gate`, and
`rationalization_prevention` sections to `critical`.

### D.4 Long-running agents and context churn

`[ref-22]` (Cursor "Best practices for coding with agents"):

- "Long conversations can cause the agent to lose focus. After many turns
  and summarizations, the context accumulates noise and the agent can get
  distracted or switch to unrelated tasks. If you notice the
  effectiveness of the agent decreasing, it's time to start a new
  conversation."
- `@Past Chats` lets a new conversation reference prior work without
  copy-pasting the entire transcript.
- **Stop hooks** (`.cursor/hooks.json`): the agent can be re-prompted
  programmatically when it stops, enabling a "grind" loop that iterates
  toward a verifiable goal (test pass, scratchpad `DONE` flag).

### D.5 What Cursor exposes vs. what it hides

Cursor's docs are explicit about what users can control (rules, skills,
plan mode, hooks, MCP) and reticent about the underlying context window
budget — Cursor does not publish the per-model rendered token budget,
the cache strategy, or the compaction trigger. Practitioners infer:

- Approximately 272 K-token effective context for Sonnet-class models
  (`[ref-19]`).
- The harness "tunes instructions and tools specifically for every
  frontier model based on internal evals and external benchmarks"
  (`[ref-22]`).
- @-mention system (`@codebase`, `@file`, `@folder`, `@web`, `@docs`,
  `@Branch`, `@Past Chats`) is the explicit user-facing context lever.

The implication for DevolaFlow: we cannot *directly* manipulate Cursor's
window. We can only influence what Cursor *sends to the model*: rules
files, skill files, dispatch payloads, and the prose we emit. All of our
compression work must operate at the *prompt-side*, not the
*platform-side*.

## Section E — X.com / Twitter Practitioner Signal

This section captures six practitioner signals from the last twelve months,
each cited with URL + paraphrase + approximate date. Where the original
post was inaccessible, the citation is to a republished blog summary
indexed by web search.

### E.1 Andrej Karpathy — "art and science" framing of context engineering

`[ref-24]` (cited as June 2025): Karpathy's now-foundational definition,
referenced in the Anthropic essay (`[ref-5]`):

> "Context engineering is the delicate art and science of filling the
> context window with just the right information for the next step."

This single tweet established the term inside the agent-tooling community
and motivated the compaction / clearing / memory taxonomy that Anthropic
later formalised.

### E.2 Simon Willison — "designing agentic loops" (Sep 30, 2025)

`[ref-25]`: Willison's now-canonical definition of an agent: "something
that runs tools in a loop to achieve a goal," and the corollary that "the
art of using them well is to carefully design the tools and loop for
them to use."

He emphasises that coding agents (Claude Code, Codex CLI) cross a
qualitative threshold once they can "exercise the code they write,
correct errors, and run experiments." Implication for our work: the loop
design is at least as important as the message format.

### E.3 Simon Willison — "Living dangerously with Claude" (Oct 22, 2025)

`[ref-26]`: documents `--dangerously-skip-permissions` (YOLO mode) as a
productivity multiplier and a safety hazard. Willison's recommendation:
*sandbox* aggressively (restricted file/network) rather than restrict the
agent's permissions inside an unrestricted sandbox. Direct relevance to
DevolaFlow: our stage-wise gate (`evaluate_gate`) is the closest analogue
to the "sandbox" pattern, because it forces a verification *event* before
the next stage starts.

### E.4 Simon Willison via Matt Webb — "Context plumbing" (Nov 29, 2025)

`[ref-27]`: re-frames context engineering as a *plumbing* problem:
"context comes from disparate sources (user activity, emails, document
changes, environmental shifts) and isn't always located where the AI
runs. The core job is moving the context to where it needs to be."

This validates our P5 invariant ("layers communicate through artifact
files, not shared memory or conversation history") — we already treat
the artifact filesystem as the plumbing layer.

### E.5 Thariq Shihipar (`@trq212`) — Claude Code prompt caching lessons (Mar 2026)

`[ref-1]`, `[ref-2]`, `[ref-4]`: see Section A and Section B.6 for the
full extraction. Most directly actionable practitioner signal in this
report.

### E.6 HumanLayer / Dexter Horthy — "Advanced Context Engineering for Coding Agents" (Q1 2026)

`[ref-28]`, `[ref-29]`: documents the "intentional compaction" pattern
that practitioners report is producing the largest single quality lift on
real codebases. Concrete claim: "successfully using these techniques with
Claude Code on 300k+ lines of Rust codebases, shipping a week's worth of
work in a day while maintaining code quality." (`[ref-28]`)

The mechanism: deliberately compress conversation state into clean
documents and *restart* in a fresh context window before reaching the
"dumb zone" where context rot dominates. This is essentially the
external-memory + sub-agent pattern from Anthropic, applied at the human-
operator level.

### E.7 Karpathy / Cursor team / others — context as the AI-coding bottleneck (Sep 2025)

`[ref-30]`: secondary press synthesis of Karpathy's September 2025
public talks where he reiterated that context, not raw model capability,
is the dominant bottleneck for AI coding productivity. He proposes
"dependency graphs over file trees" as a higher-fidelity selection
heuristic — extract relationships via tree-sitter and friends, not via
fuzzy similarity. This signal is most relevant to a future v7.x iteration
where we may want NineS to score *graph-coverage* (not just *file-
coverage*) for context selection.

## Section F — Cross-Cutting Synthesis Matrix

The matrix below crosses ten staged-context-compression techniques against
seven structured columns. Rows are ordered roughly by maturity and
operational frequency (most-mature first). Suitability codes for the
DevolaFlow hierarchy: **A**=applies cleanly, **P**=partial / needs
adaptation, **N**=does not apply at that layer.

| # | Technique | Source ecosystem | When applied | Preserves | Sacrifices | DevolaFlow L0 / L1 / L2 / L3 fit | Primary evaluation metric |
|---|---|---|---|---|---|---|---|
| 1 | Prompt caching (cached prefix discipline) | Anthropic `[ref-1]` `[ref-2]`, OpenAI `[ref-15]` | Every turn; layout decision is up-front | Static system instructions, tool schemas, project context | Mutation flexibility (no mid-session model/tool swap) | L0:A (sets layout); L1:A; L2:A; L3:P (sub-agent gets fresh prefix) | Cache hit rate, USD-per-task |
| 2 | Hierarchical summarisation | NexusSum `[ref-31]`, Anthropic compaction `[ref-5]` | Conversation length nears window limit | Decisions, unresolved bugs, named entities | Tool-call traces, intermediate reasoning | L0:A; L1:A (per-stage summary feeds next stage); L2:P; L3:N (atomic) | BERTScore retention vs. probe set, lost-fact count |
| 3 | Sliding window | classic LLM ops `[ref-32]` | Streaming long-input scenarios | Most-recent K turns | Long-tail history | L0:N; L1:N; L2:P; L3:P (last-K tool outputs) | Recall@K, last-fact survival |
| 4 | KV-cache offload | system-level (vLLM, TensorRT-LLM) | Always (server-side) | Full attention precision | Inference latency for cache-miss path | Out-of-scope: platform-level, not in our control | Cache hit rate, p99 latency |
| 5 | Sub-agent context isolation | Anthropic multi-agent `[ref-5]`, DevolaFlow P1 | Decomposable work; clear acceptance criteria | Lead-agent attention budget; reproducibility | Cross-task knowledge transfer (must be artifact-mediated) | L0:A; L1:A; L2:A; L3:A (already implemented) | Composite gate score, cross-task leak detection |
| 6 | Tool-output truncation / `clear_tool_uses` | Anthropic `[ref-6]`, Squeez paper `[ref-33]` | Tool result accumulates ≥10 % of window | Tool-use record (call happened) | Re-fetchable result payload | L0:N; L1:P; L2:P; L3:A (L3 emits/consumes tool results) | Token count post-clearing, false-recall rate |
| 7 | Episodic→semantic memory consolidation | Anthropic memory tool `[ref-6]`, Karpathy `[ref-30]` | End of session, on stage gate PASS | Durable facts, decisions, "lessons learned" | Verbatim conversation history | L0:A (status dashboard); L1:A (stage README); L2:N; L3:P (`learnings/` jsonl) | Cross-session task-success rate, retrieval precision |
| 8 | "Rolling pinning" of critical sections | DevolaFlow `task_adaptive_selector.py` round escalation | Convergence round N>1 | Sections marked critical (rationalization_prevention, gate_mechanism) | Lower-priority sections (frontmatter, version_update) | L0:N; L1:A; L2:P; L3:A (current implementation) | Section-priority hit rate per round |

### F.1 Matrix observations

- DevolaFlow already implements rows 5, 8, 9, and 10 to varying degrees.
- Row 1 (cache discipline) is the **single most important gap**: we do
  not yet enforce a layout invariant, do not measure cache-hit-rate, and
  the lean dispatch occasionally restructures sections in ways that would
  invalidate caching if the L0 dispatcher used a single chat session.
- Rows 2 (hierarchical summarisation) and 6 (tool-result clearing) are
  the second-tier gaps. Both are first-party features in Claude and
  OpenAI APIs but unaddressed in our prompt-side stack.
- Row 7 (episodic→semantic memory) is partially implemented as
  `learnings/operational.jsonl` plus the per-task-type learnings reserve;
  a v7.x iteration could promote it to a full agentic memory tool.

## Section H — Evaluation Methodology Candidates

Four measurable evaluation methods, each targeting one or more of:
**retention** (recall of facts after compression), **persistence** (cross-
session / cross-stage carry-over), **fidelity** (semantic faithfulness of
the compressed summary), **cost** (USD or token spend), **latency** (wall-
clock).

### H.1 EvoBench "Compression Probe" scenarios (retention + fidelity)

- **Dimension captured.** Retention + fidelity.
- **Instrument.** New EvoBench scenarios under
  `benchmarks/devolaflow_context/scenarios/compression_*.json`. Each
  scenario builds a synthetic predecessor artifact (~5K tokens) seeded
  with **probe facts** (file paths, error strings, version numbers, IDs)
  and **decoy facts** (plausible-but-false). The compressor under test
  emits a compressed artifact; a downstream "retrieval" pass asks
  template questions of the form "What is the version of dependency X?"
  and scores against the ground truth.
- **Baseline & threshold.** Baseline = current `compressor.py` output
  with `intensity=standard`. Pass threshold = retention ≥ 95 % on
  preserve-list facts (file_paths, version_strings, metric_values), ≥ 70
  % on free-form decisions.
- **Failure modes caught.** Hallucination of file paths (Knowledge
  Overwriting risk per the LLM Scaling Paradox cited in
  `lean-dispatch.yaml`); paraphrased version strings; lost commit hashes.

### H.2 "Cache-Layout Stability" benchmark (cost proxy)

- **Dimension captured.** Cost (cache-hit-rate proxy) + structural
  stability of the dispatch payload.
- **Instrument.** New test in `tests/test_compressor.py`:
  `test_dispatch_prefix_is_stable_across_rounds`. Builds N=3 sequential
  dispatches for the same `task_id` across rounds 1, 2, 3; computes the
  longest common prefix (LCP) of the rendered YAML; asserts LCP ≥ 80 %
  of the round-1 payload size. This is a *proxy* for cache-hit-rate
  because we cannot directly observe Cursor's cache, but a stable prefix
  is a *necessary condition* for high cache-hit-rate.
- **Baseline & threshold.** Baseline = current dispatch render. Pass
  threshold = LCP ≥ 80 % on round 1→2, ≥ 70 % on round 1→3 (some
  reinforcement section change is acceptable).
- **Failure modes caught.** Round-escalation logic that reorders top-of-
  payload sections (would invalidate prefix cache); section-priority
  changes that move headers up/down.

### H.3 NineS "context_density" capability evaluator (multi-dim)

- **Dimension captured.** Retention + fidelity, scored by NineS.
- **Instrument.** Extend NineS's analysis pipeline (`nines analyze
  --target-path <profile-output>`) to score compressed dispatch payloads
  on the existing NineS dimensions (code_quality, analysis, evaluation).
  Specifically, run `nines -f json analyze --keypoints` over the
  assembled context produced by `select_context(task_type=X)` and
  compute keypoint coverage relative to a hand-curated golden set.
- **Baseline & threshold.** Baseline = NineS keypoint coverage on
  current `select_context()` output. Pass threshold = no regression vs.
  v6.2.0 baseline.
- **Failure modes caught.** Section selection that drops sections needed
  for the task type; over-compression that strips named entities.

### H.4 Cross-stage "Persistence Probe" (persistence)

- **Dimension captured.** Persistence across L1→L2→L3 boundaries.
- **Instrument.** New harness in `tests/test_e2e_compression.py`:
  end-to-end fixture that runs Stage A (research), summarises its
  artifact, dispatches Stage B (design), and verifies that named entities
  (interface names, file paths, decision IDs) introduced in Stage A
  appear verbatim in the Stage B dispatch payload. Track a per-entity
  "carry-through" rate.
- **Baseline & threshold.** Baseline = current artifact-summary
  pipeline. Pass threshold = ≥ 90 % entity carry-through.
- **Failure modes caught.** Stage-boundary paraphrasing of named
  entities; lost interface signatures; lost decision IDs.

### H.5 Optional fifth method: latency benchmark (cost)

- **Dimension captured.** Latency.
- **Instrument.** Time `select_context(task_type=X)` end-to-end (load
  profiles, extract sections, run learnings injection) for each task
  type. Record p50 / p95.
- **Baseline & threshold.** Pass threshold = no p95 regression of
  > 15 % vs. v6.2.0. (Latency is a *governance* metric — we want
  optimisations that don't blow up the assembly cost.)
- **Failure modes caught.** Inadvertent O(n²) selection logic in a new
  compressor pass.

The table below maps each evaluation method (H.1–H.5) onto NineS's
existing capability dimensions, sourced from the NineS skill spec
(canonical: `https://github.com/YoRHa-Agents/NineS`; locally-installed at
the user-wide Cursor skills path) and the project's prior NineS self-eval
reports (`.local/research/nines_self_eval_devolaflow.json`,
`.local/research/nines_evaluation_report_v5.1.md`). Where the NineS
dimension name is inferred, the inference is flagged.

| NineS dimension | What it scores | How staged compression should move that score | Proposed v7 measurement plan |
|---|---|---|---|
| `code_quality` (capability) | Source code lint, complexity, error handling | Adding `compressor.py` extensions for tool-output truncation + summarisation should be lint-clean and well-tested → keep score ≥ 0.90 | Run `nines -f json -c nines.toml self-eval` after each v7.x bump; alert on > 0.02 drop |
| `analysis` (capability) | Quality of `nines analyze` output, keypoint extraction depth | Better-structured artifacts (Section J recs 2 + 3) increase the keypoint density per artifact | Map H.3 (NineS keypoint coverage) directly here |
| `evaluation` (capability) | Quality / coverage of evaluator harness | New EvoBench scenarios from H.1 + H.4 raise the eval-coverage score | Add H.1's `compression_*` scenarios to `data/golden_test_set/` and re-run NineS eval |
| `code_coverage` (hygiene) | Test coverage on src/ | New compressor passes need ≥ 80 % coverage to satisfy CP-2 | Run `pytest --cov=devolaflow.compressor` with each PR; floor at 80 % |
| `documentation` (hygiene, inferred) | README / SKILL coverage of new features | Each v7.x bump must update SKILL.md and CHANGELOG per documentation-sync-rules | SI-2 + SI-5 coupling already enforces this |
| `scoring_accuracy` (V1 evaluator, inferred) | NineS V1 scoring fidelity vs. golden set | Adding compression-specific golden TOMLs in `data/golden_test_set/` increases the evaluator's signal | Author 3–5 new golden TOMLs (`compression_retention_easy.toml`, `..._medium.toml`, `..._hard.toml`) |

### I.1 Mapping summary

- **H.1 (compression probe scenarios)** → primarily `evaluation` and
  `analysis` dimensions; secondarily `scoring_accuracy` once added to
  the golden test set.
- **H.2 (cache-layout stability)** → `code_quality` (because the metric
  is a unit-test) and indirectly `evaluation` (new scenario class).
- **H.3 (NineS context_density)** → directly `analysis`; reuses existing
  NineS pipeline so cost is low.
- **H.4 (cross-stage persistence)** → primarily `evaluation`; the
  end-to-end harness exercises the L1→L2→L3 boundary that NineS does
  not currently probe.
- **H.5 (latency)** → operational; not a NineS dimension. Use a separate
  `tests/test_perf.py` regression suite.

## Section J — Recommendations for v7.0.0 → v7.1.0

The following five recommendations are ranked by `(impact × confidence) /
effort`, where impact and confidence are scored 1–5 and effort is
estimated LOC + risk. All five fit comfortably inside a v7.0.0 → v7.1.0
multi-version run.

### J.1 [HIGHEST LEVERAGE] — Prompt-caching layout invariant + measurement (rec #1)

- **Rationale.** Section A + Section B.6 + Section F row 1: this is the
  single highest-leverage gap and the lowest-risk fix. Cache hit rate is
  a 5–10x cost lever per `[ref-3]`.
- **Files to touch.**
  - `workflow-system/agent/SKILL.md` (add a new "Cache Layout"
    subsection inside "Context Isolation").
  - `schemas/lean-dispatch.yaml` (declare a fixed top-of-payload
    section order).
  - `src/devolaflow/compressor.py` (add `assert_dispatch_layout(payload,
    layout_spec)` that fails fast on layout mutation).
  - `tests/test_compressor.py` (add H.2 stability test).
  - `.cursor/rules/devola-flow-rules.mdc` (add a CC-1 rule "preserve
    cached prefix").
- **Estimated LOC.** ~150 lines (60 in `compressor.py`, 50 in tests, 40
  in SKILL.md / schema / rules).
- **Expected delta.** EvoBench: no change. NineS: +0.01 to
  `code_quality` (extra invariant tests). Operational: 5–10x cost saving
  on long sessions where the L0 dispatcher is single-session (Cursor's
  Composer / Agent mode).
- **Blast radius.** Low. The invariant is *additive* — existing tests
  pass unchanged; only new tests fire on layout mutation.
- **Rollback plan.** Revert the compressor commit and the SKILL.md
  section; the schema declaration is forward-compatible (existing
  parsers ignore unknown keys).

### J.2 [SECOND] — Tool-output truncation primitive (rec #2)

- **Rationale.** Section F row 6 + Section B.3: tool-result clearing is
  Anthropic's "lightest-touch" lever and the closest analogue to OpenAI's
  `clear_tool_uses` server-side feature. Currently `compressor.py` has
  zero coverage of structured tool-result payloads.
- **Files to touch.**
  - `src/devolaflow/compressor.py` (add `truncate_tool_output`,
    `clear_old_tool_uses` helpers).
  - `schemas/lean-report.yaml` (add a `tool_results` block with `keep`
    and `cleared_at_round` fields).
  - `tests/test_compressor.py` (8–12 new unit tests).
  - `workflow-system/agent/references/context-isolation.md` (document the
    new primitive).
- **Estimated LOC.** ~250 lines (120 in `compressor.py`, 80 in tests, 50
  in docs).
- **Expected delta.** EvoBench: +5–10 composite on scenarios with heavy
  tool-output (estimated). NineS: stable. Operational: significant token
  reduction in convergence rounds where the prior round's tool outputs
  are still in scope.
- **Blast radius.** Medium. Tool-result handling touches the report
  pipeline; need to ensure the L1 Stage Agent can still reason over the
  surviving `tool_use` records.
- **Rollback plan.** Default `keep=all`, `clear_at_round=None` — disabled
  by default; opt-in per-task-type via `context_profiles.yaml`.

### J.3 [THIRD] — Hierarchical predecessor-summary primitive (rec #3)

- **Rationale.** Section F row 2 + Section B.3: the cookbook shows that
  multi-document research agents see large drops *before* hitting a hard
  context limit. DevolaFlow's predecessor_artifact summary is currently
  produced ad-hoc by the agent; promoting it to a deterministic
  primitive in `compressor.py` reduces hallucination risk per CO-2.
- **Files to touch.**
  - `src/devolaflow/compressor.py` (add `summarise_predecessor(artifact_path,
    schema, max_tokens)`).
  - `schemas/lean-dispatch.yaml` (`pred[].summary_mode: extractive |
    abstractive` toggle).
  - `tests/test_compressor.py` (10+ unit tests with the H.1 probe
    pattern).
  - `benchmarks/devolaflow_context/scenarios/compression_retention_*.json`
    (3 new scenarios: easy / medium / hard).
- **Estimated LOC.** ~350 lines (150 in compressor + helpers, 120 in
  tests, 80 in scenario JSON).
- **Expected delta.** EvoBench: +5–10 on retention-sensitive scenarios.
  NineS: +0.02 to `analysis` (richer keypoint extraction).
- **Blast radius.** Medium. Changes the *content* of dispatched
  predecessor summaries; downstream agents may need a one-version
  acclimation.
- **Rollback plan.** Toggle the new mode off via `summary_mode:
  extractive` (current behaviour).

### J.4 [FOURTH] — Cross-stage "persistence probe" harness + named-entity carry-through metric (rec #4)

- **Rationale.** Section H.4: today we have *no* end-to-end test that
  catches an L1→L2 paraphrase of a file path or interface name. This is
  the failure mode most likely to cause silent quality regressions in
  Section J.3.
- **Files to touch.**
  - `tests/test_e2e_compression.py` (new file, 200+ lines).
  - `tests/conftest.py` (add fixture `_compression_e2e_workspace`).
  - `src/devolaflow/compressor.py` (add `extract_named_entities` helper
    used by the metric).
- **Estimated LOC.** ~300 lines.
- **Expected delta.** EvoBench: catches future regressions earlier.
  NineS: +0.01 to `evaluation` once added.
- **Blast radius.** Low (tests only).
- **Rollback plan.** Skip the test class via pytest marker.

### J.5 [FIFTH] — Episodic→semantic memory promotion (`learnings/` v2 schema) (rec #5)

- **Rationale.** Section F row 7 + Section B.5: today's
  `learnings/operational.jsonl` is append-only and not curated.
  Anthropic's memory tool pattern + Karpathy's "session memory linked to
  code" suggest we promote it to a *structured* memory with confidence
  decay and per-session pinning.
- **Files to touch.**
  - `src/devolaflow/learnings.py` (extend with `consolidate_session(...)`
    and `decay_confidence(...)`).
  - `workflow-system/agent/knowledge/learnings/operational.jsonl`
    (schema migration; backwards-compatible append).
  - `tests/test_learnings.py` (10+ new tests).
- **Estimated LOC.** ~250 lines.
- **Expected delta.** Operational improvement on cross-session task
  success; not directly captured by NineS today (would need a new
  evaluator).
- **Blast radius.** Medium. The schema migration must be backwards-
  compatible — all existing entries must still parse.
- **Rollback plan.** Schema is additive (new fields default to `null`);
  rollback is simply a feature-flag in `context_profiles.yaml`.

## Section K — Open Questions / Unknowns

The following questions need explicit human input or further research
*before* the S02 Design stage commits to an implementation contract.

1. **Forced-summarisation threshold.** What token threshold should
   trigger automatic predecessor-artifact summarisation in `compressor.py`?
   Anthropic uses 150 K for compaction and 100 K for tool clearing
   (`[ref-6]`); OpenAI defaults to 200 K (`[ref-14]`). Our artifacts are
   typically 1–10 K so the absolute thresholds do not transfer; we need
   a *relative* threshold (e.g., "if predecessor artifact >25 % of L3
   token budget, force summarisation"). Decision owner: S02 Design.
2. **Plan-mode escalation propagation.** Today (`v6.1.5+`),
   `plan_mode=True` only escalates the L0 profile. Should it propagate
   downward to L1 and L2 Stage / Wave dispatches as well? Pro: consistent
   "design altitude" across layers. Con: may bloat L2 Wave context (L2's
   budget is the smallest). Decision owner: human.
3. **Cache-layout SLO.** What target cache-hit-rate should the H.2
   stability test enforce? `[ref-3]` cites 90 % as the production target
   for Claude Code. We can set the LCP threshold at 80 % (round 1→2) /
   70 % (round 1→3) but this is a guess until we have telemetry. Decision
   owner: human (depends on cost target).
4. **Tool-result clearing default.** Should we ship `keep=3` (Anthropic's
   default) or a more conservative `keep=5`? Smaller `keep` means more
   savings but higher false-recall risk. Decision owner: S02 Design,
   informed by H.1 retention data.
5. **Memory-tool surface area.** Should the `learnings/` v2 schema
   expose a Claude-style file-system-shaped tool (`view`/`create`/
   `str_replace`/etc.) or stay as a structured JSONL log? The former is
   more ergonomic for L3 Task Agents; the latter is easier to validate
   with hooks. Decision owner: human.
6. **NineS V1 evaluator authoring.** Section H.3 assumes we can author
   golden-set TOMLs that NineS will score. Can we author 3–5
   compression-specific golden tests in time for v7.0.0, or should that
   slip to v7.0.x? Decision owner: S02 Design.
7. **Cursor product roadmap dependency.** Several Section F rows
   (especially row 4: KV-cache offload, partially row 1: prompt caching)
   depend on Cursor's harness. We have **no insight** into Cursor's
   internal cache strategy. Should we proactively reach out to Cursor's
   team, or stay strictly inside our prompt-side stack for v7.x? Decision
   owner: human.
8. **Sub-agent context budget.** Today
   `context_profiles.yaml.sub_agent_context_budget` defaults to 3000
   tokens for decomposition-enabled profiles. Empirically, Anthropic
   reports sub-agents using "tens of thousands of tokens" internally
   (`[ref-5]`). Should we raise the budget for sub-agents that operate in
   the just-in-time retrieval mode? Decision owner: S02 Design.
