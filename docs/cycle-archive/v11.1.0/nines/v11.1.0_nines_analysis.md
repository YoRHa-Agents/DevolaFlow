## §3. Architecture rationality (W-3 dim 2, weight 0.20)

**Score: 5.0/10** (the lowest dimension; this is what the v11.1.0 cycle exists to fix)

### Evidence — canonical rule vs documented practice

* **A-1 §P1 canonical** (`.rules/architecture.mdc:9-12` + compiled
  `AGENTS.md`): "Dispatcher agents (Project, Stage, Wave) MUST NOT
  perform work directly. Only Task Agents execute actual work."
  Per `.rules/architecture.mdc:65-72` + A-3 budget table, the 4 layers
  have ~3K/~5K/~4K/~8K token budgets — explicitly assuming all four
  layers are present.
* **SKILL.md line 180** (`workflow-system/agent/SKILL.md:180`,
  verbatim): `**Layer collapse pattern (v10.5.0):** most cycles
  collapse L0→L3; engage standalone L1+L2 only for multi-team analyze
  with cross-stage merge (see examples/multi-stage-trace.md).` This
  contradicts A-1 in spirit — the canonical 4-layer rule is reduced
  to "advisory only when needed" by an inline note.
* **SKILL.md §"Quick Action Decision" line 64** (verbatim):
  `| **Standard** | 3-10 files, needs design or review | Full
  hierarchy (L1+L2 only-when-needed; see examples/multi-stage-trace.md) |`
  — the Standard tier (per `change_activation.classify_complexity`)
  receives the same advisory wording. The user's feedback explicitly
  rejects this for Standard-tier tasks.
* **SKILL.md §"Simple task shortcut" lines 105-106** (verbatim):
  `Skip multi-stage hierarchy. Dispatch a single Task Agent via Task
  tool with full context. Verify output and report.` This is the
  documented justification for L0→L3 collapse on Simple-tier tasks
  (which the user feedback would NOT change — cascade is required for
  STANDARD+ only).
* **Empirical evidence — D-A-1 layer-usage audit**
  (`docs/cycle-archive/v11.0.0/other/v10.5.1_layer_usage_audit.md`):
  `Total Dispatch type: lines: 0` across **14** scanned cycle docs
  (v9.x + v10.x). Standalone L1 / L2 / L3 ratios are all `0.00%`.
  L0→L3 collapse evidence ratio is `0.00%` — meaning cycles are not
  even self-reporting their dispatch shape. The empirical baseline
  for cascade-respecting practice is essentially zero.

### Evidence — code mechanisms encouraging collapse

Two distinct surfaces in `src/devolaflow/skills/change_activation.py`
default operators toward collapse:

1. **`force_no_change=True`** (`change_activation.py:248-249`,
   v10.5.0 PV-03 D-A-4):

   ```
   if force_no_change:
       return "NO_CHANGE"
   ```

   Evaluated FIRST in `activation_verdict`, this dispatch-level
   override unconditionally returns `"NO_CHANGE"` regardless of
   complexity / env / opt-out. The docstring (lines 211-216) frames
   it as "operator override wins; evaluated FIRST per A-6.3.1
   sub-rule". For STANDARD+ tasks this is the silent escape hatch
   that lets an L0 author bypass the full chain.

2. **`shortcut_verdict() → "SHORTCUT_SIMPLE"`**
   (`change_activation.py:305-369`, v9.3.0 PV-06): when
   `DEVOLAFLOW_SIMPLE_SHORTCUT=1` AND complexity ∈ {SIMPLE, TRIVIAL},
   returns `"SHORTCUT_SIMPLE"` — the dispatcher MAY skip L1 + L2.
   The docstring (lines 351-355) telegraphs that v9.7.0 will promote
   this to default-ON. **This is consistent with the user's feedback**
   (SIMPLE / TRIVIAL collapse is allowed) but the v9.7.0 default-ON
   plan is now incompatible with the cascade-restoration intent —
   v11.1.0 should NOT ship the v9.7.0 promote-to-default-ON until the
   cascade-required-for-STANDARD invariant is in place.

### Evidence — Plan-mode under-enforcement

* **Plan-mode Constraints Checklist item #1**
  (`workflow-system/agent/references/plan-mode-enforcement.md:138`
  + lines 339-341, verbatim): `Every task row is L3 (no L0-L2
  performing work — P1 enforced)`. This enforces P1 (dispatcher-not-
  implementer) but does **NOT** enforce CASCADE DEPTH — a plan can
  satisfy item #1 with a single stage / single wave / single task
  while still bypassing L1+L2 dispatch ceremony at runtime. The
  checklist is necessary but insufficient for the user's
  cascade-required intent.
* **Plan-mode Execution Model template** (`plan-mode-enforcement.md
  :117-122`): the 4-row table includes L1 + L2 rows but does not
  mark them mandatory — the template renders identically whether or
  not the L0 author actually engages L1 + L2 at runtime.

### Proposed minimal fixes (PV-02..PV-05 candidates)

1. **PV-02 — Classifier "更简明" redesign** that adds a
   `cascade_required: bool` derived field to a new struct returned by
   `classify_complexity` (or a sibling pure function
   `cascade_requirement(complexity, ...)`); pin `True` for STANDARD
   and COMPLEX. Keep the existing `Complexity` Literal contract
   byte-stable (R5 backward-compat). Add 8-12 NEW test functions

2. **PV-03 — SKILL.md cascade restoration**: rewrite line 180 to

   collapse" sub-table). Update §"Quick Action Decision" Standard
   row to drop "L1+L2 only-when-needed" and mandate cascade. Couples

3. **PV-04 — Plan-mode Constraints Checklist cascade-depth check**:
   add a 10th item: `For STANDARD+ complexity, the plan declares

   `tests/test_plan_mode_enforcement.py` (or sibling).
4. **PV-05 — New Architecture Rule A-7** (avoiding Soul per W-21
   2-cycle freeze): `A-7 — Cascade Depth Required for STANDARD+`.
   Per A-2.3 NEST-vs-APPEND decision matrix this is a workflow-level
   invariant; place under Architecture (not Workflow) because it

5. **PV-06 (optional)** — Defer the v9.7.0 promote-`SHORTCUT_SIMPLE`-
   to-default-ON plan; preserve opt-in semantics until v12.0.0
   cascade-strictness lands. Document in `references/env-flags.md`
   §"Future plans" + ghost-audit refresh per W-18.

### Why 5.0

The canonical rule (A-1) is correct and well-defined; the documentation
(SKILL.md line 180) actively contradicts it; the empirical evidence
(0% cascade ratio across 14 docs) shows the documentation is winning
over the rule. Architecture rationality is therefore middling — the
ARCHITECTURE is sound but the OPERATIONAL ENFORCEMENT has drifted to
the point that the architecture is no longer in effect at runtime. A
cycle-cycle aggressive 5.0 (vs the typical 8.0+ DevolaFlow earns on
this dimension per prior retrospectives) is the correct verdict. PV-06
re-eval (W-2 SI-2) at v11.1.0 close MUST show this dimension ≥ 8.5
to credit the cycle as delivered.

## §7. Performance impact (W-3 dim 6, weight 0.15)

**Score: 7.0/10**

### Evidence — token cost (verbatim from multi-stage-trace.md §"Counting the work")

`workflow-system/agent/examples/multi-stage-trace.md:158-176` (the

* **Cascade L0 → L1 → L2×2 → L3×7**: dispatch overhead `~33K tokens`

because parallelism > dispatch overhead.
