## 4. Key learnings

### 4.1 Calibration insight: 6/6 vs 4-5/6 projection
The patch plan's "predicted 4-5 of 6 (~70-83%)" projection was conservatively pessimistic, particularly on **P-06**:
- The patch plan rated P-06 as `low-medium` confidence ("P6 cache layout invariant complexity could trigger a defer-to-v8.x decision") — but the **strictly-additive append-after-`gate` design preserved the v7.0.0 byte baseline cleanly with `LCP = 1.00`** (a perfect prefix). The contract held: `tests/test_benchmarks.py::TestLayoutInvariantBaseline::test_layout_invariant_baseline` (the v7.0.0 byte-comparison) UNCHANGED and STILL PASSES after the schema bump.
- The pre-edit `grep -r "layout_invariant.version" .` confirmed ZERO production consumers of the bumped field — the schema version 1 → 2 nudge had no unforeseen blast radius.
- **Implication for v7.4.x patch plan:** when a patch is strictly-additive AND the only test surface is a byte-comparison golden + an LCP test, the confidence should be `medium` not `low-medium`. The risk-ascending execution order is still correct, but the projection should weight strictly-additive P6 changes at ~85% accept rather than the patch plan's implicit ~50% on P-06.

The medium-confidence patches **P-02** and **P-05** also landed clean:
- **P-02 regex precision:** measured 1.00 (10/10 TP, 0/10 FP on the held-out 20-example split) vs the 0.90 reject threshold. The 4-category `INJECTION_PATTERNS` design (separating `ignore_prior` from `new_system_prompt` from `output_redirect` from `role_override`) made each pattern narrow enough to avoid false positives on legitimate "step 1, step 2" prose.
- **P-05 retrieval lift:** measured +50.0pp auth-module retention lift vs the 30pp reject trigger; latency penalty < 10ms per call. The 0.6/0.4 query-overlap × schema-priority weighting was on the conservative side (the retrieval signal alone produced ~60% of the lift); a future patch could explore higher overlap weights or learned weights.

The high-confidence patches **P-04 / P-01 / P-03** all landed in the prior session before resume, with no surprises and the SI-10 6-step gate caught zero issues.

### 4.2 Tool failures: improvement vs v7.2.0 cycle
The v7.3.0 cycle resume notes (`.local/research/v7.3.0_cycle_resume.md` §6) documented the v7.2.0-cycle tool failures: `Shell` empty-stdout for ~5 minutes mid-cycle, `Task` stream-start timeout (background dispatched but `output_length: 0` after 600s).
- **Improvement observed in this cycle:** the post-resume run of P-02 / P-05 / P-06 hit ZERO `Task` stream-start timeouts. Background `Task` mode worked reliably for all 3 remaining patches.
- **Caveat:** during this Stage C rollup, the `Shell` tool DID return empty stdout once (on the `wc -l CHANGELOG.md && echo --- && wc -l ...` chained command, exit_code 0 with empty output). The cycle's general workaround was adopted: split into multiple parallel calls + use the `Grep` tool for line-count proxies. The pattern matches the v7.2.0 cycle's mitigation (long waits + fallback-to-other-tools).
- **Implication for v7.4.x:** the `Shell` empty-stdout symptom is intermittent but recoverable. Maintain the workaround (parallel `Grep` + `Read` + selective `Shell` calls; do NOT chain commands with `&&` when they all need to produce stdout). If frequency increases, escalate to platform.

### 4.3 SI-10 6-step gate calibration is good
The SI-10 6-step gate fired on every patch (6 patches × 5/5 effective steps = 30 gate runs since step 6 is a no-op when `.cursor/skills/devola-flow/` is absent) and caught **0** post-implementation issues. Specifically:
- Step 1 `pytest tests/ -q` caught 0 regressions per patch — every patch's L3 task agent landed clean tests.
- Step 2 `ruff check src/ tests/` caught 0 lint errors per patch.
- Step 3 `ruff format --check src/ tests/` caught 0 format violations per patch.
- Step 4 `pytest tests/test_version.py -v` caught 0 version-sync drift across all 6 `bump_version.py` runs.
- Step 5 `pytest tests/test_benchmarks.py -v` caught 0 benchmark regressions (0pp drift on the 33 v7.1.0 baseline scenarios across all 6 patch boundaries).
- **Implication for v7.4.x:** keep SI-10 as the binding pre-commit gate. Do NOT loosen any step. The 0-issue catch rate suggests gate quality is well-calibrated to the patch quality; do NOT mistake "gate caught nothing" for "gate is unnecessary" — the gate is a forcing function for the L3 agent to land clean work, not a defect detector.

### 4.4 The reflection-as-content pattern
P-03 (reflective reflex writer) activates the dormant v7.2.0 PR-C C-007 schema (`Learning.files`, `Learning.source`, `dedup_learnings`) by adding a single writer (`capture_session_reflection`) that the L3 agent or L0 dispatcher can call at session end. The two-phase pattern (v7.2.0 ships dormant schema → v7.3.0 ships writer → v7.4.x ships callers in agent prompt templates) is a pattern worth replicating:
- **Why dormant-then-active works:** dormant schemas can be tested + reviewed without behavior change; the writer is a small additive surface that's easy to test in isolation; callers can ship in a third version once the writer is proven stable.
- **Implication for v7.4.x:** identify other "dormant primitive + missing writer" pairs in the codebase. Candidates: any v7.0.x compression primitive with a docstring TODO, any v7.2.0 backlog item that ships a schema only.

### 4.5 EvoBench feedback is high-leverage input
This is the first DevolaFlow release driven entirely by external benchmark feedback (eb220) rather than internal self-update / dogfood loops (the v7.2.0 model). Lessons:
- The eb220 feedback structure (Tier 1 / Tier 2 capability tags + per-task q-scores + worst-affected enumeration + recommended focus + per-tier breakdown) translated cleanly to actionable patch hypotheses. The patch plan's mapping of Tier-N capability tags to specific patches was ~unanimous-fit (no patch had to invent its own gap rationale).
- The eb220 §"Recommended Focus" sections (🔴 Tier 1 #1/#2/#3, 🟠 Tier 2 #4/#5) are particularly load-bearing — they pre-prioritise the patch order at the feedback layer. This is much better than the v7.2.0 cycle's user-feedback model (3-line ask) which required heavier interpretation in the patch plan.
- **Implication for v7.4.x:** request `eb<NNN>_for_devola_v7.3.0.md` with the same structure (Tier 1/2 capability tags + per-task q-scores + recommended focus). If EvoBench varies the format, push back to maintain compatibility.
