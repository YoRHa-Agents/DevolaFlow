### 2.2 Architectural decoupling (the cycle's most significant deliverable)

Verbatim from commit body §"Changes": *"Decouples SKILL.md / reference-doc section discovery from concrete line numbers via the new SectionAnchorRegistry — future SKILL.md edits no longer cascade through context_profiles.yaml::sections and trigger unrelated EvoBench scenario drift."*

The shape of the decoupling:

1. **Old (v8.1.0-rc.1 and earlier)**: `context_profiles.yaml` lists sections by `[start_line, end_line]` ranges. SKILL.md edits that change line numbers force `context_profiles.yaml` updates that propagate via `select_context()` to every dispatch consumer; scoring deltas from extracting different content at the new line numbers cause EvoBench scenario drift.
2. **New (v8.2.0-pv05)**: `context_profiles.yaml` defines a `section_anchors:` mapping (anchor_name → `{file, heading}`). `select_context()` uses `_resolve_section_text(anchor)` which calls `discover_section_content(registry.lookup(anchor))` to find the section by heading text. SKILL.md edits that change line numbers DO NOT change which content is extracted; only the heading text matters.
3. **Backward-compat**: Legacy line-based path retained; `DeprecationWarning` emitted on every line-based lookup (one-shot per anchor to avoid log spam). This honours v8.x R5 alias-preservation discipline applied to runtime configuration.

Verbatim from companion retrospective §3 (the migration that was attempted then deliberately deferred): *"Root cause: the existing `sections:` registry has stale line ranges that have been extracting WRONG content for several cycles; switching to anchor-based discovery gives CORRECT content but changes token counts. Migration must be paired with baseline regen per scenario family — the work is BENCHED to v8.2.x SI-1."*

This is a remarkable finding: the v8.0.0 cycle's "stable" EvoBench scores were **stable on the wrong content**. PV-05 introduced the correct extraction mechanism but kept SKILL.md on the legacy fallback path to avoid a forced re-baseline. The migration is deliberate, audit-trailed, and queued for v8.2.x.

## 4. Key Learnings

1. **The legacy line-based registry was extracting WRONG content for many sections** (verbatim from companion retrospective §4 learning #2): *"e.g. `hierarchy_table: lines 185-195` actually extracts mid-table content from Repo-Init Pre-Dispatch Contract; `wave_task_constraints: lines 194-198` extracts selection heuristics. EvoBench scores stayed stable across cycles only because the wrong content stayed CONSISTENTLY wrong."* This is a profound learning about the limits of regression-only validation: stable scores prove "no recent change broke things" but not "the current behaviour is correct". v8.2.x migration must re-baseline scenario-by-scenario AND validate each section's extracted content against intent.

2. **Markdown heading discovery requires fenced-code-block awareness** (verbatim from companion retrospective §4 learning #1): without the `_FENCE_RE` guard, code samples in SKILL.md (e.g., plan-mode-template's nested `## Overview` examples) prematurely terminate parent sections. The fence-aware discovery added in `_heading_indices` should be promoted as a reusable utility for any future markdown analyzer in the codebase. Adopt: any markdown structural parser must distinguish "heading" from "heading inside fenced code block".

3. **Anchor-based discovery + line-based fallback is the correct migration pattern** (verbatim from companion retrospective §4 learning #3): the deprecation warning surfaces every legacy lookup at runtime, giving a measurable migration backlog without forcing a big-bang rewrite. R5 backward-compat discipline (proven in v8.0.0 P-10 and v8.0.0 P-08) scales cleanly to runtime config. Adopt: any structural refactor that changes "how data is found" should ship the new path + the old path as deprecated fallback, with one-shot DeprecationWarning per anchor.

4. **The `section_anchors:` extended YAML form (`{file: ..., heading: ...}`) is essential** for sections where the snake_case anchor name doesn't match the rendered markdown heading text (per companion retrospective §4 learning #4). The anchor-name → heading mapping varies enough across SKILL.md that auto-derivation alone is insufficient. Adopt: any registry that maps internal symbols to external content should support both short-form (auto-derive) AND extended-form (explicit mapping) entries.

5. **Opt-in primitive flips on STRICT only is the right granularity for B3 partial closures** (verbatim from companion retrospective §4 learning #5): preserves byte-stability for the other 3 profiles while letting strict-mode users immediately benefit. The pattern (boolean field on `GateProfile`, default `False`, STRICT explicit `True`) extends cleanly to the remaining 5 primitives in v8.2.x. Adopt as v8.x convention: opt-in primitive default-flips proceed STRICT-first, then AUDIT, then STANDARD, then RELAXED — never all-at-once.

6. **Three-deliverable bundling per single PV is sustainable when the deliverables share architecture** — PV-05 bundles R7 (the architectural change), B3 (a runtime-config flag flip enabled by R7's stability), and B2 (a regression-firewall scenario for R7). The three deliverables are linked by R7's enablement: B3 flips defaults that would have been risky without R7's section-anchor stability; B2 validates R7's regression-firewall. Lesson: bundling multiple gaps into one PV works when the gaps share an architectural enabler; otherwise spin separate PVs to avoid scope creep.

7. **The v8.2.0 cycle's "emergent" PV slot was used for architectural cleanup, not feature work** — PV-01..PV-04 closed Karpathy primitives 4.6, 4.7, 4.8, 4.12 (deferred features). PV-05 closed an architectural debt item (R7) plus partial closures of opt-in defaults and EvoBench scenario gaps. This is a healthy mix: 80% feature work + 20% architectural debt closure per cycle. Adopt as v8.x cycle composition convention: reserve at least 1 of every 5 PVs for architectural debt or emergent gap-analysis findings, not feature work.
