## 3. What Was Deferred and Why

- **PR 4 default-on flip for `llm_assist=True`** — DEFERRED to v8.2.x. Rollout per Stage B design §9 is staged: PR 1 (LLM client + provider abstraction) + PR 2 (compressor integration with opt-in) + PR 3 (EvoBench scenario) all landed in this single PV-01 patch; PR 4 (default-on flip + telemetry-driven validation) is queued for v8.2.x once production traffic data confirms the projected ≥+5pp `long_context_repo_qa` lift. Justification: flipping the default without telemetry would convert opt-in latency/cost into mandatory latency/cost for every dispatcher; the conservative additive discipline applies (R5 scaled to LLM features).
- **OpenAI / Anthropic real-provider integration tests** — DEFERRED to v8.2.x dogfooding. Provider abstraction is in place (`llm_client.py` ships with `openai`, `anthropic`, and `mock` provider strings); the deterministic `mock` provider is exercised by all 46 unit tests. Real-provider integration tests would require API keys + network access, not appropriate for the SI-10 step 1 fast-test gate. The structured fallback chain (HTTP 429/400/500/URLError/timeout) IS exercised against synthetic responses to prove the failure-mode coverage.
- **Cost-ceiling enforcement at runtime** — DESIGNED, NOT WIRED. The `abstractive_llm.yaml` profile defines `cost_ceiling: $0.05` per call + `latency_budget_ms: 800` per Stage B design §5/§6. Runtime enforcement (auto-fall-back when cost ceiling exceeded) is queued for v8.2.x once production cost telemetry is available. Today the ceilings are documented constants only.
- **LLM-assisted ACGenerator Stage B** — DEFERRED, paired with PV-01 architectural pattern. v8.0.0 P-10 left the same Stage A → Stage B path open for `acceptance_criteria_v2`; PV-01's `LLMClient` abstraction is reusable. v8.2.x candidate.
- **Cross-provider response normalization** — DEFERRED to v8.2.x. Each provider returns slightly different JSON shapes; PV-01 normalizes to a common dict but does not yet handle response-time skew or token-count divergence between providers. Not blocking for the mock-provider-only deterministic path used in CI.

## 4. Key Learnings

1. **The Stage A baseline IS the Stage B fallback** — design §7 framing held under implementation. By computing Stage A FIRST (always, even when `llm_assist=True`) and using its output both as the LLM's hint AND as the verbatim fallback when LLM fails, we got two architectural wins for one: (a) zero new failure modes are added on the Stage B path that aren't already exercised on Stage A, (b) the `abstractive_stage='a'` marker on the dispatch return gives EvoBench the attribution it needs to distinguish "Stage B never invoked" from "Stage B invoked then fell back". Adopt: future LLM-assisted features should default to "deterministic stage first, LLM stage as enrichment with deterministic fallback" rather than "LLM-only with no fallback".

2. **Frozen failure-mode tuple shared between modules is the right S-5 enforcement primitive** — `STAGE_B_FAILURE_MODES` and `FAILURE_MODES` are literally the same tuple object, asserted by import-time identity check. Adding a new failure mode requires updating both call sites simultaneously (because they reference the same constant) and the test suite catches drift via `TestFailureModeFrozenTuple`. This is more robust than parallel enum definitions or string constants. Adopt for any future cross-module enum that must stay synchronized.

3. **Provider abstraction without SDK dependency** — the `llm_client.py` uses urllib (stdlib) for HTTP, not the `openai` / `anthropic` SDKs. This avoids dependency-hell on CI (where SDKs may pin incompatible httpx versions), keeps the install footprint minimal (no transitive SDK deps), and forces explicit error handling at the HTTP layer (where 429 / 5xx / parse failures are visible). The trade-off: real-provider integration tests must hand-craft request/response bodies. Adopt for any future external service wrapper where SDK richness isn't strictly needed.

4. **Single-PR with 3 staged PRs of design §9 collapsed cleanly** — the design called for a 4-PR rollout but PV-01 collapsed PRs 1 + 2 + 3 into a single +2008 LOC patch (PR #74) because the LLM-client + compressor-integration + EvoBench scenario form a tightly coupled "all or nothing" first-cut. PR 4 (default-on flip) genuinely needs telemetry input first, so it remains separate. Lesson: design-doc PR staging should be re-evaluated at implementation time — if the early stages are tightly coupled and the late stage requires external input (telemetry / human review / production traffic), collapse the early stages into one PR.

5. **2008-LOC single PR was reviewable** — PV-01 is the single largest PV in v8.2.0 (+2008 / -19) and merged in 6 minutes commit-to-merge. The reason it stayed reviewable: ~50% of the diff is tests (479 + 506 = 985 LOC of new tests), ~25% is the new `llm_client.py` module (a single self-contained file with a clean interface), and ~17% is the integration into `compressor.py` (the largest "changed" file but with surgical scope around `summarise_predecessor`). Adopt: large LOC patches stay reviewable IFF (a) >40% is tests, (b) new code is in new files (not interleaved with existing files), (c) the integration file is touched at a single function. PV-01 satisfies all three.
