# v23.1.0 Kimi CLI 诊断

## 结论

- 实际执行 **2 次** Kimi CLI 探针，均 `exit=0`、未超时，wall time 分别为
  `6.306s` 和 `5.919s`。
- 两次 stdout 都是 **JSONL**，各 5 个 JSON 对象；没有 `usage`、
  `token_usage`、任何 token 计数字段，也没有 `skill_loaded`。
- 因此 v23 的 **missing usage telemetry 已确认**；这不是 JSONL 解码失败。
  当前 parser 找不到 usage，是因为输出没有落入它支持的字段位置。
- 原 v23 timeout 在本轮 **未复现**，不能归因于 auth、nonzero exit 或 parser；
  timeout 根因等级为 `INSUFFICIENT`。

## 输出结构与 parser 对照

两次 stdout 结构一致：

1. `{"role":"meta","type":"system.version","version":"0.39.1"}`
2. `{"role":"assistant","tool_calls":[...]}`
   - tool call keys: `type`, `id`, `function`
   - function keys: `name`, `arguments`
3. `{"role":"tool","tool_call_id":...,"content":...}`
4. `{"role":"assistant","content":...}`
5. `{"role":"meta","type":"session.resume_hint","session_id":...,"command":...,"content":...}`

stderr 在探针 01 为文本（19 个非空行），探针 02 为空；stderr 也没有
usage 或 skill 字段。输出摘要见两个 repository-relative artifact。

当前实现位置：

- `src/devolaflow/harness/cli_probe.py::_json_objects` 能识别上述 JSONL；
  所以 JSON/JSONL 形态本身不是失败点。
- `src/devolaflow/harness/cli_probe.py::_token_usage` 只检查：
  顶层 `usage`、顶层 `token_usage`，或直接的
  `input_tokens`/`output_tokens`/`prompt_tokens`/`completion_tokens`。
  本轮 5 个对象及嵌套对象均无这些字段，结果应为
  `status=INSUFFICIENT`，而不是 0 token。
- `src/devolaflow/harness/cli_probe.py::_skill_loaded` 只检查顶层
  `skill_loaded` 或 `metadata.skill_loaded`。本轮均不存在，所以语义是
  `null/INSUFFICIENT`，不能据此断言 skill 未加载或已加载。
- `src/devolaflow/harness/calibration_aggregation.py` 只有在每个 cell 的
  usage 与 skill telemetry 完整时才允许 ROI；本轮不能形成 token ROI 或
  skill-on/off 因果结论。

## 环境边界

仓库 harness API 本身未能在当前 shell 直接启动：`python` 命令不存在；
系统 Python 3.9 不提供 `datetime.UTC`；可用 Python 3.13 又缺少 `yaml`
依赖。为避免把 wrapper 环境错误误报为 Kimi 结果，本轮使用与
`DEFAULT_COMMAND_TEMPLATES["kimi"]` 相同的 argv 形态，直接执行 Kimi，并
仅写入本报告及 `kimi-diagnosis/` 下的脱敏 artifact。

这意味着本轮验证的是 **Kimi CLI 行为**，不是完整 `CLIProbeRunner` 的
Python wrapper 路径。wrapper 环境问题与 Kimi auth/timeout 是不同故障类别。

## Phase C 最小修复建议（不在本 Task 实现）

1. 先取得 Kimi 官方稳定的 usage-bearing `stream-json` 示例或 session/API
   usage 输出；在证据缺失时保持 `INSUFFICIENT`，不要从文本长度、tool call
   数量或 wall time 推算 token。
2. 在 `cli_probe.py` 增加**仅针对已证实字段路径**的 Kimi normalization，
   同时保留原始来源路径；若 usage 只在 stderr 或另一种输出模式出现，
   先定义明确的结构化来源边界，不要把普通文本误当 usage。
3. 为观察到的五类 JSONL event 增加 fixture，并分别覆盖：
   missing usage、已知 usage alias/嵌套路径、missing `skill_loaded`、以及
   malformed/non-JSON 行；确保 parser mismatch 与 missing telemetry 可区分。
4. 将 probe 的 `started_at`、`finished_at`、timeout phase 和 termination
   reason 写入脱敏 artifact；若要调查 timeout，再以同一 prompt/seed/salt
   重放并保留 partial stdout/stderr 的结构摘要。
5. 先修复校准执行环境的 Python/依赖一致性，再运行完整 calibration；否则
   wrapper import failure 会遮蔽真实 CLI 结果。

## 证据等级与无法核实项

证据等级：**B（直接运行、输出结构可复核，但 telemetry 不完整）**。

已核实：Kimi 可用、认证失败未发生、命令成功完成、JSONL 结构、字段缺失、
180 秒 timeout 未触发。无法核实：

- v23 原始 timeout 对应的 prompt、阶段、partial output 和进程状态；
- Kimi 0.39.1 在其他 output mode、session export 或 API response 中是否提供
  usage；
- 本轮 skill 是否实际加载，因为 CLI 没有暴露 `skill_loaded`；
- 两次 fallback probe 的精确 start timestamp；
- 缺失 usage 是 CLI 产品设计、配置差异，还是既有 parser 对其他输出形态
  的不兼容。

在这些证据补齐前，timeout 根因、usage 字段映射和 skill-on/off ROI 均应标为
`INSUFFICIENT`。
