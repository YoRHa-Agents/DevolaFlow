## 4 — Key learnings (process improvements for v12.6.0+)

### 4.1 5-surface integration template proves itself a second time

v9.4.0/v9.5.0 established the canonical 5-surface external-tool integration shape (plugin catalog + runtime registry + reference tracking + Python wrapper + workflow templates) when landing NineS + ui-pro + rtk + si-chip. v12.5.0 PV-03 + PV-04 + PV-05 applied the SAME shape VERBATIM for codegraph and it scaled cleanly: zero schema bumps, zero new env flags, zero canonical_order changes, zero Soul rule changes, all parity tests stayed green after the count-pin updates.

**Recommendation for v12.6.0+**: when integrating a new external tool, copy the codegraph 5-surface template wholesale. The pattern is now triple-validated (NineS + Si-Chip + codegraph) — future cycles encountering an external-tool integration request can copy this template and budget per-surface time accordingly (PV-03 plugin landing ~28 NEW tests; PV-04 workflow wiring ~15 NEW tests; PV-05 docs + reference budget ~5-12 NEW tests).

### 4.2 Helper-extraction template applies cleanly to non-orchestrator functions too

v12.4.0 PV-04 established the helper-extraction template for orchestrator-shaped functions (4 phases → 4 `_apply_*` helpers + linear-pipeline orchestrator). v12.5.0 PV-02 applied the SAME template to 2 non-orchestrator-shaped cc-spike targets (`load_command_mappings` is a config-loader; `apply_local_recipe` is a recipe-merger) and the result was a CORRECT decomposition into 4 helpers (load_command_mappings) + 2 helpers (apply_local_recipe — the natural bipartite split). The cc reductions were 18 → 9 and 17 → 4 respectively.

**Recommendation for v12.6.0+**: when applying the helper-extraction template, identify the natural phase count first (could be 2 / 3 / 4 / 5 — not always 4). The template's `_apply_*` / `_validate_*` / `_classify_*` naming convention scales across function shapes; only the helper count varies. Document the chosen helper count in the W-18 stanza so future audits track the decomposition reasoning.

### 4.3 Test-pin updates are mechanical and reliably catchable in PV-06 live gate

v12.5.0 PV-05 closed by authoring the eval document ahead of the actual W-9 SI-10 6-step gate run. The eval predicted "PASS" but the live gate at PV-06 caught 12 stale test-pin failures (3 reference-count assertions + 4 plugin-set assertions + 1 product-verification dispatch + 1 adapter golden + 6 dead-API allowlist + 1 codegraph.md frontmatter). All 12 were mechanical updates — no design rework needed. Total fix time: ~30 minutes of careful StrReplace edits.

**Recommendation for v12.6.0+**: schedule the live W-9 SI-10 gate as the FIRST PV-06 step (before authoring the retrospective or version bump). Catching stale test-pins early lets the retrospective accurately capture the gate-running outcome rather than predicting it. The eval document remains valid as a forward-looking scorecard, but the retrospective should cite the live-gate fix list verbatim (this retrospective §2.6 documents the 12 fixes with file paths + categories).

### 4.4 SF-4 reference set bumps require atomic 5-surface propagation

Adding `codegraph.md` as the 22nd reference required atomic edits across 5 separate surfaces:
1. The reference file itself + its frontmatter
2. `tests/test_no_ghost_features.py::_SF4_REFERENCE_SET` (the canonical test pin)
3. `scripts/sync_cursor_skill.py::MIRRORED_FILES`
4. `tests/test_reference_size_budgets.py`
5. `.rules/conventions.mdc` C-7 entry → propagated to `AGENTS.md` + `.cursor/rules/repo-governance.mdc` via `make compile-rules`

The lockstep is enforced by `tests/test_no_ghost_features.py::test_skill_reference_links_match_sf4_set`. PV-05 hit this constraint cleanly because the 5-surface enumeration is documented in the C-7 rule body itself. Future cycles adding a NEW reference can follow the C-7 checklist verbatim.

### 4.5 Bulk-freshness invariant relaxation pattern

`tests/test_v9_6_0_reference_integrations.py::test_pv04_all_21_refs_carry_2026_05_02_last_checked` originally asserted equality (`last_checked == "2026-05-02"`). v12.5.0 PV-05 added codegraph with `last_checked: "2026-05-23"` (legitimately fresher), which invalidates the equality assertion. The fix relaxed equality to floor (`>= 2026-05-02`) — a backward-compatible relaxation that preserves the no-stale-entries guard while allowing fresher additions per cycle.

**Recommendation for v12.6.0+**: when authoring count-pin or date-pin tests, prefer floor / ceiling assertions over equality whenever the property naturally drifts in one direction. Equality assertions are appropriate ONLY when the test pins a snapshot meant to never change (e.g., schema_version literal); they are inappropriate when the test guards against staleness or count regressions where forward-additions are legitimate.
