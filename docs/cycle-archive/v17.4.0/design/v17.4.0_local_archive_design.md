# Local Task Archive and Clustering — Initial Design

**Status:** Finalized design record for later implementation
**Baseline:** post-v17.3.0
**Boundary:** design-only. This document proposes a later implementation; it does
not claim that a local-task archive runtime, seed, lint, rule, or migration
already exists. No source/config/generated file, release record, deletion, or
commit is authorized by this task.

## 1. Current-state inventory

The following facts are observed in the repository or in the supplied cleanup
report. Proposals are labeled separately.

1. **There is an existing research archive, but it is not a local-task archive.**
   `scripts/archive_research_artifacts.py` copies versioned
   `.local/research/` artifacts into `docs/cycle-archive/v<version>/`, groups
   them into buckets, supports `--misc`, and uses byte comparison with
   `EXISTS`/`STALE`/`REFRESH` outcomes. It is idempotent by default and never
   deletes the research source. This is the W-19 cycle-history mechanism, not a
   clustering service for `.local/tasks/`.

2. **Change archives already have a distinct lifecycle.**
   `src/devolaflow/agent_workspace/change.py` owns the canonical
   `.local/.agent/active/` and `.local/.agent/archive/` layouts. `ChangeStore`
   lists, loads, transitions, and moves change folders. Its archive folder uses
   a date prefix and is tied to the checklist/FSM contract.
   `src/devolaflow/agent_workspace/archive.py` requires `VERIFYING` by default,
   writes `ARCHIVED`, moves the folder, consolidates optional learnings, and
   regenerates reports. It must not be repurposed as a task-cluster archive.

3. **`entropy-cleanup` is a declarative cleanup seed.**
   `workflow-system/agent/templates/seeds/entropy-cleanup.yaml` has two
   partitions: `drift-inventory` (classify stale, duplicate, and conflicting
   artifacts) and `cleanup` (review and apply approved cleanup). Its seed
   assertions are not an executable stage graph. The seed is therefore a
   plausible intent neighbor, but it currently defines no task-cluster
   manifest, path mapping, archive index, or deletion gate.

4. **Workspace discovery is deliberately narrow.**
   `src/devolaflow/workspace_context.py::scan_workspace` reports `.local/`,
   `.rules/`, `.local/.agent/`, active change directory names, up to three recent
   feedback files, one-level source-of-truth specs, a memory-case count, rule
   stems, compiled corpora, and selected human-surface anchors. It does not
   enumerate `.local/tasks/` entries, infer clusters, read task status, or scan
   archive mappings. That omission is an observed boundary, not evidence that
   task archiving is impossible.

5. **`generate_index` is only an immediate-directory listing.**
   `src/devolaflow/local/workspace.py::generate_index` renders the names of
   directories immediately below `.local/` into `.local/index.md`, preserving
   bytes on a no-op. `scaffold_local` calls it while creating the broader
   workspace. It does not generate a task index, classify task folders, or
   maintain old-path-to-new-path mappings. The current scaffold contract also
   keeps `.local/tasks/` as a required top-level directory but does not define
   subclusters.

6. **C-9 does not cover task-folder artifacts.**
   `src/devolaflow/agent_workspace/lint.py` enforces budgets for change
   artifacts, optional harness/Pathfinder artifacts, and the `.local/human/`
   surface. It has no `.local/tasks/` clustering/archive budget or semantic
   contract. Extending it would couple a task archive concern to the active
   change linter and needs an explicit design decision.

7. **No reusable `.local/tasks` clustering/archive runtime is present.**
   The source surfaces above provide scaffolding, discovery, change archives,
   and cycle-research archives, but no API that inventories task folders,
   computes cluster placement, writes a task index, records path mappings, or
   applies a reviewed task move. The supplied
   `.local/tasks/add_local_archive/add_local_archive.md` is a completed cleanup
   report and feedback source; its one-off six-cluster operation is not itself
   a runtime contract.

## 2. Embedded SI-1 gap analysis

### Deficiencies

| Priority | Gap | Evidence |
|---|---|---|
| P0 | No reusable inventory/plan/apply contract for `.local/tasks/` | No such surface in `src/devolaflow/local/`, `src/devolaflow/workspace_context.py`, or the supplied archive modules |
| P0 | Task active/done/stale placement and cluster identity are not machine-readable | `generate_index` lists only `.local/` directories |
| P0 | Deletion has no explicit protected-set, clean-check, or approval protocol | Existing W-19 and ChangeStore archive by copy/move semantics, not task cleanup |
| P1 | Brownfield flat layouts have no non-destructive adoption path | `scan_workspace` does not inspect task folders |
| P1 | Cross-reference repair is not part of any task move contract | Cleanup report explicitly records path-mapping and handoff needs |
| P1 | There is no task-specific budget or semantic lint surface | C-9 registry in `agent_workspace/lint.py` excludes `.local/tasks/` |

### File-level fix scope proposed for a later cycle

* Add a task-archive contract/reference and, only if the workflow is approved,
  a declarative `local-archive` seed.
* Add one runtime owner for inventory, plan validation, index rendering, and
  safe apply operations; do not duplicate registry data in consumers.
* Add focused tests and a bounded lint/doctor command for the new contract.
* Keep `scan_workspace`, `generate_index`, W-19 research archiving, and
  ChangeStore lifecycle semantics unchanged unless a separate approval item
  accepts the blast radius.

## 3. Six-axis triage and design decisions

### Axis 1 — Boundary and protected surfaces

**D-1 — Recommendation:** define a repository-relative, explicit archive plan
with `eligible_paths`, `destination`, `classification`, and `action`; default
to `REPORT_ONLY`. Protect `.local/.agent/`, `.local/memory/specs/`,
`.local/research/`, `.local/human/input/`, `.rules/`, and all source/config
surfaces unless a separate workflow explicitly owns them.

**Alternatives:** infer eligibility from every directory under `.local/`;
reuse the W-19 research bucket classifier; or let callers supply arbitrary
paths. These are simpler but make active runtime surfaces and provenance easy
to misclassify.

**Human decision / approval item:** confirm the protected-set extension list
and whether any non-task `.local/` directory may ever be an archive source.

### Axis 2 — Cluster identity and physical layout

**D-2 — Recommendation:** cluster by a stable, human-readable domain key, with
an explicit override recorded in the plan. Never derive identity solely from
mtime, file size, or an opaque hash.

**D-3 — Recommendation:** use stable physical paths plus a task index. A
reference example is `.local/tasks/<cluster>/active/<task-id>/` and
`.local/tasks/<cluster>/archive/<period>/<task-id>/`, with
`.local/tasks/INDEX.md` as the navigation surface. This six-cluster shape is
only an example from the cleanup report, not a canonical manifest requirement.
The protocol must work with any approved cluster count, including zero.

**Alternatives:** keep all tasks flat and make the index virtual; or create a
fixed six-cluster manifest. A virtual index avoids moves but leaves entropy in
the active directory. A fixed manifest overfits this cleanup and conflicts with
the settled principle that protocols are normative while physical examples are
not canonical.

**Human decision / approval item:** choose whether an approved move is the
default or whether the first release should be index-only.

### Axis 3 — Lifecycle and archive provenance

**D-4 — Recommendation:** keep task lifecycle separate from
`.local/.agent`'s `PROPOSED → IN_PROGRESS → VERIFYING → ARCHIVED` FSM. A task
archive may classify `active`, `done`, and `stale`, but it must preserve the
original task directory and record source, destination, reason, and timestamp
in an append-only mapping artifact.

**D-5 — Recommendation:** preserve task-local context when moving a folder;
repair links through an old-path → new-path map and an index entry. Do not
silently rewrite arbitrary text references. Unresolvable references become
reported findings requiring review.

**Alternatives:** copy instead of move; archive only a summary; or reuse
`ChangeStore.move_to_archive`. Copying is safer but duplicates authority.
Summary-only archiving loses task context. `ChangeStore` is the wrong owner
because its input and FSM are active change artifacts.

**Human decision / approval item:** decide whether `stale` is a reversible
classification only or an approval prerequisite for physical archiving.

### Axis 4 — Safety boundary

**D-6 — Recommendation:** no deletion in the default path. The runtime, if
approved, may report candidates and apply approved moves; deletion requires a
separate explicit action and an exact path allowlist.

**D-7 — Recommendation:** before deleting a clone, worktree, review tree, or
generated output, verify that the path is inside the repository boundary, is
not a symlink, is not a protected surface, is not active, and has a clean
`git status --short --untracked-files=all`. Also check staged and unstaged
diffs and, for worktrees, the worktree registry. A clean check is a safety
precondition, not permission to run `git clean`.

The design must never invoke `git clean -fdx` or equivalent destructive
commands automatically. It must retain a pre-action inventory and emit an
explicit refusal for dirty, ambiguous, missing, or unreadable paths. The
one-off cleanup report's lesson—review each clean clone/worktree before
deletion—becomes protocol guidance, not an assertion that the protocol exists.

**Alternatives:** allow deletion after a dry-run only; or delegate deletion to
the operator entirely. The former still risks an overly broad plan. The latter
is safest but leaves no repeatable verification surface.

**Human decision / approval item:** define “clean” precisely for ignored files,
nested repositories, linked worktrees, and untracked review notes.

### Axis 5 — Index, handoff, and generation ownership

**D-8 — Recommendation:** make `INDEX.md` either honestly generated or
explicitly human-maintained. If generated, the generator owns its format and
must report stale destination bytes rather than overwriting them silently.

**D-9 — Recommendation:** every physical move emits a complete old-path →
new-path mapping in an append-only handoff/migration artifact. Existing
handoff files are never edited or deleted; a subsequent run appends a new
sequence. The index is a navigation view, not the source of truth for the
mapping.

**Alternatives:** update only the index; or mark the index “auto-generated”
without a generator. The first loses references; the second creates the
false contract called out in the cleanup report.

**Human decision / approval item:** select the mapping filename/location and
whether task mappings use the existing handoff envelope schema or a dedicated
task-archive record.

### Axis 6 — Runtime, lint, and governance integration

**D-10 — Recommendation:** use one explicit local-archive owner for
inventory/classification/plan validation and safe apply; keep it distinct from
`agent_workspace.lint` and `ChangeStore`. Add semantic lint for malformed
plans, protected-path violations, duplicate destinations, missing mappings, and
index drift. Absence of an opt-in task-archive manifest should be a clean
no-op for brownfield discovery.

**D-11 — Recommendation:** add a dedicated reference if the protocol becomes
operator-facing. A new reference triggers C-7's four-piece registration:
the file, the pinned reference-set test entry, a SKILL.md navigation row, and
the `workflow-system/agent/manifest.yaml` `references:` entry. A new seed also
needs registry/seed parity and template validation.

No new `DEVOLAFLOW_*` environment variable is proposed. Activation should use
intent selection or an explicit bounded command, satisfying W-20's
reuse-first policy. S-8 remains the boundary for active change agents; a task
archive agent may not use that rule to write outside its own declared task
ownership. S-9 applies to any mapping/handoff ledger: append new records,
never mutate or delete existing ones.

**Alternatives:** prompt-only instructions with no runtime/lint; or extend the
existing change linter. Prompt-only behavior will drift and cannot enforce
deletion safety. Extending the change linter mixes independent artifact
contracts and increases false positives.

**Human decision / approval item:** approve or reject each of: new reference,
new seed, runtime helper, dedicated lint command, and any Workflow-rule text.
Each rules-layer proposal is a separate approval item; none is implied by this
design.

## 4. New seed versus `entropy-cleanup` extension

| Option | Benefits | Costs and risks | Recommendation |
|---|---|---|---|
| New `local-archive` seed | Clear intent; can declare inventory, classification, plan review, mapping, and bounded apply assertions; keeps cleanup and archival semantics distinct | Requires a registry entry, seed parity tests, likely reference/manifest work, and a new ghost-audit entry before any CHANGELOG claim | Preferred if this becomes a repeatable workflow |
| Extend `entropy-cleanup` | Reuses an existing intent and avoids a second seed name | Combines stale-content cleanup with structural task migration; makes deletion and physical moves look like generic cleanup; weakens review boundaries | Do not prefer |
| No seed; explicit design command only | Smallest registry surface and suitable for a one-off operator tool | No natural workflow routing or declarative checklist guidance; repeatability depends on prose | Acceptable for a one-cycle pilot |

The preferred choice is a new seed only after the later grill confirms that
task archiving is a recurring workflow rather than a single cleanup replay.
Regardless of choice, seed fields remain declarative knowledge; executable
behavior stays in the sole `change-driven` runtime.

## 5. Canonical and brownfield workflows

### Canonical workflow — DevolaFlow workspace

1. Read the workspace contract and inspect `.local/index.md`,
   `.local/tasks/`, and the protected `.local/.agent/` surfaces.
2. Inventory task folders without changing them; classify each as active,
   done, stale, unknown, or protected.
3. Render a dry-run plan with stable cluster keys, exact source/destination
   paths, reference findings, and a deletion-free action.
4. Obtain the later approval required by the plan and stop cards.
5. Apply only approved moves/copies; keep active change folders outside task
   clustering and preserve W-19 research archives separately.
6. Write/refresh the task index and append the path mapping. Verify that every
   source has one disposition, every destination is unique, and no protected
   path changed.

The reference physical layout may use cluster `active/` and `archive/`
subdirectories, but the protocol must not require six named clusters.

### Brownfield workflow — flat layout

1. Detect `.local/tasks/` if present, even when `.local/.agent/` or other
   canonical scaffolding is absent or incomplete.
2. Treat every child as unknown until its task metadata and path safety are
   inspected; preserve unrelated files and directories.
3. Produce a report-only inventory and a proposed mapping. Do not infer that
   a directory is disposable because its name contains `tmp`, `old`, `done`,
   or `archive`.
4. Allow an operator to retain a flat layout, adopt clusters gradually, or
   approve a subset of moves. Missing index/handoff files are findings, not
   reasons to create empty canonical scaffolding automatically.
5. Re-run the same bounded verification after an approved migration; leave
   dirty or ambiguous trees untouched.

## 6. Implementation candidates and test budget

Potential later-cycle files, subject to approval:

* `workflow-system/agent/templates/seeds/local-archive.yaml` and
  `workflow-system/agent/templates/registry.yaml` if the new seed is chosen.
* `workflow-system/agent/references/local-archive.md`, plus C-7 registration
  surfaces, if the operator-facing protocol is accepted.
* `src/devolaflow/local/archive.py` as the single runtime owner for plan
  validation, safe path checks, index rendering, and mapping emission.
* A narrowly scoped local-archive CLI/lint entry point, rather than adding
  task semantics to `src/devolaflow/agent_workspace/lint.py`.
* Focused tests such as `tests/test_local_archive.py`, seed/manifest parity
  tests, and a current-cycle ghost-audit entry before any CHANGELOG change.
* `src/devolaflow/workspace_context.py` only in a separately reviewed change
  if task inventory must enter session discovery; it should not be expanded
  implicitly by the first implementation.

Estimated test addition: about 16–24 new test functions—covering canonical
and brownfield discovery, dry-run idempotence, protected paths, dirty git
trees, symlinks, duplicate destinations, mapping append-only behavior, index
drift, and seed/reference parity. The estimate stays below W-17's per-PV
limit of 30, while each modified Python module still needs at least 80%
coverage. This is an estimate, not completed test evidence.

## 7. Frozen surfaces and constraints

The later implementation must preserve:

* `schemas/lean-dispatch.yaml` canonical order and the 17-position dispatch
  layout; no new top-level dispatch field is needed.
* Tier-A layout witnesses under
  `benchmarks/devolaflow_context/baselines/`.
* Plugin/host registries and the existing environment-flag inventory.
* `ChangeStore`/`ArchiveManager` semantics for `.local/.agent/` changes.
* W-19's cycle-research archive semantics and source provenance.
* The distinction between `.local/tasks/`, `.local/.agent/`, `.local/research/`,
  `.local/memory/specs/`, and `.local/human/`.
* S-8 ownership and S-9 append-only records. No compiled rule surface may be
  hand-edited; any approved rules change must originate in `.rules/` and use
  the compiler.

## 8. Risks and non-goals

**Risks:** a cluster taxonomy can become a second uncontrolled registry;
physical moves can invalidate links; stale/unknown classification can be
subjective; brownfield repositories may contain nested repositories and
ignored notes; index generation can overwrite human edits; and exposing task
inventory through session discovery can expand context and cache impact.

**Non-goals:** redesigning W-19, changing the active-change FSM, automatically
cleaning all of `.local/`, deleting clones or worktrees, creating a fixed
six-cluster manifest, adding a new environment flag, changing dispatch schema
  order, modifying source-of-truth specs, or turning this design into a
  runtime implementation during this cycle.

## 9. Historical pre-finalization questions

The following questions were the bounded pre-finalization grill agenda. They
are retained as part of the initial design history; all are settled in the
decision record below.

The bounded grill resolved, in order of material impact:

1. Is this a recurring workflow deserving a new `local-archive` seed, or a
   one-off explicit command?
2. Is physical clustering required, or is a virtual index sufficient for the
   first implementation?
3. What exact lifecycle/status vocabulary distinguishes active, done, stale,
   unknown, and protected?
4. Which paths are protected by default, and may any non-task path be moved?
5. What is the exact clean-tree definition for ignored files, nested repos,
   worktrees, and review notes?
6. Is deletion permanently operator-only, or may a separately approved plan
   authorize it after clean checks?
7. Should mappings reuse S-9 handoff envelopes or use a dedicated append-only
   task-archive record?
8. Should the task inventory enter `scan_workspace`, or remain an explicit
   local command to protect context budgets?
9. Which surface—reference, seed, runtime helper, or lint—is actually needed
   for the first release, and what are its C-7/test/coverage costs?
10. Are any Workflow-layer rule additions necessary? Each proposed rule must
    be approved independently; this design does not authorize one.

## 10. Grill decision record

All ten questions from §9 are settled. The decisions below define the design
for a later implementation cycle; “approved” means settled as design intent,
not authorized implementation in this cycle. Each decision records its
implications, rejected alternatives, and approval status.

### Round 1 — Workflow identity, moves, lifecycle, and protection

#### 10.1 Independent recurring workflow

**Settled answer:** Local archiving is an independent recurring workflow and
uses a new `local-archive` seed. It is not an extension of
`entropy-cleanup`.

**Implications:** The seed may declare inventory, classification, report-only
planning, approval, mapping, and bounded apply assertions. Cleanup and archive
semantics retain separate review boundaries, registries, and tests.

**Rejected alternatives:** Extending `entropy-cleanup` would combine stale
content cleanup with structural task migration and make physical moves look
like generic cleanup. A one-off command without a seed was rejected for the
recurring workflow, although an explicit command remains part of the first
operator-facing implementation surface.

**Approval status:** Settled and approved as later-cycle design intent;
implementation is deferred and not authorized in this cycle.

#### 10.2 Physical move policy

**Settled answer:** Physical moves are required, but only after report-only
planning and explicit operator approval.

**Implications:** The workflow must first emit exact source/destination paths,
classifications, reference findings, and protected-path checks. Apply may move
only the explicitly approved plan, preserve task context, and emit mappings.

**Rejected alternatives:** A virtual index alone was rejected because it
leaves entropy in the active task directory. Automatic moves, moves without a
report, and approval inferred from a dry run were rejected.

**Approval status:** Settled and approved as later-cycle design intent;
implementation is deferred and not authorized in this cycle.

#### 10.3 Lifecycle vocabulary

**Settled answer:** Lifecycle vocabulary is exactly `active`, `done`, `stale`,
and `unknown`. `protected` is a separate protection verdict/reason, not a
lifecycle state.

**Implications:** Every candidate receives one lifecycle classification plus
an independent protection result when applicable. Protected paths cannot be
made eligible merely by assigning a lifecycle value.

**Rejected alternatives:** Treating `protected` as a fifth lifecycle state
was rejected because it conflates task state with path safety. Inferring
`done` or `stale` solely from names, mtimes, or file size was also rejected.

**Approval status:** Settled and approved as later-cycle design intent;
implementation is deferred and not authorized in this cycle.

#### 10.4 Default protected and eligible surfaces

**Settled answer:** The default protected set is `.local/.agent/`,
`.local/memory/specs/`, `.local/research/`, `.local/human/input/`, `.rules/`,
and all source/config surfaces. Non-task paths are not default archive
sources.

**Implications:** The default source boundary is task-scoped and conservative.
Protected surfaces remain unchanged, and any future expansion requires a
separate workflow and explicit approval.

**Rejected alternatives:** Scanning every directory under `.local/`, reusing
the W-19 research classifier, or treating runtime/tool directories as default
task sources was rejected because active provenance and write surfaces could
be misclassified.

**Approval status:** Settled and approved as later-cycle design intent;
implementation is deferred and not authorized in this cycle.

### Round 2 — Safety, provenance, and context budget

#### 10.5 Exact clean-tree gate

**Settled answer:** “Clean” means strict
`git status --short --untracked-files=all` with staged and unstaged diff
inspection, symlink checks, nested-repository checks, worktree-registry
checks, and untracked review-note checks. Any ambiguity refuses the action.

**Implications:** The gate is a safety precondition for any later destructive
or migration-sensitive action, retains a pre-action inventory, and emits an
explicit refusal for dirty, ambiguous, missing, or unreadable paths. It never
authorizes `git clean` or equivalent deletion.

**Rejected alternatives:** Checking only the short status output, ignoring
ignored files or untracked notes, or treating a dry run as sufficient
evidence was rejected. Broad automatic cleanup was rejected.

**Approval status:** Settled and approved as later-cycle design intent;
implementation is deferred and not authorized in this cycle.

#### 10.6 Permanent deletion boundary

**Settled answer:** Deletion is permanently operator-only. `local-archive`
has no automatic deletion API.

**Implications:** The workflow may report candidates and apply approved
non-deletion moves, but it must stop before deletion and hand the exact
candidate set to the operator. Clean checks do not change this boundary.

**Rejected alternatives:** Deletion after a dry run, deletion after a clean
check, and a separately approved runtime deletion mode were rejected as
unbounded expansion of the archive contract.

**Approval status:** Settled and approved as later-cycle design intent;
implementation is deferred and not authorized in this cycle.

#### 10.7 Mapping record ownership

**Settled answer:** Physical moves use a dedicated append-only task-archive
mapping record, not the existing handoff envelope.

**Implications:** The record owns complete old-path → new-path mappings,
source/destination provenance, reason, and sequence metadata for task archive
moves. Existing handoff envelopes remain immutable and are not repurposed.

**Rejected alternatives:** Reusing the existing handoff envelope schema,
updating only `INDEX.md`, or mutating a prior mapping record was rejected
because task-archive provenance is a separate contract and must remain
append-only.

**Approval status:** Settled and approved as later-cycle design intent;
implementation is deferred and not authorized in this cycle.

#### 10.8 Task inventory and context budgets

**Settled answer:** Keep task inventory out of default `scan_workspace`; use
an explicit command to protect context budgets.

**Implications:** Discovery remains opt-in and bounded. The explicit command
owns task inventory, planning, and archive inspection without changing the
default session context or cache prefix.

**Rejected alternatives:** Expanding `scan_workspace` to enumerate task
folders by default, injecting task status into every session, or adding an
implicit archive scan was rejected because it would increase context and
cache impact for unrelated work.

**Approval status:** Settled and approved as later-cycle design intent;
implementation is deferred and not authorized in this cycle.

### Round 3 — First implementation surface and governance

#### 10.9 Minimum first implementation

**Settled answer:** The first implementation needs all of the following:

1. A new operator reference with C-7’s four-piece registration.
2. A new seed with registry/template parity.
3. A single-owner runtime helper.
4. An explicit report-only-by-default CLI/command.
5. An independent plan/index/mapping lint or doctor.

Do not expand `agent_workspace.lint`.

**Implications:** The later implementation must provide operator guidance,
declarative parity, one runtime source of truth, a safe default, and focused
contract validation. Task-archive semantics remain separate from the active
change artifact linter.

**Rejected alternatives:** Prompt-only instructions, silently extending
`agent_workspace.lint`, or shipping a runtime without a report-only command
and independent doctor/lint were rejected because they would drift or mix
independent contracts.

**Approval status:** The complete minimum is settled and approved as a
later-cycle implementation target; no implementation is authorized in this
cycle.

#### 10.10 Rules-layer proposals

**Settled answer:** Propose all three rules-layer changes as independent
approval items:

1. deletion safety;
2. mapping append-only behavior;
3. index-generation honesty.

None is authorized by this design.

**Implications:** A later proposal must describe each rule separately, update
the canonical `.rules/` source, recompile generated rule surfaces, and
provide its own evidence. No rule-layer change is implied by approval of the
local-archive design.

**Rejected alternatives:** Bundling the three rules into one implicit
approval, hand-editing compiled rule surfaces, or treating this design record
as authorization was rejected.

**Approval status:** All three are proposed for independent later approval;
all three remain unauthorized in this cycle.

The six-cluster physical shape described in the cleanup report and used in
the reference examples remains only a reference example, not a canonical
manifest.

**Finalization status:** Design is finalized for a later implementation cycle;
no runtime implementation is authorized in this cycle.
