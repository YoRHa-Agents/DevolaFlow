# Host Support Contract (HSC) 设计 — Gap Analysis + Design Memo

> 状态：设计定稿，待排入周期（W-1 / SI-1 入口物）
> 目标周期：v17.4.0（Pathfinder 已占用 v17.3.0；本周期进入实现）
> 交付形态：**仅设计**（本文），实现按本周期三个 PV 分段落地
> 目标 host 集：kimi、claude、cursor、copilot、codex、dsh（6 个）
> 方法：四路并行全库调研（host 面清单 / 桥与执法面 / DSH 宿主特性 / 五 host 能力对照）
> + 两处上游文档核验（Copilot hooks 官方文档、DSH publish 契约）

---

## 1. 背景与问题

任务原述是「升级 devola-flow skill 支持契约，需要能支持 kimi claude cursor copilot
codex dsh」。核验后结论是：**本仓不存在「支持契约」这个对象**，因此不是升级，而是从零
建立。

现状是 host 身份被**六个互不派生的注册表**各自重新声明，每个由自己的测试独立钉死。
「支持某个 host」没有定义，于是六个目标 host 的覆盖必然参差：`kimi` 缺 `devola-init`、
`dsh` 完全没有 skill 投递路径、`copilot` 没有桥。更糟的是没有任何机制能检测这种参差
——因为没有可对照的契约。

## 2. 现状分析（SI-1 (a) 缺陷枚举）

### 2.1 六个冲突注册表（A-5 违例）

| # | 注册表 | owner | 已知 host 数 |
|---|---|---|---|
| 1 | build-skill 适配器 | `src/devolaflow/adapters/registry.py` + `adapter_configs/` | 16（4 Python core + 12 YAML） |
| 2 | 安装 profile | `workflow-system/agent/manifest.yaml` | 9 |
| 3 | shell 安装目标 | `scripts/install.sh` | 12 |
| 4 | `devola-init` TOOLS | `src/devolaflow/init_project.py` | 4 |
| 5 | npm TARGETS | `packages/npm/bin/devola-flow.js` | 2 |
| 6 | host 桥 | `src/devolaflow/hostbridge/` | 5 known / 4 install / 2 session |

A-5 要求每个域注册面「恰好一个 owner 模块」。host 身份是一个域，却有六个 owner；
每个都有独立的 pin（`_REQUIRED_PROFILES`、`TOOLS`、`TARGETS`、`KNOWN_HOSTS`、
`INSTALL_HOSTS`、`SESSION_HOSTS`、`test_create_default_registry_has_4_core`）。
**六个 pin 全绿而彼此矛盾**，这正是 A-5.1「拆分注册数据使缓存推理失效」所禁止的形态。

派生缺陷（全部有据）：
- `kimicode` 在 install.sh + manifest + adapter 中存在，在 `devola-init` TOOLS 中缺失。
- npm 仅 cursor/claude（global），落后 install.sh 的 12 目标。
- `install.sh` 的 copilot / windsurf 分支**绕过 manifest** 直接下载 SKILL.md，manifest
  中它们的 profile 是死数据 → manifest 改动不会传导，属静默漂移。
- `knowledge/` 出现在 SKILL.md 导航表，却不在任何 profile 的 file set 里，从不投递。

### 2.2 三个实证发现（调研新增，非任务原设想）

#### F-1（P0，S-4 级）：DSH 桥已发布但功能性缺失

`packages/dsh-plugin/` 有 README、有 ghost pin、有 fixture、测试全绿，但对真实 DSH 无效：

1. **装不上**：`package.json` 无 `dsh.bundle.patch` 字段，仓内也无 `cordis.patch.yml`
   （`rg 'dsh\.bundle|cordis\.patch'` 全库零命中）。DSH 的 publish 契约
   （`docs/user/develop/basic/publish.md`）要求二者齐备才能 `dsh plugin add`。
   `host-bridges.md` §5 与插件 README 印的安装命令**必然失败**。
2. **匹配不到写工具**：`index.mjs::WRITE_TOOLS` =
   `{write_file, str_replace, edit_file, create_file, Write, StrReplace, Edit, MultiEdit}`。
   DSH 实际写工具是 `write` / `edit` / `str_replace_editor`（`docs/tool-catalog.md`）。
   `Set` 匹配大小写敏感，`Edit ≠ edit` → **三个写工具无一命中** → `kind` 停在
   `unknown` → 全部放行。DSH 侧 S-8 执法等于零。
3. **取不到参数**：读的是 `exec.args ?? exec.input`，DSH 实际传 `exec.arguments`
   （见 `dsh-feishu-bridge/.../pre-execute-gate.mjs` 原生用法）→ 即使命中也拿不到 path。

根因不是粗心，而是**机制缺陷**：`tests/fixtures/hostbridge/dsh.json` 是自撰形状，
测试因此只验证了「插件与自己的假设一致」，而非「与宿主真实载荷一致」。这个失败模式会
在每个新增 host 上复现，必须由契约机制封堵（见 §4.5）。

#### F-2（P0）：Copilot 有钩子，且 fail 语义与全仓不同

官方文档（`docs.github.com/en/copilot/reference/hooks-configuration`）：Copilot 支持
`preToolUse` 等 6 类钩子，配置位于 `.github/hooks/*.json`（仓库级）、
`~/.copilot/hooks/*.json`（用户级，`$COPILOT_HOME` 可改）、`~/.copilot/settings.json`
的内联 `hooks` 块；输出 `permissionDecision: allow|deny|ask`。

本仓对此**零认知**（`rg 'copilot/hooks|\.github/hooks'` 零命中），
`integration-guide.md` 现文写着 Copilot「does not claim bridge support」——该论断已失效。

关键差异：**command 型 `preToolUse` 是 fail-closed**——exit 2 判 deny，**其他任何非零
退出也判 deny**（`"Denied by preToolUse hook (hook errored)"`），即使 stdout 声明
allow；唯独**超时 fail-open**。全仓现有五桥一律 fail-open（`host-bridges.md` §4），
Claude/Codex/Kimi 用的正是「exit 2 = deny」协议——**该协议直接搬到 Copilot 会把每一次
桥内部错误变成对宿主工具的拒绝**，违反 fail-open 不变量。

#### F-3：DSH 的 skill 面完全契合却完全未用

DSH 原生 skill 发现根（`docs/subsystems/skills.md`）：`<project>/.dsh/skills`、
`<project>/.agents/skills`、`<dshHome>/skills`（`~/.dsh`，`$DSH_HOME` 可改）等六个优先级
层。frontmatter 仅强制 `name` + `description`，是 C-5 九键的**子集** → 现有 SKILL.md
可原样投递。DSH 另有 `dsh-agent-instructions` 自动加载 `AGENTS.md` / `CLAUDE.md`。
而本仓 `dsh` 无 manifest profile、无 install.sh 目标、无 adapter —— 投递面为零。

附带：DSH 的委派原语是 `subagent` / `subagent_fork`，**不叫 `Task`**；SKILL.md 现文
无条件写「delegate to L2 Task Agents via the `Task` tool」，在 DSH 上是错的指令。

### 2.3 被证伪的前提

任务原设想「升级支持契约」隐含契约已存在。核验：最接近的四个surface 都不是契约——
`manifest.yaml`（只有投递 file set，无能力语义）、`integration-guide.md`（人类文档，
无强制力）、`host-bridges.md` §2（只覆盖桥这一个轴，且 5 host）、
`docs/designs/design_delivery_architecture.md` §1.2（4-host 设计期矩阵，Claude 行已过期，
非执法面）。**结论：建立，不是升级。**

## 4. 设计方案

### 4.1 契约对象与分层

**HSC = 一份声明式 host 能力契约**：定义「支持」的可验证含义，并使每条对外支持声明
可回溯到注册表条目。

| 档 | 数 | 成员 | 义务 |
|---|---:|---|---|
| **Tier G**（保证） | 6 | cursor, claude, codex, copilot, kimicode, dsh | 必须满足 §4.2 全部 5 条 floor；extras 逐轴显式声明 |
| **Tier C1**（社区·可安装） | 4 | windsurf, zed, cline, roo | 需 adapter + budget 测试 + 有效安装路径；**不得**声明任何 extras |
| **Tier C2**（社区·仅构建） | 7 | continue, openclaw, gemini, jetbrains, amazon_q, augment, trae | 仅需 adapter + budget 测试；无安装路径义务，不得声明 extras |

合计 17。注意与「16 个 adapter」的差：`dsh` 无 adapter 而进 Tier G（F-3），
`kimicode` 是 YAML adapter 而进 Tier G ——**adapter 集与 host 集不是同一个集合**，
这本身就是 §2.1 六注册表各自为政的直接证据。

Tier C 的存在意义是**明示非保证**：现状这 11 个 host 与 6 个目标 host 在文档里同列，
读者无法区分保证等级。分档后 README / 人类文档的支持声明可分级生成。

### 4.2 能力轴（5 floor + 5 extras）

**Floor（Tier G 强制，缺一即非 supported）**

| # | 轴 | 内容 |
|---|---|---|
| F1 | `skill_delivery` | `kind`（skill-dir / rule-file / rule-tree）+ `sets` + project/global 落点路径 |
| F2 | `instruction_format` | 产物文件名 + frontmatter 契约 + budget（type/max） |
| F3 | `install_channels` | ≥1 个自动化渠道（install.sh / devola-init / npm）且渠道真实派生自 manifest |
| F4 | `doctor` | 版本戳可读、`devola-init-doctor --skills` 可核验 |
| F5 | `tests` | 安装 parity 测试 + adapter budget 测试（测试路径登记在条目内） |

**Extras（逐轴声明，未声明 = 不支持，不得对外宣称）**

| # | 轴 | 关键子字段 |
|---|---|---|
| E1 | `boundary_bridge` | `status` / `config` 路径 + `scope` / `events` / `response`（协议族） / `host_fail_mode` / `automation`（automated \| snippet \| plugin-channel \| manual） / `fixtures` + `fixture_provenance` |
| E2 | `session_resume` | `status` / 宿主事件名 |
| E3 | `subagent_dispatch` | `primitive`（原语真名：`Task` / `subagent` / none） |
| E4 | `mcp` | `status` / 配置面 |
| E5 | `tool_vocabulary` | 逐 host 的 `write` / `shell` 工具名列表 |

E5 修正一处现有设计味道：`normalize.py::_WRITE_TOOLS` 是**跨 host 扁平并集**，
host A 的工具名可在 host B 上命中，且「并集看起来很满」正好掩盖了 F-1 的漏项。改为
逐 host 声明、并集由代码派生 → 词表不全的 host 立即可见、可 lint。

### 4.3 SSOT schema 草案

`workflow-system/agent/hosts.yaml`（示例给 cursor 全条目 + copilot/dsh 关键 delta）：

```yaml
schema_version: 1
hosts:
  cursor:
    display_name: Cursor
    aliases: []
    tier: guaranteed
    version_added: "0.1.0"
    floor:
      skill_delivery:
        kind: skill-dir
        sets: [core, references, examples]   # 名字引用 manifest.yaml 的 file set
        paths:
          project: .cursor/skills/devola-flow
          global: $HOME/.cursor/skills/devola-flow
      instruction_format:
        artifact: SKILL.md
        frontmatter: c5-full
        budget: {type: lines, max: 500}
      install_channels: [install.sh, devola-init, npm]
      doctor: stamp
      tests: [tests/test_install_manifest.py, tests/test_build_skill.py]
    extras:
      boundary_bridge:
        status: implemented
        scope: project
        config: [.cursor/hooks.json, .cursor/hooks/devola-boundary.sh]
        events: {file_write: [preToolUse], shell: [beforeShellExecution]}
        response: {family: stdout-json, always_exit: 0, deny_key: permission}
        host_fail_mode: open
        automation: automated
        fixtures: [tests/fixtures/hostbridge/cursor.json]
        fixture_provenance: TBD-audit   # Phase 1 需逐 host 回溯定级，勿预设
        provenance_ref: null            # 定级为 vendor-doc 时必须补上游 URL
      session_resume: {status: implemented, event: sessionStart}
      subagent_dispatch: {status: native, primitive: Task}
      mcp: {status: undeclared}
      tool_vocabulary:
        write: [Write, StrReplace]
        shell: [Bash]

  copilot:
    tier: guaranteed
    floor:
      skill_delivery: {kind: rule-file, sets: [core],
                       paths: {project: .github/copilot-instructions.md}}
      instruction_format: {artifact: copilot-instructions.md,
                           frontmatter: none, budget: {type: chars, max: 4000}}
    extras:
      boundary_bridge:
        status: designed            # Phase 2 落地；当前不得对外声明
        scope: [project, global]
        config: [.github/hooks/devola-boundary.json, ~/.copilot/hooks/]
        events: {file_write: [preToolUse], shell: [preToolUse]}
        response: {family: stdout-json, always_exit: 0,
                   deny_key: permissionDecision}
        host_fail_mode: closed     # 关键：wrapper 必须归一化，见 §4.6
        automation: automated
        fixture_provenance: vendor-doc
        provenance_ref: "https://docs.github.com/en/copilot/reference/hooks-configuration"
      subagent_dispatch: {status: undeclared, primitive: null}

  dsh:
    display_name: DeepSeek Harness
    tier: guaranteed
    floor:
      skill_delivery:
        kind: skill-dir
        sets: [core, references, examples]
        paths:
          project: .dsh/skills/devola-flow
          global: $DSH_HOME/skills/devola-flow   # 默认 ~/.dsh
    extras:
      boundary_bridge:
        status: broken             # F-1：已发布但失效，显式记账
        automation: plugin-channel
        response: {family: waterfall, deny_kind: deny}
        host_fail_mode: open
        fixture_provenance: synthetic   # ← 不足以声明 support，lint 报错
      subagent_dispatch: {status: native, primitive: subagent}
      tool_vocabulary:
        write: [write, edit, str_replace_editor]

```

`status` 取值封闭为 `implemented | designed | broken | undeclared`。
`broken` 是有意设计的记账态：让 F-1 这类「声明与现实背离」在注册表里可见，而不是靠
CHANGELOG 考古。

### 4.4 派生视图与零消费者改动的迁移

Phase 1 的核心约束是**不动任何现有消费者**（`install.sh` 用 shell 解析器读 manifest、
`install_manifest.py`、`sync_cursor_skill.py`、npm 的 JS 都读 manifest）。方案：

1. `hosts.yaml` 成为 F1/F2 的权威来源。
2. `manifest.yaml::install_profiles` 保留原位、原格式（含「keep each profile on ONE
   line in flow style」的 shell 解析器约束），但降级为**生成镜像**。
3. 新增 parity lint：镜像与 hosts.yaml 派生结果不一致即 CI 失败。
4. manifest 继续独占 file set（`core` / `references` / `examples`）——它是 C-7 的
   install-manifest SSOT，职责不变；hosts.yaml 只按名字引用 set。

这是 A-5 表第 1 行既有先例的复用：v15.0.0 G-021 让 `plugins.yaml` 从第二 owner 降为
`runtime-plugins.yaml` 的派生视图，路径仍被 pin 住。同一手法、同一风险画像。

后续 Phase 才逐个把 `TOOLS` / `TARGETS` / `KNOWN_HOSTS` / `INSTALL_HOSTS` /
`SESSION_HOSTS` 改为从 hosts.yaml 派生，每次一个 surface、各自独立可回滚。

### 4.5 声明-证据对等（W-25 核心，F-1 的机制封堵）

**规则**：任何 `boundary_bridge.status: implemented` 声明必须有 fixture，且
`fixture_provenance` ∈ {`captured`, `vendor-doc`}：

| provenance | 含义 | 是否足以声明 implemented |
|---|---|---|
| `captured` | 从真实宿主会话抓取的载荷 | 是 |
| `vendor-doc` | 依上游官方文档构造，`provenance_ref` 必须给 URL | 是 |
| `synthetic` | 自撰形状，无外部依据 | **否** — lint 失败 |
| `TBD-audit` | 尚未回溯定级（Phase 1 迁移期的过渡态） | **否** — Phase 1 结束前必须清零 |

Phase 1 的一项交付即是把现有五桥 fixture 逐个从 `TBD-audit` 定级；任何定不到
`captured`/`vendor-doc` 的，其 host 的 `boundary_bridge.status` 必须降到 `broken` 或
`designed`，并同步修正对外文档声明。

配套两条：

1. **词表对齐**：`tool_vocabulary.write` 的每个条目必须在同 host 的 fixture 或
   `provenance_ref` 中有依据 → F-1 的「`write`/`edit` 漏项」在 lint 阶段即暴露。
2. **声明面派生**：`host-bridges.md` §2 矩阵、`integration-guide.md` 表、README 支持
   列表全部由 hosts.yaml 生成或 parity 校验。这消灭了「文档说 Copilot 没有桥、而它有」
   这一类漂移（F-2 的根因）。

### 4.6 Copilot 桥设计（fail-closed 归一化）

上游语义（已核验）：command 型 `preToolUse` 中 **exit 0 是唯一的放行途径**；exit 2 判
deny；其他非零同样判 deny；超时 fail-open。

结论：Copilot **不属于 Claude 协议族**（exit 2 = deny），而属于 **Cursor 协议族**
（stdout JSON + 恒 exit 0），仅 JSON 键名不同（`permissionDecision` vs `permission`）。
`__main__.py` 的响应分支因此按族扩展，而非新增第三种形态。

fail-open 不变量的保持方式：wrapper 在**除有意 deny 外的一切路径上 exit 0**（含 Python
缺失、spawn 失败、桥内异常）。宿主的 fail-closed 天性由 wrapper 吸收，DevolaFlow 侧
契约不变。`host_fail_mode: closed` 因此是**描述性字段**，不是不变量的例外。

补充（Phase 2 需核验，勿预设）：payload 有两种方言——camelCase `toolName`/`toolArgs`
（Copilot 原生）与 snake_case `tool_name`/`tool_input`（VS Code 兼容的 PascalCase
`PreToolUse`，且工具名报为 Claude 名如 `Bash`）。normalize 需同时接受，后者可能已被现有
`_WRITE_TOOLS` 并集覆盖。云端 agent 仅加载 `.github/hooks/*.json`。

### 4.7 DSH 双路径

## 8. 可行性结论与风险

**可行，但成本高于任务原设想**——因为要建立的不止是文档，而是一个缺失的注册域，且过程
中发现两个 P0 缺陷（F-1 已发布即失效、F-2 上游能力误判）。

成本可控的关键是 D-5：Phase 1 靠 G-021 先例把新 SSOT 做成权威 + 旧面做成生成镜像，
**零消费者改动、零行为改动**，把「统一六个注册表」这个高风险动作切成可逐个回滚的后续
Phase。新造面收敛为：一个 YAML SSOT、一个 schema、一份 reference、一个加载/lint 模块、
一条新规则。

主要风险与缓解：

1. **manifest 双写漂移**（镜像与 SSOT 不一致）→ parity lint 进 CI，与
   `test_rule_surfaces_compile_only` 同一执法形态（编译产物禁手改）。
2. **Copilot fail-closed 误接**（照抄 Claude 的 exit 2 协议 → 桥错误变宿主拒绝）
   → §4.6 归一化 + 专项 fail-open 不变量测试；`host_fail_mode` 字段使该差异在注册表
   层面显式可见。
3. **DSH 是 0.1.1-rc.2 且明示会破坏兼容**（其 README「THERE WILL BE
   COMPATIBILITY-BREAKING CHANGES」）→ 条目记 `version_added` 与被验证的 DSH 版本；
   provenance 机制保证 DSH 变更时 fixture 失配可见而非静默失效。
4. **规则膨胀**（新增 W-25）→ 仅 1 条，且替换 W-5 的手钉数字，净复杂度接近持平。
5. **范围失控**（六注册表统一诱发大重构）→ D-1 分期硬隔离：本周期纯设计，Phase 1 零
   行为改动，统一动作分散到 Phase 3/4 且各需人类 Gate。
