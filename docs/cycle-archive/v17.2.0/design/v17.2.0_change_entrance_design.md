# Change 工作区 entrance.md 工件 — Gap Analysis + Design Memo

> 状态：**已实现**（2026-08-27，用户指令「直接实现」；as-built 修正见 §8）
> 目标周期：v17.2.0（暂定；可与 Pathfinder 同周期、独立 PV——两者无耦合）
> 来源：`plan_mode_full_update` 设计合同的后续补充（用户口头追加，原话逐字见 §1）
> 形态参照：`.local/tasks/plan_mode_full_update/entrance.md`（同概念在任务档案层的手工原型）

---

## 1. 背景与用户意图（逐字，C-3）

> 「需要追加一个面向 agent 的entrance.md 作为入口，方便各种 agent工具能正确加载和响应各个子文档功能」
>
> 「devola flow 在执行任务设计时，参照这份 plan以外，除了 checklist goal等文件外，还要额外补充一个 entrance.md 以方便各种 agent快速接入」

解读：change 工作区（`.local/.agent/active/<change-id>/`）的工件集（goal /
checklist / stage / preflight / spec / STATUS / owned_files / evidence）是给
**已在协议内**的 L0/L1/L2 设计的——每类 agent 通过 dispatch payload 或
resume 协议知道该读什么。但**协议外接入者**（新开的 Cursor/Claude 会话、
非 DevolaFlow-aware 的外部 agent 工具、事后审计的人类）落到文件夹时只看到
8 个文件名，没有任何一个文件回答「我是谁的话该先读哪个」。需要一个**就地
存在的入口工件** `entrance.md`。

## 2. 现状分析（SI-1 (a)）

### 2.1 缺口

- `scaffold_change_folder`（`src/devolaflow/skills/slash_commands.py`）生成
  的 v16 checklist 布局无入口文件；工件职责说明只存在于框架文档
  （`workflow-system/agent/references/agent-workspace.md`），协议外接入者
  不知道也不该被要求先读完框架文档。
- resume 协议（五步清单）以 STATUS.yaml 为入口，但那是给协议内 L0 的；
  STATUS.yaml 是机器可读状态，不解释工件拓扑。
- 「各种 agent 快速接入」的本质诉求：**入口必须在文件夹内**——generic
  工具只能看见文件夹本身，看不见框架文档。

### 2.2 可复用先例

- `harness_preflight.md`：可选工件 + artifact-as-flag 的 lint 接线先例
  （`lint.py::CHECKLIST_ARTIFACT_BUDGETS` 注释区）。
- `.local/tasks/plan_mode_full_update/entrance.md`：入口文档的内容形态原型
  （路由表 + 阅读纪律 + SSOT 重定向），本设计将其收敛为轻量模板。
- C-9 预算表 + `devolaflow.agent_workspace.lint`：预算与必备性检查的现成
  执法面。

## 3. 决策记录

| # | 决策 | 定案 |
|---|---|---|
| D-1 | 定位 | change 工作区新增标准工件 `entrance.md`，propose 期由 `scaffold_change_folder` 生成，L0 拥有 |
| D-2 | **静态路由器，不镜像状态** | 只路由不复制：进度/轮次/blocker 永远指向 STATUS.yaml、stage.md、preflight §4 快照的**出处**，不复制数值 → 零每轮刷新义务、零漂移风险、无新 lifecycle hook |

| D-4 | 必备性 | 新 scaffold 必备（进 lint required-artifact 集）；存量 in-flight folder 在首次 resume 时由 L0 回填（单文件 < 20 行，P1 trivial waiver 适用） |
| D-5 | **零 dispatch 触碰** | 不进 `hydrate_change_context` 注入集、不动 `schemas/lean-dispatch.yaml`（canonical_order 17 不动）。entrance 服务**会话级/带外**接入；协议内 L2 已经从 dispatch payload 拿到最小上下文（P2），再注入即双重花费 |
| D-6 | 预算 | C-9 新行：`entrance.md` soft 400 / hard 800（镜像 stage.md 行；内容以表格行计，8 工件表 + 4 场景路由可容纳） |
| D-7 | 防漂移 lint | 新增 parity 检查：entrance §3 工件表的文件名集合 ↔ `CHECKLIST_ARTIFACT_BUDGETS` 键集一致（guard 级机器可验）——工件集将来增删时 entrance 不会静默过期 |
| D-8 | 个性化最小面 | 仅 §1 逐 change 个性化（goal 标题 + change-id）；§2-§4 由 scaffold 模板统一生成，框架版本升级时随模板演进——内容确定性使 scaffold 输出对同输入 byte-stable |
| D-9 | 零新增 env flag | 无激活开关：scaffold 无条件生成（W-20 合规，无新活动面） |

## 4. 设计方案

### 4.1 工件模板（scaffold 生成形态）

```markdown
---
parent: <change-id>
schema_version: 1
---

# Entrance — <change-id>

> 本 change 的 agent 接入入口。任何会话/工具接入本文件夹，先读本文件，
> 按 §2 场景路由加载所需工件——不要顺序通读全部文件。

## 1. 这个 change 是什么
<goal.md 标题逐字> → 详见 [goal.md](goal.md)

## 2. 场景路由
| 接入场景 | 读取顺序 |
|---|---|
| 会话恢复 / resume | STATUS.yaml → stage.md 当前轮 → checklist.md 未勾项 |
| 新 L2 Task 接入 | 自己 dispatch 携带的 checklist_items → owned_files.txt → spec.md |
| Review / 核证 | checklist.md 已勾项 `evidence:` 行 → evidence/ 对应文件 |
| 人类审计 / 旁观 | preflight.md §4 进度快照 → stage.md 轮次历史 → goal.md |

## 3. 工件清单
| 文件 | 角色 |
|---|---|
| goal.md | G 编号目标清单（合同锚点） |
| checklist.md | 可校验追踪表（主工件；勾选=有证据的 DONE） |
| stage.md | 轮次管控（取项/波次/历史） |
| preflight.md | 执行前确认面 + 最新进度快照（§4） |
| spec.md | 行为 delta（A-4） |
| STATUS.yaml | 机器可读状态（当前真相，先读这里） |
| owned_files.txt | 本 change 合法写入面（S-8） |
| evidence/ | 勾选证据落盘 |
| harness_preflight.md | （可选）harness-flagged 标记 + 缺口预分析 |

## 4. 纪律指针（只给出处，不复述）
- 写入面限制：owned_files.txt + S-8；回退 [x]→[ ] 仅用户可执行（checklist.md 头部纪律）
- handoff envelope append-only：S-9
- 工件预算与 lint：`python -m devolaflow.agent_workspace.lint <change-id>`
```

### 4.2 为什么是逐 change 文件而非框架文档

框架文档（references/）只对读过 SKILL.md 的协议内 agent 可见；「各种 agent
快速接入」的主体恰恰是协议外工具，它们的可见面只有文件夹本身。入口必须
就地存在——这与 `.local/tasks/plan_mode_full_update/entrance.md` 解决其目录
可发现性的逻辑同构。内容 95% 模板化（D-8），故逐 change 复制的边际成本
≈ 一次 scaffold 写盘。

## 5. 优先级排序（SI-1 (b)）

- **P0**：schema + `Change.entrance_md` 接线 + scaffold 模板。
- **P1**：lint 三项（预算/必备/parity）+ C-9 规则行 + 重编译 + 测试。
- **P2**：references/agent-workspace.md + SKILL.md 一行 + 适配器 build（W-5）。

## 6. 风险与缓解

1. **与框架文档内容重复** → D-2/D-3 硬边界：entrance 只路由、只给指针；
   纪律正文永远只在 references 与 checklist 头部，entrance 复述视为 lint 外
   的评审驳回点。
2. **工件集演进后 entrance 静默过期** → D-7 parity lint 机器兜底；模板本身
   是 scaffold 代码的一部分，随框架版本一起演进。
3. **存量 in-flight folder 缺 entrance 触发 MISSING_ARTIFACT** → D-4 回填
   路径 + 实现 PV 的 CHANGELOG「Operator-visible」注明；active folder 生命
   周期短，迁移面天然收敛。

## 7. 可行性结论

**可行，成本显著低于 Pathfinder。** 全部新造面收敛为：一个 schema、一个
dataclass 字段、一段 scaffold 模板、三项 lint、一行 C-9 规则。零 dispatch
schema 改动、零新 hook、零新 env flag、零运行时状态——entrance 是纯静态
工件，实现主体是模板字符串与 lint 断言。

## 8. As-built 修正记录（实现时对 §4 决策的两处落地调整）

1. **D-4 必备性降为 WARN 级缺失**：缺失不进 `MISSING_ARTIFACT`（FAIL）
   而是专项 `ENTRANCE_MISSING`（severity=WARN，不翻 exit code）。理由：
   硬 FAIL 会让所有存量 in-flight folder 在回填前立即 lint 失败，与 D-4
   自己声明的「首次 resume 回填」迁移路径矛盾。存在但格式/奇偶不符仍是
   FAIL（`ENTRANCE_PARENT` / `ENTRANCE_SCHEMA_VERSION` /
   `ENTRANCE_SECTION` / `ENTRANCE_PARITY`）。
2. **模板按 D-6 预算裁剪**：初版模板实测 418 token 超 soft 400，按
   「轻量路由器」原则裁剪措辞至 382 token（demo slug 下），预算 400/800
   维持不动。schema `example` 与 `_entrance_md` 渲染逐字一致，由 ghost
   测试钉死。
