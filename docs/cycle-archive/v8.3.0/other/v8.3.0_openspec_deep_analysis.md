## 1. Architecture & Structure

### 1.1 On-disk layout (per §`docs/concepts.md` §"The Big Picture")

```
your-project/
├── openspec/
│   ├── config.yaml              # Project-level config (schema + context + per-artifact rules)
│   ├── specs/                   # SOURCE OF TRUTH — current behavior
│   │   ├── auth/
│   │   │   └── spec.md          # Domain-grouped spec
│   │   ├── payments/
│   │   │   └── spec.md
│   │   └── ...
│   ├── changes/                 # IN-FLIGHT proposed modifications
│   │   ├── add-dark-mode/
│   │   │   ├── proposal.md      # WHY + scope
│   │   │   ├── design.md        # HOW (technical approach + ADRs)
│   │   │   ├── tasks.md         # Implementation checklist (numbered + checkboxed)
│   │   │   ├── .openspec.yaml   # Optional change-local metadata
│   │   │   └── specs/           # Delta specs (relative to source-of-truth)
│   │   │       └── ui/
│   │   │           └── spec.md  # ## ADDED / ## MODIFIED / ## REMOVED Requirements
│   │   └── archive/             # COMPLETED changes, preserved with date prefix
│   │       └── 2026-01-23-add-dark-mode/  # full artifact set frozen at archive time
│   ├── schemas/                 # Custom schemas (forked from spec-driven)
│   │   └── my-workflow/
│   │       ├── schema.yaml      # Workflow definition (artifact dependency DAG)
│   │       └── templates/       # Markdown templates with HTML-comment AI hints
│   └── explorations/            # `/opsx:explore` artifacts (pre-proposal thinking)
└── src/                         # Project source code (untouched by OpenSpec)
```

**Key invariant:** OpenSpec **never writes outside `openspec/`** (or its tool-adapter destinations like `.cursor/skills/openspec-*/SKILL.md`). The whole framework's blast radius is one top-level directory.

### 1.2 Source-of-truth ↔ in-flight separation

The most consequential architectural decision is the **`specs/` ↔ `changes/`** split:

| Concern | `openspec/specs/` | `openspec/changes/<id>/` |
|---------|-------------------|--------------------------|
| Audience | Long-lived behavior contract for the whole team | Single in-flight modification proposal |
| Mutability | Mutated only at archive time (atomic merge) | Mutated continuously by author + AI agent |
| Conflict surface | One spec per domain → narrow conflict surface | Per-change folder → no inter-change conflicts |
| Review surface | Diff against last archive (clean history) | Self-contained folder, easy to read |
| Audit | Every archived change preserved verbatim under `archive/<YYYY-MM-DD>-<id>/` | Active state only; archive captures final form |

This separation is the single highest-leverage pattern OpenSpec offers — it solves "where does the requirements truth live, and how do we propose changes without breaking it?" without inventing a database.

### 1.3 Artifact dependency DAG (per `docs/concepts.md` §Schemas)

Schema declares artifacts and their `requires:` edges:

```yaml
# Default `spec-driven` schema (verbatim shape)
artifacts:
  - id: proposal
    generates: proposal.md
    requires: []                  # Root node
  - id: specs
    generates: specs/**/*.md      # Glob-expansion supported
    requires: [proposal]
  - id: design
    generates: design.md
    requires: [proposal]          # Parallel sibling to specs
  - id: tasks
    generates: tasks.md
    requires: [specs, design]     # Convergence node
apply:
  requires: [tasks]
  tracks: tasks.md                # Apply phase tracks task checkboxes
```

**Two crucial properties:**
1. **Dependencies are ENABLERS, not GATES** (per `docs/concepts.md` §"Dependencies are enablers, not gates"). You can skip an artifact you don't need (e.g., skip `design.md` for a trivial change). The DAG only blocks the *next-creatable* set, not progress.
2. **Implementation tracks `tasks.md` checkboxes** — apply phase reads checkbox state, marks completed items, can be resumed across sessions.

## 2. Workflow / Lifecycle Mechanics (OPSX)

OPSX is the v3+ workflow (the rebrand of the legacy spec workflow). It defines actions instead of phases.

### 2.1 Slash command surface

| Command | Profile | Action |
|---------|---------|--------|
| `/opsx:explore` | Core | Free-form thinking before structure. No artifacts created — produces `openspec/explorations/<topic>.md` |
| `/opsx:propose` | Core | Default quick path: scaffold change + generate proposal + specs + design + tasks in one shot |
| `/opsx:apply` | Core | Implement tasks; tick checkboxes as work completes; can be resumed |
| `/opsx:archive` | Core | Merge delta specs → source-of-truth; move change folder to `archive/<date>-<id>/` |
| `/opsx:new` | Expanded | Scaffold change folder only (no artifacts yet) |
| `/opsx:continue` | Expanded | Create the next ready-to-create artifact (DAG-driven) |
| `/opsx:ff` | Expanded | Fast-forward: create all planning artifacts (proposal+specs+design+tasks) at once |
| `/opsx:verify` | Expanded | Validate implementation matches artifacts |
| `/opsx:sync` | Expanded | Sync delta specs into main without full archive (rare) |
| `/opsx:bulk-archive` | Expanded | Archive multiple completed changes |
| `/opsx:onboard` | Expanded | Guided walkthrough of an end-to-end change for new contributors |

**Profiles:**
- `core` (default): 4 commands — keeps the surface tiny for new users
- `expanded`: 11 commands — full toolbox for power users; opt-in via `openspec config profile`

### 2.2 Action-not-phase philosophy (per `docs/opsx.md`)

> "You're 'in planning phase', then 'in implementation phase', then 'done'. But real work doesn't work that way. You implement something, realize your design was wrong, need to update specs, continue implementing. Linear phases fight against how work actually happens."
>
> OPSX approach: **Actions, not phases — create, implement, update, archive — do any of them anytime. Dependencies are enablers, not gates.**

### 2.3 Lifecycle finite-state machine

```
[FRESH IDEA]
    │
    ├──→ /opsx:explore ──→ [EXPLORATION ARTIFACT]
    │       (optional)              │
    │                               ▼
    └─────────────────────→ /opsx:propose (or /opsx:new + /opsx:continue×N or /opsx:ff)
                                    │
                                    ▼
                          [CHANGE FOLDER WITH PLANNING ARTIFACTS]
                                    │
                                    ▼
                                /opsx:apply  ←─── (loop until tasks.md checkboxes all ticked)
                                    │
                                    ▼
                                /opsx:verify (optional)
                                    │
                                    ▼
                                /opsx:archive ──→ [SOURCE-OF-TRUTH UPDATED + CHANGE PRESERVED IN archive/]
```

State is **derived from filesystem** (presence of files + checkbox count + folder location); no separate state DB.

### 2.4 Archive merge mechanics (per `docs/concepts.md` §Archive)

When `/opsx:archive` runs:
1. **Apply deltas**: each `## ADDED` requirement appended to source-of-truth spec; each `## MODIFIED` replaces existing requirement with same heading; each `## REMOVED` deletes from source-of-truth.
2. **Move folder**: `openspec/changes/<id>/` → `openspec/changes/archive/<YYYY-MM-DD>-<id>/` (date prefix yields chronological sort).
3. **Preserve artifacts**: ALL of the change's `proposal.md`, `design.md`, `tasks.md`, plus original delta `specs/` are kept verbatim in archive.

Net effect: source-of-truth grows organically as deltas merge; archive is an append-only ledger of why each requirement got there.

## 3. Schema & Artifact System

### 3.1 Spec content rules (per `docs/concepts.md` §Spec Format)

```markdown
# Auth Specification

## Purpose
Authentication and session management for the application.

## Requirements

### Requirement: User Authentication
The system SHALL issue a JWT token upon successful login.

#### Scenario: Valid credentials
- GIVEN a user with valid credentials
- WHEN the user submits login form
- THEN a JWT token is returned
- AND the user is redirected to dashboard
```

| Element | Purpose | Constraint |
|---------|---------|-----------|
| `## Purpose` | Domain summary (1–3 sentences) | Required |
| `### Requirement:` | Specific behavior the system must have | Heading is the requirement's stable ID |
| `#### Scenario:` | Concrete given/when/then example | Multiple per requirement encouraged |
| `SHALL` / `MUST` / `SHOULD` / `MAY` | RFC 2119 keywords | Communicates intent strength |

Specs are explicitly **behavior contracts, not implementation plans**. Internal class names, library choices, step-by-step impl details belong in `design.md` or `tasks.md`.

### 3.2 Delta spec format (per `docs/concepts.md` §Delta Specs)

```markdown
# Delta for Auth

## ADDED Requirements
### Requirement: Two-Factor Authentication
The system MUST support TOTP-based two-factor authentication.
#### Scenario: 2FA enrollment
- GIVEN a user without 2FA enabled
- WHEN the user enables 2FA in settings
- THEN a QR code is displayed for authenticator app setup

## MODIFIED Requirements
### Requirement: Session Expiration
The system MUST expire sessions after 15 minutes of inactivity.
(Previously: 30 minutes)

## REMOVED Requirements
### Requirement: Remember Me
(Deprecated in favor of 2FA. Users should re-authenticate each session.)
```

| Section | Meaning | Archive merge action |
|---------|---------|----------------------|
| `## ADDED Requirements` | New behavior | Appended to source-of-truth |
| `## MODIFIED Requirements` | Changed behavior | Replaces existing requirement (heading match) |
| `## REMOVED Requirements` | Deprecated behavior | Deleted from source-of-truth |

This is the single most adoptable pattern from OpenSpec for brownfield agent work.

### 3.3 Progressive rigor (per `docs/concepts.md` §Lite vs Full)

> "Most changes should stay in Lite mode."

- **Lite spec**: short behavior-first requirements + clear scope/non-goals + a few acceptance checks. Default for routine changes.
- **Full spec**: cross-team, API/contract changes, security/privacy concerns, expensive-to-rework ambiguity. Opt-in for high-risk changes.

### 3.4 Custom schemas (per `docs/customization.md`)

```yaml
name: research-first
version: 1
artifacts:
  - id: research
    generates: research.md
    instruction: "..."           # AI prompt augmentation per artifact
    template: research.md        # Templates live in <schema>/templates/
    requires: []
  - id: proposal
    generates: proposal.md
    requires: [research]
  - id: tasks
    generates: tasks.md
    requires: [proposal]         # Skip specs+design entirely
apply:
  requires: [tasks]
  tracks: tasks.md
```

**Schema resolution order** (highest to lowest):
1. CLI flag: `--schema <name>`
2. Change metadata (`.openspec.yaml` in change folder)
3. Project config (`openspec/config.yaml` `schema:` field)
4. Default (`spec-driven`)

**Schema validation:** `openspec schema validate <name>` checks YAML syntax, template existence, no circular dependencies, valid artifact IDs.

### 3.5 Project config (per `docs/customization.md` + `docs/opsx.md`)

```yaml
# openspec/config.yaml
schema: spec-driven

context: |
  Tech stack: TypeScript, React, Node.js
  API conventions: RESTful, JSON responses
  Testing: Vitest for unit tests, Playwright for e2e

rules:
  proposal:
    - Include rollback plan
    - Identify affected teams
  specs:
    - Use Given/When/Then format for scenarios
  design:
    - Include sequence diagrams for complex flows
```

**Injection mechanism** (verbatim from docs):
- `<context>...</context>` tags prepended to every artifact's AI prompt
- `<rules>...</rules>` tags injected ONLY for matching artifact ID
- 50 KB context size limit; invalid YAML reported with line numbers

This is a **near-perfect match** for what DevolaFlow's `applicable_rules` field in TaskDispatch is trying to do, except OpenSpec ships a working config file devs can edit by hand.

## 4. Tool Adapter & Distribution Surface

### 4.1 Multi-tool installer (per `docs/supported-tools.md`)

**27+ supported tools**, each receives skills + commands at install time:

| Tool | Skills path | Commands path |
|------|-------------|---------------|
| Cursor | `.cursor/skills/openspec-*/SKILL.md` | `.cursor/commands/opsx-<id>.md` |
| Claude Code | `.claude/skills/openspec-*/SKILL.md` | `.claude/commands/opsx/<id>.md` |
| Codex | `.codex/skills/openspec-*/SKILL.md` | `$CODEX_HOME/prompts/opsx-<id>.md` |
| GitHub Copilot | `.github/skills/openspec-*/SKILL.md` | `.github/prompts/opsx-<id>.prompt.md` |
| Continue | `.continue/skills/openspec-*/SKILL.md` | `.continue/prompts/opsx-<id>.prompt` |
| Gemini CLI | `.gemini/skills/openspec-*/SKILL.md` | `.gemini/commands/opsx/<id>.toml` |
| ... 21 more |

`openspec init --tools claude,cursor` installs only selected tools; `--tools all` installs all 27; `--tools none` skips. `openspec update` regenerates after upstream changes.

### 4.2 Profile-driven generation

```bash
openspec config profile core      # 4 commands (default)
openspec config profile expanded  # 11 commands
openspec init --profile core      # one-shot non-interactive override
```

Profile selection drives **which** skills + commands get generated; tool selection drives **where**. Decoupled cleanly.

### 4.3 Postinstall + telemetry hooks (per `scripts/postinstall.js` + README)

- `postinstall.js` runs after npm install — typically prints `openspec init` hint
- `OPENSPEC_TELEMETRY=0` or `DO_NOT_TRACK=1` opt-out
- Auto-disabled in CI environments (`CI=true` env)
- Collects only command name + version (no args, no paths, no PII)

## 5. Customization & Extensibility

### 5.1 Three customization tiers (per `docs/customization.md` §0)

| Tier | What | Best for |
|------|------|----------|
| Project Config | `openspec/config.yaml` (schema + context + rules) | Most teams |
| Custom Schemas | Forked or scratch-built schemas in `openspec/schemas/` | Teams with unique processes |
| Global Overrides | `~/.local/share/openspec/schemas/` (user-level, shared across projects) | Power users |

### 5.2 Schema fork command

```bash
openspec schema fork spec-driven my-workflow
# Copies <packagedir>/schemas/spec-driven/ to openspec/schemas/my-workflow/
```

After fork: edit `schema.yaml` to change DAG; edit `templates/*.md` to change AI prompts. Validation: `openspec schema validate my-workflow` (syntax + circular dep check + template existence).

### 5.3 Templates with HTML-comment AI hints

```markdown
<!-- templates/proposal.md -->
## Why
<!-- Explain the motivation for this change. What problem does this solve? -->

## What Changes
<!-- Describe what will change. Be specific about new capabilities or modifications. -->

## Impact
<!-- Affected code, APIs, dependencies, systems -->
```

HTML comments are stripped from the final artifact but visible to the AI generating it. This is a clean way to embed prompt-engineering inside what looks like an ordinary template.

### 7.2 ADAPT (with significant modification)

| Pattern | Why modify | DevolaFlow form |
|---------|-----------|-----------------|
| Behavior-first specs (no impl details) | DevolaFlow already mixes impl in research artifacts; the discipline is good but the rule needs to be enforced via lint, not just convention | Add `tests/test_change_spec_format.py` lint that flags forbidden tokens in `.local/.agent/active/<id>/spec.md` |
| RFC 2119 keywords (SHALL/MUST/SHOULD/MAY) | Adopt for `goal.md` and `acceptance.md` only — over-specifying for impl-level docs is overkill | Document in `references/agent-workspace.md` as soft convention |
| Cross-platform path discipline (per OpenSpec's own `config.yaml`) | DevolaFlow is Python; uses `pathlib.Path` already | (no action; existing practice already consistent) |
| Schema validate command (`openspec schema validate`) | DevolaFlow's existing `pytest tests/test_schemas.py` covers this; rebrand if useful | Run `pytest tests/test_agent_workspace_schemas.py` per W-9 SI-10 step 1 |

### 7.3 REJECT (anti-patterns or wrong fit)

| Pattern | Reason rejected |
|---------|-----------------|
| 27-tool adapter surface as a v8.3.0 deliverable | Over-extends scope; DevolaFlow's 4-adapter charter is intentional; expand later |
| Hardcoded TypeScript instructions (the legacy workflow OPSX rebuilds away from) | Not relevant — DevolaFlow already externalizes templates in YAML |
| `npm install -g` distribution model | DevolaFlow uses `pip install` from GitHub URL; matches Python ecosystem; no change |
| `/opsx:onboard` guided walkthrough | Defer to v8.4.0; nice-to-have, not blocking v8.3.0 user asks |
| Per-tool command path patterns (e.g., `.gemini/commands/opsx/<id>.toml`) | Lock-in risk; each tool's path conventions can change. Stay at 4 well-tested adapters |
| Archive merge auto-merging into source-of-truth at `/opsx:archive` time | DevolaFlow has gates + convergence loops; auto-merge bypasses W-3 / SI-3 evaluation. Keep manual gate before merging deltas into source-of-truth |

## 8. Recommendations for v8.3.0 Adaptation

### 8.1 Architectural mapping (binding decisions)

| Decision | OpenSpec equivalent | DevolaFlow form | Where decided |
|----------|---------------------|-----------------|---------------|
| **Active changes live in** | `openspec/changes/<id>/` | `.local/.agent/active/<change-id>/` | A1 (user explicit) |
| **Archive lives in** | `openspec/changes/archive/<date>-<id>/` | `.local/.agent/archive/<YYYY-MM-DD>-<change-id>/` | A1 (user explicit) |
| **Handoff envelopes live in** (not in OpenSpec) | (DevolaFlow-specific extension) | `.local/.agent/handoff/<from>__<to>__<id>__<seq>.yaml` | A1 (user explicit, no OpenSpec analog) |
| **Source-of-truth lives in** (M-004 ADR) | `openspec/specs/<domain>/spec.md` | **`.local/memory/specs/<domain>/spec.md`** (NEW; sibling to operational.jsonl) | M-004 ADR §design.md |
| **Project config lives in** | `openspec/config.yaml` | `.local/.agent/config.yaml` | A1 (extension of `.local/.agent/`) |
| **Schema definitions live in** | `openspec/schemas/<name>/schema.yaml` | `schemas/agent-workspace/*.yaml` (in repo) — DevolaFlow doesn't ship custom schemas per-project | M-004 ADR §design.md |
| **Slash commands live in** | `.cursor/commands/opsx-<id>.md` etc. | `.cursor/commands/devola-<id>.md` etc. (4 adapters: Cursor, Claude, Codex, Copilot) | M-007 / v8.2.9 |
| **Lifecycle FSM** | propose → apply → verify → archive | propose → apply → verify → archive (mirror) | v8.2.6 |
| **Lite vs Full mode** | OPSX `core` vs `expanded` profile | `change-driven` workflow `mode: lite \| full` | v8.2.6 |

### 8.2 What we are NOT taking from OpenSpec

1. **Auto-merge at archive time**: DevolaFlow's `/devola:archive` will write a *proposed* merge to a staging area; an explicit gate (composite ≥ 8.5) MUST PASS before deltas land in source-of-truth. This preserves W-3 / SI-3 + W-4 / SI-4 invariants.
2. **27-tool adapter surface**: stays at 4 (Cursor + Claude + Codex + Copilot) for v8.3.0; expansion is a separate v8.4.0 + cycle.
3. **Telemetry**: DevolaFlow has none and v8.3.0 will not introduce any.
4. **`/opsx:onboard` and `/opsx:bulk-archive`**: deferred to v8.4.0+.
