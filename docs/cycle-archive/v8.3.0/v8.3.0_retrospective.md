## §4. Key Learnings (Process / Tooling / Architecture)

### §4.1 Deferred frozenset closure pattern is a clean drift-prevention marker

PV-06 introduced `_DEFERRED_DOC_TEMPLATES_V8_2_9 = frozenset({"change-driven"})` to mark that the `change-driven` template's SKILL doc surface coupling was deliberately deferred to PV-09. The frozenset acts as an explicit closure marker — when PV-09 closes the deferral, it MUST drop the frozenset entry (test enforcement), preventing silent drift between landing-the-code and registering-the-doc. This pattern worked clean in the v8.3.0 cycle and **should be codified for future cross-PV deferrals**. Possible future use cases: bridging cache layout transitions across multiple patches, bridging schema additions before consuming code lands.

### §4.2 Cache layout v4→v5 transition went cleanly with positions 1-15 byte-identical — 3rd successful additive transition

The PV-05 P6 transition appended `change_context` at position 16, preserving positions 1–15 byte-identical. This is the **3rd successful additive transition** after v8.0.0 P-08 (v2→v3) and v8.0.0 P-10 (v3→v4). v7.0.0 + v7.3.0 + v8.0.0 P-08 + P-10 byte-baselines all continue passing — **4 successive schema generations of additivity now proven**. The pattern is mature: append-only, never reorder, document at `schemas/lean-dispatch.yaml#layout_invariant.canonical_order`. v8.4.0+ should consider whether to formalize this as an enforcement rule (e.g., `assert_dispatch_layout_byte_identical_for_positions(payload, 1, 15)` on every dispatch).

### §4.3 Auto-merge with `gh pr merge --merge --delete-branch` saved time vs manual reviews

All 9 PV PRs landed via `gh pr merge --merge --delete-branch` after CI green + per-PV STATUS report verification. This skipped manual review steps that would have added ~5-10 min per PR (~45-90 min cycle-wide). For L0-orchestrated single-author cycles where the L3 STATUS report already documents the change comprehensively, auto-merge is the appropriate default. v8.4.0+ should retain this pattern. **Caveat:** for multi-author cycles or cycles with riskier semantic changes (e.g., breaking-change PVs), manual review remains preferred.

### §4.4 Plugin runtime two-backend support (pip + npm_then_init) added complexity — consider abstracting in v8.4.0+

PV-01's `plugins/installer.py` supports two install backends: `pip` (for Python tools like nines) and `npm_then_init` (for Node tools like ui-pro). The two-backend support was necessary for the v8.2.0 user feedback PATCH ("nines, ui-pro 作为依赖插件"), but it introduced a non-trivial branch in the installer code path. v8.4.0+ should consider:
1. Abstracting the install backend to a strategy interface (`InstallStrategy` ABC with `pip_install`, `npm_init`, future `cargo_install`, etc.)
2. Defining the registry (`runtime-plugins.yaml`) format more strictly (today it carries free-form `install_cmd` strings)
3. Adding signature verification (`expected_sha256` per plugin) — currently DEFERRED per L3 STATUS report

### §4.5 R5 strict byte-identical preservation is now byte-counted, not approximate

PV-08 memory bridge ships with **71/71 existing learnings tests passing byte-identical** — counted explicitly, not "71+". This is a tighter discipline than v8.2.0 PV-03 SessionState refactor's "all 71+ existing tests" claim. **Going forward**: when introducing R5 backward-compat changes, the L3 STATUS report SHOULD report the exact count of byte-identical existing tests (e.g., "X/X tests pass byte-identical") rather than the approximate "X+ tests" pattern. Codify in v8.4.0+ patch plan template.

### §4.6 PV count of 9 is large but manageable when each PV has ≤ 1 day effort

The v8.3.0 cycle's 9 PVs landed in ~2 days of L0 wall-clock time (vs v8.2.0's 5 PVs in ~10 hours; v8.0.0's 13 patches in ~16 hours per its retrospective). The per-PV time for v8.3.0 is comparable to v8.0.0 because each PV was scoped to ≤ 1 day of L0 dispatch + L3 implementation. The 4.7× over-delivery on tests (+743 actual vs +159 forecast) suggests the forecast methodology systematically under-counts test growth from new module surfaces — v8.4.0+ patch plan forecasts should use a higher per-module test multiplier (e.g., +30 tests per net-new Python module instead of +10).

### §4.7 100% accept rate streak extends to 45/45 lifetime PV cycles

Cycle accept rate: v7.2.0 (4/4) → v7.3.0 (6/6) → v7.5.0 (8/8) → v8.0.0 (13/13) → v8.2.0 (5/5) → **v8.3.0 (9/9)** = **45/45 lifetime PV cycles, 100% accept rate**. The plan-driven decomposition (SI-1 patch plan with 8 mandatory fields per patch) remains the structural reason. v8.4.0+ should preserve this discipline.

### §4.8 Versions.json was not backfilled for intermediate versions (v7.3+ through v8.2.0) — append-only discipline

Observation: `workflow-system/human/demo/version-timeline/versions.json` last entry is v7.2.0; intermediate versions (v7.3.0, v7.5.0, v7.7.0, v7.8.0, v8.0.0, v8.1.0-rc.1, v8.2.0) are not backfilled. The v8.3.0 release roll-up appends v8.3.0 at the end per ST-7 mandate, but the intermediate gap is a known issue tracked separately. **v8.4.0+ should consider** whether to backfill the missing entries as a documentation-only patch, or to formally accept that versions.json is a "highlights timeline" rather than a complete release log (CHANGELOG.md remains the complete log per ST-1). For this v8.3.0 release, append-only was the correct minimal-scope approach.
