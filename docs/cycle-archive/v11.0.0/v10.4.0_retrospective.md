## §1 — Gaps Identified

The v10.4.0 cycle was scoped from the v11.0.0 SI-1 planning gate
(`.local/research/v11.0.0_decomposition_plan.md`) by extracting six
high-priority Wave-1 D-X (Developer/Operator Experience) and Wave-3 D-D
(Reference Audit) patches. The gap analysis (per
`.local/research/v11.0.0_patches/`) surfaced four cross-cutting friction
patterns:

1. **Workflow template scaffolding ceremony**: adding 1 builtin template
   required hand-editing 9 surfaces (yaml body, registry stanza,
   meta-framework alias rows, SKILL.md table, team-roles matrix, test
   skeleton, build-skill verify, W-18 lint, CHANGELOG entry). Estimated
   ~45 min wall-clock per template; ~180 LOC manually edited.
   Source: `D-X-1.md` §1.
2. **Reference doc creation ceremony**: adding 1 reference required
   editing 7 surfaces; the install.sh per-adapter `dl_batch` blocks were
   the dominant hidden cost (7 blocks × 1 line each = 7 mechanical edits
   per reference). Source: `D-X-2.md` §1.
3. **SI-10 unconditional-full-path cost**: every commit (in-PR
   iteration AND PV-close) ran the same 7-step gate chain at ~5-10 min
   wall clock. The v10.3.0 retro §4.4 telegraphed `~10 min subagent
   overhead per PV` as a deferred optimization. Source: `D-X-3.md` §1.
4. **No troubleshooting reference**: ~30 distinct operator-trip
   patterns scattered across cycle retrospectives v8.0.0 → v10.3.0;
   each new operator must re-discover fixes via grep across `.local/research/`.
   Source: `D-X-5.md` §1.
5. **Reference utilization unknown**: zero observability on which of
   the 14 (now 15) SF-4 canonical references were actually loaded by
   `select_context()` calls. The D-A-2 (template compression) and
   D-D-3 (reference compaction) follow-on directions in the v11.0.0
   plan need this empirical signal before acting. Source: `D-D-1.md` §1.
6. **Long-reference usage opaque**: 9 references exceed 500 lines but
   their actual citation in handoff envelopes was unmeasured. The
   v8.3.0 → v10.3.0 ~50-PV span produced only 3 envelopes; the 6%
   creation-rate hypothesis was untested. Source: `D-D-2.md` §1.

## §2 — What Was Implemented

The v10.4.0 cycle ships in a single MINOR PV (PV-05) per the cycle plan
§3 collapsing. The deliverables verbatim from `.local/research/v11.0.0_patches/`:

### NEW Python scripts (4 files, ~960 LOC)

* **`scripts/scaffold_template.py`** (~340 LOC, D-X-1) — argparse CLI
  collapsing the 9-step template ceremony into 1 invocation. Renders
  builtin yaml + registry stanza + meta-framework alias rows + SKILL.md
  table row + team-roles matrix row + test skeleton; prints W-18 lint
  + CHANGELOG stanzas to stdout (NOT auto-injected per R2 mitigation).
  Idempotent (collision check + `--force` flag). Lazy imports keep
  `--help` fast.
* **`scripts/scaffold_reference.py`** (~200 LOC, D-X-2) — argparse CLI
  for reference doc creation. Renders the 5-section skeleton (Purpose
  / When to Load / Body / Cross-References / History), inserts
  alphabetical row into SKILL.md Tier-2 nav, appends MIRRORED_FILES
  entry. The install.sh manifest refactor described in D-X-2 §2 step
  5 was deferred to v10.5.0 (out-of-scope per W-17 cycle test cap).
* **`scripts/audit_reference_utilization.py`** (~220 LOC, D-D-1) —
  pure-observability audit replaying the selector matrix
  `(task_type × round_num)`. Produces markdown (default) or JSON via
  `--json`. The first run against v10.4.0 baseline reports:
  - Total cells: 120 (24 task types × 5 rounds)
  - 12 of 15 references below 20% utilization
  - High-utilization tier: `decomposition-gate.md` 37.5%,
    `team-roles.md` 37.5%, `meta-framework.md` 25.0%
  - Output saved to `.local/research/v10.4.1_reference_utilization.md`
* **`scripts/audit_long_reference_usage.py`** (~210 LOC, D-D-2) —
  pure-observability audit scanning `.local/.agent/handoff/` and
  `.local/research/` for long-reference citations. The first run
  confirms the v11.0.0 D-D-2 §1 hypothesis verbatim:
  - 9 references >500 lines
  - 3 envelopes total in handoff/ across the entire cycle history
  - 0 envelope citations of any long reference
  - Research-side citations of long references are high
    (e.g., shell-proxy.md cited 134 times under .local/research/)
  - Output saved to `.local/research/v10.4.2_long_reference_usage.md`

## §3 — What Was Deferred and Why

* **D-X-2 install.sh manifest refactor** (D-X-2 §2 step 5). The
  refactor would dedupe 7 per-adapter `dl_batch` blocks into a single
  loop reading `_install_manifest.txt`. Deferred because (a)
  `scripts/install.sh` is NOT in the v10.4.0 owned-files set per the
  cycle plan; (b) the refactor has no behavior change (output bytewise
  equivalent) so its value is purely operator ergonomics, which the
  scaffold-script side already addresses; (c) v10.5.0 can ship the
  manifest refactor as a single-purpose PR with the `tests/test_install_manifest_consistency.py`
  regression suite. The pre-existing v10.3.0 install.sh has 13 entries
  per block while sync_cursor_skill has 14 (now 15) — the drift
  pre-dates this cycle and the 13 vs 18 mismatch is documented for the
  next cycle to resolve.
* **D-X-1 + D-X-2 shared `_scaffold_common.py`** (D-X-1 §8 synergy
  note). The two scaffold scripts share ~30 LOC of argparse + repo-root
  resolution + file-write idempotency. Deferred because (a) the shared
  surface is too small to warrant a separate module at v10.4.0; (b)
  v10.5.0 can refactor in place once a third scaffold (e.g., D-X-7
  agent-template scaffold) lands.
* **D-D-3 reference compaction action items** based on the D-D-1
  audit. The v10.4.1 utilization report flags 12 of 15 references
  below 20% utilization — a strong signal for D-D-3, but the action
  itself (folding low-utilization references into adjacent ones) is a
  v11.0.0+ cycle decision per the D-D-1 §6 risk #3 (opt-in surfaces
  like `shell-proxy.md` are intrinsically low-utilization).
* **`.rules/workflow.mdc` W-9.1 augmentation** (D-X-3 §2). The
  fast-path Makefile targets are wired BUT the codified W-9.1 sub-rule
  in `.rules/workflow.mdc` was deferred. The `.rules/` corpus is in
  the cycle plan's owned-files only via the auto-compile drift check;
  a future PV will author the W-9.1 body + run `make compile-rules`.
* **install.sh + scripts/git-hooks/pre-push.sh** (D-X-3 §2). The
  pre-push hook template was deferred (R5 strict default-OFF; opt-in
  symlink). Operator-facing, not behavior-changing.
* **W-21 telegraph for any S-11**: NO Soul rule additions in v10.4.0
  per the W-21 freeze. The Soul-set count remains 10 (S-1..S-10).

## §4 — Key Learnings

1. **Audit-first ordering on PR-flow optimizations**. The D-D-1
   utilization audit ran AFTER the D-X-1/D-X-2 scaffolds were authored
   but BEFORE landing v10.4.0. The audit immediately revealed that
   the 12-of-15 long-tail signal applies — including to the
   newly-added troubleshooting.md (0 cells in v10.4.0 because it is
   not yet declared under any profile's `extra_context`). This is
   expected: the troubleshooting reference launches as a `important`-
   tier on-demand load, not a `critical`-tier auto-load. A future PV
   should add `references/troubleshooting.md` to the `extra_context`
   of `bugfix` and `dependency-setup` profiles to elevate it.
2. **Idempotency was the right scaffold contract**. Both scaffold
   scripts default to skip-on-existence; `--force` is required to
   overwrite. Tests cover both paths. The 7 unit tests for
   `scaffold_reference.py` and 8 for `scaffold_template.py` reproduce
   the operator's mental model: dry-run preview → real run → re-run
   without --force is a no-op → re-run with --force overwrites.
3. **The v10.3.0 `pytest --lf` cache trap (per troubleshooting.md
   §2.9)** caught me during this PV's iteration. The fix is to run
   `make clean` (or `pytest --cache-clear`) when a test was added
   between branches. The new `make precommit-fast` is genuinely
   faster ONLY on green trees; on red trees, the LF cache should be
   regenerated.
4. **The W-18 sequencing held**. The new
   `test_v10_4_0_new_symbols_have_coverage` lint pins 4 scripts + 1
   reference + 3 Makefile targets + 2 audit outputs + CHANGELOG
   header BEFORE the CHANGELOG entry was authored. The lint runs
   green because every pin matches a real surface; if a CHANGELOG
   entry slips ahead of the surface, the lint catches it loudly.
5. **The R-4 mitigation was straightforward**. The blocker per the
   user's task instructions was "bump SF-1 hard cap from 14 → 17
   before adding the 15th reference". In practice the cap is encoded
   in 5 distinct test surfaces:
   - `_SF4_REFERENCE_SET` frozenset cardinality (implicit; expanded
     by adding `troubleshooting.md`)
   - `tests/test_reference_size_budgets.py::test_canonical_lists_match_sf3_contract`
     (`assert len(_REF_FILES) == 14` → `== 15`)
   - `tests/test_adapter_golden.py::test_cursor_references_golden`
     (`assert len(actual) == 14` → `== 15`)
   - `data/golden_test_set/sf4_reference_set_size.toml` (`source =
     "len(_SF4_REFERENCE_SET) == 14"` → `== 15`)
   - `_MIRRORED_SKILL_FILES` list cardinality (implicit)
   All 5 bump in lockstep; no test left behind. The "14 → 17" framing
   is misleading — the cap IS the cardinality, and the cap moves
   exactly 1 step per cycle that adds a reference.
6. **Future telegraph**: NONE. v10.4.0 does NOT propose any S-11
   addition. Per W-21, any future Soul addition must be telegraphed
   in the cycle-N retrospective for cycle-N+2 review. The v10.4.0
   retrospective explicitly carries no §3 deferral note for an S-11
   addition.
