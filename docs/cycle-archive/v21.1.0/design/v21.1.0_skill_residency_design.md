# v21.1.0 T7 Skill Residency Design

## Decision

`skill_residency` is the sixth HSC extras axis. It describes whether a host
has a declared, evidenced way to observe skill loading during a run. It does
not describe installation delivery: `floor.skill_delivery` remains the
delivery/install contract and is never used as proof that a particular run
loaded the skill.

The axis requires `status`, `scope`, `observation_method`, `fixtures`,
`fixture_provenance`, and `reason`. Statuses use the existing closed set:
`implemented`, `designed`, `undeclared`, `broken`, and `native`.
`implemented` requires a `captured` or `vendor-doc` fixture; `vendor-doc`
also requires `provenance_ref`. The current cycle has no real residency fixture,
so no host is upgraded to `implemented`.

## Current declarations

Claude, Codex, and KimiCode are `designed`: their supported CLI probe
channels can parse a JSON `skill_loaded` boolean, but the repository has no
captured host fixture proving the channel's runtime semantics. Cursor,
Copilot, DSH, Windsurf, Zed, Cline, Roo, Continue, OpenClaw, Gemini,
JetBrains, Amazon Q, Augment, and Trae are `undeclared`: their delivery
surfaces remain in the HSC, but no stable runtime observation channel or
fixture is declared. All entries use `TBD-audit` only to record the evidence
gap; it is not implementation evidence.

## Runtime fact contract

`devolaflow.host_contract.validate_skill_observation()` receives a canonical
host or alias and an observed value of `true`, `false`, or `null`.
`devolaflow.harness.cli_probe` calls it for every probe result. The legacy
`skill_loaded.value` and `skill_loaded.status` fields remain intact. Additive
fields identify the canonical host, `probe-runtime` provenance, the HSC
status/provenance, and `hsc_validation`.

The probe's boolean is a recorded runtime fact only. A `designed`,
`undeclared`, or `broken` HSC declaration yields
`hsc_validation.status: INSUFFICIENT` even when the CLI reports a boolean.
Missing output, unavailable executables, timeout, or an unavailable channel
normalizes to `observed: null`, `value: null`, and `status: INSUFFICIENT`
with an explicit reason. Neither the arm name nor `skill_delivery` is
allowed to infer loading.

## Evidence and channel limits

Probe-supported channels are currently `claude`, `codex`, and `kimi`; `kimi`
resolves to canonical host `kimicode`. Their JSON output is the sole runtime
fact source for this helper. A successful subprocess without a
`skill_loaded` field is still insufficient for residency observation.
Other host channels are not silently substituted with install paths, prompt
arms, synthetic fixtures, or vendor assumptions.

The next evidence step is to capture one real fixture per candidate host
channel and review its payload against the declared observation method. Until
then, reports may contain observed booleans from a probe, but they must retain
the HSC validation result and must not claim implemented host capability.
