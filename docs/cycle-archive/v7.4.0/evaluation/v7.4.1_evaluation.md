### 5.1 Commit strategy (decision deferred to L0 per S-6 protected branch workflow)

Both v7.4.0 staged work AND v7.4.1 patch are uncommitted at session start. L0 must choose:

- **Option A — single rollup commit on a fresh feature branch.** Branch name: `feat/v7.4.0-rollup-with-v7.4.1-fix` (or `feat/v7.4.x-rollup`). Single commit covers v7.4.0 work (`.local/`, `.rules/`, `AGENTS.md`, `local/` module, 35 new tests) + v7.4.1 patch (CHANGELOG, version bump, B-1 fix). Pro: minimal git surface; Con: PR review obscures the v7.4.1 regression-fix narrative behind the larger v7.4.0 scope.
- **Option B — two distinct commits on a single feature branch.** Branch name: `feat/v7.4.0-and-v7.4.1`. Commit 1: `feat: v7.4.0 .rules/ + .local/ + repo-init workflow`. Commit 2: `fix: v7.4.1 cli.py coverage regression + version bump`. Pro: PR reviewers see the v7.4.1 patch as a focused B-1 closure; preserves history clarity; mirrors the v7.3.0 cycle's per-patch feature-branch precedent (per CHANGELOG `[7.3.0]` "feature branch `feat/v7.3.0-pNN-<name>` → single `feat()` commit → lightweight `v7.2.x` tag → `--no-ff` merge").
- **Option C — two feature branches.** Branch 1: `feat/v7.4.0-rules-local-init` (v7.4.0 work, lightweight `v7.4.0` tag). Branch 2: `fix/v7.4.1-cli-coverage` (v7.4.1 patch, lightweight `v7.4.1` tag). Pro: maximum history clarity; Con: 2 PRs, 2 reviews, more cycle latency.

**Recommendation: Option B** preserves history clarity AND lets PR reviewers see the v7.4.1 patch as a focused regression-fix, without the overhead of two separate PRs. Tag `v7.4.1` (annotated, mirroring the v7.3.0 precedent of an annotated tag for the headline release; the v7.4.0 commit can carry a lightweight tag if desired). Merge `--no-ff` into `main` only after PR review per S-6 protected-branch workflow.
