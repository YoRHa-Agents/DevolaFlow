## 4. Key Learnings (process improvements for v7.5.x+ SI-1)

### L-1 — SI-10 composite-coverage gate has a per-module blind spot

The SI-10 step 1 (`pytest -q`) and the implicit composite gate (`pyproject.toml [tool.coverage.report] fail_under = 80`) BOTH PASS even when an individual modified module drops to 63% — because composite stays well above 80% (was 93.91%; the 3 new 100%-coverage modules in `src/devolaflow/local/` mathematically masked the cli.py regression). Phase 1 pre-flight ONLY caught B-1 because the L3 analyst ran an EXPLICIT per-module coverage spot-check beyond the SI-10 6 steps (gap analysis §2 last-paragraph "Per-module spot-check on v7.4.0-touched files").

**Recommendation for v7.5.x:** consider adding a 7th SI-10 step OR extending Step 1 with `--cov-fail-under-per-module=80` (or equivalent ratchet) so per-module drift surfaces automatically without requiring an analyst to know to look. Candidate implementations:

1. Native pytest-cov flag (if `pytest-cov` supports per-module thresholds in the installed version — check `pip show pytest-cov`).
2. A custom `pytest` plugin or post-test script that parses `coverage.json` + a `.coveragerc-modified-modules` allowlist.
3. A pre-commit hook that diffs `git diff --stat` against the coverage report and fails if any `src/devolaflow/*.py` modified file is < 80%.

File a v7.5.x backlog item: "SI-10 step 7 — per-module coverage ratchet on modified modules".

### L-2 — `[project.scripts]` registration without test → pre-existing anti-pattern

Both v7.3.0 (per its retrospective implication) and v7.4.0 added `[project.scripts]` console-script entries shipping CLI shims without same-PR test coverage. v7.4.1 closes the 3 v7.4.0 instances; the v7.5.x analyst should check whether v7.3.0 or earlier left any similar gaps and prophylactically test in v7.5.x.

**Recommendation:** add a CONTRIBUTING.md (or extend repo-governance Rule C-1 / CP-7) clause:

> **Any new `[project.scripts]` entry MUST ship a unit test in the same PR.** The test should at minimum exercise the entry-point function with a tmp_path-mocked `Path.cwd()` + `monkeypatch.setattr(sys, "argv", […])` + `capsys` for stdout assertions, and assert the exit-status branches (`sys.exit(0)` happy path + `sys.exit(1)` error paths).

This is a structural prevention for L-1's per-module blind spot — if the test exists, the per-module coverage stays high by construction.

### L-3 — Patch surface as the "no-regression" guarantee

v7.4.1 deliberately confined its writes to `tests/` + `CHANGELOG.md` + version-string patterns. The OFF-SCOPE filter (no compressor / schemas / gate / context_profiles / scenarios / SKILL section edits) GUARANTEES no SI-4 EvoBench drift (verified 0 pp), no P6 invariant risk (verified 3 layout-invariant tests still PASS), no SF-1 budget pressure beyond the existing 1-line headroom (verified 499 unchanged).

**Recommendation for future regression-verification patches:** codify this filter explicitly in the gap-analysis template (already implicitly captured in `.local/research/v7.4.1_gap_analysis.md` §5 "Out of scope" sub-section — promote to a reusable section in the SI-1 template). The "Out of scope" enumeration becomes a binding contract for the Phase 2 implementation L3 agent: any edit to a listed file is auto-rejected.

### L-4 — Pre-existing v7.4.0 staged work UNCOMMITTED at session start

Both v7.4.0 (the new `local/` module + `.rules/` + `AGENTS.md` + 35 new tests) and the v7.4.1 patch are uncommitted at session start. L0 must decide commit strategy:

- **Option A:** single rollup commit covering v7.4.0 work + v7.4.1 patch on a fresh feature branch
- **Option B:** two distinct commits on a single feature branch — `feat: v7.4.0 .rules/ + .local/ + repo-init workflow` then `fix: v7.4.1 cli.py coverage regression + version bump`
- **Option C:** two separate feature branches with two separate PRs

**Recommendation:** **Option B** — preserves history clarity AND lets PR reviewers see the v7.4.1 patch as a focused regression-fix. v7.3.0 cycle precedent (per CHANGELOG `[7.3.0]` "feature branch `feat/v7.3.0-pNN-<name>` → single `feat()` commit → lightweight `v7.2.x` tag → `--no-ff` merge to main") used per-patch feature branches with `--no-ff` merges; for v7.4.x this rolls up smaller (only 2 commits, not 6) so a 2-commit single-branch workflow suffices. Tag v7.4.1 as ANNOTATED (mirroring v7.3.0 precedent for headline releases); v7.4.0 can be lightweight if used.

### L-7 — User-intent translation

The user-facing prompt was "/devola-flow self update and make sure 没有功能回退，并修复至 7.4.1版本" ("no functional regression, fix at v7.4.1"). This was a 1-sentence Chinese-mixed-English prompt. The Phase 1 analyst translated it into:

1. SI-10 6/6 PASS verification (the binding pre-commit gate)
2. Per-module CP-2 spot-check (catches the 98% → 63% regression that SI-10 misses)
3. Version bump 7.4.0 → 7.4.1 (the user's explicit "至 7.4.1版本")
4. CHANGELOG documentation (S-4 / CP-1 no-ghost-features)

The translation was clean — no requirements were over- or under-specified relative to the prompt. The ambiguous term "功能回退" (functional regression) was correctly interpreted to include per-module coverage regression (a quality regression even though no feature behaviour broke).

**Implication for v7.5.x:** when user intent is short and includes "no regression" language, the analyst should explicitly enumerate the regression dimensions checked (composite coverage, per-module coverage, behavioural regressions, schema regressions, EvoBench regressions, SKILL budget regressions) so the verification scope is auditable.
