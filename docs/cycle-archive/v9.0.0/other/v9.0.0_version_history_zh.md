## 执行摘要 (Executive Summary)

本回顾文档记录了从 DevolaFlow v2.1.0 (2026-04-07) 到 v8.4.0 (2026-04-23) 共 **82 个版本 / 预发布变体 (PVs)**，跨度约 17 个日历日的高强度迭代，由 S01-T01..T05 并行编写的 5 个时代清单聚合而成。Git 账本中持有 **77 个带注解 git tag**，最早从 `v4.3.0` 开始（v2.x 与 v3.x 的大部分时代仅有 CHANGELOG）。整个周期内交付了五个具有架构里程碑意义的拐点：**v6.0.0 → v6.2.0** 巩固了 4 层 Agent 层级强制执行，确立了 YAML 驱动的适配器注册表（4 → 11 个平台）；**v7.0.0** 推出了缓存布局不变量 (`schemas/lean-dispatch.yaml#layout_invariant`)，成为后续所有派遣模式扩展的承重契约；**v8.0.0** 以单个 13 补丁周期吸收了全部 14 条 Karpathy "ChatGPT Vibes Engineering" 原语；**v8.3.0** 引入了 `.local/.agent/{active,handoff,archive}/` 工作区原语并新增 4 条 Soul / Architecture / Conventions 规则（S-8、S-9、A-4、C-9）；**v8.4.0** 以 RTK + 快速路径 memory router + shell-proxy 四件套封顶整个时代，验证了 single-source-of-truth 注册表模式。

头部度量指标轨迹显示 **测试数从 254 (v3.0.0) → 822 (v5.4.0) → 1009 (v6.2.0) → 1525 (v7.7.0) → 3216 (v8.4.0)** 增长（在记录窗口内 12.7× 扩展）；**NineS 综合分在 v5.4.2 → v6.1.0 共 7 个版本期间维持在 0.7405（零源代码改动），随后在 v6.1.1 仅靠工具配置一举跃升到 0.8805 (+18.9%，无 `src/` 改动)，并在 v8.4.0 周期内 6 次测量字节稳定在 0.9050**；**EvoBench 场景数从 3 (v3.0.0 起源) → 17 (v3.3.0) → 25 (v4.2.0) → 30 (v5.4.0) → 39 (v7.3.0) → 48 (v8.4.0)**，>5% 回归阈值守卫 (W-4 / SI-4) 在被提升为 Soul 级规则之前已经在超过 30 个补丁周期内得到运营验证。补丁接受率到 v8.4.0 汇总时累计达到 **49 / 49 = 100% 终身接受率**，其结构性原因是 v9.0.0 必须保留的 SI-1 "每补丁 8 项必填字段" 分解纪律。

### 第 v2.x 时代 — S02 关注的异常

- **版本号跳跃 (0.1.0 → 2.1.0)**：单次发布跳过 v1.x 与 v2.0.0 两段。`.local/feedbacks/feedback_for_v2.0.0.md` 文件明确要求一个标记为 v2.1.0 的发布。值得在多版本回顾中标注为项目首次非单调版本步进。

- **Acceptance Readiness Gate 摇篮**：v2.2.0 引入 `acceptance_readiness` gate 类型加上 `GateInput` / `GateProfile` 上的 `acceptance_readiness_criteria` 和 `acceptance_readiness_threshold`。后续任何 gate 模块改动 (W-11 / CP-4) 都建立在这个 v2.2.0 表面之上。
- **SKILL.md 压缩里程碑**：v2.2.0 记录了 449 → 293 行的削减，并附带 "Zero degradation verified across 7 output types" 与 "254/254 tests pass, all 4 adapters verified"。这是后来成为规则 C-4 / SF-1 的 < 500 行 tier 上限的最早一次有据可查的强制执行。
- **Lean message format 起源**：v2.2.0 的 "Lean Message Templates" 是后来成为规则 C-2 (`schemas/lean-dispatch.yaml`、`schemas/lean-report.yaml`) 与 P6 cached-prefix 不变量（规则 A-2）的种子。值得在 S02 标记为层间协议谱系的起点。
- **反馈驱动的发布回路**：v2.1.0 是任何正式 SI-1 规划关卡之前 "反馈文件 → 发布" 流水线已经存在的文档证据。该反馈文件命名指向 v2.0.0，但明确把 v2.1.0 作为实现目标 — 用户诉求与发布之间 1 个周期的提前期。

### 第 v3.x → v5.x 时代 — 与 v9.0.0 相关的模式

在 v3.x–v5.x 中观察到的 5 个模式仍然是 v8.x 的承重组件，并应当为 v9.0.0 规划提供信息：

1. **Plan-mode 层级强制执行是反复出现的失败模式** — 首次在 v3.2.0 / v3.3.0 中处理（"Plan Mode Hardening: rigid hierarchy constraints"），在 v3.6.0 中发生回归并被再次修复（"P1 Dispatcher-Not-Implementer not enforced — root cause: 5 gaps in SKILL.md"），在 v3.7.0 中被再次加强（"Plan template now embeds the 4-layer delegation model explicitly"）。即使 v3.8.0 lifecycle hooks 让强制执行变得"确定性"，同样的漂移仍在 v4.0.1 的 "L2 now reads `model_hint`" SKILL 修复中被观察到。v9.0.0 应当预期这种漂移会再次发生，并设计能够捕捉 SKILL 级强制执行衰减的回归测试，而不仅仅是 runtime hook 合规性 — 当前的 Soul Rule **S-1** 直接源自该谱系。

2. **Verbatim / lean 压缩是分层设计，而不是单一特性** — 该设计跨越了 4 个版本累积形成：v3.9.0 引入声明式规则（`preserve_list` / `drop_list`，`lean-dispatch.yaml` / `lean-report.yaml` 中的 3 个 intensity tier），v4.0.0 添加 `compression_intensity` dispatch 字段 + 按层边界的 `compression_defaults`，v4.1.0 添加 runtime `compressor.py` validator + `format_compliance` EvoBench 维度，v4.1.1 用边界条件测试加固。该教训 — schema → 边界默认 → runtime validator → benchmark 维度 → 健壮性扫描 — 即当前编码在 **C-2**（Lean Message Format）和 **C-3**（Verbatim Extraction）中的模板。v9.0.0 在添加任何新的压缩相邻字段时应当遵循同样的 5 步扩展。

3. **自我改进反馈循环自 v3.9.0 起一直是每个收敛周期的中央引擎** — `feedback.py`（`FeedbackCollector` / `FeedbackAnalyzer` / `ProposalGenerator`）随 "max 3 proposals/workflow, confidence floor 0.7, scope lock, cooldown" 防护栏一同发布，在 v5.3.0 通过 `ProposalGenerator.generate_reinforcement()` 桥接到 gate，而 v5.1.0-pre 来自 `gate/reinforcement.py` 模块随后成为权威注入点（`applicable_rules.reinforcement`，每轮上限 5 条规则，按严重度过滤）。这是当前规则 **W-8**（Convergence Round Reinforcement）和 **SI-9** 的运行时主干。v9.0.0 应当把 feedback→reinforcement 桥接视为承重原语，而不是可选插件。

4. **NineS 属于研究 / 迭代，而不是 gate scoring** — v4.3.0 明确纠正了这一点："NineS role correction: NineS repositioned from gate scoring tool to research/iteration tool. **谱系**：诞生于 v6.0.4 的 `AdapterRegistry` + `DataDrivenAdapter`（4 → 11 平台通过 YAML），在 v6.1.2 中通过 `keep_sections` transform 验证 "registry 拥有数据，所有 consumer 委派" 的形态成熟，在 v8.4.0 PV-02/03/04 跨 `shell_proxy/registry.py::WHITELIST` + `memory_router/cache.py::MemoryCase` + `shell_proxy/commands.py::CommandMapping` 形式化。按 v8.4.0 retro §4.1 #5：*"consider documenting it as a 5th canonical Architecture Rule in v8.5.0 (provisionally A-5)"*。**v9.0.0 应当形式化为 Architecture Rule A-5**，配以 CI test 在引入新的 whitelist/recipe 表面而无 single-owner 模块时失败。

### 2. R5 strict 零开销 env-flag opt-in（v9.0.0+ 默认纪律）

**谱系**：自 v3.9.0 的 "Lean Compression Rules" 3 intensity tier 起隐式存在（按 intensity 设置 opt-in）；自 v6.1.5 plan-mode `DEVOLAFLOW_PLAN_MODE` env var + marker file 起显式；在 v7.0.0..v7.0.3 周期的"opt-in → 经过 3 个版本 benchmark 证据后默认开启"中成熟；在 v8.4.0 PV-02..PV-04 中达到最终形态，含**三层编纂**（unit `monkeypatch.setattr(Path, "read_text", watcher)` + integration full pytest 在 env-flag off 时 byte-identical pass + EvoBench `*_disabled.yaml` 场景在 floor 90 之上）。按 v8.4.0 retro §4.1 #4：*"make this the default for all opt-in features in v8.5.0+"*。**v9.0.0 应当作为所有新特性的默认纪律采用** — 没有特性可以不带 (a) env-flag、(b) off 时 zero-IO、(c) byte-identical pre-PV test、(d) EvoBench `disabled` 场景而发货。

### 3. P6 cache-layout invariant additivity (v7.0.0 → v8.4.0 baseline-stable)

**谱系**：起源于 v7.0.0（`schemas/lean-dispatch.yaml#layout_invariant` 12-key canonical + `assert_dispatch_layout()` runtime validator + Rule 6 P6）；在 5 次连续 schema generation 上证明 additive（12 → 13 v7.2.6 `repos:` → 14 v8.0.0 P-08 `behavioral_guidelines` → 15 v8.0.0 P-10 `acceptance_criteria_v2` → 16 v8.3.0 PV-05 `change_context`）；v7.0.0 + v7.3.0 byte-baseline 在 v8.4.0 仍 PASS。按 v8.3.0 retro §4.2：*"the pattern is mature: append-only, never reorder. v8.4.0+ should consider whether to formalize this as an enforcement rule (e.g., `assert_dispatch_layout_byte_identical_for_positions(payload, 1, 15)` on every dispatch)"*。**v9.0.0 应当增加显式 byte-identicality 断言 + 在 v7.0.0 + v7.3.0 + v8.0.0 + v8.3.0 byte-baseline 上的自动回归 test**，使任何重排序在到达 review 之前在 CI 中失败。

### 4. 自我改进反馈循环是核心收敛引擎 (v3.9.0 → v9.0.0)

**谱系**：`feedback.py`（`FeedbackCollector` / `FeedbackAnalyzer` / `ProposalGenerator` 含 "max 3 proposals/workflow, confidence floor 0.7, scope lock, cooldown"）在 v3.9.0 发货；`gate/reinforcement.py`（`findings_to_reinforcement` 把每轮上限 5 条规则注入 `applicable_rules.reinforcement`）在 v5.1.0-pre 发货；在 v5.3.0 通过 `ProposalGenerator.generate_reinforcement()` 桥接；在 v6.0.3 通过 `ProposalGenerator.generate_round_dispatch()`（v5.3.0 dead-wire 闭合 — *"v6.0 中单次 ROI 最高的干预"*）接入到生产 caller；在 v8.0.0 P-04 中以确定性 fence-to-instruction 映射扩展。**v9.0.0 必须把 feedback→reinforcement 桥接视为承重原语，而不是可选插件** — 当前规则 **W-8** 与 **SI-9** 直接源自该谱系。

### 5. SKILL 级强制执行衰减是反复出现的失败模式（治理纪律）

**谱系**：首次在 v3.2.0 / v3.3.0（"Plan Mode Hardening: rigid hierarchy constraints"）处理；在 v3.6.0（"P1 Dispatcher-Not-Implementer not enforced — root cause: 5 gaps in SKILL.md"）发生回归并以 27 行强制执行块再次修复；在 v3.7.0（Plan Mode 加入 MVP-SKILL.md）再次加强；v4.0.1 需要又一次 SKILL 修复以让 L2 读取 model_hint；v6.1.5 需要 SKILL 更新以加入 v6.1.5 plan-mode runtime hook；v7.4.6 需要 `SKILL.md §"Reinforcement Rules"` 压缩以恢复 headroom；v7.8.0 在三次 runtime-only 修复未能触达 prompt-only L0 之后必须把 §"Repo-Init Pre-Dispatch Contract" 直接嵌入 SKILL.md。该模式现在编纂为 Soul Rule **S-1**。**v9.0.0 应当设计能够捕捉 SKILL 级强制执行衰减的回归 test**（line-range parity test、frontmatter parity test、强制 section 存在 test），而不仅仅是 runtime hook 合规性。

### 6. Plan-mode 层级强制执行（反复漂移；S-1 起源）

**谱系**：与模式 5 谱系相同，但具体关于 L0/L1/L2/L3 层级契约。v3.2.0 / v3.3.0（rigid hierarchy）、v3.6.0（P1 Self-Check 4 点）、v3.7.0（Plan template 嵌入 4 层模型）、v3.8.0（lifecycle hooks 用于确定性强制执行）、v6.1.5（plan-mode env var + marker file）。**v9.0.0 应当预期此漂移会再次发生**，并为每个周期预算 1 个 patch 用于 plan-mode 强制执行 audit。

### 7. Anti-ghost meta-test 基础设施节奏 (v7.4.4 P-01 → 每个 v9 minor)

**谱系**：`tests/test_no_ghost_features.py`（517 行，32 tests，初次引入时跟踪 21 个当前失败 test 的 `pytest.mark.xfail(strict=True)` markers）在 v7.4.4 P-01 发货；strict-XPASS-fails-suite 技巧把每个 patch 的 marker 删除转化为 forcing function。v7.5.0 audit 驱动了 8 个 ghost-cleanup patch（v7.4.3 → v7.4.10）闭合 41 个 ghost 中的 35 个。按阶段 3 回顾：*"The infra caught all 5 P-08 builtin templates with stale `team_overrides: {}` blocks BEFORE the cleanup ... ### 8. EvoBench 驱动的 release gating (v3.0.0 起源 → v6.0.5 100% baseline 覆盖 → v7.3.0 周期模板 → v8.x 例行)

**谱系**：在 v3.0.0 确立（"EvoBench Benchmark Suite"）；在 v3.3.0 扩展到 17 个场景，含加固阈值（`min_composite >= 80.0, max_noise_ratio <= 0.1, min_relevance >= 0.8`）；到 v4.2.0 达 25；到 v5.4.0 达 30；在 v6.0.5 闭合 3-of-29 baseline 覆盖 gap（通过 `generate_baseline.py` 闭合 89.7pp gap）；v7.3.0 成为完全由外部 benchmark 反馈驱动的首个 DevolaFlow 发布（`eb220_for_devola_v7.1.1.md` → 6/6 patch 接受 vs 4-5/6 预测）；v8.0.0..v8.4.0 例行 33→48 场景，0 回归 > 5%。"无 >5% 回归" 纪律现在是 Soul 级规则 **W-4** / **SI-4**。**v9.0.0 应当为任何新压缩相邻特性复用 3 步扩展模式**（场景 → 重新校准至 ≤0% 结构噪声 → 收敛后收紧 `min_composite`）。

### 9. Prompt-side 治理契约嵌入 (v7.8.0 教训 — 定义 v8.x+ 模式)

**谱系**：v7.4.1 → v7.5.0 → v7.7.0 三次 `repo-init` 复发证明了 runtime-only 强制执行（Python `run_hooks`）对 prompt-only L0 编排器（Claude Code / Cursor / Codex）不可见。v7.8.0 通过把 5 条 `repo-init` canonical 路径直接嵌入到 `SKILL.md §"Repo-Init Pre-Dispatch Contract"` 加 `devola-init-doctor` CLI 闭合该问题。v8.3.0 PV-02 之后又添加 4 条新硬规则（S-8/S-9/A-4/C-9）全部 prompt-side。**v9.0.0 必须保持此纪律**：如果一个契约对 prompt-only 编排器重要，把它嵌入 SKILL.md 或 Tier-1 reference，**而不是**只在 `run_hooks` consumer 才能看到的 Python helper 中。

### 10. NineS 属于研究 / 迭代，而不是 gate scoring (v4.3.0 边界，v6.1.1 plateau-break)

**谱系**：v4.3.0 明确把 NineS 角色从 gate scoring 工具纠正为 research/iteration 工具（"Removed `nines_provider` from gate advisor configs"）；v5.0.0 完成 v2.0.0 CLI 迁移；v5.2.0 把边界编纂为 SI-2；v6.1.1 tool-config audit 突破了 7 个版本的 NineS plateau（0.7405 → 0.8805 = +18.9% **零源码改动**）；v8.4.0 在 6 次测量中维持 byte-stable 0.9050。EvoBench（本仓库）依然是 gate 权威。**v9.0.0 必须保持此边界完整**（当前规则 **W-2** / **SI-2** 明确把 NineS 限定在分析 + self-eval，永远不进入 gate composite）。v6.1.1 回顾洞察 — *"每次'分数 plateau'都值得一次 tool-config 审计，再假设 code-quality 工作"* — 应当治理任何 v9.0.0 NineS plateau 诊断。

### 11. Lean compression 分层设计 — schema → boundary → runtime → benchmark → robustness (v3.9.0 → v4.1.1 模板)

**谱系**：跨 4 个版本累积形成：v3.9.0 引入声明式规则（`preserve_list` / `drop_list`，`lean-dispatch.yaml` / `lean-report.yaml` 中的 3 个 intensity tier）；v4.0.0 添加 `compression_intensity` dispatch 字段 + 按层边界的 `compression_defaults`；v4.1.0 添加 runtime `compressor.py` validator + `format_compliance` EvoBench 维度；v4.1.1 用边界条件 test 加固。5 步扩展模板（schema → 边界默认 → runtime validator → benchmark 维度 → 健壮性扫描）编纂在当前规则 **C-2**（Lean Message Format）和 **C-3**（Verbatim Extraction）中。**v9.0.0 应当在添加任何新的压缩相邻字段时遵循同样的 5 步扩展**（例如，directed-compaction 扩展、按层 recency decay 调优）。
