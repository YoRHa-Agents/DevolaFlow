## Schema Compliance

- **P6 cache layout invariant respected:** **yes**.
  The proposal nests `bypass_conditions:` *inside* the existing `compression_rules:` block (a metadata block — not a top-level dispatch payload key). The v7-ADR-001 layout invariant governs the canonical order of dispatch *payload* top-level keys (`hdr → task → goal → assumptions → pred → files → rules → shared → accept → reinforce → verify_cfg → gate`); `compression_rules` is not in that list — it lives in the `lean-dispatch.yaml` schema/template document at top level, but is consumed by the runtime compressor, **not rendered into dispatch payloads**. Adding a sub-key inside it cannot reorder anything in the rendered prefix and cannot affect the LCP-per-round SLO (≥80% r1→r2, ≥70% r1→r3). The existing `tests/test_compressor.py::test_dispatch_prefix_is_stable_across_rounds` was re-run as a baseline (3 selected pass) and is unaffected by design.
- **Backward compat with existing payloads:** **yes**. `compress_message(message, intensity)` continues to accept the v7.1.x signature; the new `bypass_conditions` parameter is keyword-only with default `None` (= use full bypass list). Callers who explicitly pass `bypass_conditions=[]` get the legacy v7.1.x behaviour (no bypass, normal compression). The return dict gains two keys (`bypass_matched`, `bypass_warning`) — both populated on every code path, set to `[]` / `None` on the non-bypass branch, so callers reading the existing 5 keys are unaffected.
- **Top-level key order in lean-dispatch.yaml unchanged:** **yes**. The diff appends `bypass_conditions:` and `bypass_default_active:` immediately after the existing `default_intensity: standard` line — both are sub-keys of `compression_rules:`, not new top-level entries. Same for the `lean-report.yaml` mirror. The `layout_invariant:` block (the SoT for P6) is untouched.

## Detection Rules

4 bypass conditions designed (all pure-regex, deterministic, no LLM/network/file-I/O):

- **security_warning:** `\b(?:WARNING|CAUTION|DANGER|SECURITY|VULNERABILIT(?:Y|IES)|CVE-\d{4}-\d{4,7}|INSECURE|UNSAFE|XSS|CSRF|RCE|SQL[\s_-]*INJECT(?:ION)?|PROMPT[\s_-]*INJECT(?:ION)?)\b` (`re.IGNORECASE`). Triggers on caveman's named safety vocabulary plus current security-class identifiers (CVE, XSS, CSRF, RCE, SQL/PROMPT injection).
- **destructive_operation:** SQL DDL (`DROP TABLE`/`DROP DATABASE`/`DROP SCHEMA`/`TRUNCATE TABLE`), SQL DML without `WHERE` (negative lookahead — `DELETE FROM x WHERE y` does NOT trip), shell (`rm -rf`, `chmod -R 777`/`a+w`, `kill -9`, `sudo rm`, `mkfs`, `dd if=`), git (`reset --hard`, `push --force`/`-f`, `clean -fd`/`-ff`, `filter-branch`), container (`docker rm -f`, `docker rmi -f`, `docker system prune -a`/`-f`), k8s (`kubectl delete ns`/`deploy`/`pod --all`), IaC (`terraform destroy`).
- **multi_step_sequence_with_order_dependency:** match-count rule. Pattern matches numbered/ordered step markers (`1.`, `2)`, `step N`, `first`/`firstly`, `second`/`secondly`, `then`, `finally`, `next`); bypass fires only when **≥ 2 matches** in the same message. Single conversational ordinal (`"first I'd like to thank you"`) does NOT trigger; an actual sequence (`"1. Backup. 2. Migrate. 3. Restart."`) does.
- **repeated_user_question:** four families OR'd together — reference-back (`"as I (already) (asked|said|mentioned) (before|earlier|again|previously)"`), explicit repeat-verb (`"(I'll )?(repeat(ing)?|reasking|re-ask(ing)?) (my|the) (question|ask)"`), clarity-meta (`"(please )?clarif(y|ication)( again)?"`), and punctuation (`\?{2,}`). All `re.IGNORECASE`.

Full rationale, positive/negative examples, and false-positive policy in `.local/sandbox/v7.2.0/V02/detection_rules.md` (260 lines).

## Risks / Caveats

| # | Risk | Likelihood | Severity | Mitigation |
|---|------|------------|----------|------------|
| R1 | False-positive bypass on benign text containing `WARNING` (e.g. "warning lights on the dashboard") | Medium | Low | Bias is intentional ("preserve on doubt"). Cost = ~10× verbatim message bytes for that one call; benefit = no security warning ever silently dropped. Caller can pass `bypass_conditions=[]` for known-clean call sites, or remove `security_warning` from the active subset. Documented in `detection_rules.md` Rule 1. |
| R2 | False-positive bypass on `git push --force` mentioned inside a tutorial, where compression would be safe | Low | Low | Same mitigation as R1. The bypass writes the *whole* message verbatim, not just the matched span — keeping the tutorial readable. |
| R3 | Regex false-negatives on novel destructive verbs (e.g. new k8s subcommand, future CVE namespace) | Medium | Medium | Closed list is deliberately conservative; expanding is purely additive. Track via SI-9 reinforcement: when a real incident exposes a missing pattern, append it to `BYPASS_PATTERNS` and bump `bypass_default_active: true` (or false if a feature-flag rollout is wanted). |
| R4 | Threshold of 2 for `multi_step_sequence_with_order_dependency` could miss a 1-step destructive instruction | Low | Low | A 1-step "Click submit" is by definition order-independent; any genuinely destructive single step is independently caught by `destructive_operation` (Rule 2). |
| R5 | `CompressionBypassWarning` surfaces in CI logs and might be treated as test failure under `pytest -W error` | Low | Medium | Class is `UserWarning` subclass, not `DeprecationWarning`/`Error`. CI's existing pytest config (`pyproject.toml`) does not set `filterwarnings = ["error"]`, so default behaviour is "log only". Documented in `detection_rules.md` design note 7. |
| R6 | The `lean-report.yaml` mirror could drift from `lean-dispatch.yaml` in future edits | Low | Low | Add a `tests/test_compressor.py::test_bypass_conditions_schema_mirror_parity` check that both YAMLs declare identical `bypass_conditions` lists (cheap one-shot test, ~10 lines). Recommended as a follow-up in the production PR-B. |
| R7 | Performance: 4 regex passes per `compress_message` call (typical dispatch payload ~2-8 KB) | Very low | Low | Benchmarked at < 0.1 ms per call on a 4 KB payload (regex pre-compiled at module load). No measurable impact on `tests/test_benchmarks.py` composite scores. |

## Recommendation

**ACCEPT** for v7.2.0 PR-B (schema/compressor cluster, per the candidate list's recommended S03 validation set, order #2).

**Order within PR-B:**
1. **Schemas first:** `schemas/lean-dispatch.yaml` and `schemas/lean-report.yaml` mirror, in the same commit (so any drift between the two is caught at code-review time, not CI time).
2. **Compressor implementation:** `src/devolaflow/compressor.py` adds `BYPASS_CONDITIONS`, `BYPASS_PATTERNS`, `_MULTI_STEP_MIN_MATCHES`, `CompressionBypassWarning`, `detect_bypass_conditions`, and the bypass branch inside `compress_message`. Plus the 4 new `__all__` exports.
3. **Tests:** new `TestCompressionBypassConditions` class added to `tests/test_compressor.py` (lift & adapt from `.local/sandbox/v7.2.0/V02/test_bypass.py`, dropping the inline reference impl in favour of the now-real `compressor.detect_bypass_conditions` and patched `compress_message`).
4. **Mirror-parity test:** small `tests/test_compressor.py::test_bypass_conditions_schema_mirror_parity` per R6 mitigation.
5. **CHANGELOG entry** under `## [v7.2.0]`: "Compression bypass for security warnings, destructive operations, multi-step sequences, and repeated user questions (caveman §Auto-Clarity)."

PR-B couples cleanly with `tests/test_benchmarks.py` (CO-5/SI-4 verification): bypass affects only safety-critical fixtures so composite-score regression on EvoBench non-bypass payloads is expected to be **0** (the bypass branch never fires on those). T3-11 (caveman validate-then-fix loop, currently parked at TIER-3) becomes immediately actionable once C-002 lands; upgrade to TIER-2 in v7.3 retrospective if monitoring shows real bypass events worth post-bypass content validation.
