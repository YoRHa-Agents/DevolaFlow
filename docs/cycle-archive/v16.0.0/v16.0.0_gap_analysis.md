## 3. Dedicated S-1 wording revision case

### 3.1 Exact current v15 wording — preserved verbatim

> Dispatcher agents (Project, Stage, Wave) MUST NOT perform work directly. Only Task Agents execute actual work — writing code, running tests, authoring documents, performing reviews. L0-L2 agents MAY use Read, Glob, Grep, SemanticSearch for planning/orchestration. L0-L2 MUST NOT use Write, StrReplace, Shell (for code/test/build), or EditNotebook to implement. Trivial exception: single file, < 20 lines.

This paragraph is copied verbatim from `.rules/soul.mdc` and is the audit copy
that the v16 ADR/archive must retain even if the source wording changes. It may
remain active only with the complete v15 four-layer runtime. It MUST NOT remain
active with the v16 mapping `L0=Project, L1=Wave, L2=Task`: its `L0-L2 MUST
NOT` band would then prohibit L2 Task from using every implementation tool and
leave the system with no legal implementing layer.

### 3.2 Exact proposed v16 wording

> Dispatcher agents (Project, Wave) MUST NOT perform work directly. Only Task Agents execute actual work — writing code, running tests, authoring documents, performing reviews. L0-L1 agents MAY use Read, Glob, Grep, SemanticSearch for planning/orchestration. L0-L1 MUST NOT use Write, StrReplace, Shell (for code/test/build), or EditNotebook to implement. Trivial exception: single file, < 20 lines.

### 3.3 Proof that dispatcher-not-implementer scope is unchanged

1. **Role-set and invariant-reach proof.** In v15,
   `D15={Project@L0, Stage@L1, Wave@L2}` and `I15={Task@L3}`; the S-1
   prohibition reaches exactly `D15`. In v16,
   `D16={Project@L0, Wave@L1}` and `I16={Task@L2}`; the revised prohibition
   reaches exactly `D16`. In both states, `D ∩ I = ∅`, `D ∪ I` equals the
   complete current role set, every dispatcher is prohibited from
   implementation, and the sole Task role remains outside the dispatcher ban.
   Stage is deleted, not reclassified.
2. **Operation-set proof.** The allowed read/planning operations remain exactly
   `Read, Glob, Grep, SemanticSearch`. The forbidden implementation operations
   remain exactly `Write, StrReplace, Shell (for code/test/build), EditNotebook`.
   Only the dispatcher layer range changes from L0–L2 to L0–L1 because Task is
   renumbered from L3 to L2.
3. **Permission and responsibility proof.** Stage decomposition, gate
   evaluation, and reinforcement assembly move to Project/Wave orchestration in
   A-1; no code, test, document-authoring, or review work moves out of Task.
   The dispatcher and Task permission sets do not expand.
4. **Exception proof.** `Trivial exception: single file, < 20 lines.` remains
   byte-for-byte unchanged.
5. **Atomic-correspondence proof.** The renumbering is semantic-preserving only
   when the following surfaces migrate as one releasable changeset:
   `.rules/soul.mdc` S-1; `.rules/architecture.mdc` A-1/A-3/A-7;
   `agent_workspace.layers` current role/token tables; cascade defaults and
   validators; current-emission handoff and change-status schemas; SKILL and
   hierarchy/message docs; and their rule/schema/runtime tests. The v16
   correspondence is S-1 `{Project, Wave}` + ban `L0-L1` ↔
   `CURRENT_LAYER_ROLES={L0:Project,L1:Wave,L2:Task}` ↔ current dispatcher
   header tokens `{project,wave}` ↔ cascade depth 3 ↔ current artifact tokens
   `{L0,L1,L2}`. A partial old/new cross-product is not a renumbering and is a
   release blocker.
6. **Compatibility-boundary proof.** Legacy schema-v1 maps may normalize
   historical `Stage`, `L3`, and old L1/L2 meanings on read, with provenance and
   without rewriting artifacts. They do not define the current role set, may
   not be emitted by v16 writers, and cannot be used to excuse a mismatch
   between active S-1 and current tokens.
7. **Invariant and Soul-count proof.** P1 remains
   dispatcher-not-implementer; P3 typed messages, P4 bounded escalation, and P5
   artifact contracts remain intact. P2 budgets and A-7 depth change only
   because one dispatch hop is removed. S-1 is revised in place, S-2 through
   S-10 are not renumbered, and the Soul count remains exactly **10**.

Therefore the proposed edit is a role-enumeration and layer-index correction,
not a relaxation of S-1, but that conclusion holds only for the complete v16
correspondence above.

### 3.4 Approval bar and rollback

* The S-1 wording change is a highest-priority SI-3 architecture item. It may
  land only if SI-3 architecture rationality is **≥9.5/10** and the reviewer
  accepts the unchanged-scope proof above.
* The v15 paragraph in §3.1 must be copied verbatim into the v16 ADR/archive;
  compiled outputs are generated from `.rules/soul.mdc`.
* **Forward path:** the surfaces listed in §3.3(5) must land and become active
  atomically. Intermediate implementation commits may exist only on the same
  non-releasable migration branch; no merge, tag, package, or release may expose
  a mixed state.
* **Rollback if rejected or scored below 9.5:** atomically restore the complete
  v15 four-layer contract and runtime: active S-1 is exactly §3.1; A-1 restores
  Project → Stage → Wave → Task; the layer SSOT restores
  `L0=Project, L1=Stage, L2=Wave, L3=Task` and current dispatcher tokens
  `project|stage|wave`; cascade restores four-layer semantics/default depth 4;
  handoff/status schemas and emitters restore v15 current tokens including L3
  Task; and SKILL/docs/tests restore the same four-layer model.
* **Forward-fix alternative:** before any release, correct active S-1 to §3.2,
  regenerate compiled rule surfaces, and satisfy every §3.5 blocker against the
  already-migrated v16 runtime.
* A partial rollback is forbidden. In particular, old S-1 plus v16
  `L0/L1/L2` current tokens is not a conservative superset: it bans L2 Task.
  A-1 cannot override a contradictory P0 Soul rule. The only releasable states
  are the complete v15 rollback or the complete v16 forward state.

### 3.5 Release-blocker parity checks

M4 and release preflight must reject every state except one of these two
complete tuples:

* **v15 tuple:** active S-1 dispatcher roles
  `{Project,Stage,Wave}`, ban `L0-L2`; current layer SSOT
  `{L0:Project,L1:Stage,L2:Wave,L3:Task}`; current dispatcher headers
  `{project,stage,wave}`; current artifact tokens `{L0,L1,L2,L3}`; cascade
