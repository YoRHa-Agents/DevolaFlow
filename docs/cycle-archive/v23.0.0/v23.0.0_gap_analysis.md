# v23.0.0 — W-1 Gap Analysis

> 状态：仅研究与文档；本轮不实现代码、不修改计划文件。  
> 证据边界：反馈 `.local/feedbacks/feedback_for_v21.md` 第 18–24 行，
> 当前源码、测试、宿主契约、已有 harness 账本及 v21/v22 归档基线。

## 1. 反馈与现状

### D-1 / P0 — `entrance.md` 仍可能缺席：根因是写入边界而非模板内容

反馈指出：`entrance.md` 经常没有和其他 Devola 风格任务文件一起建立到
指定工作区。

证据：

- `src/devolaflow/skills/slash_commands.py::scaffold_change_folder` 的规范
  路径会构造 `Change`，填入 `entrance_md`，然后调用
  `Change.to_active_folder`；这条 happy path 能生成入口文件。
- `src/devolaflow/agent_workspace/change.py::Change.from_active_folder` 的
  `_read()` 对缺失文件返回空字符串；因此一个已存在但不完整的任务目录可以
  被加载，缺失不会在读取时失败。
- 同一模块只在后续 `to_active_folder()` 写入时用
  `render_entrance_md()` 回填。回填是 post-hoc repair，不是首次任务目录
  创建的原子完整性条件。
- `src/devolaflow/_workspace_lint/advanced_semantics.py::_check_entrance`
  把缺失报告为 `ENTRANCE_MISSING`，说明 lint 能在事后发现问题，但不能保证
  文件在第一批 artifact 中出现。
- `src/devolaflow/lifecycle/runtime_wiring.py::fire_file_write` 的契约是
  逐文件所有权检查；其文档明确 raw/out-of-band 写入可绕过该 adapter。
  现有入口测试主要覆盖规范 scaffold 和后续 backfill：
  `tests/ghost/test_features_v20_0.py`、`tests/ghost/test_features_v21_3.py`
  与 `tests/test_agent_workspace_change_layout.py`，没有覆盖中断、部分写入、
  直接创建任务目录或多 writer 竞态下的首批完整性。

根因判断：入口模板已经有单一所有者，但“任务目录首批 artifact 必须完整且
包含 `entrance.md`”没有由统一创建事务或创建后不可绕过的完整性门负责。当前
实现把保证分散在规范 scaffold、Change 回填和事后 lint 三处；任一低层写入、
中断或非规范 writer 都能留下缺入口的半成品。因此 v23 应先重划创建/提交边界，
再决定回填是否保留，不能只增加另一个补丁式 `write_text()` 调用。

### D-2 / P0 — 长时等待占用推进窗口：缺少等待期间的安全并发调度契约

反馈要求：制定和执行计划时避免长时等待；若外部任务不得不长时间运行，
应同步推进其他不抢资源的并发任务。

证据：

- `workflow-system/agent/SKILL.md` 的 “Subagent Hang Prevention” 已定义
  task-type timeout、五分钟进度报告以及十分钟无进展升级；这是超时/升级
  规则，不是“等待期间如何挑选独立任务”的调度规则。
- `workflow-system/agent/references/wave-dispatch.md` 将 `parallel` 限定为
  已声明的同一 wave，并规定失败 sibling 继续；未声明为 parallel 的
  `all` 路径仍是 sequential。
- `src/devolaflow/dispatch.py::dispatch_wave_tasks` 只有在
  `sync_barrier.mode == "parallel"` 且任务数大于 1 时才进入并发 executor；
  默认/`all`/非 parallel 模式走 sequential。
- `src/devolaflow/harness/calibration.py::CalibrationRunner.run` 对矩阵使用
  顺序 `for` 循环；达到 `total_timeout_seconds` 后，剩余规格直接记录为
  `outer_timeout` 的 `INSUFFICIENT`，没有等待期间的独立队列推进或可恢复
  的分批调度。
- `src/devolaflow/agent_workspace/dispatch_executor.py` 的 bounded
  concurrency 能隔离已提交任务的执行，但没有表达资源冲突、等待原因、
  可继续 sibling 集合或外部任务进度事件。

根因判断：仓库已有“并发执行器”和“任务超时”，但没有把两者提升为
workflow-level scheduler contract：等待任务、可安全推进任务、资源互斥、
进度心跳、取消/恢复和公平性都没有统一状态模型。结果取决于 caller 是否
碰巧把任务放进 parallel wave，而不是计划/执行阶段的强制行为。

### D-3 / P0 — preflight 后 blocker 未形成 sibling continuation

反馈要求：preflight 授权后如出现 blocker，应同步推进未被 blocker 影响的
任务；只有全部任务无法或不应推进时才停工。

证据：

- `src/devolaflow/lifecycle/preflight_authorization.py::guard_preflight_authorization`
  对无效签名、镜像 hash 或 authorization seal 抛出 `HBP001`；
  `collect_preflight_authorization_violations` 仅收集该 violation。
- `src/devolaflow/lifecycle/validate_dispatch.py` 把 preflight violation
  加入 `pre_dispatch` findings；严格路径会阻断该 dispatch。HBP-01 本身
  必须阻断未授权的 checklist round，这一点不能被削弱。
- `workflow-system/agent/references/execution-protocol.md` 的 PAUSE 段落
  写有 “Wave continues other tasks”，但其 escalation 表和 HBP-01 描述
  没有给出授权后单个 blocker 的 sibling selection、状态转移、资源隔离、
  checkpoint 或最终 join 条件。
- `dispatch_wave_tasks`/`AsyncDispatchExecutor` 的 sibling continuation
  只发生在任务已经成功提交到 wave 后：它捕获单个 callable 的异常并继续
  其他已提交 callable；它不能把一个被 preflight/dispatch gate 拒绝的任务
  转换为“blocked sibling”并自动选择未受影响的下一项。
- `tests/test_agent_workspace_preflight_runtime.py` 覆盖 stop whitelist、
  签名快照和事务性 drift；`tests/test_preflight_loop_guard.py` 覆盖 HBP
  授权门，但未形成“一个 blocker、一个继续、一个暂停/终止”的 wave-level
  回归矩阵。

根因判断：当前 gate 将“当前 dispatch 是否允许开始”和“已开始 wave 中某
任务失败后的 sibling 处理”混为两个未连接的表面。缺少 blocker scope
（task/wave/project）、可继续任务判定、blocked/deferred 状态和 join/stop
语义，因此授权后的后续 blocker 只能阻断当前调用或依赖人工理解，不能稳定
保证 sibling continuation。

### D-4 / P1 — 层级 token 注入超过预期，但实际分量未被测量

反馈要求继续压缩各层注入，在保留有效约束的同时降低 token 消耗。

证据：

- `workflow-system/agent/context_profiles.yaml` 定义层级 hard cap：
  L0 5,000、L1 5,000、L2 8,000 tokens；同时存在 profile token budget、
  rules、learnings、extra_context、summary 和 tool truncation 多个叠加
  来源。
- `src/devolaflow/harness/telemetry.py::_slice_injection_metrics` 明确记录
  当前 host 注入的是完整 `AGENTS.md` 估计，slice 只是配置可提供的 saving；
  文档写明 host side 尚未接线到 sliced corpus。
- v22.1.0 归档账本的 dispatch record 为
  `tokens_injected_measured=1509`、L2 `tokens_budget=8000`，表面
  `budget_compliance_ratio=1.0`；但同一 record 的
  `host_rule_tokens=12430`、`slice_savings_pct=33.5`。这两个指标说明
  “序列化 dispatch payload 未超 L2 cap”不能推出“宿主实际注入未超预算”。
- `src/devolaflow/harness/context_tokens.py` 只有 caller 显式提供
  `skill_text`、`rule_text`、`report_envelope` 或 `context_tokens` 时才会
  记录分量；缺失值保留为 null。现有
  `tests/test_context_token_accounting.py` 正是按 missing/empty 分开验证，
  没有为真实六宿主注入建立观测。
- v22.1.0 final verified evaluation 的 context token summary 中
  `skill_tokens`、`rule_tokens`、`report_tokens` 的 observed records 均为
  0，状态均为 `INSUFFICIENT`。因此反馈中的“超过预期”是有效的优化信号，
  但当前仓库还不能给出每宿主、每层、每 task type 的实测超额。

根因判断：预算断言、配置 slice 估计和宿主实际 prompt 观测没有形成同一条
measurement pipeline；当前合规率偏向测 dispatch 序列化形状，实际 host
injection 仍有盲区。v23 应先补齐分层观测和可复现实验，再按数据压缩规则，
避免以配置 savings 或缺失值冒充真实节省。

## 2. 优先级排序

1. **P0 — D-1 入口完整性**：缺失入口会破坏任务 onboarding、resume 和
   artifact contract，且应在首批写入时被阻止，而不是等 lint 或下一次写入。
2. **P0 — D-3 blocker 后 sibling continuation**：必须同时保持 HBP-01
   未授权阻断和授权后局部故障的安全继续，避免一个局部 blocker 停掉可独立
   推进的工作。
3. **P0 — D-2 长时等待并发推进**：直接影响外部 CLI/网络任务的可用吞吐；
   需要与 D-3 共用可继续队列、资源声明和进度事件。
4. **P1 — D-4 token 注入与 harness**：先建立真实测量和不确定性边界，再
   做压缩；在没有实际 component data 时不能宣称成本下降或质量不变。

依赖关系：D-1 需要先明确任务目录的创建/提交边界；D-2 与 D-3 需要共同的
wave scheduler 状态模型；D-4 的 harness 设计应在压缩实现前冻结 measurement
identity，以免优化前后无法匹配。

## 4. Token harness 必须满足的证据契约

### 4.1 六宿主矩阵与两层证据

Harness 必须覆盖六宿主：Cursor、Claude Code、Codex、GitHub Copilot、
KimiCode、DeepSeek Harness。每个 cell 至少按 task class、层级、skill-on/off
arm、replicate 记录输入 token、输出 token、总 token、wall time、skill
residency、结果状态和原始证据引用。

证据分为两层，不能混称：

1. **CI fixture replay**：六宿主都必须有可审计的 fixture 或明确的
   `INSUFFICIENT`/undeclared 状态；验证 schema、解析、脱敏、聚合、预算和
   byte-stable replay。fixture 的 provenance 必须是 `captured` 或合格的
   `vendor-doc`；synthetic 只能测试解析边界，不能支持 implemented claim。
2. **Operator live measurement**：实际安装并运行宿主时单独记录 live
   provenance、命令、环境、配置 digest 和 host response。不得把 fixture
   replay 的 token 或 skill_loaded 复制到 live 结果。

### 4.2 Claude/Codex/Kimi 的真实验证

Claude Code、OpenAI Codex、KimiCode 必须进行真实 CLI 验证，不能只使用
fixture：实际命令必须以非 shell 拼接方式执行，记录 exit code、wall time、
输入/输出 token usage、`skill_loaded`（不可观测则为 null +
`INSUFFICIENT`）、skill-on/off arm、task class、replicate 和失败诊断脱敏。
认证失败、CLI 不存在、timeout、缺 usage 或缺 skill state 都必须保留为
`INSUFFICIENT`，不可推算成零或 PASS。

Cursor、Copilot、DeepSeek Harness 若没有稳定的 live runtime observation
channel，仍须进入六宿主 CI fixture/replay 矩阵；其 runtime residency
不能因 skill delivery 文件存在而自动推断。当前 HSC 中 Claude/Codex/Kimi
仍是 designed 且无 fixture，Cursor/Copilot/DSH 的 skill residency 是
undeclared，这些现状必须先被证据化再升级声明。

### 4.3 W-3 可复现性与不确定性

每次 operator live run、CI replay 和任何 baseline/current comparison 都
必须把以下字段同时带入 harness output、telemetry ledger 和 StatusReport
metadata face：

- `run_id`：一次完整 run 的稳定身份；不能用它代替实验 salt。
- `salt`：若由 caller 提供，必须原样保存；未提供就是
  `salt_status: INSUFFICIENT`。内容派生的 generated run ID 不是实验 salt。
- `repo_ref`：运行所针对的 branch/tag/ref，并保留可验证的 `repo_sha` 和
  `base_ref` 状态。
- `variance/uncertainty`：每个可比较 cell 的 `n`、warmup、均值/分位数、
  离散度（如 variance 或标准差）及适用的 CI/误差界；timeout、缺失样本、
  吸收失败的原因和样本数必须显式保留。

缺少其中任一影响结论的字段，或只有单次无方差数据时，结论状态必须为
`INSUFFICIENT`。不得将生成的 identifier 写成实验 salt，也不得从
`slice_savings_pct`、配置预算或缺失 usage 推导实际成本下降。质量/成本
比较还必须保持 matched workload identity、source revision 和 repository
reference；否则只报告工程状态，不报告因果改进。
