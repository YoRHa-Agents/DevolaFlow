## §4 Key learnings (multi-agent ladder mechanics)

1. **Ghost-split pull-forward paid for itself.** L0's §7.1 decision to move G-027 from
   v14.5.0 to v14.3.0 meant v14.4.0/v14.5.0/v15.0.0 appended domain files in `tests/ghost/`
   instead of queueing on a 12,405-line monolith ("worst merge-conflict surface in repo",
   F-R20). Corollary: move-heavy refactors make raw `+def test_` counts meaningless —
   v14.3.0 reads +132 raw but +21 net. **W-17 audits must always be net-of-moves.**
2. **Mid-flight sibling drift is real and lands at cycle close.** The `dependency_setup`
   benchmark expectation (`expected_sections: agent_teams`) was silently invalidated by a
   sibling wave's SKILL/template rewrite and only surfaced at the W-16 close regen
   (87.23 → 99.89 after the expectation refresh). When one wave rewrites prompt surfaces
   that another wave's expectations consume, the consuming artifact needs a re-derivation
   step in the same release, not at close.
3. **Wave ownership blur breaks per-PV accounting.** v14.4.0 shipped 4 work blocks in one
   PR; W-17's per-PV cap became unauditable after the fact (net +34 vs cap +30, no
   per-task attribution recorded). Owned-files discipline (S-8) worked for code conflicts,
   but dispatches should also record **per-task test-function attribution** so the cap is
   checkable without forensics.
4. **W-16 "regen at first drift, else at close" is the right contract.** No drift at cycle
   open (v14.2.0 §5 verdict) meant zero interim regens across 5 rungs; the single
   wholesale regen fired exactly when the v15.0.0 content rewrites moved 7 scenarios past
   the envelope. One regen per cycle, fully accounted, floors intact.
5. **PERMISSIVE-IN-MINOR → STRICT-IN-MAJOR graduated 6 flips with zero flip-time
   breakage.** The v14.3.0 permissive period surfaced violations as warnings while the
   suite grew around the strict contracts, so the v15.0.0 flips were re-pins, not
   firefights. Every flip carried a per-flip opt-out — compatibility scored 9.6.
6. **The strict bar did its job.** An honest 9.35 against an operator-set 9.5 produced
   NOT-READY with a 5-item costed gap list instead of an inflated pass — the failure mode
   W-21/SI-3 exist to prevent. The composite is still series-best (9.02 → 9.125 → 9.35
   across the last three MAJOR-bar evaluations), so the bar is discriminating, not
   punitive.
7. **R2 correction (2026-06-12) — the v14.4.0 "+34" never breached the per-PV cap; a
   release total was conflated with a PV delta.** §4.3 above and the SI-3 W-17 ledger
   (`v15.0.0_evaluation.md` §3.3: "net +34 vs cap +30, no per-task attribution
   recorded") were wrong on the attribution point. The PR #149 body carried the split
   verbatim: "W-17: +34 (PV-1 29, PV-2 4, close 1; cycle ~71/150)". Per-PV that is
   29 ≤ 30, 4 ≤ 30, 1 ≤ 30 — **the W-17 per-PV cap was respected in every PV**; the +34
   is the RELEASE total across 2 PVs + release close. No waiver is required. The
   deduction was an aggregation artifact: the evaluation's counting basis
   (`git diff <ref> -- tests/ | grep -cE '^\+\s*def test_'` between release tags) spans
   the whole release and cannot see PV boundaries, while W-17's cap is per-PV.
   **Going-forward rule: release-close reports — the SI-3 W-17 ledger and this W-7
   retrospective — must carry per-PV splits next to every per-release diff total, so
   W-17 audits never again conflate a release total with a PV cap.** The PR-body
   convention that preserved the attribution here ("+N (PV-1 a, PV-2 b, close c)") is
   the minimum required form; §4.3's per-task-attribution-in-dispatches recommendation
   stands as the stronger version of the same rule.
