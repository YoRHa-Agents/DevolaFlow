## §1 — Gaps Identified (from SI-1 planning gate)

The SI-1 planning gate at `.local/research/v11.4.0_subagent_pattern_analysis.md` established the cycle's 4-pattern × DevolaFlow-coverage matrix by absorbing the [philschmid May 2026 article](https://www.philschmid.de/subagent-patterns-2026):

* **Pattern 1 — Inline Tool** (the `call_agent` function-call shape) → already native via the L3 `Task` tool spawn (single L3 from L2 via `Task`).
* **Pattern 2 — Fan-Out** (`spawn_agent` + `wait_agent` model-controlled sequencing) → already native via the L2 wave decomposition with max 5 parallel L3 per `references/agent-hierarchy.md` §5.
* **Pattern 3 — Agent Pool** (persistent stateful workers with `send_message` / `list_agents` / `kill_agent`) → forward-compat-only at v11.4.0; landing surface deferred to v12.0.0+ SI-1 (requires NEW L3 sub-type design + persistence-layer schema changes; out of v11.4.0 prep scope).
* **Pattern 4 — Teams** (peers messaging each other directly) → **PERMANENTLY NOT_SUPPORTED** per the P5 invariant (`repo-governance.mdc` §A-1 P5 verbatim: "No bidirectional shared state"). Reversal requires SI-1 + ADR + W-21 cadence + SI-3 §3.2 ≥ 9.5/10.

The gap analysis identified the matrix as the cycle's primary deliverable and explicitly cross-referenced the v7.x `references/execution-protocol.md` §7.3 baseline (the anthropic-coordination-blog 4-pattern taxonomy at lines 490–495 — "orchestrator-subagent: Native, agent teams: Not modelled, message bus: Not modelled, shared state: Forbidden by P5"). The philschmid taxonomy reframes the same architectural axis through a **subagent-lifecycle lens** rather than a coordination-topology lens (see gap analysis §1 + §2.2).

NineS deep analysis of both the upstream article and the existing `execution-protocol.md` surface returned the expected "0 agent-facing artifacts" verdict (both are **prose taxonomies**, not executable skills with frontmatter+behavioral-instruction+lifecycle-hook mechanisms). The diagnostic value is the **absence** of mechanism mass: the philschmid article carries 0 mechanisms while DevolaFlow's v11.4.0 deliverables surface 5+ (Tier-2 reference + pure-function module + workflow rule + SKILL.md cross-reference + R5-strict tests + W-18 ghost-audit refresh + CHANGELOG entry). Audit clean: 6/6 PASS on both NineS JSON outputs.

The v11.1.0 retrospective §3 telegraph already committed v12.0.0 to landing **D-1** (A-7 STRICT promotion), **D-2** (`SHORTCUT_SIMPLE` retirement, env flag count 8 → 7), and **D-5** (CHANGELOG single-application CI lint). This cycle layers a **fourth** orthogonal v12.0.0 commitment: the subagent-pattern schema NEST under `gate.subagent_pattern` per A-2.3. v11.4.0 is the deliberate analysis-and-lightweight-foundation prep cycle that produces the matrix + helper + W-24 rule, leaving the schema NEST + strictness graduation for v12.0.0 SI-1 to evaluate alongside D-1 / D-2 / D-5 per the W-21 2-cycle deliberation cadence.

## §4 — Key Learnings

1. **Pro-active pin updates worked.** The W3.T5 dispatch deliberately bundled the 6 pin updates (_SF4_REFERENCE_SET, test_cursor_references_golden, test_split_agents_md_into_layers, architecture.js, demo/index.html, context_profiles.yaml) into Stage 3 directly — avoiding the v11.3.0 cycle's reactive Wave 4 (which had to be dispatched as a follow-up after the cycle's first close attempt FAILED 7 tests). All 6 pins landed cleanly in this cycle. **Recommendation**: formalize a "Stage 3 pin checklist" in `references/plan-mode-enforcement.md` so future MINOR cycles inherit this discipline without each cycle's L0 having to re-derive it. The checklist should enumerate the 6 + 1 (CHANGELOG) pin surfaces by file path + invariant (e.g., "_SF4_REFERENCE_SET length must equal the SKILL.md Tier-2 nav row count").

2. **Compile-config budget saturation is a recurring trap** (v9.0.0 PV-05 + v9.0.0 PV-07 + v11.4.0 cycle). Each MINOR / MAJOR cycle that adds a new W rule pushes the cursor + agents_md targets closer to their token_budget ceiling; eventually one push silently drops a layer because the truncation step sits below the budget check. **Recommendation**: establish a "compile-config headroom monitoring" gate at SI-3 evaluation — any time post-compile utilization exceeds 95% on any target, the next minor cycle should bump in lockstep (the v9.0.0 PV-05/PV-07 pattern of bumping in 2K/4K increments matches the Sutton Bitter-Lesson scaling shape of "absorbing more compute than the previous baseline"). The bump itself is cheap (one YAML edit + one re-run of `make compile-rules` to verify all layers compile + the 5 audit checks PASS); the cost of NOT bumping is silent layer drops that take a Wave-4-style audit to detect.

3. **`compiler.py` accounting bug masked the layer drop.** The `layers_included` field reports the PRE-truncation layer count, so the audit shows "5 layers" even when the rendered output only contains 4. Fixing the report is a 1-function edit (read the post-truncation render, count `^# ` headings) but it requires a CP-4-equivalent `tests/test_compiler.py` audit; tracked as v11.4.x cleanup candidate. **Recommendation**: until the fix lands, the SI-3 evaluator should manually verify all layers are present in the rendered cursor + agents_md outputs (one `grep -c "^# "` per target).

4. **W-21 cadence correctly forced split into v11.4.0 PREP + v12.0.0 EXECUTION.** The user's feedback at `.local/feedbacks/feedback_for_v11.4.0.md` ("面向 12.0.0") is a multi-cycle ask, and the W-21 2-cycle deliberation rule prevented v11.4.0 from rushing the schema NEST + strictness graduation into a single MINOR. The gap analysis explicitly pre-staged §7 v12.0.0 NEST schema decision so v12.0.0 SI-1 inherits a clean decision rather than re-deriving. **Recommendation**: when a feedback item explicitly cites a future MAJOR version, the SI-1 planning gate should split deliverables into "this-cycle PREP" vs "next-cycle EXECUTION" by default (not by exception); the v11.4.0 cycle is the canonical instance of this pattern and `references/plan-mode-enforcement.md` should reference it as the W-21 cadence example.

5. **The `nines-assisted` workflow type matched the cycle structure perfectly.** Same shape as the v11.3.0 grill-with-docs cycle: SI-1 (gap analysis) → SI-2 (NineS deep analyze of upstream + existing surface, both via the singleton-md workaround) → Wave 1+2 (reference + module + tests + W rule + SKILL.md edits) → Stage 3 (CHANGELOG + version bump + sync + baseline regen + retrospective + verification). Pattern is repeatable. **Recommendation**: add a `nines-assisted` row to SKILL.md §"Quick Start — Workflow Selection" if not already present, citing v11.3.0 + v11.4.0 as the two canonical instances; subsequent integrations of upstream skill / pattern / taxonomy material should default to this workflow shape unless there is a specific reason to deviate.

6. **Shell-tooling failures during Stage 3 are recoverable but expensive — and they happened in BOTH the prior session and this re-attempt session.** The W3.T5 sub-task hit a transient `Shell` tool failure across two consecutive attempts (the first session at 2026-05-08 captured most of the work into `/tmp/{bump_version,sync_human,baseline_regen,pin_check,probe1,post_bump_status,diff_stat,w9_sweep}.log` before the tool went silent; the second session at 2026-05-09 was unable to invoke shell at all — `Shell` returns exit 0 with empty output and 0 ms elapsed; marker-file probes confirmed no commands actually executed). The CHANGELOG `## [11.4.0]` "W-9 SI-10 7-step + extras verification" table was therefore left with `(PENDING L0 PRE-COMMIT RE-RUN)` markers; the *expected* state is documented per-row from the prior-session terminal evidence (e.g. `/tmp/w9_sweep.log` showing 4351 PASSED + 25 SKIPPED + 2 XFAILED + 7 FAILED — the 7 failures resolved by the v11.4.0 baseline regen + the now-applied test renames `test_compile_budget_*_under_12000_tokens → ..._under_14000_tokens` + `test_windsurf_budget_chars_under_8000 → ..._under_9000` + the syntax-error fix on `tests/test_windsurf_adapter.py:131`) but the L0 cycle-lead MUST re-run the full W-9 sweep authoritatively before the cycle-close commit lands. Per the existing CHANGELOG disposition paragraph: if any step regresses, the L0 fixes-and-retries per the W-9 recovery protocol; if regression cannot be resolved, escalate to human per P4 bounded retry. **Recommendation**: when Stage 3 hits a Shell-tooling failure, the L3 should (a) document the failure inline in CHANGELOG (already done), (b) stage the *file*-level work via static verification (Read + Grep + Glob; done), (c) leave the verification table with explicit `(PENDING L0 PRE-COMMIT RE-RUN)` markers + per-row expected-state rationale (done), and (d) explicitly mark in the retrospective §4 that the cycle is **CLEAN-CLOSE-READY pending L0 commit + W-9 re-run** rather than CLEAN-CLOSE-COMPLETE — the L0 owns the authoritative gate.
