## §3 What was deferred and why

### §3.1 v9.7.0 PV-02 helper not yet wired into runtime dispatch

The `dedup_predecessor_summaries` helper ships as a pure library at
v9.7.0 PV-02 (matching the v9.3.0 PV-05 `AsyncDispatchExecutor`
library-only pattern). The actual runtime wire-in into
`feedback.py::generate_round_dispatch` is **deferred to a future PV**
(likely v9.8.0 or later) for two reasons:

1. **Decoupled landing risk**: wiring the helper in the same PV as
   the schema bump would couple two distinct change-classes. The
   library-only landing lets the schema-v6 baseline stabilize across
   the cycle before runtime activation introduces dynamic ledger
   payloads.
2. **Empirical tuning needed**: the bytes-on-wire savings depend on
   real convergence round empirical signal (how often round-N>1
   pred summaries actually duplicate round N-1's). Wiring without a
   measurement window risks silent degradation; deferring to a
   future PV with an EvoBench scenario covering convergence-loop
   density (round 1 → round 2 → round 3) is the disciplined path.

Telegraphed as a v9.8.0/v9.9.0 candidate in the v10.0.0 cycle plan
addendum.

### §3.2 W-21 Soul-set freeze — no S-11 candidate proposed for v9.7.0

The Soul layer remains at **10 entries** (S-1..S-10) per the v9.0.0
PV-07 freeze. v9.7.0 introduced no immutable invariants requiring
Soul-level codification. Two PV-03 candidates were considered and
rejected:

1. **"L2 wave dispatchers MUST use `dispatch_wave_tasks` when
   wave.mode == parallel AND len(tasks) > 1"** — rejected because
   the existing P1 (Dispatcher-Not-Implementer) covers the
   architectural constraint; codifying a specific helper as Soul
   would over-fit (a future PV that swaps to a different parallel
   primitive would face artificial lift). Telegraphed for v9.9.0
   (cycle N+2) Soul-eval per W-21 governance.
2. **"`predecessor_dedup_ledger` field MUST appear at canonical
   position 17 if present"** — rejected because A-2.2 already
   covers the append-only invariant generically; a v9.7.0-specific
   Soul rule would shadow A-2.2.

### §3.3 W-17 test cap overshoot

Cycle running total post-v9.7.0: **+185 of 150 cap** (+35 overshoot).
Driven by:

* v9.4.0 plugin lifecycle test scaffold (+60 in single cycle)
* v9.6.0 reference-pinning density (+24)
* v9.7.0 +22 (within budget; total balanced across PV-02..PV-04)

Mitigation telegraphed for v10.0.0 MAJOR rollup: the cycle close has
been forecast at ~0 NEW tests budget. The cumulative ledger
re-balances at the major rollup commit.

## §4 Key learnings

### §4.1 Schema bumps cascade across many test files

PV-02's schema bump 5 → 6 with `predecessor_dedup_ledger` at position
17 forced updates to **8 test files** that hardcoded "length 16" /
"version 5". Lesson: **the canonical_order length and schema version
should be referenced via a single source-of-truth constant** (e.g.,
`_V9_1_4_CANONICAL_ORDER_LENGTH` was already this pattern; tests
that bypassed it ate the cascade). Future PVs that bump the schema
should grep for hardcoded numbers FIRST and consolidate via shared
constants.

### §4.2 Library-only landings need explicit dead-API allowlists

PV-02's `dedup_predecessor_summaries` and PV-03's `dispatch_wave_tasks`
+ PV-04's `warmup_selector_cache` all required `DEFAULT_ALLOWLIST`
entries because the canonical caller is either (a) the LLM-driven
Task tool (PV-03) or (b) a test-driven harness (PV-02 / PV-04). The
v9.3.0 PV-05 `AsyncDispatchExecutor` precedent (using the
`_dispatch_executor_dead_api_pins` tuple in
`agent_workspace/__init__.py`) was followed for PV-02
(`_dead_api_pins` in `compressor/__init__.py`).

### §4.3 Latency harness jitter is real (~5-15% per primitive)

The v9.7.0 final `select_context.p95` measured 2027 µs vs the v9.6.0
mid-cycle 1601 µs — a 27% increase that is **harness jitter**, not a
regression (the cumulative 97.5% improvement vs v9.2.4 is unchanged).
Lesson: single-run latency comparisons should be interpreted with a
±15% noise band; cumulative-gain reports (PV-05 deliverable) should
cite the cycle-anchor baseline (v9.2.4) rather than per-PV deltas.

### §4.4 PV-01 measurement gates the cycle's ambition

PV-01's re-baseline at v9.6.0 showed zero regression from v9.5/v9.6
work AND incidental improvements in `select_context.p95` (-20%).
This let v9.7.0's ambition stay **modest** (3 micro-optimizations,
no architectural rework) rather than chasing phantom regressions.
Lesson: **always re-baseline at cycle start** — it sometimes
reveals that the cycle's premise is wrong (in this case, the
"perf-again" framing assumed regressions; PV-01 disproved that
assumption and let PV-02..PV-04 focus on net-new gains).
