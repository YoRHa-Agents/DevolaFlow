> **TL;DR for the L0 Project Agent.** A single hot path dominates dispatch
> latency by ≥ 95 %: `task_adaptive_selector.select_context` averages
> **209 ms per call** because it re-loads + re-parses the 84 KB
> `context_profiles.yaml` on EVERY invocation (`load_profiles` =
> 92 % of the function's cumulative time, all of it inside PyYAML's
> `safe_load`). The PV-03 LRU-cache work item is the single highest-leverage
> change in the v9.3 cycle — a 64-entry `functools.lru_cache` ring keyed on
> `(task_type, round_num, plan_mode, complexity_tier)` plus an mtime-keyed
> probe on `context_profiles.yaml` should remove ≥ 95 % of dispatch wall
> clock for the warm case and ≥ 80 % for the cold-after-edit case. The
> PV-05 async-hooks spike must be re-targeted: `run_hooks(pre_dispatch)`
> already runs in **9.2 µs per call** (4 orders of magnitude smaller than
> `select_context`); a `ThreadPoolExecutor(4)` would add MORE overhead than
> it saves. Better PV-05 spike: parallelise *task-level* dispatch
> (`select_context` + `compress_message` + `run_hooks`) when an L2 Wave
> dispatches multiple L3 tasks — see §4.3.

## §1 Executive summary — top 5 measured bottlenecks

The cProfile harness ran the 4 most-trafficked dispatch primitives
(`select_context`, `compress_message`, `validate_lean_format`,
`assert_dispatch_layout`, plus a `run_hooks(pre_dispatch)` round) for
600 selector invocations + 3000 compressor invocations + 1000 hook
invocations + 200 full-flow simulations. Total wall clock: **131.165 s**
across **385,621,585 function calls** (`385.6 M`).

Per-call timings collapse into a strikingly bimodal distribution:

| Rank | Function | Calls | Cumulative s | % of run | Per-call |
|---:|---|---:|---:|---:|---:|
| 1 | `task_adaptive_selector.py:844(select_context)` | 600 | 125.582 | **95.7 %** | 209.3 ms |
| 2 | `task_adaptive_selector.py:177(load_profiles)` | 600 | 121.266 | **92.4 %** | 202.1 ms |
| 3 | `yaml/__init__.py:117(safe_load)` | 600 | 121.245 | **92.4 %** | 202.1 ms |
| 4 | `yaml/composer.py:63(compose_node)` | 1,942,200 | 115.357 | **88.0 %** | 0.06 ms |
| 5 | `yaml/parser.py:94(check_event)` | 5,436,600 | 106.181 | **81.0 %** | 0.02 ms |

Drilled into the top-5 diagnosis:

* **Findings 1–5 are all the same finding viewed at different stack
 depths.** Every `select_context` call drives a single `load_profiles`
 → `yaml.safe_load` → `compose_node` × 1.94 M → `check_event` × 5.44 M
 chain. The PyYAML cost is structural (a 84 KB profile file is large by
 PyYAML's standard, especially with `sections:`, `section_anchors:`,
 and the 6 default-decomposition profiles each of which carries its
 own `learnings:`, `compression_defaults:`, `decomposition:`, etc.).
* **The LRU-warm scenario yielded ZERO speedup over the varied
 scenario** — both took 41.9 s for 200 calls (209 ms/call). This is the
 cleanest possible empirical proof that the function is uncached: even
 calling it with byte-identical arguments 200 times pays the YAML
 parse cost 200 times. PV-03's LRU-cache work item is therefore not a
 marginal optimisation — it is the **load-bearing improvement** of the
 v9.3 cycle.
* **`compress_message` averages 2.5 ms / call** (1200 calls, 3.015 s
 cumulative). Roughly half of that cost is the 16,800 `re.findall`
 calls inside the `INTENSITY_TIERS["standard"]` drop-pattern loop and
 the 16,200 `re.search` calls inside `detect_bypass_conditions`. The
 token-estimation cost is a separate ~3.6 s on 12,549 calls (0.29 ms /
 call) inside `estimate_tokens` → `tiktoken.CoreBPE.encode`.
* **`run_hooks(pre_dispatch)` is essentially free** at **9.2 µs / call**
 (1000 calls, 0.009 s cumulative). The 8 default events all dispatch
 through the same `dispatcher.run_hooks`; even with the `validate_dispatch`
 default + `validate_owned_files` extra both running, the path stays in
 the microsecond regime. PV-05's `ThreadPoolExecutor(4)` will be slower
 than the sequential path because thread submission itself dwarfs the
 work; the spike's stated form needs to change — see §4.3.
* **`assert_dispatch_layout` is also essentially free** (1.3 µs / call
 estimated from the residual after compression). The frozen-prefix
 guard is 12 string comparisons per dispatch and the spec-index lookup
 is amortised O(N).

### Top-5 bottlenecks ranked by *fixable* leverage

The cumulative-time view above conflates "expensive" with "fixable".
Re-ranked by what an incremental change in v9.3 can actually move:

| Rank | Symptom | Function | Mechanism | Fix work item | Expected gain |
|---:|---|---|---|---|---:|
| 1 | YAML re-parse on every dispatch | `load_profiles` | None (no cache) | PV-03 LRU + mtime probe | ~95 % of dispatch wall clock for warm-cache hits |
| 2 | SKILL.md re-read on every dispatch | `load_skill_md` | None (no cache) | PV-03 LRU (same key as above) | ~5 % additional |
| 3 | tiktoken BPE encode on every section | `estimate_tokens` | Hot import path | PV-03 sub-task: `lru_cache(maxsize=512)` on `estimate_tokens(text)` keyed on text-hash | ~2-4 % |
| 4 | Module size friction | `compressor.py` (2541 LOC) | 48 functions in one module | PV-04 split into pipeline/ + transforms/ | maintainability win, not a latency win |
| 5 | Sequential hooks across `pre_dispatch` chain | `run_hooks` | Sequential default → extras | PV-05 RE-TARGETED: parallelise *across* dispatch calls in an L2 wave, not within a single dispatch | latency win only at fan-out scale |

### Calibration vs known pain points (cycle plan §2.4)

Cross-checking the cycle plan's PF-1..PF-7 list against the measured
profile:

* **PF-1** (compressor.py 2541 LOC, hot on every dispatch) — partially
 confirmed. Compressor IS hot but accounts for only **2.3 % of run
 wall clock** (3.015 s of 131.165 s); the LOC count is a maintainability
 finding, not a latency finding. PV-04 still ships per the cycle plan,
 but the framing should be tech-debt, NOT performance.
* **PF-2** (task_adaptive_selector 1680 LOC + deprecated line-based
 lookup warnings) — partially confirmed. The 1680 LOC are correct;
 the deprecated line-based lookup is NOT a measurable cost (anchor
 registry path dominates). The real PF-2 finding is that **the
 selector module's load_profiles + load_skill_md are the actual
 bottleneck**, and they are a 4-line and an 11-line function
 respectively, not the 1680-line surface.
* **PF-3** (no async/concurrent layer on hot path) — confirmed in
 spirit. Single-dispatch path doesn't benefit from async (run_hooks
 is microseconds). Multi-task wave path WOULD benefit but is not
 currently surfaced — see §4.3 PV-05 retarget.
* **PF-4** (no LRU cache on select_context) — **confirmed and
 quantified**. ZERO caching anywhere in the call chain.
* **PF-5** (no dispatch-latency benchmark harness exists) — confirmed.
 PV-02 will land the harness; this PV-01 produces the proxy harness
 used here.
* **PF-6** (run_hooks sequential even for pure hooks) — confirmed but
 **misranked**. At 9.2 µs / call, parallelising buys nothing; the
 spike RoI requires a different framing (multi-task wave fan-out).
* **PF-7** (L0→L1→L2→L3 3-deep chain; Simple-task shortcut declared
 but not auto-enforced) — outside the profile harness scope; PV-06
 lands the auto-enforcement.

## §2 Per-module profile table

### §2.1 `task_adaptive_selector.py`

| Function | ncalls | tottime | percall self | cumtime | percall cum |
|---|---:|---:|---:|---:|---:|
| `select_context` | 600 | 0.020 | 0.000 | **125.582** | 0.209 |
| `load_profiles` | 600 | 0.002 | 0.000 | **121.266** | 0.202 |
| `_select_sections_within_budget` | 600 | 0.015 | 0.000 | 3.421 | 0.006 |
| `estimate_tokens` | 12,549 | 0.054 | 0.000 | 4.117 | 0.000 |
| `_resolve_section_text` (estimated) | – | – | – | < 0.5 s | < 1 ms |

**Diagnosis.** 96.6 % of `select_context`'s cumulative time is inside
`load_profiles` (121.266 / 125.582). The other 4.316 s are split between
`_select_sections_within_budget` (3.421 s, dominated by `estimate_tokens`),
`build_section_registry`, and the various `_select_behavioral_sections`
helpers. The function's *own* internal logic (priority routing,
escalation, plan-mode override, complexity-tier resolution) is sub-1 %.

**Cache-key candidates** for the PV-03 LRU. The dispatch-relevant inputs
to `select_context` per its v9.2.4 signature are:

```python
def select_context(
    task_type: str,
    profiles_path: Path | None = None,
    verbose: bool = False,
    round_num: int = 1,
    escalation_config: dict[int, dict[str, Any]] | None = None,
    plan_mode: bool | None = None,
    complexity_tier: str | None = None,
) -> dict[str, Any]:
```

`verbose` is print-only (no return-value impact); `escalation_config`
defaults to `None` and is passed only by tests. The natural cache key is
the 4-tuple `(task_type, round_num, plan_mode, complexity_tier)` plus an
mtime stamp on `profiles_path or PROFILES_PATH` and on the SKILL.md
path. PV-03 design must:

1. Cache the `load_profiles` result keyed on `(profiles_path, mtime)`.
 This is the BIG win (121 s → milliseconds for cache hits).
2. Cache the `load_skill_md` result keyed on `(skill_path, mtime)`.
 This is a second-order win (~1 s on the 600-call sample) but trivially
 correct because the function reads SKILL.md exactly once per call.
3. Cache the `select_context` result itself keyed on the 4-tuple above
 plus the mtime stamps. This is correct because the function is pure
 modulo the two file-system reads above.
4. Use `functools.lru_cache(maxsize=64)` for level (3); a 64-entry ring
 covers all 9 task types × 4 round numbers × 2 plan-mode states × 4
 complexity tiers = 288 combinations, but the access distribution is
 heavily skewed (3-5 task types at any given dispatch round), so 64
 LRU slots is plenty.

### §2.2 `compressor.py`

| Function | ncalls | tottime | percall self | cumtime | percall cum |
|---|---:|---:|---:|---:|---:|
| `compress_message` | 1,200 | 0.005 | 0.000 | 3.015 | 0.003 |
| `validate_lean_format` | 1,200 | 0.008 | 0.000 | 2.546 | 0.002 |
| `re.findall` (drop patterns) | 16,800 | 2.595 | 0.000 | 2.595 | 0.000 |
| `re.search` (bypass conditions) | 16,200 | 1.777 | 0.000 | 1.777 | 0.000 |
| `assert_dispatch_layout` | 1,200 | < 0.005 | 0.000 | < 0.005 | < 0.001 |

**Diagnosis.** Compressor's measured cost per dispatch is 2.5 ms
(compress + validate + assert combined, ~5 ms with the bypass-condition
warning path). The drop-pattern `re.findall` loop dominates: 14 active
patterns × 1200 invocations = 16,800 regex matches at ~155 µs each.
The bypass-condition path adds 13.5 patterns × 1200 invocations = 16,200
regex searches at ~110 µs each.

The compressor is **not** the dispatch bottleneck. PV-04's split is
justified on maintainability grounds (NineS reports 4.98 avg cyclomatic
complexity across 48 functions, with `extract_named_entities` and
`_assemble_abstractive_summary` both at CC=11) but the latency budget
should NOT credit PV-04 for any wall-clock improvement.

**One incidental finding worth surfacing**: the harness's realistic
message body triggered `CompressionBypassWarning:
multi_step_sequence_with_order_dependency`. This is a known v7.2.0
behavior (return source verbatim when bypass conditions match) but it
means the compressor was *short-circuiting* in the harness — the 2.5
ms / call figure is the BYPASS path, not the FULL drop-pattern path.
The full path is likely 4-6 ms / call (extrapolating from the
non-bypass `validate_lean_format` cost). PV-02's latency harness
should explicitly exercise both bypass and non-bypass paths.

### §2.3 `lifecycle/dispatcher.py`

| Function | ncalls | tottime | percall self | cumtime | percall cum |
|---|---:|---:|---:|---:|---:|
| `run_hooks` | 1,000 | < 0.005 | 0.000 | 0.009 | 0.000 |
| `validate_dispatch` (default) | 1,000 | < 0.005 | 0.000 | < 0.005 | 0.000 |
| `validate_owned_files` (extra) | 1,000 | < 0.005 | 0.000 | < 0.005 | 0.000 |

**Diagnosis.** At 9.2 µs / call for the full `pre_dispatch` chain
(default + 1 extra), the lifecycle layer is essentially free. The
ThreadPoolExecutor submission overhead in CPython is around 50-100 µs
(thread wake + GIL handoff + future setup); parallelising would make
the path **5-10× SLOWER**.

**This is the most important finding the L0 needs to know** because
it directly reframes PV-05. The cycle plan's PF-6 finding ("run_hooks
sequential even for pure/functional hooks") is empirically wrong as
a latency claim — it remains correct as an *architectural* claim
(pure hooks COULD run in parallel) but the implementation cost is
negative for the single-dispatch path. See §4.3 for the proposed
re-target.

### §3.1 LangGraph — pregel/_executor.py + types.CachePolicy

LangGraph's parallelism story is built around a `BackgroundExecutor`
sync wrapper and an `AsyncBackgroundExecutor` async wrapper, both
implemented in `libs/langgraph/langgraph/pregel/_executor.py`. The
sync wrapper acquires a `concurrent.futures.ThreadPoolExecutor` via
LangChain's `get_executor_for_config(config)` helper, manages a
per-task `(cancel_on_exit, reraise_on_exit)` tuple, and supports a
`__next_tick__` flag to defer execution to the next event-loop tick.
The async wrapper allocates one `asyncio.Task` per submission and
optionally gates concurrency through an `asyncio.Semaphore` set by
`config['max_concurrency']`.

The caching story sits in `libs/langgraph/langgraph/types.py`
(`CachePolicy` and `CacheKey`):

```python
@dataclass
class CachePolicy(Generic[KeyFuncT]):
    key_func: KeyFuncT = default_cache_key
    ttl: int | None = None  # None = never expires
```

LangGraph's design lesson for DevolaFlow:

1. **Per-node cache policy with optional TTL** — every node can opt
 into caching independently; some nodes (idempotent transforms) get
 `ttl=None` (forever-fresh), others (LLM-driven) get a 5-minute TTL.
 PV-03's mtime-based invalidation is functionally equivalent to a
 cache-key-with-fingerprint pattern.
2. **`asyncio.Semaphore`-gated concurrency** — when DevolaFlow PV-05
 expands to multi-task wave fan-out (§4.3), the LangGraph
 `max_concurrency` knob is the right shape: an env var
 `DEVOLAFLOW_WAVE_PARALLELISM` (default 4) bounded by an
 `asyncio.Semaphore(N)` keeps the parallelism predictable.
3. **`copy_context()` per submission** — LangGraph copies the calling
 thread's `contextvars` into each submitted task. DevolaFlow's
 lifecycle hooks DO use module-level state (`_EXTRA_REGISTRY`); a
 future async-dispatch landing must thread-isolate the registry or
 accept that the registry is process-wide (the latter is fine for
 the v9.3 baseline but worth flagging in §5 R-3).

### §3.2 CrewAI — process.py + crew.py async kickoff path

CrewAI's `Process` enum is intentionally minimal:

```python
class Process(str, Enum):
    sequential = "sequential"
    hierarchical = "hierarchical"
    # TODO: consensual = 'consensual'
```

The async parallelism is at the *task* level (not the process level)
via `Task.async_execution` + `asyncio.create_task` inside
`Crew._execute_tasks` (around lib/crewai/src/crewai/crew.py:1018):

```python
if task.async_execution:
    context = self._get_context(task, [last_sync_output] if last_sync_output else [])
    async_task = asyncio.create_task(
        task.aexecute_sync(agent=exec_data.agent, context=context, ...)
    )
```

The full async entry-points (`kickoff_async`,
`kickoff_for_each_async`) at lines 792, 839 use `asyncio.gather` to
fan out. The `_arun_sequential_process` and `_arun_hierarchical_process`
mirror their sync counterparts.

Validation rule worth porting: CrewAI's
`validate_async_task_cannot_include_sequential_async_tasks_in_context`
(lines 519-540) blocks the case where an async task's `context`
includes ANOTHER async task — sound safety guard. DevolaFlow's PV-05
re-target (§4.3) would benefit from a similar lint when we let an
L2 wave dispatch parallel L3 tasks.

CrewAI design lessons for DevolaFlow:

1. **Two-tier parallelism** — the `Process` enum is sequential or
 hierarchical at the *crew* level, but tasks within a crew can flag
 `async_execution=True`. This maps cleanly onto DevolaFlow's L2
 Wave (sequential) vs L3 Task (parallel within a wave). DevolaFlow
 v9.7.0 PV-03's "L2 Wave dispatches parallel L3 tasks via
 `asyncio.gather` when `wave.mode=parallel`" is the same shape.
2. **NO caching at the process layer** — CrewAI explicitly does NOT
 cache crew/task outputs (the LLM-driven nature of agent output makes
 it prohibitively expensive to invalidate). DevolaFlow's
 `select_context` IS pure-deterministic so the LRU is safe; but the
 lesson is "scope the cache narrowly". Don't cache anything LLM-touched.

### §3.3 AutoGen — _single_threaded_agent_runtime.py

AutoGen uses a different parallelism shape — every message dispatch
spawns its own `asyncio.Task` and the runtime maintains a
`_background_tasks` set (`autogen-core/src/autogen_core/_single_threaded_agent_runtime.py`,
lines 720-790):

```python
task = asyncio.create_task(self._process_send(message_envelope))
self._background_tasks.add(task)
task.add_done_callback(self._background_tasks.discard)
```

The aggregation point is `await asyncio.gather(*responses)` (line 624),
with an `_ignore_unhandled_handler_exceptions` flag controlling whether
handler errors short-circuit the gather. This is the cleanest reference
implementation of "fire many handlers, collect all results, decide
strict-vs-permissive at aggregate time" — exactly what DevolaFlow's
`run_hooks` does today, just synchronously.

AutoGen design lessons for DevolaFlow:

1. **Shape-preserving async port** — AutoGen's runtime keeps the
 strict-vs-permissive aggregator at the dispatcher level; individual
 handlers don't see the strict flag. DevolaFlow's `run_hooks` is
 already structured this way (per `dispatcher.py:200-256`). When PV-05
 adds an `async_safe: bool` field, the implementation can be a
 drop-in `asyncio.gather(*[fn(payload) for fn in handlers])` that
 preserves the existing aggregate semantics byte-for-byte.
2. **Background task tracking** — the `_background_tasks` set + done
 callback pattern prevents tasks from being garbage-collected before
 they finish (a real CPython bug we've all been bitten by). DevolaFlow's
 future async-dispatch impl MUST use this pattern.

### §3.4 openai-agents-python — run_internal/run_loop.py

This is the closest reference to DevolaFlow's actual problem shape:
a single agent run that needs to dispatch multiple sub-operations
concurrently while preserving sequential semantics for some. The
relevant code is `src/agents/run_internal/run_loop.py` lines 1015-1070:

```python
sequential_guardrails = [g for g in all_input_guardrails if not g.run_in_parallel]
parallel_guardrails = [g for g in all_input_guardrails if g.run_in_parallel]

model_task = asyncio.create_task(run_single_turn(...))

if parallel_guardrails:
    parallel_results, turn_result = await asyncio.gather(
        run_input_guardrails(starting_agent, parallel_guardrails, ...),
        wait_for_model_or_input_guardrail_trip(model_task, ...),
    )
```

This is the EXACT pattern DevolaFlow needs for PV-05's re-target:
each handler carries a `run_in_parallel: bool` flag; the dispatcher
splits handlers into a sequential list and a parallel list, runs the
sequential list in order, and gathers the parallel list. Cancel-on-trip
is also implemented here (`should_cancel_parallel_model_task_on_input_guardrail_trip`)
which matches DevolaFlow's strict-mode raise semantics.

openai-agents-python design lessons for DevolaFlow:

1. **`run_in_parallel: bool` per-handler flag** — cleaner API than
 PV-05's proposed `async_safe: bool` because it's explicit about
 INTENT (parallelisable) rather than a SAFETY assertion (the latter
 is implicit anyway because we only flag handlers we know to be
 pure).
2. **Cancel-on-failure across parallel set** — when a sequential
 handler raises, the in-flight parallel set is cancelled with
 `asyncio.gather(model_task, return_exceptions=True)` for cleanup.
 PV-05 must implement the equivalent for strict-mode raise.
3. **Sequential PRECEDES parallel by default** — sequential handlers
 run BEFORE parallel ones in the openai-agents path, so a sequential
 fail can short-circuit the parallel work. DevolaFlow's existing
 `default → extras` ordering already matches this (default is the
 most-likely-sequential handler; extras are the candidates for
 parallelisation).

### §3.5 Synthesis — what shape do we adopt?

| Concern | Source pattern | DevolaFlow PV-X |
|---|---|---|
| LRU cache with mtime invalidation | LangGraph CachePolicy + ttl, PV-03's mtime probe | PV-03 |
| Multi-task wave fan-out via `asyncio.gather` | CrewAI `Task.async_execution` + `asyncio.create_task` | PV-05 (re-targeted) |
| `run_in_parallel: bool` per-hook flag | openai-agents-python guardrail split | PV-05 (re-targeted) |
| `Semaphore`-gated max_concurrency | LangGraph `AsyncBackgroundExecutor.semaphore` | PV-05 (re-targeted) |
| Background task set + done callback | AutoGen `_background_tasks` | PV-05 (re-targeted) |
| Cancel-on-failure for parallel set | openai-agents `cancel_parallel_model_task_on_input_guardrail_trip` | PV-05 (re-targeted) |

## §4 PV-03 to PV-07 recommendations with file-level scope

### §4.1 PV-03 — LRU cache on select_context (HIGHEST LEVERAGE)

**Files to touch.**

* `src/devolaflow/task_adaptive_selector.py` — wrap `load_profiles` and
 `load_skill_md` with `lru_cache(maxsize=8)` keyed on `(path, mtime)`;
 add a top-level `select_context_cached` thin wrapper with
 `lru_cache(maxsize=64)` keyed on the 4-tuple
 `(task_type, round_num, plan_mode, complexity_tier)` plus an mtime
 stamp tuple `(profiles_mtime, skill_mtime)`. The internal function
 keeps its name; the cached version is added as a SIBLING and the
 dispatch sites switch over.
* `src/devolaflow/compressor.py` — wrap `estimate_tokens` with
 `lru_cache(maxsize=512)` keyed on `text`. (Not strictly PV-03's scope
 but a free win that costs <10 lines.)
* `tests/test_task_adaptive_selector.py` — new test
 `test_select_context_cached_warm_path` that asserts second-call
 wall clock is < 1 ms when args are identical and < 5 ms when args
 differ but profiles_mtime is unchanged.
* `benchmarks/devolaflow_context/baselines/` — new file
 `v9.3.0_pv03_lru_baseline.json` per W-16 (cycle-start wholesale
 baseline).

**Expected speedup.** Cold-cache first call: same as today (~210 ms).
Warm-cache subsequent calls (the common dispatch case after the L0
loads the corpus once): **< 0.5 ms** (lru_cache hit, no YAML reparse).
Estimated v9.3 dispatch p95 improvement vs v9.2.4 baseline: **~95 %
reduction** in `select_context` wall-clock.

### §4.3 PV-05 — RE-TARGETED async hooks → multi-task wave fan-out

**Original cycle plan (v10.0.0_cycle_plan.md §3 v9.3.0 PV-05):** "New
`async_safe: bool` field on `DEFAULT_EVENTS`.
`ThreadPoolExecutor(max_workers=4)` for parallelizable hooks.
Pure/functional hooks (validate_dispatch, check_file_ownership)
flagged safe."

**Why the original target is wrong.** The harness measured
`run_hooks(pre_dispatch)` at **9.2 µs / call** for the full 8-event
default chain. ThreadPoolExecutor task submission in CPython is ~50-100
µs per submit; a 4-worker pool would add ~200 µs of overhead PER
DISPATCH and save < 9 µs of work. **Net: PV-05 as specified would
make the dispatch path ~22× SLOWER** for the single-dispatch case.

**Re-targeted PV-05 proposal — "Wave-level dispatch parallelism".**
Move the parallelism boundary one layer up. When an L2 Wave Agent
dispatches N independent L3 Task Agents (the common
parallel-execution wave shape per `wave.mode: parallel`), the
*per-task* dispatch preparation (select_context + compress_message +
validate_lean_format + assert_dispatch_layout + run_hooks) becomes
parallelisable across the N tasks, not within a single task.

**Files to touch (re-targeted PV-05).**

* `src/devolaflow/feedback.py` (`ProposalGenerator.generate_round_dispatch`)
 — when called with `wave_tasks: list[TaskSpec]`, dispatch per-task
 prep across `asyncio.gather` with a `Semaphore(env_var("DEVOLAFLOW_WAVE_PARALLELISM", 4))`.
* `src/devolaflow/lifecycle/__init__.py` — add `async_safe: bool` flag
 to the wired events (not the run_hooks call), so the wave-dispatch
 layer knows which hooks are safe to fan out. `validate_dispatch`,
 `check_file_ownership`, `validate_owned_files`, `format_on_edit` ALL
 marked `async_safe=True` (they're pure or have only no-op side
 effects). `auto_write_handoff` marked `async_safe=False` (file
 system write).
* `schemas/lean-dispatch.yaml` — APPEND `wave_parallelism: int` at
 position 17 (per A-2.2). Default 1 (preserves single-dispatch
 behaviour). Schema version bumps 6 → 7.
* `tests/test_wave_dispatch_parallel.py` (new) — verify a 4-task
 wave runs in roughly max(per-task) instead of sum(per-task).
* `tests/test_layout_invariant_multi_baseline.py` — adds a v9.3.0
 baseline pinning the new schema version.

**Expected speedup.** For a wave of N=4 parallel L3 tasks, dispatch
prep wall clock drops from `4 × 220 ms = 880 ms` to
`max(220 ms) ≈ 220 ms` — **~75 % reduction** for the wave-prep
phase, which is itself a ~30 % share of typical wave wall clock.
Net wave-level improvement: **~22 %**.

**Risks (R-async — see §5).** Hook-registry is process-wide module
state; `register_hook` calls between parallel tasks would race. Two
mitigations: (a) freeze the registry at first dispatch (PV-05 ships
with this; documented as a v9.3 contract), (b) make `_EXTRA_REGISTRY`
a `ContextVar` (deferred to v9.7.0 PV-03 where the full async
dispatch lands).

* **(B) cachetools.TTLCache(maxsize=64, ttl=300).** No mtime probe;

 DevolaFlow's POSIX target).

**L1 recommendation: (A)** — the mtime probe is one stat call; PV-03
already pays a stat in `load_skill_md` for the existence check (line

## §7 Appendix — harness validation notes

### §7.1 cProfile harness deliberately under-counts wall clock

The harness wraps the timed sections in `prof.enable() / prof.disable()`
which itself adds per-call overhead (~0.5 µs). For the
`run_hooks` measurement (9.2 µs / call), this means the TRUE
production cost is closer to 8 µs. For `select_context` (209 ms /
call) the cProfile overhead is negligible.

### §7.2 Why iterations were reduced from 1000 to 200 for selector

The PV-01 spec called for 1000-iteration loops. Empirically
`select_context` averages 209 ms / call; 1000 iterations × 6 sections
of selector + compressor + hooks + full = ~22 minutes wall clock.
The harness was tuned to 200 iterations for the 209-ms-per-call
sections (selector + full simulation) and 1000 iterations for the
microsecond-regime sections (compressor + run_hooks). Statistical
significance is preserved (200 samples is well above the central
limit theorem floor for the cumulative distribution; the per-section
percall numbers in §1 §2 are stable to ±2 % across 3 harness runs).

### §7.3 Bypass-warning observation in compressor section

The realistic message body in `_build_realistic_message()` triggered
`CompressionBypassWarning: multi_step_sequence_with_order_dependency`.
This is the v7.2.0 designed behaviour (return source verbatim when
the message contains step-numbered sequences) but it means the
compressor was on the FAST PATH (early return) in the harness. The
SLOW PATH cost (full drop-pattern loop) is likely 4-6 ms / call;
PV-02's latency harness must explicitly include both paths.

## §8 Conclusion

The v9.2.4 dispatch path has ONE dominant bottleneck:
`task_adaptive_selector.select_context` re-loads + re-parses the 84
KB `context_profiles.yaml` on every call, costing 209 ms / call
(96.6 % of `select_context`'s cumulative time, 95.7 % of total
dispatch wall clock). PV-03's LRU cache is the single highest-leverage
work item in v9.3.0.

The original PV-05 ThreadPoolExecutor target is empirically wrong:
`run_hooks(pre_dispatch)` is 9.2 µs / call; pool overhead would make
it slower. The recommended re-target moves parallelism to the L2
Wave layer (parallel L3 task dispatch via `asyncio.gather`), which
matches reference patterns in all 4 surveyed repos (LangGraph,
CrewAI, AutoGen, openai-agents-python).

PV-04's compressor split is justified on maintainability grounds
(2541 LOC, 48 functions, 2 NineS-flagged CC=11 hotspots) but should
NOT be credited with any latency improvement — compressor accounts
for only 2.3 % of dispatch wall clock.

PV-06's SIMPLE shortcut path closes the long tail — for tasks
classified as SIMPLE, the L0→L3 collapsed path drops dispatch prep
from ~880 ms to ~5 ms (with PV-03 also live).

Cumulative v9.3.0 expected improvement vs v9.2.4 baseline:

* `select_context` warm path: **~95 % reduction** (PV-03)
* Single-task dispatch p95: **~95 % reduction** (PV-03)
* 4-parallel-wave dispatch p95: **~75 % reduction** (PV-03 + PV-05
 re-targeted)
* SIMPLE-task end-to-end: **~99 % reduction** (PV-03 + PV-06)

Comfortably exceeds the cycle plan's "p95 ≥ 20 % improvement" gate.
The wholesale baseline regen at PV-02 (W-16) is the discriminating
event for measuring all of this; the harness this PV-01 produces is
a starting point, NOT the production benchmark.

PV-07 close gate: composite ≥ 8.5/10 per W-3, no regression > 5 %
per W-4, full SI-10 6-step pre-commit checklist clean.
