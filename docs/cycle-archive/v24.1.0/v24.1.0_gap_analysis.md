# v24.1.0 Gap Analysis — Digesting v24.0.0

Cycle: v24.1.0 (MINOR) · Entry composite 9.83 (READY),
`.local/research/v24.1.0_harness_entry.json`

W-1 entry gate. v24.0.0 shipped risk parking and workspace compaction and then
told us where they hurt. This lists what the evidence says is wrong, in the
order the evidence surfaced it, with the file-scoped fix for each.

## Method

Three sources, no speculation:

1. the v24 retrospective §7, which telegraphed three follow-ups;
2. running v24's own tools against the real repository workspace rather than
   a fixture, which is where the funnel failure below surfaced;
3. reading the harness ledger end to end after the F-00 fix.

## F-10 — The scan-to-plan funnel dead-ends on every real folder (BLOCKER)

`devola-compact scan` reported three over-threshold folders and told the
operator to run `plan`. `plan` reported `movable_tokens: 0` for all three.

The cause is that automatic classification in
`src/devolaflow/workspace_compact/engine.py::_classify` only moves closed
risks and files under a historical directory name (`loops`, `rounds`,
`history`, `logs`). Real workspace weight is none of those: it is one large
hand-written design document sitting in the folder root, which classifies
`LIVE` and retains.

The `--include` escape hatch existed and worked, but nothing in the output
mentioned it, and `_plan_payload` listed only `MOVE` entries — so the operator
could not even see which files were candidates. The feature was reachable only
by reading the source.

Fix: `CompactPlan.candidates` surfaces retained `LIVE` entries ranked by
tokens; `_plan_note` names the heaviest one and the exact flag; `bloat.py`
suggestion text points at the same path. Summaries are now computed for
retained candidates too, because a bare path does not tell an operator whether
a file still earns its place.

## F-11 — The recommended invocation could not run (CRITICAL)

`--folder` was registered ahead of `add_subparsers` on both CLIs, so
`devola-parking status --folder X` and `devola-compact plan --folder X` both
failed with `unrecognized arguments`. Only the pre-subcommand order worked.

`bloat.py::suggestion_text` printed
`devola-compact plan --folder <path>` — the order that fails.

Fix: a shared parent parser registers `--folder` (and `--telemetry`) on every
subparser as well; `_resolve_shared_options` folds the two positions together.
Both orders now produce byte-identical output, pinned by a test on each CLI.

## F-12 — Compaction had no net-benefit accounting (MAJOR)

Retrospective §7 telegraphed this: v24's dogfood run relocated 432 tokens and
spent nearly all of them on the digest it wrote, a net of 2.9%. That reading
was only available after the fact.

Fix: `digest.py::render_digest_rows` splits rendering from the ledger so
`estimate_digest_tokens` can price the digest a plan *would* write by
rendering it — exact, not a constant that would drift on the next layout
change. `CompactPlan` gains `digest_tokens`, `net_tokens`, and
`pays_for_itself`; the plan note says so in words when a move would make a
folder more expensive to read.

## F-13 — `bypassed` was dead telemetry vocabulary (MAJOR)

`workspace_compact/telemetry.py` declares three outcomes. Only `applied` and
`planned` were ever written by production code; `bypassed` appeared solely in
tests. The ledger therefore could not distinguish "no plan was made" from "a
plan was made and declined itself" — the two cases that decide whether
compaction is worth suggesting at all.

Fix: `console.py` emits `bypassed` when nothing is eligible and when a plan
does not pay for its digest, with the reason recorded.

## F-14 — F-00 is a class of failure, not one bad row (CRITICAL)

The v24 fix named `iteration-delta-gate` as a retired gate the reader accepts.
That repaired one row. `aggregator.py` still raises from roughly forty
distinct validation points, and `load_ledger_records` aborts the whole read on
any of them — so the next unforeseen row (a future schema field, a torn write,
a renamed constant) costs the entire evidence base again.

Fix: `load_ledger_records(..., quarantine=[...])` isolates a rejected row and
continues. Strict remains the default, so existing callers are unchanged.
`evaluate` opts in and surfaces `quarantined_rows` at the tail of its envelope
— appended, never inserted, because the key order is pinned. Isolation stays
loud: every quarantined row is logged at WARNING and returned. A ledger where
no row survives still fails, so isolation can never manufacture an empty PASS.

## F-15 — `BloatFinding.over_by` ignored the scan's own threshold (MINOR)

`over_by` subtracted the module default rather than the threshold the scan
filtered on — the same defect class fixed for `suggestion_text` in v24. Fix:
`BloatFinding` carries the threshold it was measured against.
