## 4. Key learnings for v9.2.0

1. **Doc-vs-code lies survive for cycles until a clean-context audit catches them.** Soul Rule S-9 (in `.rules/soul.mdc`, compiled into `AGENTS.md` + `.cursor/rules/repo-governance.mdc`) cited `tests/test_handoff_envelope_immutable.py` + `lifecycle/check_envelope_append_only.py` as enforcement surfaces, but neither existed on disk through v9.0.1 — the rule was a prompt-only lie for a full cycle because the rule-surface tests (`tests/test_no_ghost_features.py`) did not assert that every rule-cited file resolves to a concrete path. v9.1.0 closes the specific S-9 instance (G-001 + G-002) but v9.2.0 SHOULD generalize the fix: extend the ghost-audit to walk every `.rules/*.mdc` source, extract every `<path>/<file>` reference, and assert the referenced path exists in the working tree. Lesson: **every rule citation is a ghost-feature claim; the ghost-audit must cover rule corpora, not just source symbols**.

2. **CHANGELOG claims must correspond to a green test run at the moment the entry is authored** (W-18 ghost-audit precondition sharpened). During the v9.1.0 cycle close we caught that the prior session's CHANGELOG `## [9.1.0]` entry was authored with W-9 "6/6 PASS" claims, but the entry existed in the working tree BEFORE `make sync-human-docs` had run and BEFORE the demo `index.html` "What's New" + `versions.json` v9.1.0 entry + `shared/i18n.js` v910 keys were on disk. The resume session had to discover the trailing work by diffing `git status` against the CHANGELOG narrative. This is a W-18 ghost-audit lesson: **every claim in a CHANGELOG entry MUST correspond to a green test run at the moment the entry is authored**, otherwise resume sessions discover trailing work. v9.2.0 SHOULD add a pre-commit lint that walks the latest `## [vX.Y.Z]` block and asserts every `### Verification Checklist` "PASS" bullet has a corresponding test that was collected in the CI run producing the commit — the CHANGELOG becomes a checklist the CI verifies against, not a free-form narrative composed ahead of the verification.

3. **Auto-compile in `install_local` closes the lifecycle-activation gap at zero operator cost.** The v9.0.0 PV-07 rule-compiler work produced a beautifully layered `.rules/` → `AGENTS.md` + `.cursor/rules/repo-governance.mdc` pipeline, but `devola-init local` never invoked it — fresh repos received `.rules/` sources without compiled governance until the operator discovered `devola-init sync-rules` manually. G-007's `install_local(compile_rules=True)` default-on + `--no-compile` opt-out flips the experience: scaffolding now produces terminal-ready state, not deferred state. Lesson for v9.2.0 and beyond: **scaffold commands should produce terminal-ready output, with opt-out flags for advanced users, not opt-in flags for basic users** — the same pattern should be audited across every `devola-init` subcommand.

4. **Per-PV test cap discipline held at +27/+30 — signals W-17 is right-sized for MINOR cycles that close doc-vs-code drift without schema bumps.** v9.1.0 added 27 NEW test functions (3 + 12 + 4 + 4 + 2 + 5 + 1) within the +30 per-PV cap, covering the full S-9 triangle (test + hook + dispatch integration) plus two new `.rules/`-corpus lints (G-013 + G-014). The cap produced the right pressure: it forced authors to favour parametrized extensions over new test functions where possible (the 12 `test_lifecycle_envelope_append_only.py` tests cover a single hook across 12 scenarios rather than splitting into 12 separate modules). Lesson: **W-17's +30 cap is right-sized for a single-PV MINOR cycle scoped to doc-vs-code closure; future schema-bump cycles (v9.2.0+ if the payload grows) will likely need stricter parametrize-over-new-function discipline to stay under the cap**.
