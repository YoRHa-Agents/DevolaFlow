## 1. 背景与问题

现有 preflight 是任务开始前的一次性检查闸门。但很多 harness 缺失（缺 fixture、缺
golden、缺 make target、缺脚手架）不是一次 preflight 能发现的——它们随任务推进才
暴露，等主线 L2 撞上时已经是 blocker。需要一个前瞻侦察角色 **Pathfinder**：在主线
执行的同时探索后续几步的基建缺失，提前预警并触发补建。

## 2. 现状分析（SI-1 (a) 缺陷枚举）

### 2.1 「旁路角色」核验结论：现存的是伪类别

任务原设想「结合 reviewer 等各个旁路角色统一设定」。逐一核验后，**现存角色没有一个
是真旁路**（与主线 L2 并发执行、有独立通信通道的角色数为零）：

| 候选 | 实际形态 | 证据 |
|---|---|---|
| Reviewer | 顺序 L2 特化（`type: review`）；两段评审 = 「两个**顺序**的 L2 Review Task」 | `workflow-system/agent/references/team-roles.md` §8 |
| Generator-Verifier | 顺序波次模式；并发派发被明文列为 unsuitable（"generator and verifier dispatched simultaneously"） | `workflow-system/agent/references/subagent-patterns.md` §5 |
| Preflight | 阻塞式生命周期闸门（propose 之后、checklist 轮之前，L0+人签字），不是角色 | `workflow-system/agent/templates/builtin/change-driven.yaml`; `references/execution-protocol.md` §1 |
| Harness builder | 作为角色不存在；只有 seed 模板 + CLI + 普通 L2 Implement 任务 | `workflow-system/agent/templates/seeds/harness-construction.yaml`; `references/harness-construction.md` |
| Grill mode | 唯一号称 parallel-orthogonal，但并行对象是 plan mode（计划期、面向操作者），非主线 L2 | `references/grill-mode.md` §1, §8.3 |
| Fan-out 并行 L2 | 真并发，但那是主线波次本身（≤5 任务/波、4 并发在飞），不是旁路 | `references/agent-hierarchy.md` §6 |

**推论**：Pathfinder 不是「加入现有旁路家族」，而是开创这个类别。

### 2.2 机制真空与可复用资产

真空：
- 全库无 DAG 分析器、无前瞻/侦察机制。
- `schemas/wave-definition.schema.yaml` 的 `dependency_matrix_ref` 是从未落地的
  TODO（L1 目前在 dispatch payload 内联组装依赖）。

可复用资产（复用率高于预期）：
- `src/devolaflow/harness/gap.py`：`build_gap_report` / `compare_gap_reports`
  （增量对比）/ `render_capability_review` —— 侦察逻辑主体现成。
- `harness_preflight.md` 有完整 schema（`schemas/agent-workspace/harness-preflight.yaml`）
  与 artifact-as-flag 先例（presence ⇒ harness-flagged，零 dispatch 字段）。
- Handoff envelope 三种 kind（TaskDispatch / StatusReport / **EscalationEvent**），
  `HandoffStore` 运行时 API，S-9 append-only —— 通信通道零新造。
- 17 个 lifecycle 事件；`post_dispatch` 是明文预留的扩展槽。
- Fan-out 执行器（`src/devolaflow/dispatch.py::dispatch_wave_tasks`）真实异步，
  `depends_on` + `sync_barrier` 现成。

### 2.3 被证伪的前提

任务原设想「统一成一套架构下的不同 plugin 来激活」。核验：插件注册表
（`workflow-system/agent/knowledge/runtime-plugins.yaml`，A-5 SSOT）注册的是
**外部工具 CLI**（rtk / codegraph / si-chip 等），激活 = 装二进制 + stage 映射，
**不是 agent 角色**。角色的现成机制是 team-roles 的 L2 任务特化
（`TaskDispatch.task.type` 激活）。统一的正确宿主是后者，不是插件表。

## 4. 设计方案

### 4.1 角色定义

`pathfind` = 第六种 L2 任务特化。职责：以 D-2 操作性定义为准侦察后续基建缺失，
产出结构化 gap 报告。**不写产品代码、不写测试代码**——唯一写入面是自己的报告
artifact（change 文件夹内 + evidence/）与 handoff envelope（S-8 合法写入面的
子集，无需特殊 ownership）。

与相邻角色的边界：
- vs Reviewer：reviewer 评「已产出的东西对不对」（任务形状）；PF 评「后面要跑的
  东西缺不缺基建」（基建形状）。
- vs Preflight：preflight 是 t=0 的一次性闸门劳动；PF 是 t>0 的可重入侦察。
- vs L1：波次依赖规划、dependency map 组装是 L1 职责，PF 只读不产出（D-16）。

### 4.2 执行形态

- PF 作为 wave N 的一个普通并行 L2 槽位（≤5 容量含 PF；是否带侦察由 L1 依赖图权衡）。
- 节律：首次出动全量粗扫 + 细扫近两波；此后每波边界增量刷新（`compare_gap_reports`）。
- 预算：`context_profiles.yaml` 新增 `pathfind` 任务类型，token 预算 ~5K
  （低于 L2 基准 8K；侦察是只读+写报告的轻量工作）。

### 4.3 协同协议

- 报告 artifact：`.local/.agent/active/<change-id>/pathfinder_report.md`
  （每次扫描刷新；分「blocker 级」与「backlog」两段），raw gap JSON 进
  `evidence/`（沿用 evidence 目录既有字节上限）。
- 每次刷新伴随一封 StatusReport envelope（seq+1，S-9）；L1 波次边界聚合进
  WaveReport；L0 消费后按 D-15 分流。
- blocker 级 gap 直接发 EscalationEvent（现成 P4 升级轨道），不等波次边界。
- C-9 新增预算行：`pathfinder_report.md` soft 800 / hard 1600
  （镜像 harness_preflight.md 行）。

### 4.4 激活（双轨，零新增 env flag）

1. 自动轨：change 为 harness-flagged（`harness_preflight.md` 存在）时，L0 默认在
   首个执行波编入 PF 槽位——artifact-as-flag，沿用 harness_preflight 先例。
2. 手动轨：自然语言 opt-in（触发词沿 W-22 `classify_grill_intent` 模式另建
   `classify_pathfind_intent`），供非 harness-flagged 场景按需启用。

### 4.6 次周期：机制统一（D-7/D-8/D-9）

- Preflight 拆分：闸门语义（签字/stop card/阻塞）留 L0+human；起草劳动
  （config 盘点、gap 清单、harness_preflight 撰写）改由 `type: preflight` L2 执行。
- HarnessBuild 新建 `type: harness_build`，承接 D-3 两段式的修复执行者
  （现由普通 Implement 兼任）。
- Reviewer 已在机制内，零改动。
- 影响面：`change-driven.yaml` stage 定义、`execution-protocol.md`、
  `team-roles.md`——W-5 全套联动，故独立成周期（D-9），不与 Pathfinder 同期。

## 6. 后续工作项与防停滞机制（D-18）

一期（Pathfinder 落地周期）结项/归档时，L0 必须物化以下追加工作项，
**每项启动需人类 Gate 签字**：

| # | 工作项 | 内容 | 防停滞锚点 |
|---|---|---|---|
| F-1 | 机制统一周期 | §4.6 全部内容 | 一期 retrospective §3 强制记录（W-7）；次周期 SI-1 gap analysis **必须显式处置**（采纳，或再延期须书面理由）——沿用 W-21 telegraph 先例 |
| F-2 | Pattern 3 预埋清理 | 独立 change + ADR：移除 `AGENT_POOL_FORWARD` / `gate.subagent_pattern` NEST / W-24 相应规则文本修订 | 同上；ADR 未立案前不得动任何相关代码 |
| F-3 | pool runtime 待定设计归档确认 | §5 内容随 W-19 归档进 `docs/cycle-archive/` | 归档动作本身即闭环 |

防停滞机制小结：**记录义务（W-7 §3）+ 处置义务（次周期 SI-1 显式回应）+ 启动闸门
（人类签字）** 三件套——遗留项可以被再延期，但不允许无声蒸发。

## 7. 优先级排序（SI-1 (b)）

- **P0**（一期核心）：角色定义 + `pathfinder.md` reference + seed + context profile
  + 报告 schema + 激活分类器。
- **P1**（一期治理配套）：C-9 预算行 + lint 接线 + ghost audit + 测试（≤+30）。
- **P2**(一期收尾)：SKILL.md 联动 + 4 适配器 build（W-5）。
- **Deferred**：F-1 机制统一周期、F-2 清理 ADR（均需人类 Gate 启动）。

## 8. 可行性结论

**可行，且成本低于任务原设想。** 波次交错形态零架构障碍：并发用现成 fan-out，
通信用现成 envelope 三 kind，侦察逻辑主体复用 `harness/gap.py`，激活复用
artifact-as-flag 先例，schema 零改动。全部新造面收敛为：一个 L2 type、一份
reference、一个 seed、一个 profile、一个报告 schema、一个纯函数分类器。

主要风险与缓解：
1. 槽位占用稀释主线吞吐 → 双轨激活（默认只对 harness-flagged 开）+ 5K 瘦身预算。
2. 报告时效性（波次边界节律下 blocker 漏报）→ 增量刷新 + EscalationEvent 即时轨；
   时效性事故计入常规 harness telemetry，作为 F-1/F-2 之外是否重提常驻形态的证据。
3. 「统一」范围失控 → D-9 分期硬隔离：本周期纯新增，重构独立成周期且有人类 Gate。
