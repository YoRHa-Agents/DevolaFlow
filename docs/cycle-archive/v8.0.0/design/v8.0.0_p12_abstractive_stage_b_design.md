## 1. Scope and intent

Stage B is the **LLM-assisted** abstractive path that complements the
Stage A heuristic landed by P-12 in v8.0.0. Stage A's deterministic
density-routed compression is good for ~90 % of predecessor artifacts
because it is:

* zero-cost (pure regex + token counting),
* zero-latency (~1 ms per call on 50k-token inputs),
* CO-2 verbatim (named entities never mutated), and
* trivially testable (pure function).

But Stage A leaves a long tail of artifacts on the table:

* Multi-section technical decisions where the relationship BETWEEN
  sections matters more than any single section's density (e.g., an
  ADR with `Context → Decision → Consequences → Alternatives` —
  entities split across 4 sections; each section is "dense" but a
  human-readable one-paragraph summary across all four would carry
  more information per token than 5×4 = 20 verbatim lines).
* Long convergence histories (round 7+ of a single task) where the
  USEFUL content is the diff between rounds, not any one round's body.
* Cross-artifact synthesis (e.g., 3 different `pred[*]` artifacts that
  collectively describe the same migration) where the dispatcher would
  benefit from a unified narrative rather than 3 independent extractive
  blocks.

Stage B addresses these via a **bounded LLM call** with strict
fallback semantics, gated by the same `summary.mode='abstractive'`
opt-in that Stage A reads today.

## 2. Decision triggers (when to invoke Stage B)

Stage B is invoked when ALL of the following hold:

1. `complex_feature.summary_mode == 'abstractive'` (P-12 Stage A gate —
   already wired) AND the dispatcher resolved this section for the
   current task type.
2. `complex_feature.stage_b == true` (NEW field, default false).
3. Stage A output exceeds `complex_feature.stage_b_min_savings_pct` of
   input (default 30 %) — only escalate to Stage B when Stage A already
   shows the section bench is worth a deeper pass.
4. Cumulative LLM cost for THIS dispatch's predecessor block is below
   `complex_feature.stage_b_cost_ceiling_usd` (default $0.05 per dispatch).
5. Wall-clock budget for THIS dispatch's predecessor block is below
   `complex_feature.stage_b_latency_budget_ms` (default 800 ms total
   across all `pred[*]` artifacts).

If ANY condition fails → fall back to Stage A output unchanged. The
dispatcher MUST log which condition failed (S-5 No Silent Failures).

## 3. Prompt template

```text
SYSTEM:
You are a CO-2 verbatim summariser. Your job is to compress the
predecessor artifact below into ≤{max_tokens} tokens while preserving
EVERY entity from the verbatim list. Do NOT paraphrase entity values.
Do NOT introduce facts not present in the artifact. Output a single
markdown block with the same heading hierarchy as the input.

VERBATIM ENTITIES (MUST appear character-for-character in your output):
{entities_block}

USER:
Artifact: {artifact_path}
Mode: stage_b_abstractive
Stage A snapshot (use as a HINT, not as ground truth):
{stage_a_summary}

Full artifact body:
{artifact_body}

OUTPUT REQUIREMENTS:
1. Single markdown block, ≤{max_tokens} tokens.
2. Every entity from VERBATIM ENTITIES MUST appear unchanged.
3. Preserve heading hierarchy (do not flatten H2→H1).
4. If you cannot meet (1) AND (2), respond with the literal string
   "STAGE_B_ABORT: <reason>" and nothing else. The caller will fall
   back to Stage A.
```

The `entities_block` is built verbatim from
`extract_named_entities(artifact_body)` — same call Stage A makes —
so the LLM has an authoritative list of file paths, version strings,
commit hashes, task IDs, metric values, error messages, acceptance
bullets, and interface signatures it MUST keep.

## 4. Fallback strategy (failure modes → action)

| # | Failure mode | Detection | Action |
|---|--------------|-----------|--------|
| F1 | LLM call timed out | wall-clock > `latency_budget_ms` | Return Stage A output verbatim |
| F2 | LLM returned `STAGE_B_ABORT: ...` | string match on first line | Return Stage A output verbatim, log abort reason |
| F3 | LLM output exceeds `max_tokens` | `estimate_tokens(output) > max_tokens` | Hard-truncate via `_truncate_to_tokens()` then **verify entities still present**; if any entity missing → fall back to Stage A |
| F4 | LLM dropped a verbatim entity | post-output diff: `set(entities) - set(extract_named_entities(output))` | Return Stage A output verbatim, log dropped entity list |
| F5 | LLM API returned non-200 | exception in HTTP client | Return Stage A output verbatim, log status code |
| F6 | Cumulative dispatch cost exceeded | `current_cost > cost_ceiling_usd` | Return Stage A output verbatim, log cost overrun |
| F7 | LLM output failed schema (e.g., not markdown) | parser raises | Return Stage A output verbatim |

In all 7 failure modes the dispatcher MUST set
`predecessor[i].abstractive_stage = 'a'` (instead of `'b'`) in the
status report so downstream auditors can see Stage B was attempted but
fell back. This is critical for SI-4 benchmark regression analysis —
otherwise we can't tell "Stage B is broken" from "Stage B was never
invoked" in the EvoBench rollup.

## 5. Latency budget

* Per `pred[*]` artifact: ≤ 400 ms (P95) — measured at LLM API boundary,
  excluding network jitter via warm-pool.
* Per dispatch (sum across all `pred[*]`): ≤ 800 ms (P95).
* End-to-end dispatch render with Stage B: ≤ +300 ms vs. Stage A
  (P95 budget — measured by `tests/test_e2e_compression.py` micro-bench).
* Hard kill: any single LLM call exceeding 2× P95 budget is killed and
  fallback F1 is triggered.

The 800 ms per-dispatch ceiling is chosen so a single task agent's
predecessor block adds at most ~5 % to the wall-clock of a 16 s typical
dispatch (per v7.5.0 `eb220` measurement). Beyond that, the cost stops
being justified by the density gain.

## 6. Cost ceiling

* Per dispatch: ≤ $0.05 USD (default). Override via
  `summary.stage_b_cost_ceiling_usd` per-profile.
* Per agent run (cumulative): tracked by `gate/budget.py`
  (P-03 deliverable in v8.0.0 W2). Stage B cost is added to the
  per-task token budget; exceeding either trips fallback F6.
* Model selection: `quality` tier model (e.g., gpt-4o, claude-sonnet-4.6)
  for `complex_feature` profile; `balanced` tier for all others.
  No `budget` tier for Stage B — the savings don't justify the
  hallucination risk on a budget model.

For a typical 50k-token long-context dispatch with 3 `pred[*]`
artifacts, Stage B would cost ~$0.03 (well within ceiling) and save
~12k tokens of dispatch payload (24 % reduction). Stage A on the same
input saves ~6k tokens (12 % reduction) at zero cost — so Stage B's
incremental ROI is ~6k tokens per $0.03, or ~200k tokens per dollar.

## 7. Integration points with Stage A

Stage B is **strictly downstream** of Stage A — it never replaces
Stage A, only refines its output:

```python
def summarise_predecessor(artifact_path, mode='abstractive', ...):
    # ... existing Stage A path ...
    stage_a_result = _assemble_abstractive_summary(sections, text, max_tokens)
    cf = load_profiles().get('complex_feature', {})
    if not (cf.get('stage_b') and _stage_b_should_invoke(...)):
        return stage_a_result  # current v8.0.0 behaviour (unchanged)
    # NEW v8.2.0 PV-01:
    stage_b_result = _invoke_stage_b_llm(
        artifact_path, text, stage_a_result.summary_text, entities, max_tokens
    )
    if stage_b_result is None:
        return stage_a_result  # fallback (any of F1-F7)
    return stage_b_result
```

This means:

* Stage A's output is ALWAYS computed (it's the fallback baseline
  AND the LLM's hint).
* No P6 schema change needed — `stage_b` is a NESTED field under the
  existing top-level `complex_feature` section landed by P-12.
* No new top-level dispatch keys — `canonical_order` length and
  version stay frozen at v8.0.0's values.
* Backward-compat: configurations without `complex_feature.stage_b`
  continue to use Stage A only (default false).
* Stage B can be disabled globally by setting
  `complex_feature.stage_b_enabled: false` (kill switch).

## 8. Testing strategy (v8.2.0 PV-01)

Tests required for Stage B landing:

1. `test_stage_b_calls_llm_when_all_conditions_met` — mock LLM, assert
   it was invoked with correct prompt.
2. `test_stage_b_fallback_F1_through_F7` — 7 unit tests, one per
   failure mode, asserting Stage A output is returned and logging
   shows correct reason.
3. `test_stage_b_preserves_entities_e2e` — real LLM call (gated by env
   var, opt-in CI job), verify all 8 entity classes survive.
4. `test_stage_b_cost_ceiling_trips_at_boundary` — mock cost tracker,
   send artifact whose Stage B cost is `ceiling - $0.001` then
   `ceiling + $0.001`, assert second call falls back.
5. `test_stage_b_latency_budget_kills_runaway` — mock LLM that sleeps
   3× the budget, assert hard-kill at 2× budget.
6. `test_stage_b_disabled_falls_back_to_stage_a_byte_identical` —
   regression guard for the kill switch.
7. EvoBench scenario `abstractive_stage_b_long_context.yaml` —
   target +5 pp lift over Stage A on `long_context_repo_qa`
   (P-12 already targets +3 pp for Stage A alone).

Coverage floor for `_invoke_stage_b_llm()` and helpers: 90 % (CP-2
+ defensive code path requirement).

## 9. Rollout plan (v8.2.0 PV-01)

* **PR 1**: Add `complex_feature.stage_b` field + kill switch + tests
  for the config surface only. No LLM call yet. Default disabled.
* **PR 2**: Implement `_invoke_stage_b_llm()` with mocked LLM client.
  All 7 failure-mode tests passing.
* **PR 3**: Wire real LLM client behind feature flag. Run EvoBench
  comparison `Stage A only` vs `Stage A + Stage B` on
  `long_context_repo_qa`. Land if delta ≥ +5 pp.
* **PR 4**: Enable Stage B by default by setting
  `complex_feature.stage_b: true`. Monitor cost and latency budgets in
  production for 2 weeks. Roll back via kill switch if either metric
  exceeds 1.5× expected.

## 10. Open questions deferred to v8.2.0 PV-01 design refresh

1. Should Stage B be invoked at the `pred[*]` level (per-artifact) or
   at the dispatch level (all-artifacts together)? Per-artifact is
   simpler; whole-dispatch could enable cross-artifact synthesis. ADR
   needed.
2. What's the right `entities_block` size limit before the prompt
   becomes token-inefficient? Current Stage A pulls every entity from
   `extract_named_entities()`; for a 50k-token artifact that may be
   ~200 entities = ~600 tokens of prompt overhead. May need a
   sub-sampler.
3. How does Stage B interact with `directed_compact()` (P-02)? Should
   directed compaction run BEFORE Stage B as a pre-filter, or AFTER as
   a post-filter? Pre-filter is cleaner but loses entity context the
   LLM might need.
4. What's the right model selection algorithm? Static `quality` tier
   may be wasteful for short artifacts; `balanced` may hallucinate on
   long ones. Need cost vs accuracy curve.
5. Should we cache Stage B outputs? A given artifact + entity-list +
   max_tokens triple could be hashed to a cache key. Cache hit would
   be ~$0.0001 vs ~$0.01 cold call. But cache invalidation on artifact
   changes is non-trivial.
