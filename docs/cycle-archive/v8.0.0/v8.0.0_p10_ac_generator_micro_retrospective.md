## 1. Gaps Identified

`.local/research/tweet_analysis_harness_engineering_v7.8.md` §4.14 + `.local/research/v8.0.0_patch_plan.md` §1 capability table (line 70) jointly flagged **Automatic Acceptance Criteria Generation** as a **P2** gap and the closure pin for the entire **Karpathy "Goal-Driven Execution"** primitive series. Per patch_plan §3 P-10 (lines 393-422):

- **Gap 4.14 (Automatic Acceptance Criteria Generation) — `acceptance_criteria` was only `list[str]`.** Verbatim from capability table line 70: *"4.14 | 自动验收标准生成 | `acceptance_criteria` 仅为 `list[str]`"*. At the v7.8.0 baseline, the dispatch payload's `acceptance_criteria` field was a flat list of human-readable strings — there was **no machine-verifiable structure**. An L3 task agent receiving `acceptance_criteria=["pytest tests/foo.py PASS", "lint clean"]` had to LLM-parse the string to derive a verification command, with no schema guarantee that the string contained a verification target at all. The gate's `acceptance_criteria_results` consumer had no way to auto-execute the verification — it was strictly an advisory contract that depended on the L3 agent and gate-side dispatcher manually agreeing on string semantics each round.
- **Karpathy "Goal-Driven Execution" gap (per upstream tweet analysis v7.8 §4.14).** Verbatim from upstream: *"Define success criteria. Loop until verification passes."* Pre-P-10, DevolaFlow had a `goal` slot + a string-based `acceptance_criteria` slot, but no **executable verification contract** binding the two. P-08 (behavioral_guidelines BG-004 `goal_loop`) instructed agents to re-anchor on the goal each round; P-10 closes the loop by giving the goal a **machine-checkable acceptance verdict** so the round-N+1 agent can short-circuit ITERATE → ADVANCE the moment all criteria PASS without depending on subjective LLM self-assessment.
- **C7 — P6 schema strict-serial constraint (the second of two).** Verbatim from patch_plan §2 line 105: *"C7 (本计划新增, P6 风险): 若 P-08 与 P-10 同时落地 schema 字段, 必须**串行化** (P-08 在 Wave 1, P-10 在 Wave 5; 两个字段分别 append 到 `repos` 之后, 顺序: position 14 = `behavioral_guidelines` (P-08), position 15 = `acceptance_criteria_v2` (P-10) — `acceptance_criteria` 现存 alias 保留向后兼容)"*. P-10 is the **second-and-final** P6 schema touch of the v8.0.0 cycle and the **only patch** to extend `canonical_order` beyond length 14 (set by P-08). This is a strictly higher-risk operation than P-08's first touch because (a) it leaves the schema at length 15 / version 4 — a state never previously committed to disk, (b) it must preserve **two prior byte-baselines** (v7.0.0 length 13 + post-P-08 v7.3.0 length 14) simultaneously, (c) it depends on P-08's correct cache-prefix preservation as its own pre-condition.

This was the single largest backward-compat risk in the entire v8.0.0 cycle — a careless schema rename here would break ≥50 existing tests transitively and force every existing dispatcher to migrate in lockstep.

## 3. What Was Deferred and Why

### 3.1 `acceptance_criteria_v2` auto-wiring into `evaluate_gate` / `evaluate_ladder` — **DEFERRED** (orchestrator opt-in only at v8.0.0 cut)

Same pattern as P-05 (`evaluate_ladder`), P-07 (`record_round_with_ratchet`), P-09 (`complexity_detector`): P-10 ships the primitive but the wiring into L0/L1/L2 dispatchers is opt-in. Orchestrators that want auto-AC verdicts must explicitly thread `acceptance_criteria_v2` into their dispatch payload AND supply `acceptance_criterion_verdicts` (or a runner) to `evaluate_gate`. **Rationale**: the `ac_generation.enabled=false` meta default + the legacy `acceptance_criteria: list[str]` alias preservation mean the primitive is safe to enable everywhere, but flipping the auto-wiring default would (a) change the gate composite distribution for every existing dispatch, (b) force every L3 task agent to consume the v2 field even when the v7.x string-based field is sufficient, (c) break the byte-identicality of v7.x payloads under `assert_dispatch_layout`. v8.0.x SI-1 candidate: auto-thread `ACGenerator.generate(goal, task_type)` into the L1 Stage Agent's dispatch composer once a v8.0.x dogfooding loop has battle-tested the pattern matcher on production traffic.

### 3.2 STANDARD / RELAXED / AUDIT profile `ac_generation.enabled` — **DEFERRED**

Verbatim from commit body lines 49-53: only `feature` + `refactor` profiles override to `enabled=true`; STANDARD / RELAXED / AUDIT inherit the disabled meta default. **Rationale**: STANDARD is the most-used profile in production; flipping its `ac_generation.enabled` from `false` to `true` would shift every dispatch's contract surface (adding `acceptance_criteria_v2` payload), invalidating cached comparisons across the v7.x → v8.0.0 boundary. v8.0.x SI-1 candidate: empirically calibrate which profiles benefit from auto-AC by measuring per-profile gate composite uplift on real convergence traces.

### 3.3 LLM-assisted ACGenerator (Stage B) — **DEFERRED to v8.2.0 PV-01** (alongside abstractive Stage B)

P-10 ships the **deterministic Stage A** (pattern-matching synthesiser, no LLM, no subprocess for generation; subprocess only at evaluate time for test runners). The Stage B path — LLM-assisted goal → criteria expansion with quality reasoning — is queued for v8.2.0 alongside the abstractive summariser Stage B (deferred by P-12 in the same way). Both Stage B patches share the same architectural pattern: deterministic Stage A ships in v8.0.0 to lock in the contract surface; LLM-assisted Stage B follows in v8.2.0 once production traffic data justifies the latency + cost + non-determinism trade-off. **Rationale**: shipping both Stage A and Stage B together would have (a) doubled the patch's owned-file count beyond the ≤6 ceiling, (b) introduced an LLM dependency at v8.0.0 cut that the rest of the gate stack does NOT take, (c) coupled the schema commitment (length=15 / version=4) to LLM availability — a violation of the "deterministic primitives ship first, LLM enhancements ship second" v8.x architectural principle.

### 3.4 EvoBench scenario `auto_ac_specificity.yaml` — **DEFERRED to v8.0.x**

Per patch_plan §3 P-10 line 408: *"EvoBench delta: 新 1 scenario `auto_ac_specificity.yaml` composite ≥ 85; 既存 36 scenarios 0pp 漂移 (acceptance_criteria_v2 是 opt-in)"*. P-10 shipped with **0 new EvoBench scenarios** — only the existing 36 scenarios were verified at 0pp drift (the additivity proof was the higher-priority benchmark target). **Rationale**: EvoBench scenario authorship for AC quality requires curating a representative agent-trace input + a target composite score, both of which need empirical calibration on real ACGenerator outputs. The new scenario is queued for the v8.0.x rollup once enough real-world `generate()` calls have been collected. The 0pp drift on the 36 existing scenarios + the 3 byte-baselines (v7.0.0 length=13, v7.3.0 length=14, v8.0.0-p10 length=15) is the additivity proof that the schema bump did not perturb any existing scenario.

### 3.5 Removal of legacy `acceptance_criteria: list[str]` alias — **DEFERRED to v9.0.0 major** (per patch_plan §9 R5 mitigation)

Verbatim from patch_plan §9 R5 mitigation line 678: *"v8.2.0 收口前不删除 `acceptance_criteria` 旧字段 (留待 v9.0.0 major)"*. The legacy alias stays in `validate_dispatch.py` for the entire v8.x line; removal is scheduled for v9.0.0. **Rationale**: backward-compat is a **major version contract** in DevolaFlow's semver discipline — removing the alias mid-v8 would break every external consumer that hadn't migrated to `acceptance_criteria_v2`. v8.x's commitment is "additive only at the schema layer; removals only at major boundaries" — P-10 honors this.

## 4. Key Learnings

- **The third additive P6 bump is the strongest empirical proof that P6 scales.** P-10 takes the schema to its third generation (v7.2.6 v=2 length=13 → P-08 v=3 length=14 → P-10 v=4 length=15) while preserving the v7.0.0 + v7.3.0 byte-baselines. Both prior baselines STILL PASS at v8.0.0-p10. **Codify** for v8.x and beyond: every additive P6 bump must (a) update the existing `TestLayoutInvariantBaseline` byte-baselines with NEW baselines at the prior version (e.g., v7.0.0 + v7.3.0 baselines at this patch — v8.0.0 baseline added at next bump), (b) add a `TestSchemaAdditivity` class to the new feature's test file proving the additivity contract, (c) keep `assert_dispatch_layout` accepting BOTH the prior version AND the new version, (d) keep `compressor.DEFAULT_DISPATCH_LAYOUT` in sync with the new length.
