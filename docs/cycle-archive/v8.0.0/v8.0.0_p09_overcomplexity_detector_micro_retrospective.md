The four ground-truth gaps closed by this patch:

- **Gap 4.13 (Overcomplexity Detector) — gate had no complexity dimension.** At the v7.8.0 baseline, the `evaluate_gate` scorer consulted test_results, lint_status, build_status, acceptance_criteria_results, and (via P-07) ratchet/oracle subset — but **no signal whatsoever** about whether the agent's solution was over-engineered. An agent could satisfy every test + lint + AC pin while authoring a 500-line solution to a 50-line problem; the gate would happily ADVANCE. There was no `cyclomatic_complexity` threshold, no `lines_changed` budget, no `files_touched` ratio check, no `nesting_depth_max` ceiling.
- **Karpathy "Simplicity First" primitive missing from gate.** Per patch_plan §3 P-09 line 365: *"4.13 (Overcomplexity Detector) + Karpathy Simplicity First 准则 (Task A §7.2 辅助决议: 复用 NineS)"*. The Karpathy guidelines have an explicit "simplicity_check" primitive (already injected via P-08's `behavioral_guidelines` field as `BG-002 simplicity_check: warn — over-engineering audit (3 smells)`), but the gate had no enforcement layer to **verify** the agent followed it. P-08 told agents to self-audit; P-09 verifies the audit was honest.
- **NineS deep-analysis result discarding.** The repo runs `nines analyze --depth deep --agent-impact --keypoints` regularly (per `nines.toml` configuration) and produces rich complexity findings — but pre-P-09 those findings were **read-only research artifacts** living in `.local/research/`. The findings never fed back into the gate decision loop. P-09 closes this loop by wrapping NineS subprocess output as `ComplexitySignals` consumable by `evaluate_gate`.
- **NineS unavailability blast radius.** Per patch_plan §5 line 677 R4: *"NineS subprocess 不可用 (`nines` CLI 缺失或版本不匹配) | P-09 依赖 `nines analyze --depth deep --agent-impact --keypoints` subprocess"*. Without a fallback strategy, P-09 would have been a hard dependency on the NineS binary being installed at runtime — unacceptable for a v8.0.0 release that ships into environments (CI runners, fresh dev clones, ephemeral worktrees) where NineS may be absent. P-09 had to ship with a **conservative MOCK fallback** that produces safe-default `ComplexitySignals` when the binary is missing.

Critical-path role: P-09 is the **last patch in Stage S03** (W4 closure) and the **second-to-last patch in the entire v8.0.0 cycle** if measured by tag chronology (only P-13 changelog backfill remains as a non-feature housekeeping patch). **Verdict thresholds** (verbatim from commit body lines 21-23):

| Verdict | Trigger conditions (any-of) |
|---|---|
| `OK` | All signals within tier budget |
| `WARNING` | `cc > 10`, `lines > module budget`, `files > module budget`, `nesting > 4`, NineS WARN-severity finding present |
| `CRITICAL` | `cc > 15`, NineS ERROR-severity finding, function ratio > 0.5 |

The CRITICAL path is reserved for **objective overcomplexity** (extreme cyclomatic complexity, NineS escalation, or > 50% functions modified — a sign the agent is rewriting rather than minimally patching). The WARNING path is the lighter touch — it injects a `ReinforcementBlock` with "Solution may be overcomplicated" guidance for the next round, rather than blocking the current round.

**4 Task Complexity Tiers with Monotonic Budgets** — per patch_plan §3 P-09 + commit body line 13 *"4 task complexity tiers (trivial/simple/standard/complex) with monotonic budgets"*:

| Tier | Use case | Budget rationale |
|---|---|---|
| `trivial` | Single-file < 20-line edits (P1 dispatcher exception scope) | Tightest budgets — 1 file, ~50 lines, cc ≤ 5, nesting ≤ 2 |
| `simple` | Bug fixes, small refactors | Modest budgets — 2-3 files, ~150 lines, cc ≤ 8 |
| `standard` | Typical feature implementations | Default budgets — 4-6 files, ~400 lines, cc ≤ 10, nesting ≤ 3 |
| `complex` | Cross-cutting refactors, schema changes | Widest budgets — 8+ files, ~800 lines, cc ≤ 15, nesting ≤ 4 |

**Monotonicity guarantee**: each tier's budget is strictly ≥ the previous tier's budget on every dimension. A complex-tier task that satisfies trivial-tier budgets is automatically OK; a trivial-tier task that bursts complex-tier budgets is automatically CRITICAL. This is what makes the verdict computation a simple per-dimension comparison rather than a complex multi-tier interpolation.

**Conservative MOCK Fallback** (verbatim from commit body line 28):

> *"Subprocess wrapper falls back to MOCK signals when nines binary missing or fails."*

When `wrap_nines_complexity(target_path)` cannot invoke NineS (binary missing, subprocess timeout, non-zero exit), it returns a **conservative `ComplexitySignals` instance** that errs on the side of OK verdict — never WARNING or CRITICAL. **Rationale**: false-negatives (missing a real overcomplexity issue) are recoverable via human review at the gate; false-positives (blocking a fine solution because NineS happened to be missing) would erode agent trust and undermine adoption. The MOCK path also logs a structured fallback signal (per S-5 — never silently swallow a degraded mode) so observability tooling can flag NineS-availability degradation.

The 0pp drift on the 36 existing scenarios proves the `complexity_detector=None` default contract holds.

### 3.2 Auto-wiring complexity_detector into orchestrator dispatchers — **DEFERRED (orchestrator opt-in only at v8.0.0 cut)**

Same pattern as P-07: P-09 ships the primitive but the wiring into L0/L1/L2 dispatchers is opt-in. Orchestrators that want complexity-aware gating must explicitly thread a `ComplexityDetector` instance into their `evaluate_gate` call. **Rationale**: the conservative MOCK fallback means the primitive is safe to enable everywhere, but the gate composite weight (0.10 in STRICT / AUDIT) does change the score curve, and we want at least one v8.0.x dogfooding cycle on production traffic before flipping the default.

### 3.3 STANDARD / RELAXED profile complexity_weight — DEFERRED

Verbatim from `profiles.py` docstring: *"STANDARD/RELAXED default to 0.0 (opt-in only)"*. Only STRICT and AUDIT enable complexity_weight by default. **Rationale**: STANDARD is the most-used profile in production; flipping its complexity_weight from 0.0 to (say) 0.05 would shift the composite score distribution for every existing dispatch, invalidating cached comparisons across the v7.x → v8.0.0 boundary. v8.0.x SI-1 candidate: empirically calibrate a STANDARD complexity_weight that preserves the median score distribution while still surfacing genuine overcomplexity outliers.

### 3.4 NineS subprocess version pinning — DEFERRED to runtime check

Per patch_plan §5 line 677 R4 mitigation: *"`nines.toml` 在仓库根存在 (已存在); `self-update` workflow stage (1) check-refs 必 verify NineS v3.3.0 可用; NineS 不可用时 manual analysis fallback (W-2 允许)"*. P-09 does not enforce a NineS binary version at import time — instead, the `wrap_nines_complexity()` subprocess wrapper falls back to MOCK on any failure (missing binary, version mismatch causing non-zero exit, malformed output). **Rationale**: hard version pinning at import time would block import in any environment without the exact pinned NineS version — too brittle. The runtime fallback + structured logging is the right balance for v8.0.0; v8.0.x SI-1 candidate: add an explicit `nines_version_check()` helper that orchestrators can call at startup if they want fail-fast semantics.

### 3.5 CHANGELOG entry — DEFERRED to aggregate `[8.0.0]` rollup at S05 G1

Same pattern as P-01 / P-02 / P-03 / P-04 / P-05 / P-07 / P-08 / P-11 / P-13. The aggregate entry will reference P-09 by tag + 4.13 closure + complexity_detector + 4 tier budgets + NineS subprocess wrapper + MOCK fallback + 74-test suite + STRICT/AUDIT 0.10 weight.

## 4. Key Learnings

- **Subprocess wrappers MUST have a conservative MOCK fallback or they become hard runtime dependencies.** P-09's `wrap_nines_complexity()` returns safe-default `ComplexitySignals` when the NineS binary is missing or fails — never WARNING, never CRITICAL. **Rationale**: a v8.0.0 release that hard-required the NineS binary at runtime would be unshippable into CI runners, fresh dev clones, ephemeral worktrees, or any environment without the binary. The conservative-MOCK pattern lets the primitive ship with zero install friction while still providing real value when the binary IS available. **Codify** for v8.x: any new gate primitive that wraps an external CLI (NineS, ruff, pytest, ...) MUST (a) provide a MOCK fallback that errs on the side of OK verdict, (b) emit a structured S-5-compliant log entry on fallback so observability tooling can flag degradation, (c) test both the happy path AND the fallback path explicitly. P-09's 74-test suite includes 4 fallback-path tests — that's the regression pin.
- **Monotonic budget tiers turn N-dimensional verdict computation into trivial per-dimension comparison.** The 4 tiers (trivial / simple / standard / complex) have strictly-increasing budgets on every dimension (cc, lines, files, nesting). This means: a trivial-tier task that bursts ANY budget = WARNING/CRITICAL; a complex-tier task that satisfies ALL budgets = OK. No interpolation, no weighted scoring, no judgement calls. **Adopt** as v8.x design pattern: when a verdict depends on multiple thresholds, prefer monotonic tier ladders over weighted multi-dimensional scoring. The verdict logic stays a simple if-cascade (trivially testable, trivially debuggable); the budgets themselves can be tuned independently per dimension. The 4-tier ladder also maps cleanly to the trivial/simple/standard/complex task complexity tiers used elsewhere in the codebase (P-08 behavioral_guidelines per-tier defaults), giving a unified vocabulary across primitives.
- **0.10 complexity_weight on STRICT/AUDIT is the correct default for "Simplicity First" enforcement.** A weight of 0.10 means complexity contributes up to 10% of the gate composite — enough to surface genuine overcomplexity (a CRITICAL verdict reduces composite by ~10pp, demoting an ADVANCE candidate to ITERATE), but not so much that it dominates the gate decision (the other 90% still come from test/lint/build/AC). STANDARD/RELAXED at 0.0 means non-opt-in profiles see ZERO change vs v7.8.0. **Codify** for v8.x: when adding a new dimension to the gate composite, default STRICT/AUDIT to a conservative 0.05-0.10 weight, default STANDARD/RELAXED to 0.0. Calibrate weights upward only after a v8.0.x dogfooding cycle has collected real composite-distribution data. The "additive opt-in by tier" pattern is what lets the gate evolve without regressing existing convergence loops.
- **Reuse external NineS analysis infrastructure rather than duplicating cyclomatic-complexity calculation.** P-09 wraps `nines analyze` rather than reimplementing radon-style cc calculation in-process. **Rationale** (verbatim from patch_plan §3 P-09 line 376): *"复用 NineS 节省: 不重复造圈复杂度计算器, effort 估算从 L 降至 M"* — effort dropped from L (~10h) to M (~5h) by reusing existing infrastructure. The trade-off: P-09 inherits NineS's update cadence (need to re-run `nines analyze` to get fresh signals) and version-compat surface (NineS binary version drift). The MOCK fallback (§3.4 above) absorbs the version-drift risk; the cadence trade-off is acceptable because the gate is invoked at convergence-round boundaries (not per-edit), so a 30-second NineS subprocess is amortised over many edits. **Adopt** as v8.x sourcing principle: when a primitive needs analysis that an external tool (NineS, ruff, mypy, ...) already does well, prefer subprocess wrapping over reimplementation; budget the integration effort by external CLI behaviour, not by reimplementation effort.
- **NineS feeds back into the gate, completing the analysis-action loop.** Pre-P-09, NineS findings were generated → stored in `.local/research/` → read by humans → manually triaged into patch_plan items. P-09 closes the loop: NineS findings → `wrap_nines_complexity()` → `ComplexitySignals` → `ComplexityDetector.evaluate()` → `ComplexityVerdict` → gate composite → ITERATE/ADVANCE decision. **Document** as v8.x architectural milestone: P-09 is the FIRST patch in the v8.x cycle to convert NineS from a research tool into a runtime gate signal. This unlocks future patches (v8.1.0+) to wrap other NineS analysis dimensions (dead-code detection, naming conventions, doc-coverage) as additional gate primitives following the P-09 template. The "research artifact → runtime signal" promotion is the core architectural pattern; P-09 proves it works for cyclomatic complexity.
- **5-min commit-to-merge is the v8.x speed record (lower bound on velocity for opt-in-only primitives).** P-09 achieved ~5 min commit-to-merge — the **fastest of the entire v8.0.0 cycle** so far (compare: P-07 9 min, P-08 22 min, P-11 ~15 min). The differentiator vs P-07: same opt-in-by-default contract pattern, but P-09 had **no `task_adaptive_selector.py` touch** (P-07 did, requiring extra regression validation across 391 existing tests). **Document** for v8.x: the velocity ceiling for an opt-in primitive is bounded by (a) whether the primitive touches `task_adaptive_selector.py` (slowest file in the test matrix), (b) whether the primitive forces an SF-4 reference set extension (the P-08 22-min coupling tax). Pure gate-only opt-in additions (P-09 template) can ship at 5-min cadence; this is the v8.x velocity floor target.
- **Strict twin-write serialisation on `gate/scorer.py` works as designed.** P-07 and P-09 both write to `gate/scorer.py` (P-07 adds `ratchet=None` parameter; P-09 adds `complexity_detector=None` parameter). Per patch_plan §5 line 560: *"`gate/scorer.py` 二方共写 (P-07 + P-09): 必须串行化为 P-07 → P-09 (W4 内子排序)"*. P-07 merged at `e586d77` (2026-04-22T05:29:43+0800), P-09 merged ≈6h later at `88317b9` (2026-04-22T11:28:22+0800). Zero merge conflicts on `gate/scorer.py` because P-09's diff was authored against the post-P-07 main, not against the pre-P-07 baseline. **Codify** for v8.x: when two patches touch the same file, the wave-ordering must be enforced **at PR-creation time** (not just at merge time) — the second-mover patch must rebase against the first-mover's merge before opening its PR. P-09 followed this discipline; the 5-min merge cadence is the reward.
- **The commit body's "what lands" section is the canonical patch documentation.** P-09's commit body enumerates: 6 files changed, verdict thresholds (3-line summary), 4 task complexity tiers, complexity_detector=None default invariant, MOCK fallback, SI-10 6/6 PASS with verbatim numbers (2301 passed / 14 skipped / 2 xfailed). This is enough for a future S05 G1 retrospective author (or human reviewer) to reconstruct the patch's intent, scope, and verification status without reading any code. **Adopt** as v8.x convention: every feature commit MUST have a "what lands" section structured as (a) per-file change summary, (b) verdict / threshold / behavioural-spec table, (c) invariant statements (what does NOT change), (d) SI-10 6/6 PASS results with verbatim numbers. The retrospective authoring task (this very file!) becomes a verbatim extraction job rather than a research / archaeology job.
