## 4. Key Learnings

- **Additive P6 transitions REQUIRE the additivity proof in CI.** The P-08 commit body explicitly cites the closing test: *"v7.0.0 byte-baseline AND v7.3.0 byte-baseline STILL PASS — additivity proven (`tests/test_benchmarks.py::TestLayoutInvariantBaseline`)"*. Without this dual-baseline pinning, an additive change could silently re-order an earlier position (e.g., swap positions 5 and 6) and CI would not catch it. **Adopt** for v8.x: every future P6 addition (P-10's `acceptance_criteria_v2` at position 15, any future top-level keys) must add a new byte-baseline at the previous version (e.g., `v7.4.0` baseline before adding position 15) to maintain the chain. The byte-baseline regression tests are the single source of truth for "no positions reordered".
- **`assert_dispatch_layout()` accepts BOTH old and new schema versions.** Verbatim from commit body: *"`assert_dispatch_layout()` accepts BOTH: v2 payloads (no `behavioral_guidelines` field) — backward compat / v3 payloads (with `behavioral_guidelines` at canonical end) / Reorder attacks ... are correctly rejected"*. This is the v7.x→v8.x backward compat backbone — it lets v7.x dispatchers (or any tooling pinning the v2 schema) continue producing valid payloads with no behavioral_guidelines field, while v8.x dispatchers can produce v3 payloads with the field. **Reinforce**: every future schema bump must update `assert_dispatch_layout` to accept N versions back (currently 2: v2 + v3) and explicitly reject reorder attacks. The 6 tests in `TestAssertDispatchLayoutBackwardCompat` are the regression pin.
- **Token budget pre-bump is the defense against benchmark drift on schema additions.** When a schema adds a new top-level field, the lean-format serialiser produces slightly larger payloads, which can push tight profiles over their token budgets and shift expected-section selection. P-08 absorbed this **proactively** by bumping `feature` +150, `refactor` +200, `design` +150 — the per-profile bumps were calibrated empirically (verbatim from commit body — "calibrated to absorb behavioral_reserve so expected-section selection stays byte-stable on existing benchmarks"). The result: 36/36 EvoBench scenarios at 0pp drift. **Adopt** for v8.x: every patch that adds a top-level dispatch field must (a) measure the per-profile token cost, (b) pre-bump opt-in profiles by exactly that delta, (c) keep non-opt-in profiles unchanged so they remain byte-identical v7.x, (d) verify EvoBench 0pp drift before merge.
- **The two-commit explicit-not-silent split (feat + coupling) is the v8.x convention for SF-4 cascades.** Same pattern P-11 used (feat + coupling for template_count 20→21 / profile_count 23→24). P-08's coupling commit is the largest in the v8.0.0 cycle so far (29 files, 5 rule files + 16 human docs + 6 build scripts + 2 test files). **Codify**: when a patch adds a Nth canonical reference to SF-4 (or bumps any count tracked by tests/scripts/rules), the coupling commit must (a) be a separate commit on the same PR, (b) carry a `coupling(P-NN):` prefix, (c) enumerate the cascade rationale in the commit body, (d) re-generate human docs via `scripts/generate_human_docs.py` so DS-3 / ST-3 bilingual completeness holds. The 22-min commit-to-merge cycle (vs P-05's 9 min) is the "coupling tax" — accept it; the alternative (silent in-feat-commit cascade) is a SF-3 / CP-3 violation.
- **`select_context` cc 16 → 7 via 5 helper extraction is the canonical refactor pattern.** P-08 extracted 5 helpers: `_select_behavioral_sections` (cc 7), `_compose_behavioral_block` (cc 5), `_resolve_active_profile` (cc 5), `_resolve_dispatch_overrides` (cc 6), `_append_optional_blocks` (cc 4). Each helper is **single-responsibility** (one clear refactor extracted), **named after its semantic role** (not the implementation), **leading-underscore private** (no public API surface added). Result: parent function cc dropped from 16 to 7 (54% reduction), every helper ≤ 7 (under target 8). **Adopt** as v8.x canonical refactor recipe: when a function exceeds cc 8, extract the 4-7 most cohesive sub-flows as private helpers; aim for parent cc ≤ 7 (not the floor of 8 — leave headroom for future feature additions).
- **The R7 line-registry decoupling is now a v8.0.1 P0 candidate.** The headline deferral (SKILL.md Tier 3 row deferred) traces to a deeper architectural issue: `context_profiles.yaml`'s section registry uses **line numbers** (e.g., `reference_navigation: lines 420-448`) to extract content from SKILL.md. ANY edit to SKILL.md shifts those line numbers and propagates to per-profile budgets. P-08 documented this as the "R7 mitigation" deferred to v8.0.1. **Reinforce** as the v8.0.x P0 architectural cleanup: replace line-number registry with **section-anchor registry** (e.g., `reference_navigation: from "## References" to "## Templates"`) so SKILL.md edits don't cascade through the line registry. This is now the v8.0.1 SI-1 entry-point.
- **"190/200 lines, Large tier ≤1000" gives 810 lines of headroom for v8.0.x BG additions.** The new `references/behavioral-guidelines.md` is 190 lines and the AC pinned ≤200 (per AC #3). The Large tier ceiling is 1000 (per SF-1). This means **810 lines of headroom** for future BG additions (e.g., BG-005 reflection, BG-006 minimal-diff-discipline) without tier escalation. **Action item for v8.0.x**: when adding a new BG primitive, reuse the same `behavioral-guidelines.md` file (don't fragment); only escalate to a separate file when the page exceeds 1000 lines.
- **First P6 touch is the v8.0.0 watershed.** Before P-08, every v8.0.0 patch held canonical_order at length 13 / version 2. After P-08, it's length 14 / version 3 — the lean-dispatch schema has now committed to a backward-compat-via-additivity contract for the entire v8.x line. **Document** in the v8.0.0 retrospective (S05 G1): the first P6 touch is the cycle's most architecturally significant moment, more than any single feature addition. Future cycles (v8.1.0, v8.2.0, v9.0.0) inherit this contract — additivity-only, position 1-14 frozen, every new field appended after position 14 (or 15 after P-10).
