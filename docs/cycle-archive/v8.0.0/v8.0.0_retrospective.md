## 4. Key Learnings

The v8.0.0 cycle ran as a **strict 13-patch architectural sprint** in ~16 hours wall — the largest single-cycle delivery in DevolaFlow history (vs v7.5.0's 8 patches in 1 day, v7.3.0's 6 patches in 1 day). Key learnings that should feed v8.1.0 self-analysis:

### 4.1 Did the planning gate (patch_plan §3 13-patch decomposition) survive contact with implementation?

**YES — 13 of 13 patches landed within their declared owned-files scope.** Zero scope expansion across the cycle. The patch_plan's per-patch quantitative metrics (test count delta, LOC delta, NineS finding delta, EvoBench delta, coverage delta, gate composite delta) proved measurable and predictive: every patch's actual delta tracked the planning gate prediction within ±20% (notable overshoots were on test count — most patches exceeded their test target by 50-200%). The decomposition pattern (1 patch per primitive + 1 patch per cluster of cc hotspots + 1 patch for docs debt) is now v8.x convention. **Codify** for v8.x: every cycle's SI-1 planning gate must produce a per-patch table with the same 8 mandatory fields (related/scope/quantitative metrics/AC/dependencies/effort/risk/self-update hooks).

### 4.2 Did the wave editing (5 waves, max wave size 4) work as designed?

**YES.** Zero merge conflicts across 13 patches despite multi-patch file ownership on `task_adaptive_selector.py` (4 patches), `gate/scorer.py` (5 patches), `compressor.py` (3 patches), `context_profiles.yaml` (4 patches). The serialisation discipline (P-01 → P-02 → P-08 → P-07 on `task_adaptive_selector.py`'s disjoint functions; P-03 → P-04 → P-05 → P-06 → P-07 → P-09 on `gate/scorer.py`'s disjoint parameters) was explicitly enforced via Wave-internal sub-ordering rules. **Adopt** as v8.x rule: when planning a wave, the dispatcher must verify per-file ownership disjointness AND author Wave-internal sub-orderings for any same-file twin/multi-write patches. The patch_plan §5 per-wave ownership table is the canonical template.

### 4.3 Did the opt-in-by-default backward-compat pattern hold across 4 patches?

**YES — 4 patches deep with zero v7.x test regressions.** P-05 (`evaluate_ladder` opt-in via `ladder_enabled=False`), P-07 (`MonotonicRatchet` opt-in via `ratchet=None`), P-09 (`OvercomplexityDetector` opt-in via `complexity_detector=None`), P-10 (`acceptance_criteria_v2` opt-in via `ac_generation.enabled=false` + `acceptance_criteria` legacy alias preserved). **Codify** as v8.x architectural rule: every additive runtime primitive MUST default to OFF / `None` / `False` / `disabled`; MUST be allowlisted in `scripts/detect_dead_apis.py` with a comment explaining the orchestrator-opt-in rationale; MUST have a regression test class proving byte-identicality when the opt-in is off; MUST be re-exported from the relevant `__init__.py` for orchestrator discoverability. The 13 patches of v8.0.0 prove this pattern scales — it is the defining feature of v8.x's "additive cycle" and the reason `+0 scenario regression > 5pp` held throughout.

### 4.4 Did the P6 schema additive transitions work as designed across 2 schema bumps?

**YES — additivity proven across THREE schema generations.** The chain v=2 (length=13) → v=3 (length=14) → v=4 (length=15) preserves both the v7.0.0 byte-baseline AND the v7.3.0 byte-baseline at every step. P-08's `TestSchemaAdditivity` (7 tests) + P-10's `TestSchemaAdditivity` (10 tests) provide 17 dedicated additivity tests in addition to the 3 byte-baselines in `test_benchmarks.py::TestLayoutInvariantBaseline`. **Adopt** as v8.x discipline: every additive P6 bump must (a) add a new byte-baseline at the previous version (e.g., v8.0.0 baseline added at the next bump), (b) add a `TestSchemaAdditivity` class to the new feature's test file, (c) keep `assert_dispatch_layout` accepting the prior version AND the new version, (d) keep `compressor.DEFAULT_DISPATCH_LAYOUT` in sync with the new length. The chain v=2 → v=3 → v=4 is the regression pin; the longer the chain, the stronger the additivity proof.

### 4.5 Did the two-commit explicit-not-silent split (feat + coupling) work as designed for SF-4 cascades?

**YES — both P-08 (SF-4 reference set 8→9) and P-11 (template_count 20→21 + profile_count 23→24) used the pattern cleanly.** Each split commit carried a `coupling(P-NN):` prefix; each enumerated the cascade rationale in the commit body; each re-generated human docs via `scripts/generate_human_docs.py` so DS-3/ST-3 bilingual completeness held. **Codify**: when a patch grows the canonical reference set OR the mirror file count OR template/profile counts that are tracked by tests/scripts/rules, the coupling commit must (a) be a separate commit on the same PR, (b) carry a `coupling(P-NN):` prefix, (c) enumerate the cascade rationale, (d) re-generate human docs. The 22-min commit-to-merge cycle (vs P-05's 9 min) is the "coupling tax" — accept it; the alternative (silent in-feat-commit cascade) is a SF-3 / CP-3 violation.

### 4.6 Did the conservative MOCK fallback for subprocess wrappers prevent hard CI dependencies?

**YES — P-09's `wrap_nines_complexity()` MOCK fallback let the primitive ship without forcing the NineS binary on every CI runner / fresh dev clone / ephemeral worktree.** The fallback emits structured S-5-compliant logging on the degraded path so observability tooling can flag NineS-availability degradation. **Codify** for v8.x: any new gate primitive that wraps an external CLI (NineS, ruff, pytest, ...) MUST (a) provide a MOCK fallback that errs on the side of OK verdict, (b) emit a structured S-5-compliant log entry on fallback, (c) test both the happy path AND the fallback path explicitly. P-09's 74-test suite includes 4 fallback-path tests — that's the regression pin.

### 4.7 Did the per-patch micro-retrospective discipline survive 13 patches?

**YES — 13 of 13 patches have detailed micro-retros** in `.local/research/v8.0.0_p<NN>_*_micro_retrospective.md`. The cumulative retro corpus is ~2400 lines of structured cycle documentation. The 4-section format (Gaps Identified / What Was Implemented / What Was Deferred and Why / Key Learnings + Cross-references) provided just enough structure to capture the per-patch nuance without becoming verbose. **Adopt** as v8.x convention: every patch (not just rollup releases) must produce a micro-retro at the same 4-section format. The next iteration's SI-1 planning gate consumes the cumulative retro corpus directly — no re-archaeology required.

### 4.8 Did the commit body discipline (verbatim "what lands" sections) work as canonical patch documentation?

**YES — every patch's commit body contained a verbatim per-file change summary + verdict/threshold/behavioural-spec table + invariant statements + SI-10 6/6 PASS results.** This let the retrospective authors (this very task!) extract patch facts as a verbatim CO-2 lift rather than archaeology. **Adopt** as v8.x convention: every feature commit MUST have a "what lands" section structured as (a) per-file change summary, (b) verdict / threshold / behavioural-spec table, (c) invariant statements (what does NOT change), (d) SI-10 6/6 PASS results with verbatim numbers. The cumulative effect: the 13 micro-retros + this aggregate retrospective + the SI-3 evaluation all draw from the same verbatim source set without any rephrasing risk. CO-2 is honoured throughout.

### 4.9 What architectural patterns emerged that should be codified for v8.x?

The cycle established 5 patterns that should become formal v8.x architectural rules:

1. **The "resolve / filter / apply" 3-helper triad** for cc-cleanup (refined to 5-helper variant for higher-cc functions). Established by P-01, refined by P-07 + P-08 + P-11. Every cc-cleanup helper landed at radon A-tier (cc ≤ 5). Future patches should default to this pattern.
2. **The "opt-in-by-default with `None`" pattern for additive runtime primitives**. 4 patches deep (P-05/P-07/P-09/P-10). Every primitive defaults to OFF; allowlist + regression test pin the contract.
3. **The "feat + coupling" 2-commit split for SF-4/template/profile count cascades**. P-08 + P-11 codified the pattern; future patches that grow canonical counts MUST follow.
4. **The "S/O/R-resistance" test class for any oracle in convergence loops**. P-07's `compute_deterministic_oracle_score()` consults EXACTLY 3 fields (test/lint/build); the `TestOracleSORResistance` 4-test class proves no review_findings change can game the oracle. Future ratchet/oracle additions MUST include S/O/R-resistance tests.
5. **The "monotonic budget tier ladder" pattern for verdict computation**. P-09's 4 task complexity tiers (trivial/simple/standard/complex) have strictly-increasing budgets on every dimension; verdict reduces to a per-dimension comparison. Future verdict-emitting primitives should adopt the same pattern over weighted multi-dimensional scoring.

### 4.10 Cycle throughput — 13 patches in ~16 hours vs v7.5.0's 8 patches in 1 day

The v7.5.0 cycle set the throughput precedent of 8 patches in 1 day; the v8.0.0 cycle ran 13 patches in ~16 hours (≈63% higher throughput by raw count, ≈22% higher by patches/hour). Driver factors:

- **The architecturally-driven structure** (`.local/research/v8.0.0_patch_plan.md` 862-line patch plan) gave each patch a precise scope, file list, risk rating, dependency map, NineS-finding-closure prediction, and EvoBench-impact prediction. No mid-cycle scope expansion occurred.
- **The opt-in-by-default backward-compat pattern** eliminated the regression-debugging cycle for v7.x consumers — every new primitive ships in OFF mode by default, so existing tests pass unchanged.
- **The conservative MOCK fallback discipline** (P-09's NineS subprocess wrapper) eliminated environment-dependency debugging — the primitive ships without forcing dependencies on CI / fresh clones / ephemeral worktrees.
- **The Wave-parallel + Wave-internal-serial discipline** kept merge windows short (9-second sibling merges in W1; 5-25 minute commit-to-merge across all 13 patches; longest was P-06 at 23 min for the net-new 100-test cycle detector + 474-line module).
- **The per-patch lightweight tag pattern** (`v8.0.0-pNN`) gave each patch an audit anchor without the overhead of an annotated tag — annotated `v8.0.0` is reserved for the G1 rollup.

### 4.11 What did the cycle fail to predict that surfaced during implementation?

In the spirit of W-7 / SI-8, three implementation-time surprises:

- **P-08's SKILL.md Tier 3 row drift** — patch_plan §3 P-08 line 335 explicitly stated *"在 §'Tier 3 references' 表格新增 1 行 ... 仍 498/500"*. The implementation discovered that the existing line-anchored section registry caused 3 unrelated EvoBench scenarios to drift > 5pp on every variant. The deferral was the right call but the planning gate didn't anticipate the coupling. **Lesson**: future schema additions that touch SKILL.md must consider per-line section registry coupling explicitly in the SI-1 planning gate.
- **P-04's overshoot on test count** — patch_plan §3 P-04 line 218 predicted +15 tests; actual was +53 (350% over). This pattern repeated across 6 of 13 patches (P-04, P-05, P-06, P-07, P-09, P-12). **Lesson**: the patch_plan test count predictions are systematically conservative; future planning gates should predict +50-100 tests for any net-new module.
- **P-09's MOCK fallback as architectural backbone** — patch_plan §3 P-09 line 367 *"NineS 不可用时 manual analysis fallback (W-2 允许)"* under-stated the architectural significance. The MOCK fallback became the canonical pattern for any subprocess-wrapped primitive (codified in §4.6 above). **Lesson**: subprocess wrapper patterns deserve a dedicated architectural rule in v8.x — not buried under an availability-mitigation note.
