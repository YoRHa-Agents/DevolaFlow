## §4 — Reorganization design (recommendation; deferred to v13.0.0)

When gate count crosses the 10-threshold, partition into **3 functional groups**:

| Group | Member gates | Wall-clock (est. parallel) | Failure semantics |
|---|---|---:|---|
| **Group A: Hygiene** | pytest, ruff check, ruff format, test_version | ~17s | Any failure → block commit immediately (fail-fast) |
| **Group B: Validation** | test_benchmarks, check-cursor-skill, multi-baseline-byte-test, iteration-delta-gate | ~10s (parallel within group) | Any failure → block commit immediately |
| **Group C: Snapshot** | W-19 archive validation, reference-rosetta currency, auto-collection schema, degraded-mode contract | ~5s (parallel within group) | Failure logged but commit allowed if Groups A + B green; cycle-lead reviews at next-PV opening |

**Wall-clock projection post-reorganization** (sequential A → B → C): 17s + 10s + 5s
= **~32s end-to-end**. **Parallel** (max of A=17s; B + C absorbed): **~17s**.

**Compared to the v15.0.0 forecast** (12 sequential gates, no reorg): ~55s.
Reorganization saves **~38s per commit at v15.0.0**, **~13s per commit at v13.0.0**
(when reorganization first lands).

## §5 — Decision matrix: append vs merge vs partition

When the next cycle proposes a NEW SI-10 gate, apply this decision rule:

| Test | Action |
|---|---|
| Gate measures the SAME PHENOMENON as an existing gate (e.g., a NEW pytest invocation; a NEW ruff variant) | **MERGE** — extend the existing gate's scope; don't append |
| Gate is independent + fast (< 5s) + critical for correctness | **APPEND** within current group (current `release-preflight` sequential chain) |
| Gate is independent + slow (≥ 5s) + critical for correctness | **APPEND**; once total wall-clock ≥ 60s OR gate count ≥ 10, **PARTITION** at next opportunity |
| Gate is independent + slow + advisory (not block-on-fail) | **PARTITION** into Group C immediately upon addition |

This is the same NEST-vs-APPEND decision rule pattern as **A-2.3** (canonical_order)
applied to the gate chain. The pattern is portable across multiple registry surfaces:
the `[FROZEN_PREFIX] + [APPEND_TAIL]` invariant for canonical_order positions 1-12 +
13+ has its analogue in `[GROUP_A_FAIL_FAST] + [GROUP_B_VALIDATION] + [GROUP_C_ADVISORY]`
for SI-10 gates.

## §6 — Rationale for the gate-count = 10 threshold

Why not threshold at 8, 9, 11, or 12?

* **8** — too aggressive. v11.0.0 cycle would already be at 8 (forecast); reorganization
  forced into v11.0.0 surface area when no real wall-clock pressure exists yet.
* **9** — premature. Single-gate-per-MAJOR rate suggests v12.0.0 reaches 9; gives only
  1 cycle of telegraph before mandated action.
* **10** — appropriate. 2-cycle telegraph runway (v11.0.0 forecast + v12.0.0 telegraph
  → v13.0.0 execution) matches the W-21 Soul-set 2-cycle deliberation cadence (per
  ADR-007 D4 #1). Wall-clock ~45s is the empirical pain threshold per developer feedback
  in `.local/research/v10.0.0_retrospective.md` perf section.
* **11 / 12** — too late. Wall-clock ~50-55s already past the developer-pain threshold;
  the pain is observable BEFORE the reorganization arrives.

## §9 — W-21-pattern multi-cycle deliberation

D-O-4's recommendation operates on a **W-21-pattern multi-cycle deliberation cadence**
(NOT under W-21 itself; W-21 governs Soul rules only). The cadence is:

* Cycle N (v11.0.0): forecast + recommendation telegraphed (this artifact).
* Cycle N+2 (v11.2.0 / v12.0.0): cycle plan SI-1 references the forecast; decides
  whether to execute reorganization at v13.0.0 OR push back to v14.0.0+.
* Cycle N+3 (v13.0.0): if telegraph confirmed, ship the 3-group reorganization.

The 2-cycle gap is structural (mirrors W-21 D4 #1 + the v10.0.0 retrospective §"2-cycle
telegraph cadence is real" learning). It is NOT a hard rule; cycle planners MAY execute
sooner if pain materialises faster.
