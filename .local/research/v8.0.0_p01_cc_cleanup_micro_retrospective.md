## 4. Key Learnings

- **Dispatch-table refactoring pattern beats nested if/elif chains for cc-cleanup.** `_apply_transform` 25→3 was achieved by lifting per-transform branches into module-level `_xform_*` handlers + a class-level `_TRANSFORM_HANDLERS: dict[str, Any]` dispatch dict. This pattern simultaneously reduces cc, surfaces the supported-transform set as a single source of truth (parametrised test `test_apply_transform_dispatch_table_covers_all_known_transforms` exploits this), and makes future transform additions a 1-line dict entry rather than a new elif branch. **Recommend** adopting this as the default refactor pattern in next-cycle (v8.1.0+) cc-grooming patches; can be codified as a Cursor rule under `.cursor/rules/` if frequency justifies.
- **Helper-extraction with `_resolve_X / _filter_Y / _apply_Z` triad reads pipeline-style.** `select_stages_for_runtime` reduced 18→3 by becoming a 3-line orchestrator that reads as `resolve → filter → apply`. This idiom (also applied to `refresh_reference_dependency` as `load → diff → commit`) makes the call-site self-documenting AND keeps each helper independently testable. **Recommend** P-07 use the same triad framing for `apply_round_escalation` to maintain stylistic consistency across the file.
- **`pytest.importorskip` for analysis-tool dependencies keeps CI environments clean.** Adding radon as a test-only optional dep via `pytest.importorskip("radon.complexity")` allowed 6 cc-enforcement parametrised tests to live in-tree without forcing the dependency on every CI runner. This pattern preserves the ≤6 owned-file contract AND lets the cc-enforcement assertions self-tighten future regression (any future commit that pushes a covered callable above its threshold fails the test). **Adopt** as the canonical pattern for code-quality-tool integration tests in v8.x.
- **Public-API byte-identicality preserves 1500+ existing tests with zero regressions.** All 5 modules' public symbol tables are byte-identical pre/post refactor (PR #59 §Design Notes 2nd bullet — "verified by passing the existing 1589-test suite untouched, plus byte-diff of CLI output for `task_adaptive_selector`"). The wrap-not-modify discipline is what made this a 21-minute commit-to-merge cycle — no downstream owners needed to adapt. **Reinforce** in the next iteration: any cc-cleanup patch that breaks public APIs should be reclassified as a behavioral patch with its own decomposition gate.
- **Measurement-tool drift between NineS and radon is real.** PR #59 documented that radon's branch-fork baseline read 25/15/18/15/12/11 vs. NineS's pre-cycle 22/15/13/12/12/12 (3 of 6 callables differ). This means the cc-finding *count* can be tool-dependent (and our self-eval threshold logic should normalize on one tool). **Action item for v8.1.0 self-analysis (S06)**: pick one tool as canonical (proposal: radon, since it's already pinned in `tests/test_complexity_cleanup.py`) and document the choice in `.cursor/rules/` so NineS's `--depth deep` invocations and our `pytest tests/test_complexity_cleanup.py` enforcement agree.
- **Single-PR mini-cycle works well for low-risk refactor patches.** P-01 went `branch → 1 commit → PR → merge → tag` in <30 minutes wall-time with full SI-10 6/6 PASS. The L0 dispatch's risk-isolation framing (`Wave 1 quick wins + 早期风险隔离`) is validated — establishing the per-patch lightweight-tag pattern for the rest of the v8.0.0 cycle.
- **Out-of-scope cc findings should be explicitly named in the retro, not just the deferred-to patch.** This retro names `select_context` and `apply_round_escalation` by callable + cc-value to make the deferral auditable — a pattern subsequent micro-retros should keep so the G1 SI-3 evaluation can verify (3 NineS finding closures listed per patch) actually sums to (NineS cycle-end finding delta).
