## 4. Key learnings

The cycle ran as a strict single-day batch — **8 patches in 1 day** vs the v7.3.0 cycle's 6 patches in 1 day, slightly higher throughput. Specifically:

### 4.1 Did the meta-test infrastructure (P-01) catch ghosts that humans missed?

**YES.** The `tests/test_no_ghost_features.py` infra (517 lines, 32 tests) caught all 5 P-08 builtin templates with stale `team_overrides: {}` blocks BEFORE the cleanup. Without P-01, the deletion of `WorkflowTemplate.team_overrides` would have left orphan `team_overrides: {}` blocks in the 5 builtin templates (`full-pipeline.yaml`, `product-verification.yaml`, `nines-assisted.yaml`, `self-update.yaml`, `research-design-review-refine.yaml`) — they would have parsed without error (defensive `raw.get("team_overrides", {})` populator returns empty dict regardless of whether the field exists on the dataclass), but the schema doc would have implicitly contradicted the dataclass. The `strict=True` xfail marker on `test_dataclass_field_has_consumer[team_overrides]` forced removal of BOTH the dataclass field AND every YAML reference to it in the same patch — exactly the kind of "spread-out forgetting" that human review tends to miss.

The infra also caught the latent bug in `_skill_quick_reference_names()` helper (`section.splitlines()` instead of `section.group(1).splitlines()`) — the bug had been MASKED while the test was xfailed, then surfaced when P-03 removed the marker. Without P-01's xfail-strict-flip discipline, the helper bug would have stayed silent indefinitely.

### 4.2 Did the xfail-flip-to-xpass workflow feel natural?

**YES.** Each patch's marker removal acted as a forcing function — a clean "definition of done" anchor that maintainers could verify via a single `pytest tests/test_no_ghost_features.py -v` run. The mechanic worked because:

1. **Strict=True semantics** make XPASS a hard suite failure rather than a quiet upgrade — there is no way to silently leave the marker in place after closing the ghost.
2. **Reason strings cite the closing patch by ID** (`"G-B1: ... — closes in P-06"`), so a maintainer scanning the test file can see exactly which patch is expected to remove the marker.
3. **Per-parameter parametrize markers** (refactored in P-04 from a single test-level marker to per-parameter markers on `test_dataclass_field_has_consumer`) gave each ghost its own removable marker, avoiding the "remove one marker, expose 4 unrelated XPASS failures" failure mode.
4. **K-category tests (5 tests covering G-K1..G-K12) carried NO xfail** because P-02 had already closed those 12 ghosts in v7.4.3 — they pin the closure as regression guards. This dual-mode (xfail for not-yet-closed + pin for already-closed) gave the test file a clear closure trajectory and a regression boundary in the same artifact.

### 4.3 Did the lifecycle-hook implementation (P-05) surface architectural assumptions in SKILL.md that the implementation contradicts?

**YES.** SKILL.md §"Lifecycle Hooks" had previously claimed:

> System-level enforcement (100% compliance). Optional per-dispatch; default: none.

This was a **paper-only promise**: there was zero implementation. When P-05 designed the actual hooks, two architectural assumptions surfaced:

1. **"100% compliance" is incompatible with the default-permissive design discipline of the rest of DevolaFlow.** Other validation surfaces (`validate-template`, `validate-gate`, `check-drift`) all carry advisory-default-with-strict-opt-in semantics. Forcing lifecycle hooks to 100% compliance would have introduced an inconsistent enforcement model. P-05 RESOLVED this by adopting `strict=False` as the default and `strict=True` as the opt-in — the SKILL.md text was rewritten to "Permissive default (warn + log); strict opt-in raises HookViolation" to match.
2. **The "On Violation" column language ("Block + escalate", "Reject + log (P1)", "Auto-retry ≤ P4 limit")** describes BEHAVIOUR THE HOOKS DO NOT CONTROL — those are downstream-orchestrator responsibilities. The hooks' actual responsibility is to RAISE `HookViolation` so the orchestrator can decide. P-05 RESOLVED this by renaming the column header to "On Violation (strict)" and softening the row text accordingly.

The rewrite was a verbatim 11-line-for-11-line swap (preserved SF-1 budget at 498/500 lines and tokenizer-stability for EvoBench `feature` profile section selection, so the `lifecycle_hooks` extracted token count stayed ≤126 vs OLD 119 and `dispatch_report` ≤417 vs OLD 420 under the deterministic `len(text)//4` fallback estimator). Without the implementation forcing the SKILL.md text to be honest, the false promise would have stayed in the public-facing docs indefinitely.

### 4.5 Cycle throughput — 8 patches in 1 day vs v7.3.0's 6 patches in 1 day

The v7.3.0 retrospective set the throughput precedent of 6 patches in 1 day — twice the v7.0 cycle rate. The v7.5.0 cycle ran 8 patches in 1 day (≈33% higher throughput). Driver factors:

- **The audit-driven structure** (`.local/research/v7.5.0_ghost_audit.md` §5 patch table) gave each patch a precise scope, file list, risk rating, dependency map, and SKILL/EvoBench-impact prediction. No mid-cycle scope expansion occurred — every patch landed within its predicted file boundary.
- **The xfail-strict forcing function** (P-01) made each subsequent patch's "definition of done" mechanically verifiable: marker removal + `pytest -v` clean. This eliminated the "is this actually finished?" debate that often blocks per-patch acceptance.
- **The stack-PR pattern** (each patch's branch based on the previous accepted patch's branch — see §4.6 below) eliminated rebase-conflict serialisation between patches; the 8 PRs landed in a clean stack with each subsequent merge being trivial because the predecessor was already in `main`.

### 4.6 Stack-PR pattern — did the stacked-PR base-on-previous-branch pattern work cleanly?

**YES.** The v7.5.0 cycle adopted a strict stack-PR pattern: P-02's branch was based on `main`; P-01's branch was based on P-02's branch (which was already merged); P-06's branch was based on P-01's branch (which was already merged); etc. The v7.5.0-rollup branch (this rollup) is based on P-08's branch (the LAST accepted state).

Benefits observed:

1. **Zero rebase conflicts between patches.** Each PR added new tests / new markers / new files; the `tests/test_no_ghost_features.py` line numbers shifted across patches but the marker removals were always semantically isolated to one well-defined region.
2. **The `git log --oneline 062c369..HEAD` produces a clean linear history** (8 patch commits + 1 rollup commit, no merge commits between patches because the cycle is single-author serialised — only the L0 merges to `main` introduce merge commits at PR-acceptance time).
3. **Each PR's diff is reviewable in isolation** — P-04 (951 insertions / 70 deletions) and P-05 (1595 insertions / 56 deletions) were the largest patches but had cleanly bounded scopes.

### 4.7 Items NOT addressed (transparent failure modes for the next cycle)

In the spirit of W-7 / SI-8, the cycle did NOT achieve the following — these are explicit failure modes for the next iteration to consider:

- **No NineS-driven mid-cycle re-evaluation.** NineS v3.3.0 was used at the start (informally — the gap audit was authored manually) and at the end (this rollup's SI-2 self-eval). Mid-cycle NineS rounds could have caught the P-04 scope ambiguity (input_mapping vs mode-only) earlier, before the user "mode_only" decision was needed.
- **No automated cross-patch SKILL.md budget tracker.** SF-1's 500-line ceiling on SKILL.md was tracked manually — three patches (P-03, P-05, P-07) all touched SKILL.md, and the cycle's net headroom went from 1 line (499/500) to 2 lines (498/500) only because P-03 explicitly cut 6 lines from §"Reinforcement Rules" to make room. A `pre-commit` hook checking SKILL.md line count + per-section token estimate at commit time would have caught budget pressure earlier.
- **G-J3 + G-J4 not actually verified** (only sanity-pinned in P-01's tests/test_no_ghost_features.py). The audit §3.J Cat J subtotal lists these as "(unverifiable in read-only audit)"; the cycle did not run `pytest --collect-only` against the v7.5.0 final state to compare against the CHANGELOG-claimed test counts. The v7.6.x SI-1 gate should explicitly close this.
