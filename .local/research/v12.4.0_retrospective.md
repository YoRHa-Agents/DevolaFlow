## 4 — Key learnings (process improvements for v12.5.0+)

### 4.1 Helper-extraction template is the canonical refactor pattern for cc-spike sweeps

PV-03 (evaluate_gate) + PV-04 (build_mapping_from_dict + _collapse_block) all used the same shape: extract 4 named `_apply_*` (or `_validate_*` or `_collapse_*`) private helpers from the high-complexity function, each helper at cc ≤ 8, with the orchestrator becoming a linear pipeline at cc ≤ 7. The pattern is now triple-validated — future cycles encountering cc ≥ 20 functions can copy this template verbatim. v12.5.0+ PV-N would absorb the 2 NEW WARNING-tier cc-spikes (`load_command_mappings` cc=16, `apply_local_recipe` cc=16) using this exact pattern.

**Specific copy-paste recipe for v12.5.0+**:
1. Identify the 4 logical phases inside the cc=N function
2. Extract each phase as a private `_<verb>_<phase>(args) -> <return_type>` helper, targeting cc ≤ 8
3. Refactor the orchestrator to a linear pipeline of helper calls (cc ≤ 7)
4. Add `tests/test_<module>_complexity.py` pinning helper cc ≤ 8 + orchestrator cc ≤ 7 + property-based byte-identical-verdict guard
5. W-18 stanza in `tests/test_no_ghost_features.py` pinning the 4 NEW helper symbols
6. Run W-4 sweep at PV close to verify zero regressions

### 4.2 PV-01 NineS deep + L0-only audit as twin entry-gate inputs scales cleanly

v12.4.0 PV-01 produced BOTH the standard NineS deep analyze (`v12.4.0_nines_deep_evaluate_gate.json` + `v12.4.0_nines_deep_commands.json` + `v12.4.0_nines_deep_bullets.json`) AND the historical-feedback-driven L0-only audit (`v12.4.0_l0_only_audit.md`). The 2 entry-gate inputs fed DISTINCT D-N items (NineS deep → D-2/D-3 cc-spike refactors; L0-only audit → D-4 leak cluster). This is the FIRST v12.x cycle where the entry-gate produced 2 independent SI-1 inputs — and it scaled cleanly: each input had a clear ownership PV (PV-03/PV-04 for cc-spike, PV-05 for L0-only) without overlap.

**Recommendation for v12.5.0+**: when historical-feedback constraints surface mid-cycle (e.g. v12.1.1 user-feedback themes informing v12.4.0 D-4), produce a companion audit artifact at PV-01 (not waiting until the implementation PV). The companion audit gives the implementing PV concrete per-row verdicts (e.g. PV-05's 11 demotions + 22 explicit-skip additions) rather than requiring re-analysis during implementation.

### 4.3 PV-05 NEW (historical-feedback) added cleanly to a planned 5-PV cadence

v12.4.0 was originally scoped as a 5-PV cycle (PV-01 SI-1 + PV-02 tooling + PV-03 cc-spike #1 + PV-04 cc-spike pair + PV-05 cycle-close per v12.3.0 retro §6). Mid-cycle, the v12.1.1 user-feedback themes surfaced the NEW D-4 L0-only leak cluster, which expanded the cycle to 6 PVs (PV-05 became the L0-only impl PV; PV-06 absorbed cycle-close). The expansion did NOT cause:
* Cumulative test-cap overrun (W-17): cycle total ~65 NEW tests vs +150 cap (85 slots of headroom)
* Per-PV test-cap overrun (W-17): max PV is PV-04 at ~22 vs +30 cap
* W-4 regression: PV-05 captured 2 IMPROVED scenarios; zero regressions
* Composite regression: 9.40 vs v12.3.0 9.225 — actually +0.175 improvement

**Confirms** the v12.3.0 retro §4.5 alternation pattern at the budget level: EXPANSION MINOR cycles CAN absorb mid-cycle scope addition if the additions follow the same shape as the existing PVs (PV-05 used the YAML-config-edit + lifecycle-hook pattern that PV-04 v12.2.0 established, just for a different cluster of surfaces).

**Recommendation for v12.5.0+**: if mid-cycle historical-feedback evidence surfaces a NEW deficiency, prefer ABSORBING it as a NEW PV (not stretching an existing PV) when the addition follows an established pattern. Stretch an existing PV only if the addition is small (< 5 NEW tests + < 100 lines of code) AND fits the same scope as the PV's primary deliverable.

### 4.4 W-4 sweep at PV-03 + PV-04 + PV-05 close (not just cycle close) caught baseline regen need cleanly

Per W-16 v12.3.0 PV-04 clarification ("wholesale regen MAY land at cycle start OR cycle close — whichever PV first observes baseline drift"), v12.4.0 ran W-4 sweep at the close of each PV that touched the W-4 critical path: PV-03 (gate scorer), PV-04 (commands.py — on the RTK proxy path), PV-05 (context_profiles.yaml). PV-03 + PV-04 sweeps stayed GREEN against v12.3.0_baseline (zero scenario drift > 5%). PV-05 sweep caught 2 scenarios crossing the baseline_diff threshold (both IMPROVED, not regressed), which triggered the v12.4.0_baseline.json wholesale regen at PV-05 close.

This pattern WORKS — incremental per-PV sweep + cycle-close regen-only-if-drift-detected = no cumulative drift across PVs. The v12.2.0 retro §4.2 wholesale-vs-piecemeal lesson informed this discipline (the v12.2.0 cycle deferred regen entirely because no PV drifted; v12.4.0 deliberately regenerated at PV-05 close because PV-05 was the PV that drifted).

**Confirms**: W-16 wording ("MAY land at cycle start OR close") is operationally correct and prevents both anti-patterns (per-PV piecemeal drift + bleed-through cycle-end audit chasing).

### 4.5 OPT-IN extras pattern (PV-05 banner hook) is the canonical S-10 byte-id preservation idiom

v12.2.0 PV-04 wired `reject_subagent_quality_score` as a DEFAULT extra in `lifecycle/__init__.py` — operators got the hook without opting in. v12.4.0 PV-05 deliberately DEPARTED from that precedent for the banner hook: `register_pre_dispatch_extra()` is operator-invoked, NOT default-wired. This preserves S-10 byte-id contract for v12.3.0 callers byte-identically.

The departure is the CORRECT one for NEW hooks — default-wiring a NEW hook breaks the S-10 byte-id contract for the prior cycle's callers (their `run_hooks("pre_dispatch", ...)` would emit a DIFFERENT result than v(N-1)). Default-wiring is reserved for cycles that ALSO bump the schema version (which v12.4.0 explicitly does not).

**Recommendation for v12.5.0+ and beyond**: NEW lifecycle hooks ship OPT-IN by default (via a `register_<event>_extra()` helper); strict graduation to default-wired requires a future MAJOR cycle (per W-21 2-cycle cadence + DEFAULTS-PERMISSIVE-IN-MINOR / STRICT-IN-NEXT-MAJOR). The v12.2.0 PV-04 default-wired pattern stays available for hooks where the byte-id contract is ALREADY allowed to drift (e.g. when the cycle bumps schema version 6 → 7).
