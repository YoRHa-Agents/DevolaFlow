## §3 — Notable findings

(Top 5 highest-impact findings, comparable to `v10.0.0_nines.md` §"Capability scores".)

### Finding 1 — `structure_recognition = 1.0000` byte-identical to v10.0.0

The A-2 cache-prefix invariant held across 5 PATCH PVs + this MINOR
cycle-close. NineS's structure-recognition axis runs an independent
package + module + framework + dependency-edge + coupling check; all
5 sub-axes returned 1.0 (or weighted ≥0.62 for the layout-inference
sub-axis which always rounds against single-package codebases like
DevolaFlow). The A-2.4 multi-baseline byte test (now pinning 10
baselines through v10.2.0) corroborates byte-for-byte.

### Finding 2 — `decomposition_coverage = 1.0000` (1230/1230 elements captured)

The 5 helper extractions across PV-04 + PV-05 + the cycle's other
new modules left every Python element NineS-discoverable. Files
analyzed grew from 96 (v10.0.0) → 105 (v10.3.0) per `module_count`,
yet element-coverage stayed at 100%. No NineS finding flagged any
file as un-parseable.

### Finding 3 — `code_review_accuracy = 1.0000` with 39 warnings + 3 errors but 0 false positives

NineS's mid-cycle deep-analyses on `src/devolaflow/si_chip_bridge/`
(PV-03), `src/devolaflow/plugins/` (PV-03), and
`src/devolaflow/lifecycle/` (PV-03) surfaced 10 actionable
complexity warnings; PV-04 closed 2 (`pre_plugin_invocation` 18→≤10,
`post_skill_edit` 13→≤7) and PV-05 closed 1 (`installer.read_last_checked`
15→8). The remaining 7 high-CC functions are deferred to v10.3.x or
v10.4.0 as deterministic micro-PVs per `v10.2.4_iteration_round2.md`
§5. False-positive rate stays at 0.0 — NineS findings translate
1:1 to actionable refactors.

### Finding 4 — `index_recall = 0.8000` unchanged (4/5 query test)

NineS's symbol-index recall stayed at 0.80 — the canonical 5-query
test (one query "sandbox isolation" continues to miss exact-top1
because NineS V3.3.0's index doesn't match against the
`devolaflow.shell_proxy.sandbox` module's docstring header verbatim).
This is a known NineS V3.3.0 limitation, NOT a DevolaFlow regression.
Documented as upstream A1.x ticket candidate (out of DevolaFlow PR
scope per W-2 manual fallback precedent).

### Finding 5 — `docstring_coverage` -0.68pp (deferred to v10.4.0)

The 5 PV-04 helper extractions (`_resolve_upgrade_threshold_hours`,
`_run_install_then_upgrade_for_plugin`, `_compute_fingerprint`,
`_load_existing_fingerprints`, `_run_si_chip_evaluation`) and the 1
PV-05 extraction (`_parse_log_event_timestamp`) shipped with the
parent function's docstring extended (or the helper documented
inline) — but NineS's docstring-coverage probe only counts top-level
docstrings on functions, classes, methods. The 9 net new module
elements without first-line docstrings dropped the coverage from
98.08 → 97.40 (-0.68pp). The floor (50.0%) is far below, so no SI-3
deduction. Tracked as v10.4.0 maintenance to add helper docstrings.

## §7 — Cycle plan baseline note

The cycle plan §3 PV-06 prescribed `--baseline-version v10.1.0` for
the W-2 cycle-close self-eval. The `--baseline-version` flag in
NineS V3.3.0 is a labeling/versioning hint for the report metadata —
it does NOT change the actual scoring (which always runs against
the live codebase + golden-test fixtures + V3.3.0 evaluators). The
delta comparison in §1 above uses the v10.0.0 archived NineS report
because v10.1.0 did not produce a cycle-close NineS run (v10.1.0
was a single-PV human-voice MINOR, not a multi-PV cycle close — see
v10.1.0 retrospective).

For audit reproducibility, the raw v10.3.0 NineS report bears the
metadata `version: "v10.1.0"` (passed as `--baseline-version`) but
the substantive comparison against an archived NineS baseline uses
v10.0.0. This naming-vs-comparison decoupling is documented in
v9.7.0 retrospective §3 ("baseline-label vs comparison-baseline
distinction") and in the W-2 manual fallback precedent.
