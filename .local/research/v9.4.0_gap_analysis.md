## 2. Empirical evidence — `ensure_plugin()` is the dead wire

Confirmed by walking the import graph at v9.3.0 head:

```bash
$ grep -c "ensure_plugin" src/devolaflow/plugins/installer.py src/devolaflow/plugins/__init__.py
src/devolaflow/plugins/installer.py:2
src/devolaflow/plugins/__init__.py:3

$ for f in $(find src/devolaflow -name "*.py"); do
    if grep -q "ensure_plugin" "$f"; then echo "$f"; fi
  done
src/devolaflow/plugins/installer.py
src/devolaflow/plugins/__init__.py
```

**Verdict:** 2 file hits — both are intra-package self-references (`installer.py` defines the function; `__init__.py` re-exports it for the public API). ZERO calls from any:

* dispatcher path (`src/devolaflow/feedback.py`, `src/devolaflow/lifecycle/*`)
* slash-command surface (`src/devolaflow/skills/slash_commands.py`)
* CLI entry point (`src/devolaflow/cli.py`)
* template runtime (`src/devolaflow/template_engine/`)

This is the v6.0.3-style dead-wire ghost: the API is mature (1030 LOC, 3 backends, schema v1+v2, distinguish-cmd v8.3.1, JSONL install log) but completely UNINVOKED by any production code path. Operators rely on **manual** `pip install nines` / `npm install -g uipro-cli` / `curl ... | sh` invocations OR on the `auto_install: true` registry-level default that NEVER actually fires because nothing calls `ensure_plugin()` in the first place.

NineS deep analyze (`v9.4.0_nines_plugins.md`) confirms `ensure_plugin` lives at `installer.py:759` (cyclomatic complexity 14) and is the single canonical entry point — there is no parallel "upgrade" entry point and no callable wrapper for batch processing.

## 3. Deficiencies enumerated (priority-ranked, ≥ 8 per W-1 contract)

### 3.1 Critical (blockers for v9.4.0 close)

#### D-P-1 — `pre_plugin_invocation` lifecycle hook missing  *(CRITICAL)*

**Source:** cycle plan §2.1 P-4 + the cycle plan v9.4.0 PV-02 row.
**Surface:** `src/devolaflow/lifecycle/`.
**Evidence:** `src/devolaflow/lifecycle/__init__.py` registers 8 default hooks (`pre_dispatch`, `post_dispatch`, `file_write`, `task_stop`, `format_on_edit`, `pre_shell_call`, `envelope_write`, `pre_handoff`) — none of them is bound to plugin-installation.
**Fix:** Author `src/devolaflow/lifecycle/pre_plugin_invocation.py` (~150 LOC). Wire into `lifecycle/__init__.py::DEFAULT_EVENTS` at position 9 per A-2.2 append-only.
**Owned files in PV-02:** `lifecycle/pre_plugin_invocation.py` (NEW), `lifecycle/__init__.py` (EDIT — add 1 import + 1 register call + extend tuple).

#### D-P-2 — Dispatcher wiring missing *(BLOCKER UX)*

**Source:** cycle plan §2.1 P-1 + the §3 evidence above.
**Surface:** `src/devolaflow/feedback.py::ProposalGenerator._emit_dispatch`.
**Evidence:** `_emit_dispatch` already orchestrates 3 lifecycle events on every dispatch (`pre_dispatch` → `post_dispatch` → `pre_handoff`); adding `pre_plugin_invocation` to that loop is the canonical wiring point. After v9.4.0 PV-03 the `rg "ensure_plugin"` hit-count grows from 2 → 4 (the new `pre_plugin_invocation.py` + the new `feedback.py` call site).
**Fix:** Extend the `(_HOOK_PRE_DISPATCH, _HOOK_POST_DISPATCH, _HOOK_PRE_HANDOFF)` tuple in `feedback.py` to include `_HOOK_PRE_PLUGIN_INVOCATION`. Resolve the workflow's plugin candidates from the dispatch payload + registry (`runtime-plugins.yaml#plugins[*].invoked_by_workflows`).
**Owned files in PV-03:** `src/devolaflow/feedback.py` (EDIT), `tests/test_dispatch_plugin_autoinstall.py` (NEW).

#### D-P-3 — Env-flag policy: opt-in or opt-out? *(CRITICAL design)*

**Source:** W-20 reuse-first vs new-flag policy.
**Surface:** `workflow-system/agent/references/env-flags.md`.
**W-20 §3 orthogonality analysis:**

* **Existing flag candidate 1: `DEVOLAFLOW_AUTO_INSTALL`** (default-ON, opt-OUT). Read by `installer.py::ensure_plugin` to control whether the install actually executes vs raises `PluginVersionMismatch`. **Different surface** — this controls the install primitive, not the dispatcher pre-flight.
* **Existing flag candidate 2: `DEVOLAFLOW_AGENT_WORKSPACE`** (default-OFF, opt-IN). Activates the workspace lifecycle (active/handoff folder management). **Different surface** — orthogonal to plugin pre-flight (an operator could want one without the other).
* **Verdict:** NEW flag justified per W-20 §3. The new `DEVOLAFLOW_AUTO_INSTALL_PLUGINS` activates a **distinct runtime surface**: the dispatcher's pre-flight plugin install hook. It composes with `DEVOLAFLOW_AUTO_INSTALL` in a meaningful way (`AUTO_INSTALL_PLUGINS=1 + AUTO_INSTALL=0` = audit mode where the hook fires + ensure_plugin reports the version mismatch but does not install).

**Activation rule:** `DEVOLAFLOW_AUTO_INSTALL_PLUGINS=1` (R5 strict — `"1"` only; rejects `"true"`/`"yes"`/`"on"`/`"01"`/`"1\n"`/`""`). Default-OFF; opt-in for v9.4.0. This protects existing operators who rely on the v9.3.x pure-passthrough dispatch behaviour from any latency / network-call surprise.
**Fix:** Author the flag in the new `pre_plugin_invocation.py` module. Document in `references/env-flags.md` §2.13 (the canonical inventory). Author R5 strict zero-IO test.
**Owned files in PV-02:** `lifecycle/pre_plugin_invocation.py` (NEW — defines `ENV_FLAG`), `tests/test_pre_plugin_invocation.py` (NEW — proves zero IO when off), `references/env-flags.md` (EDIT — §2.13 entry).

### 3.2 Major (must ship for v9.4.0)

#### D-P-4 — Daily-upgrade surface absent *(MAJOR)*

**Source:** cycle plan §2.1 P-2 + user feedback "auto-upgrade daily".
**Surface:** `src/devolaflow/plugins/installer.py` + `src/devolaflow/cli.py`.
**Evidence:** No `upgrade_plugin` function exists in `installer.py`. The legacy `PluginRegistry.upgrade()` method on `registry.py` only handles the legacy v0 plugins schema; never wired to the runtime registry. No `last_checked` field anywhere. No CLI subcommand.
**Fix in PV-04:**
1. Add `upgrade_plugin(plugin_id)` to `installer.py` (delegates to `_install_via_<backend>` for the upgrade command).
2. Add `_LastCheckedTracker` helper (reads `plugin_install.log` JSONL, groups by `plugin_id`, returns last `ts` per plugin).
3. Add `refresh_all(force: bool = False)` orchestrator (iterates registry, checks staleness vs registry default, upgrades stale plugins).
4. Author `devolaflow plugins {list,status,refresh}` CLI subcommand group (new `cli.py` entry).
**Owned files in PV-04:** `installer.py` (EDIT — add functions), `cli.py` (EDIT — add `plugins_cmd`), `pyproject.toml` (EDIT — add `devolaflow-plugins` script entry), `tests/test_plugin_upgrade.py` (NEW).

#### D-P-5 — Schema v3 bump for `upgrade_cmd` + `upgrade_check_frequency_hours` *(MAJOR)*

**Source:** cycle plan §2.1 P-5 + cycle plan v9.4.0 PV-04 row.
**Surface:** `workflow-system/agent/knowledge/runtime-plugins.yaml`.
**Evidence:** Current `runtime-plugins.yaml` is `schema_version: 2`. No row in any plugin entry carries `upgrade_cmd`. The `defaults:` block lacks `upgrade_check_frequency_hours`. Backward-compat: `_SUPPORTED_SCHEMA_VERSIONS = frozenset({1, 2})` in installer.py (line 83) — must be extended to `{1, 2, 3}`.
**Fix in PV-04:**
1. Bump `runtime-plugins.yaml` to `schema_version: 3`.
2. Add `upgrade_cmd` per plugin (defaults to `install_cmd` when omitted, since pip / npm / curl install commands are typically idempotent and re-running them performs the upgrade).
3. Add `defaults.upgrade_check_frequency_hours: 24` (configurable per registry).
4. Extend `_SUPPORTED_SCHEMA_VERSIONS` to `{1, 2, 3}`.
**Owned files in PV-04:** `runtime-plugins.yaml` (EDIT — schema bump), `installer.py` (EDIT — extend supported set + parse new field).

#### D-P-6 — Dispatcher cannot resolve "which plugin does this stage need?" *(MAJOR)*

**Source:** cycle plan §2.1 P-3.
**Surface:** `src/devolaflow/feedback.py` (the dispatcher) + `runtime-plugins.yaml`.
**Evidence:** `runtime-plugins.yaml#plugins[*].invoked_by_workflows` is a list of workflow names. The dispatcher knows the workflow name (from `dispatch.workflow_name` or template metadata) but no helper exists to invert the lookup `workflow_name → list[plugin_id]`. Without the helper, the PV-03 wiring would have to embed the lookup logic inline.
**Fix:** Add `plugins_for_workflow(workflow_name) -> list[str]` helper to `installer.py`. Plain dict lookup; no mutation. Re-export from `__init__.py`.
**Owned files in PV-03:** `src/devolaflow/plugins/installer.py` (EDIT — add helper), `src/devolaflow/plugins/__init__.py` (EDIT — add to `__all__`).

## 5. Out-of-scope deferrals (W-7 retrospective inputs)

* **Si-Chip integration** — explicitly v9.5.0 (cycle plan §3 Phase 3, Q2=B DEEP). This v9.4.0 minor ships the **pre-condition** infrastructure (auto-install + auto-upgrade) that v9.5.0 builds on.
* **Refactor `ensure_plugin` cyclomatic complexity** — NineS flagged C-14 at `installer.py:759`. Deferred to a future maintenance PV (telegraphed candidate v9.7.0 PV-N or v10.1.x); decomposing the function would invalidate the v8.3.1 R5 strict byte-stable contract pinned by `tests/test_plugins.py`.
* **`pre_plugin_invocation` parallel batch installs** — first version installs serially (sequential `for plugin_id in resolved_ids`). Telegraphed candidate for v9.7.0 PV-03 (async dispatch) since the latency profile of N pip installs in serial is small relative to a single curl-script install.
* **Plugin SHA pinning beyond best-effort heuristic** — `installer.py::_verify_sha256` remains the v8.2.1 best-effort design. Full per-artifact hashing is design.md §6 implementation hint deferred indefinitely.
