## §1 — Admission philosophy

A patch is **mainline-admitted into v11.0.0** if and only if it satisfies ALL 9 hard gates below. Failure of any gate triggers one of:

- **REJECT** — direction does not become a v11.0.0 patch (defer to v11.1.0+ OR drop entirely)
- **REWORK** — patch design must be revised before re-submission
- **CONDITIONAL** — admit with explicit caveat (e.g., "applies only to large repos")

**Hard gates (must pass ALL):**

1. **G-1 Internal-value gate** — clear DF-internal benefit (not EvoBench)
2. **G-2 Both-tier gate** — measurable improvement on BOTH small + large project
3. **G-3 Zero-deps gate** — no requirement for external tool changes (NineS/Si-Chip/RTK/ui-pro side)
4. **G-4 Cycle-budget gate** — fits within W-17 +30/PV and +150/cycle test caps
5. **G-5 Soul-freeze gate** — adds 0 Soul rules (S-11 candidate only deferred per W-21)
6. **G-6 Cache-prefix gate** — no edits to canonical_order positions 1-12 (A-2.1 frozen prefix)
7. **G-7 Compatibility gate** — zero breaking changes to public API surface (functions, env flags, schemas, file paths)
8. **G-8 Test coverage gate** — every NEW Python module ≥ 80% coverage; modified module not regress (CP-2)
9. **G-9 Documentation completeness gate** — patch ships with: (a) CHANGELOG entry, (b) W-18 ghost-audit lint refresh, (c) updated reference if SKILL/CLAUDE/CIM-changing, (d) bilingual EN/ZH if user-facing

## §2 — Per-gate concrete checks

### G-1 Internal-value gate

**Pass:** PDS §5 benefit_metrics shows ≥ 1 quantitative DF-internal metric improvement; PDS §6 admission_verdict ∈ {PASS, CONDITIONAL_PASS}; the metric is from `v11.0.0_evaluation_methodology.md` §4.X bucket (NOT EvoBench).

**Reject if:** PDS §5 cites EvoBench `q` / `pass_rate` / `gap_score` as the primary metric.

### G-2 Both-tier gate

**Pass:** PDS §3 small_project_eval AND §4 large_project_eval both show pass criterion met.

**CONDITIONAL pass if:** Only one tier passes AND the PDS explicitly notes applicability bounds (e.g., "applies only to repos with ≥ 4 plugins"). Such patches ship as `--opt-in` env flag, NOT default.

**Reject if:** Neither tier shows benefit OR one tier shows regression > 5%.

### G-3 Zero-deps gate

**Pass:** PDS §8 dependencies field lists ONLY internal `<dir-id>` references; ZERO entries naming external repos.

**Reject if:** Patch description requires "Si-Chip to add X" or "NineS to expose Y" — these belong on the upstream issue tracker, not in DevolaFlow's cycle.

### G-4 Cycle-budget gate

**Pass:** Sum of NEW test functions across ALL admitted patches ≤ 150 (W-17 cycle cap); each PV's bundle ≤ 30 (W-17 per-PV cap).

**Calculation:** Each PDS §7 effort_estimate maps to test budget:
- S → up to +10 tests
- M → up to +25 tests
- L → up to +60 tests (multi-PV; spread across cycle)

**If over budget:** L0 must drop lowest-priority `stretch` patches (per §3 prioritization) until budget fits. Patches that increase functionality but require >30 tests in one PV must be split into multi-PV plans.

### G-5 Soul-freeze gate

**Pass:** No PDS proposes a S-11+ Soul rule.

**Reject if:** Any PDS introduces S-* governance — those go through W-21 (2-cycle telegraph + SI-3 §3.2 ≥ 9.5/10) which is OUT-OF-SCOPE for v11.0.0 admission.

### G-6 Cache-prefix gate

**Pass:** No PDS proposes edits to `canonical_order` positions 1-12 (A-2.1 FROZEN PREFIX); APPEND to position 18+ allowed (A-2.2 APPEND-ONLY tail); NEST inside existing key allowed (A-2.3 nest-vs-append rule).

**Reject if:** Any PDS proposes reordering / renaming / removing canonical positions 1-12.

### G-7 Compatibility gate

**Pass:** PDS §2 patch_design lists files-touched; for each touched file, the change is one of:
- Pure-additive (new function/module/field)
- Pure-internal (refactor with byte-identical observable behaviour)
- Documentation-only

**Reject if:** Public API rename (function signature, env flag name, schema field name, file path).

**Soft-reject (REWORK) if:** Public API deprecation without 1-cycle alias path.

### G-8 Test coverage gate

**Pass:** PDS §2 patch_design includes test surface (new tests OR existing tests cover modified path); PDS §7 effort_estimate accounts for test authoring.

**Reject if:** "Tests can be added later" pattern (per SKILL.md "Rationalization Prevention" table).

### G-9 Documentation completeness gate

**Pass:** PDS §2 patch_design enumerates documentation deliverables matching its scope:

| Patch scope | Required docs |
|----|----|
| Python module change | CHANGELOG entry + W-18 lint refresh |
| SKILL.md / CLAUDE.md change | + W-12 adapter build verify + W-5 coupling triple |
| Reference doc add | + SF-3 sync_cursor_skill.py update + SF-1 line budget verify |
| User-facing change | + ST-3 bilingual completeness (EN+ZH) |
| Schema change | + multi-baseline byte test + W-13 benchmark guard |

**Reject if:** PDS misses a required doc surface for its scope.

## §3 — Tiering & prioritization (post-gate-pass selection)

After all 9 gates pass, patches are tiered by `core` / `standard` / `stretch` per the PDS admission summary line. The selection algorithm:

1. **All `core` patches admitted** — these define the mandatory v11.0.0 spine.
2. **`standard` patches admitted** in dependency-DAG topological order, until W-17 cycle budget exhausted.
3. **`stretch` patches admitted** only if budget remains AND no dependency cycles formed.
4. **`defer` patches** explicitly listed in v11.0.0 retrospective §3 ("What was deferred and why") for forward telegraphing.

**Tie-breaker** (when two patches have equal tier + equal effort): patch with **higher cross-direction dependency count** (i.e., other patches depend on it) goes first.

## §4 — v11.0.0 cycle shape constraints

The selected patch set must additionally satisfy:

| Constraint | Source | Limit |
|----|---|---|
| MAJOR cycle composition | v10.0.0 precedent | 3-7 MINOR PVs + 1 MAJOR rollup |
| Per-MINOR PV count | v10.0.0 precedent | 4-7 PVs per MINOR (5-PATCH + 1-cycle-close pattern from v10.2.0) |
| Cycle-cumulative LOC delta | empirical | < +5K LOC (else cycle becomes review-blocking) |
| Cycle-cumulative reference doc additions | C-4 budget | ≤ 2 new references (each ≤ 1000 lines) |
| Cycle-cumulative example additions | C-4 budget | ≤ 1 new example (≤ 1600 lines) |
| Cycle-cumulative SKILL.md delta | SF-1 ceiling | ≤ +20 lines (current 460 → 480 max) |
