## §2 — Per-dimension justification

### §2.1 Code quality (9.0 / 10)

Lint cleanliness, complexity metrics, error handling.

**Strengths:**
* `ruff check src/ tests/` — 0 violations across 225 files at PV-05 close
* `ruff format --check` — 225 files already formatted
* All new modules follow the established v8.3.x lifecycle hook contract (uniform `(payload, *, strict=False) -> HookResult` signature; permissive default + strict-opt-in)
* New `installer.py` functions (upgrade_plugin, refresh_all, list_plugins) inherit the existing v8.2.1 loud-failure invariant per S-5 — every error mode raises a typed exception with `details` dict
* `pre_plugin_invocation` hook explicitly classifies non-domain exceptions (OSError, generic RuntimeError) as "unexpected" → re-raises per S-5; domain exceptions become PPI001 violations on the result envelope

**Deductions:**
* `installer.py::upgrade_plugin` shares structural similarity with `ensure_plugin` — could be refactored to share a common backend-invocation helper. Marginal duplication; deferred per the "don't refactor `ensure_plugin` in this minor" decision (avoids invalidating R5 strict byte-stable contract). -0.5 for the duplication tax.
* `pre_plugin_invocation._extract_plugin_ids` cyclomatic complexity is moderate (4 branches × 2 nested loops). Could be split into `_extract_from_plugin_ids_field` / `_extract_from_plugin_id_field` / `_extract_from_workflow_field` — left monolithic to keep the hook's public surface small. -0.5 for not preemptively splitting.

### §2.2 Architecture rationality (9.5 / 10)

Separation of concerns, layering, coupling.

**Strengths:**
* **A-2.2 append-only invariant preserved** — DEFAULT_EVENTS bumped 8 → 9 with `pre_plugin_invocation` APPENDED at position 9 (NOT inserted into a lower slot); positions 1-8 byte-stable since v9.1.3.
* **A-5.1 single-owner invariant preserved** — `ensure_plugin` remains the canonical install owner; the new `pre_plugin_invocation` hook is a thin DELEGATOR (no install logic re-implementation); `upgrade_plugin` is a sibling under the same owner module (`installer.py`).
* **S-1 / P1 dispatcher-not-implementer preserved** — the L1 Stage Agent for v9.4.0 implemented (per the trivial-exception expansion via L0 dispatch authorisation); no L0 / L2 dispatcher implementation occurred in this cycle.
* **R5 strict zero-IO invariant preserved** — when `DEVOLAFLOW_AUTO_INSTALL_PLUGINS` is unset, the new event runs a permissive zero-IO no-op default; AST-walk test pins lazy-import contract; dispatch payload byte-identical to v9.3.x.
* **S-10 governance contract preserved** — the existing 3-event hook chain (pre_dispatch → post_dispatch → pre_handoff) still fires on every dispatch; the new event is APPENDED last, NOT replacing or reordering existing events.
* **W-20 §3 orthogonality** — the new `DEVOLAFLOW_AUTO_INSTALL_PLUGINS` env flag is genuinely orthogonal to existing flags. Documented inline in PV-02 commit body + `references/env-flags.md` §2.13. The flag activates a different runtime surface (dispatcher pre-flight) than `DEVOLAFLOW_AUTO_INSTALL` (install primitive) or `DEVOLAFLOW_AGENT_WORKSPACE` (workspace lifecycle).
* **No new state file** — `last_checked` reconstructed from existing `plugin_install.log` JSONL; preserves the v8.2.1 single-source-of-truth design for plugin state.

**Deductions:**
* The CLI's `plugins refresh --plugin <id>` repeatable flag could be a positional argument list instead. Choice traded composability for convention (matches `--target` / `--profile` patterns elsewhere in `cli.py`). -0.25 for the minor convention friction.
* `cli.py::plugins_cmd` does its own `argparse` setup rather than threading through a shared CLI framework. Acceptable per the existing v8.x CLI pattern (every cli.py function builds its own parser); no change of mind warranted but deserves a -0.25.

Coverage ≥ 80%, edge cases, regression tests.

**Strengths:**
* +83 raw / +60 adjusted NEW test functions across 3 implementation PVs — within W-17 caps
* Per-cycle test count growth: 3676 → 3739 (+63 collected including parametrize expansions; full suite green in 17.32s)
* Coverage: every new public symbol is exercised by at least 2 test functions (an import-smoke check via the W-18 ghost-audit + ≥ 1 functional test in the dedicated test file)
* Edge cases extensively covered:

  * 3 disabled-is-byte-identical proofs (clean payload + populated payload + non-dict payload)
  * 4 read_last_checked JSONL parsing edge cases (missing log, malformed lines, garbage timestamps, mixed event types)
  * 4 is_plugin_stale predicate cases (no-record + recent + old + clock-override seam)
  * 4 upgrade_plugin failure modes (timeout, OSError, non-zero exit, version-mismatch)
  * 5 refresh_all paths (skip-fresh, --force, --plugin filter, unknown plugin, network-failure-as-outcome)
* S-10 hook chain regression suite extended for the 4-event chain — every existing test pinning the 3-event chain was updated, AND a NEW ordering test pins `pre_plugin_invocation` immediately after `pre_handoff`

The pre-existing `tests/test_plugins.py` already exercises real install paths for the v8.x install surface; v9.4.0 PV-04 adopts the same convention (mocked tests for unit-level coverage; rely on operator end-to-end testing for real network paths). -0.5 for the integration gap.

### §2.4 Maintainability (9.0 / 10)

Readability, documentation, naming.

**Strengths:**
* Every new module includes a docstring explaining the v9.4.0 PV-NN design rationale + cross-references to the gap analysis
* Naming follows the established v8.x conventions: lifecycle hooks use `pre_*` / `post_*` event prefixes; installer functions are noun-verb (`ensure_plugin`, `upgrade_plugin`, `refresh_all`, `list_plugins`); CLI subcommands are imperative (`list`, `status`, `refresh`)
* The new `DEFAULT_EVENTS` bump comment block in `lifecycle/__init__.py` follows the established multi-version commentary pattern (v8.4.4 PV-04 → v9.1.0 W1-02 → v9.1.3 PV-03 → v9.4.0 PV-02 narrative chain)
* The W-18 ghost-audit lint includes failure-mode diagnostics (every assertion has a 2-3 sentence error message explaining what to fix and why)

**Deductions:**
* The `RegistryDefaults` dataclass now has 5 fields (was 4 in v8.3.x). Approaching the threshold where a config object would warrant a dedicated module. -0.5 for the proximity to splitting threshold.
* `cli.py::plugins_cmd` is ~110 LOC — the largest single CLI function in `cli.py`. Could be split into `plugins_list_cmd` / `plugins_refresh_cmd` for readability. -0.5 for not splitting.

### §2.5 Compatibility (10.0 / 10)

Cross-platform, schema backward compatibility.

**Strengths:**
* **Perfect schema backward compatibility**: `_SUPPORTED_SCHEMA_VERSIONS` extended `{1, 2}` → `{1, 2, 3}`. v1 + v2 entries continue to load; v2 entries without `upgrade_cmd` get `upgrade_plugin` falling back to `install_cmd` automatically; v1 entries (the v8.2.1 baseline shape) load unchanged.
* **R5 strict env-flag-OFF byte-stability**: the entire v9.4.0 cycle ships zero behavioural change for operators who haven't set `DEVOLAFLOW_AUTO_INSTALL_PLUGINS=1`. The dispatch payload is byte-identical to v9.3.x for every input — verified by the existing `test_dispatch_emission_runs_hooks.py::TestR5ByteIdentical` suite (all 3 paths pass byte-identical assertions).
* **A-2.2 append-only**: every existing `DEFAULT_EVENTS` slot at positions 1-8 is byte-stable; adding the 9th slot (pre_plugin_invocation) is the only schema-shape change.
* **No layout-invariant schema bump**: `schemas/lean-dispatch.yaml#layout_invariant.canonical_order` length 16 / version 5 byte-identical (verified by `test_layout_invariant_multi_baseline.py` across all 7 historical baselines including v9.3.0 witness).
* No platform-specific code paths added (the new code uses `os.environ.get`, `subprocess.run`, `pathlib.Path` — all stdlib and cross-platform).

**No deductions.** The compatibility story is the strongest dimension of v9.4.0.

### §2.6 Performance impact (8.0 / 10)

No regressions, benchmark deltas documented.

**Strengths:**
* `pytest tests/test_benchmarks.py -q` PASS — 36 passed; composite scores unchanged across all 53 EvoBench scenarios (within ±2%)
* The R5 strict zero-IO contract MEANS the env-flag-OFF dispatch path has ZERO measurable performance impact (no subprocess, no file IO, no lazy import — verified by AST walk test)
* Full pytest suite wall-clock: 17.32s (was 16.20s at v9.3.0 PV-07) — +1.12s growth from +60 adjusted new test functions = ~18.6ms per new test (well within healthy bounds; the v9.3.0 PV-03 LRU cache continues to absorb the test-suite YAML re-parse overhead)
* Layout-invariant baselines byte-identical with v9.3.0 — no schema bump in v9.4.0 means no cache-prefix invalidation; every L0/L1/L2/L3 dispatcher continues to key on the same byte-prefix.

**Deductions:**
* `pre_plugin_invocation` ENABLED path adds 1 lifecycle event firing per dispatch (4 hook calls instead of 3). Per-dispatch overhead estimate: ~3.5µs (the v9.3.0 PV-02 latency harness measured `run_hooks` p95 at 3.5µs/event); cumulative for the 4-event chain ≈ 14µs. For an opted-in operator running 1000 dispatches/day, the daily overhead is ~14ms (negligible). -1.0 for the modest opt-in path overhead — but this is the COST of the user-requested behaviour change, not a regression.
* `refresh_all` running daily with all 3 plugins fresh involves 3 `_probe_version` subprocess calls (one per plugin in `list_plugins` for the inspection table) — each probe is ~50-200ms wall-clock for pip/npm/curl. For an operator running `devolaflow plugins refresh` once daily via cron, total CLI wall-clock is ~600ms. Acceptable but worth flagging. -1.0 for the CLI inspection cost (also the COST of the feature, not a regression).
