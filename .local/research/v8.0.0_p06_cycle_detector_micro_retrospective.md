## 1. Gaps Identified

`.local/research/tweet_analysis_harness_engineering_v7.8.md` §4.4 + `.local/research/v8.0.0_patch_plan.md` §1 capability table (line 60) jointly flagged **Cycle Detection Middleware** as a **P1** gap. Per patch_plan §3 P-06 (line 264):

- Gap **4.4** (Cycle Detection Middleware) — *"不存在 (`gate/` 无 `cycle_detector.py`)"* — at the v7.8.0 baseline, the gate subsystem had **no mechanism** to detect tool-call / edit oscillation across rounds of the convergence loop. An L3 task agent stuck in a tool-call cycle (e.g., repeatedly editing the same file with the same content, repeatedly running the same failing test, repeatedly applying-then-reverting an edit) would burn the entire round budget on near-duplicate work before P4 bounded retry escalated. The cycle was only visible AFTER the round budget was exhausted — too late to inject a corrective `MUST NOT` reinforcement rule.
- Verbatim from `tweet_analysis_harness_engineering_v7.8.md` §4.4 (per the patch commit body line 4, citing Karpathy *"fail fast on cheap signals"*): the requirement is a **3-path detector** that catches oscillation early enough to inject a `MUST NOT repeat ...` `ReinforcementRule` into round N+1's dispatch — saving the round budget for productive work instead of duplicates.
- The **3 detection paths** (per patch_plan §3 P-06 line 268 + the L3 task contract):
  - **`exact_match`** — ≥2 consecutive snapshots with identical signature (severity `major`; escalates to `critical` at ≥4 consecutive)
  - **`fuzzy_match`** — ≥`window_size` consecutive snapshots whose pairwise Jaccard similarity ≥`similarity_threshold` (default 0.8 per the L3 task contract)
  - **`edit_oscillation`** — A→B→A pattern over the last 3+ snapshots sharing ≥1 file path
- NineS finding delta: **0** for this patch — gap 4.4 is a pure additive new-module addition, not a complexity hot-spot refactor (per patch_plan §3 P-06 — no `[NineS:CC-*]` finding cited; the `gate/` module had no cc warning attached to the missing cycle detector since the function literally did not exist).
- Critical-path role: P-06 sits inside **S02 W02** (the only patch in W02), sequenced AFTER S02 W01 (P-05 + P-08 + P-12 trio). Per patch_plan §3 P-06 line 288 *"P-03 (cycle_detector 与 budget 共享 per-round 监控, P-03 先落地)"* — P-06 depends functionally on P-03 (token-budget breaker) for the per-round monitoring infrastructure; P-03 already landed in W2. P-06 is also functionally adjacent to P-04 (deterministic fence) — both are reinforcement-rule emitters using the same `gate/reinforcement.py` module.

## 3. What Was Deferred and Why

- **`schemas/lean-dispatch.yaml` UNCHANGED — no new top-level dispatch key.** P-06 routes cycle reports into the existing `verdict.details` mapping (which is part of the `lean-report.yaml` schema, not `lean-dispatch.yaml`). This is the correct architectural split: cycle detection is a **report-time** signal (computed during scorer evaluation), not a **dispatch-time** input. Verbatim from commit body: *"`lean-dispatch.yaml` UNTOUCHED — `canonical_order` length=14, `version`=3 PRESERVED (verified by `tests/test_cycle_detector.py::TestSchemaInvariants`)"*. **Zero P6 / A-2 surface area for P-06** — the layout invariant baselines remain untouched. Same discipline as P-03 / P-04 / P-05.
- **`schemas/lean-report.yaml` has no `layout_invariant`** — appends are inherently P6-safe per `.cursor/rules/devola-flow-rules.mdc` Rule 6 / ADR-001. P-06 leveraged this to add the `cycle_detected` + `cycle_details` blocks at the end of the file without any P6 ceremony. **Document** for future patches: report-time signals (lint failures, fence failures, cycle detections, complexity findings) belong in `lean-report.yaml` (no P6 invariant); dispatch-time fields (behavioral guidelines, AC v2) belong in `lean-dispatch.yaml` (strict P6 invariant). Mixing the two layers is the most common architectural mistake to avoid in v8.x reinforcement-emitter patches.
- **Decision NOT mutated when cycle detected.** Verbatim from commit body: *"Decision is NOT mutated (S-5 — explicit signal, never silent PASS->FAIL escalate)"*. P-06 deliberately does NOT change a PASS verdict to FAIL when a cycle is detected — instead, it attaches the `cycle_detected=True` flag + `cycle_details` mapping + pre-computed `suggested_rule` to `verdict.details`. The L2 Wave agent reading the report makes the explicit decision to (a) inject the suggested rule into round N+1, (b) escalate to human, or (c) tolerate (e.g., the cycle is benign — same tool call repeated because of an external dependency). **Adopt** as v8.x convention: detector modules emit **signals**, not verdicts. Verdict mutation is the L2 Wave agent's responsibility per the P5 Artifacts as Contracts discipline (each layer owns its decisions).
- **`window_size=3` and `similarity_threshold=0.8` are CONSTRUCTOR defaults, not hard-coded constants.** Per the L3 task contract (cited in commit body line 7-9), the defaults are `window_size=3` and `similarity_threshold=0.8`. Both are settable per-instance via the `CycleDetector(window_size=N, similarity_threshold=T)` constructor. **Deferred** — making the defaults configurable per-profile (so a STRICT profile uses `threshold=0.7` and STANDARD uses `0.85`) is a v8.0.x ergonomic improvement that requires per-profile EvoBench drift validation. For now, callers must instantiate with explicit kwargs if they need non-default behaviour.
- **No tests yet for the `critical` severity escalation at ≥4 consecutive identical signatures.** Verbatim from commit body line 33-34: *"exact_match — >= 2 consecutive snapshots with identical signature (severity 'major'; escalates to 'critical' at >= 4 consecutive)"*. The 4-consecutive critical escalation is documented in the algorithm but not yet pinned by a test class. **Deferred** — adding a `TestExactMatchCriticalEscalation` test class (≥4 consecutive identical signatures → severity == 'critical') is a 1-test follow-up, defer to a v8.0.x test-coverage patch.
- **`fuzzy_match` Jaccard similarity is symbolic-tokenization based.** The current implementation tokenises signatures into bag-of-tokens and computes pairwise Jaccard similarity. **Deferred** — semantic similarity (e.g., embedding-based) would catch oscillation patterns where the signature differs in tokens but means the same thing (e.g., `read_file('a.py')` vs `read_file('a.py', limit=100)`). Adding semantic similarity would require LLM calls (latency + cost + non-determinism); save for v8.2.0 alongside Stage B abstractive (P-12 deferred).
- **CHANGELOG entry for P-06** — DEFERRED to **aggregate `[8.0.0]` rollup at S05 G1**, same pattern as P-01 / P-02 / P-03 / P-04 / P-05 / P-08 / P-11 / P-12 / P-13. The aggregate entry will reference P-06 by tag + new module + 100-test addition + 96% module coverage + 3-path detection algorithm + closure of gap 4.4.
- **Per-round monitoring shared with P-03 token-budget breaker — INTEGRATION NOT YET WIRED.** Per patch_plan §3 P-06 line 288: *"P-03 (cycle_detector 与 budget 共享 per-round 监控, P-03 先落地)"* — P-06 was supposed to share per-round monitoring infrastructure with P-03. P-06 instantiates its own `CycleDetector` separately from P-03's `TokenBudgetBreaker`. **Deferred** — wiring them through a shared `RoundMonitor` middleware is a v8.0.x ergonomic improvement; for now, callers must instantiate both independently.

## 4. Key Learnings

- **Deterministic id format `C-{cycle_type}-{seq:03d}` is the second instance of the `<prefix>-{type}-{seq:03d}` pattern P-04 codified.** P-04 codified `F-{fence_type}-{seq:03d}` for fence-failure rules; P-06 follows with `C-{cycle_type}-{seq:03d}` for cycle-detection rules. The `:03d` zero-pad keeps lex-sort matching numeric-sort up to 999 occurrences. **Validates** the v8.x recipe documented in P-04's retro: every future deterministic-instruction generator (P-09 `complexity_to_instruction`, P-10 `auto_ac_to_instruction`) should use `<prefix>-{type}-{seq:03d}`. P-06 is the first **second** instance of this pattern, proving the recipe is reusable.
- **`MUST NOT repeat ...` mandate format complements P-04's `MUST fix ...` mandate format.** P-04's fence rules use `MUST fix {fence_type} error at {file}:{line}: {msg}` (positive corrective action); P-06's cycle rules use `MUST NOT repeat ...` (negative prohibition on the just-observed bad pattern). **Codify** for v8.x: deterministic-instruction generators should use `MUST` (positive) for fix-this-thing rules and `MUST NOT` (negative) for don't-do-this rules. The verbatim mandate prefix is what makes the rule deterministically parseable by L3 task agents — they can grep for `MUST NOT repeat` to identify cycle-injection rules without LLM inference.
- **Detector emits signals, not verdicts.** Verbatim from commit body: *"Decision is NOT mutated (S-5 — explicit signal, never silent PASS->FAIL escalate)"*. P-06's cycle detector populates `verdict.details.cycle_detected=True` + `cycle_details` mapping + pre-computed `suggested_rule`, but **does not** change the verdict from PASS to FAIL. This is the correct separation of concerns: detection is a measurement (the detector's job); verdict mutation is a policy decision (the L2 Wave agent's job). **Adopt** as the v8.x architectural pattern for all gate-side detectors (cycle, complexity, oversize, etc.): they MUST emit explicit signals to `verdict.details`, but MUST NOT mutate `verdict.decision` directly. Policy mutation belongs in higher layers (L2 Wave or L0 Project).
- **`lean-report.yaml` has no `layout_invariant` — additions are inherently P6-safe.** P-06 added `cycle_detected: bool` + `cycle_details: object` to `lean-report.yaml` with **zero P6 ceremony** (no length bump, no version bump, no byte-baseline regression test). This is because `lean-report.yaml` is the **report-side** schema (gate output), not the **dispatch-side** schema (gate input). The P6 invariant is intentionally one-directional: dispatch payloads must be cache-stable (so prefix caches stay warm), but report payloads are read once per round and discarded — caching them is wasteful. **Document** explicitly: when adding signal fields, prefer `lean-report.yaml` (no P6 ceremony) over `lean-dispatch.yaml` (full P6 ceremony). The split is a load-bearing architectural decision documented in `.cursor/rules/devola-flow-rules.mdc` Rule 6.
- **Pre-computed `suggested_rule` in `verdict.details` saves the L2 Wave agent from re-deriving the rule.** When a cycle is detected, P-06's `_attach_cycle_report` helper calls `cycle_to_instruction(report)` immediately and stores the resulting `ReinforcementRule` in `verdict.details.suggested_rule`. The L2 Wave agent reading the report can inject `suggested_rule` into round N+1's dispatch **verbatim** (no re-derivation). **Adopt** as v8.x convention: when a detector emits a signal that has a canonical reinforcement-rule mapping, **pre-compute the rule at detection time** and attach it to the report. Don't make every consumer re-call the `_to_instruction` helper — once is enough, in the right place (gate-side, with full context).
- **96% coverage on a 474-line net-new module with 138 statements (5 missed) is the v8.x quality bar.** P-06's `cycle_detector.py` lands at 96% line coverage (133/138 statements). The 5 missed lines are *defensive guards* (verbatim from commit body: *"5/138 lines missed (defensive guards)"*) — code paths that should never execute in correctly-instantiated scenarios but exist for robustness. **Codify** for v8.x: net-new modules in `src/devolaflow/` should target ≥95% line coverage; only defensive guards (validators, assertion paths, unreachable branches with explicit raise) are acceptable as un-covered. **Reinforce**: the missing-lines list in coverage reports must be reviewable in 30 seconds; if there are >5 un-covered lines per module, more tests are needed.
- **23-min commit-to-merge cycle on a +1886 LOC patch is the v8.x large-feature benchmark.** P-06 is the largest patch in the v8.0.0 cycle so far (1886 LOC, vs P-05's 1401, P-08 feat's 1171). The 23-min cycle is possible because (a) the 3 detection paths were pre-locked in the patch_plan, (b) the dataclass shape (`CycleReport`, `StateSnapshot`) was pre-decided, (c) the 6-AC contract was pre-locked (no AC re-negotiation during authoring), (d) the byte-identicality regression-pin pattern (`cycle_detector=None` byte-identical) was inherited from P-03 / P-04 / P-05 (no new pattern to design), (e) the deterministic-id format was inherited from P-04 (just substitute `C` for `F`). **Reinforce**: pattern reuse across consecutive patches in the same module is what enables 20-30 min cycles on net-new 400+ line modules. Future detectors (P-09 complexity, P-10 AC) should aim for the same wall by reusing P-04 / P-06 patterns.
- **`gate/scorer.py` has now grown from 4 opt-in parameters across the cycle (P-03 `breaker`, P-04 `extra_checks`, P-05 `ladder_enabled` via profile, P-06 `cycle_detector`).** Each parameter defaults to `None` / `False` / disabled-profile, preserving byte-identical pre-existing behaviour. **Action item**: by end of v8.0.0, `evaluate_gate` will have ≥6 opt-in parameters (ratchet from P-07, complexity from P-09 still to come). **Document** in `references/execution-protocol.md`: the parameter list ordering (since Python kwargs are order-insensitive, this is style not contract). **Reinforce** for v8.1.0 SI-1: consider consolidating the 6+ opt-in detectors into a single `gate_options: GateOptions` dataclass to reduce the parameter explosion. Until then, the opt-in-default-None pattern is the v8.0.x convention.
- **End of S02 — 4 patches landed in ≈1.5 wall hours.** S02 timeline: P-05 commit 18:10:32Z → P-06 merge 20:40:55Z = 2h30m wall for 4 patches (P-05 + P-08 + P-12 + P-06). Per-patch averages: ~9 min for the 3 W01 patches in parallel-style sequence (P-05 9 min, P-08 22 min including coupling commit, P-12 9 min) and 23 min for the W02 P-06 patch. **Reinforce**: the W02-after-W01 sequencing worked correctly — P-06 went after the W01 trio so that `gate/scorer.py` co-write conflicts (P-05 owns `evaluate_ladder`, P-06 owns the `cycle_detector` parameter on `evaluate_gate` / `evaluate_ladder`) were resolved by W01-first sequencing. **Validate** the *"Wave-internal parallel + wave-between stack with sub-wave ordering for hot files"* topology design (plan §Overview line 43) — S02 is the proof point that 4-patch waves with 1 schema-touching patch (P-08) + 3 disjoint patches (P-05, P-12 in W01; P-06 in W02) can land in <3 hours wall.
