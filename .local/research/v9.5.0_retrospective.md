### 3.2 PV-05 dogfood DEFERRED (the BIG one — per the v9.5.0 user requirement)

**The v9.5.0 user requirement is explicit:**

> *"ensure those things are genuinely effective with clear verification benchmarks and tested gains BEFORE applying them. If not, summarise into a feedback document."*

**Why we DEFERRED instead of applying Si-Chip's per-file shrink suggestions:**

1. **No iteration_delta computable at v9.5.0 cut.** The full Si-Chip evaluation pipeline (`aggregate_eval.py`) requires real-LLM with-ability + no-ability run data which the v9.5.0 cycle deliberately did not generate (out of scope per L0 dispatch). Without iteration_delta, we cannot gate APPLY/DEFER per Si-Chip spec §23.
2. **Si-Chip's count_tokens probe is a static budget check, not an effectiveness measure.** It tells us the SKILL files are larger than Si-Chip's default budgets. It does NOT tell us that shrinking would improve agent task success rates.
3. **DevolaFlow's existing C-4 tiered LINE budgets** (Default <500 / Large ≤1000 / XL ≤1600) target a different skill profile from Si-Chip's default token budgets. An auto-shrink would delete operator-essential reference content that exists because some past PV's gap analysis identified an operator information gap.

The deferred-changes feedback doc (`.local/feedbacks/v9.5.0_sichip_deferred.md`) enumerates every per-file finding with proposed shrink candidates (e.g. env-flags.md compress per-flag tables 12 rows → 5 rows, ~50% body reduction) so operators can drive the eval cycle in v9.6.0+.

### 3.3 Out-of-scope deferrals (W-7 retrospective inputs for v9.6.0+)

* **Async batch-evaluate of Si-Chip's references** — PV-04's `post_skill_edit` evaluates the touched skill file synchronously. Async batch evaluation of all 10 DevolaFlow references at once is a v9.7.0 candidate (paired with v9.7.0 "Performance Overhaul #2").
* **Si-Chip `templates/` regeneration** — Si-Chip ships its own templates. DevolaFlow uses these as black-box references; we do NOT regenerate them locally (S-7 — external resources are read-only references).
* **NineS + Si-Chip dual-evaluation** — both tools ship complementary evaluation surfaces. Cross-correlation analysis is a v10.0.0 cycle-rollup candidate, not a v9.5.0 in-cycle item.

## §4 — Key learnings (process improvements for next cycle)

### 4.1 The dispatcher pattern of "ship plumbing first, dogfood next cycle" works

The v9.4.0 cycle shipped the auto-install + daily-upgrade plumbing per the user requirement; v9.5.0 then USED that plumbing to ship Si-Chip integration (`pre_plugin_invocation` hook auto-installs si-chip when `skill-optimization` workflow runs). This 2-cycle sequencing pattern (plumbing → consumer) is now the proven cadence for cross-cycle integration work. Recommended for the v9.6.0..v9.7.0 telegraphed work as well.

### 4.2 IEEE-754 epsilon on threshold gates is mandatory boilerplate

The v9.5.0 PV-02 `apply_or_defer` threshold gate hit the classic IEEE-754 boundary case (`0.6 - 0.5 = 0.0999...` being treated as below `0.10`). The fix (`APPLY_DEFER_EPSILON = 1e-9` in `runner.py`) is now the recommended pattern for any future threshold comparisons in DevolaFlow that involve float arithmetic. v9.6.0 should audit existing gate primitives (composite ≥ 8.5, regression tolerance ±2%, etc.) for the same potential boundary issue.

### 4.3 Forward-declared APIs in DEFAULT_ALLOWLIST must always cite the consumer PV

PV-02 added 2 NEW allowlist entries (`count_tokens`, `run_dogfood_cycle`) for APIs that landed before their PV-04 production caller. This forward-declaration pattern works ONLY when the allowlist comment cites the consumer PV explicitly. Future PVs that add new public APIs WITHOUT immediate callers MUST follow the same pattern (cite the consumer PV in the allowlist comment) — see PV-04's `metadata_to_json` entry as a co-located example.

### 4.4 The W-17 cycle cap (≤ +150 NEW tests per cycle) is now uncomfortably tight

Cycle cumulative as of v9.5.0 close: v9.3.0 +36, v9.4.0 +60 adjusted, v9.5.0 +43 = **+139 of +150 cap**. The remaining v9.6.0 + v9.7.0 + v10.0.0 close PVs collectively have only **+11 NEW test functions of headroom**. Recommended for v9.6.0 cycle-start: actively prune redundant tests in existing test files OR negotiate a W-17 cap bump (currently codified at "v9.0.0 PV-05 spec §5" — a v10.0.0 cycle-rollup PV would be the natural place to revisit). Mid-cycle audit per W-17 happens at v9.6.0 PV-05 (the cycle's halfway point).

### 4.5 Si-Chip's iteration_delta methodology is the right effectiveness gate, but requires real-LLM eval data

The v9.5.0 cycle proved out the mechanical plumbing (bridge module + lifecycle hook + templates) but could not exercise the actual effectiveness gate without real-LLM eval runs. The v9.6.0 cycle's "Self-Improvement #2" telegraph should explicitly include real-LLM eval-data generation as a PV deliverable; otherwise Si-Chip integration risks remaining a "shipped but never used in anger" surface — the same anti-pattern the v9.4.0 PV-01 audit found in the original `ensure_plugin()` dead-wire.

### 4.6 The 6-PV cycle structure (4 implementation + 1 dogfood + 1 close) handles user-requirement-driven minors well

v9.5.0's structure (PV-01 plugin reg + PV-02 bridge + PV-03 templates + PV-04 hook + PV-05 dogfood + PV-06 close) was a clean fit for the user requirement decomposition. The dogfood PV (PV-05) being potentially a no-op commit when prerequisites aren't available is a valuable pattern — it forces the cycle to acknowledge "we shipped the gate but haven't proven the gain yet" honestly rather than fake-passing the dogfood. Recommended for v9.7.0 telegraphed work.
