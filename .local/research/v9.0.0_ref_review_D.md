## Cross-batch observations

### Structural-template insights for v9.0.0 (per task brief special attention)

1. **Single-PV-per-section structure works exemplary at the cycle scale**. `shell-proxy.md` §3-§6 each correspond exactly to one cycle PV (PV-01/02/03/04) with consistent subsection numbering: `§N.1 Module layout / §N.2 Activation contract or registry / §N.3 invariants / §N.4 schema / §N.5 graceful degradation`. This is the most navigable reference structure in the repo and **should be the canonical template for any v9.0.0 12th SF-4 reference** — assuming the cycle has ≥ 3 PVs to cluster.
2. **Recency reduces drift only for COMPILED facts, not RUNTIME contracts**. agent-workspace.md (older by 1 minor) has no Soul Rule violations and only soft drift (forward-pinned versions, stale "deferred to v8.4.0+" note). shell-proxy.md (newest, just shipped) has a **Soul Rule violation** AND **3 schema-vs-doc drifts** — all in the runtime API surface (§5.2/§5.3/§6.3). The lesson: **REFERENCE refreshes need to validate not just frontmatter (`last_updated`) but every API surface mention against the canonical schema or source code**. v9.0.0 should consider adding a `tests/test_reference_api_alignment.py` that parses `MemoryCase`-style code blocks in references and asserts their fields match the dataclass / schema (mirrors `tests/test_no_ghost_features.py::_SF4_REFERENCE_SET` discipline).
3. **Cross-reference reciprocity is asymmetric and silent**. shell-proxy.md cites agent-workspace S-8/S-9 rules; agent-workspace.md does not cite shell-proxy.md or memory_router. **Recommendation for v9.0.0** — when a new reference (12th, 13th, ...) cites an existing reference, the reciprocal cross-link MUST be added to the older reference's §References subsection in the same PR. Codify as a SF-* convention rule extension OR test in `tests/test_reference_size_budgets.py` (already enforces the canonical 11-entry list per `_SF4_REFERENCE_SET`).
4. **Forward-defined version pins outlive their forward window**. Both refs use `(v8.X.Y)` annotations to tag features — but when those version slots aren't actually published (v8.2.5/v8.2.7/v8.2.8 → never shipped; M-007 deferred from "v8.4.0+" still pending at v8.4.0), the pins become misleading historical fictions. v9.0.0 SI-1 should mandate either (a) pin to the actually-shipped version OR (b) use a `(planned for v8.X.Y)` prefix so readers know the slot is forward-defined.
