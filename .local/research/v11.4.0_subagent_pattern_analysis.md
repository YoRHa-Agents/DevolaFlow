## §1 — Executive Summary

The philschmid article ([https://www.philschmid.de/subagent-patterns-2026](https://www.philschmid.de/subagent-patterns-2026), May 5 2026) introduces a **4-pattern taxonomy** for how a main agent manages subagents, **ordered by main-agent control over the subagent lifecycle**: **Inline Tool** (the `call_agent` function-call shape), **Fan-Out** (`spawn_agent` + `wait_agent` with model-controlled sequencing), **Agent Pool** (persistent stateful workers with `send_message`/`list_agents`/`kill_agent`), and **Teams** (peers messaging each other directly). The article frames the taxonomy as model-capability-graduated: Pattern 1 works with any tool-using model; Pattern 4 needs frontier-class models for **every** team member. This is the 2026 update of the same author's earlier "Rise of Subagents" post and the structural successor to the anthropic-coordination-blog 4-pattern taxonomy that DevolaFlow ALREADY mapped in `workflow-system/agent/references/execution-protocol.md` §7.3 (table at lines 490–495 — "orchestrator-subagent: Native, agent teams: Not modelled, message bus: Not modelled, shared state: Forbidden by P5"). The philschmid taxonomy reframes the same architectural axis with a **subagent-lifecycle lens** rather than a coordination-topology lens — this differs in emphasis but shares the same underlying decision points (control vs. autonomy, sync vs. async, single-task vs. persistent).

DevolaFlow needs this analysis because the v12.0.0 cycle (per `docs/cycle-archive/v11.1.0/retrospective.md` §3 telegraph) is already committed to landing **D-1** (Architecture rule A-7 cascade-depth STRICT promotion), **D-2** (`SHORTCUT_SIMPLE` retirement), and **D-5** (CHANGELOG CI lint) — three orthogonal but cycle-coupled graduations. The user's feedback at `.local/feedbacks/feedback_for_v11.4.0.md` ("提供关于多层级 subagent 角色设定的优化方案和选型验证清单 … 面向 12.0.0") layers a **fourth** v12.0.0 commitment onto the cycle: a multi-tier subagent role-selection optimization plus an operator-quotable **selection verification checklist**. v11.4.0 is the deliberate **analysis-and-lightweight-foundation prep cycle** that produces (a) the 4-pattern × DevolaFlow-coverage matrix, (b) a pure-function selection helper that operators can invoke without any schema change, and (c) the W-24 workflow rule that codifies the natural-language activation contract — leaving the schema change (NEST `gate.subagent_pattern` per A-2.3) and the strictness graduation for v12.0.0 SI-1 to evaluate alongside D-1 / D-2 / D-5. This split honours W-21's 2-cycle-deliberation Soul-set freeze cadence (no S-11 proposed; the new W-24 lands at Workflow per the same Soul-vs-Architecture decision-rule that placed A-7 at Architecture in v11.1.0 PV-05), W-16's wholesale-baseline-regen-at-MINOR-cycle-start discipline, W-17's per-PV test-cap discipline, and W-20's env-flag-reuse-first policy.

The NineS mechanism detector scans for 5 categories (`behavioral_instruction`, `context_compression`, `distribution`, `persistence`, `safety`). Cross-walking the 4 philschmid patterns against these 5 categories surfaces where each pattern would land in a DevolaFlow mechanism set:

| Pattern | behavioral_instruction | context_compression | distribution | persistence | safety |
|---|:---:|:---:|:---:|:---:|:---:|
| 1 Inline Tool | ✓ (single-call subagent prompt) | ✓ (subagent context isolation per P2) | ✓ (Task tool spawn) | — (single-task) | ✓ (P5 artifact contract) |

| 3 Agent Pool | ✓ (per-agent role prompt) | ✗ (state retained across messages — no compression) | ✓ (persistent worker registry) | ✓ (per-agent conversation history) | ⚠ (P1 cascade discipline at risk if pool depth confuses the dispatcher) |

Patterns 1 and 2 land cleanly across all 5 categories — they preserve P5 (artifacts as contracts) because every subagent reports back to the parent via a structured TaskReport, never via direct peer messaging. Pattern 4 fails the `safety` category because the Forbidden-by-P5 cross-agent shared state is the safety boundary that DevolaFlow's 4-layer hierarchy (P1 dispatcher-not-implementer + P5 artifacts-as-contracts) was designed to enforce. This is consistent with execution-protocol.md §7.3's row "shared state: Forbidden by P5" — the philschmid Pattern 4 is the same axis under a different name.

## §3 — 4-Pattern Decomposition (verbatim citations from upstream article)

The article's "Choosing a Pattern" summary table (verbatim from `.local/research/v11.4.0_subagent_patterns_source/article.md`):

| Pattern | Tools | Main Agent Role | Agent Lifetime |
| --- | --- | --- | --- |
| Inline Tool | `call_agent` | Caller | Single task |
| Fan-Out | `spawn_agent`, `wait_agent` | Dispatcher | Single task |
| Agent Pool | `spawn`, `send`, `wait`, `list`, `kill` | Coordinator | Multi-turn |
| Teams | All above + cross-agent `send_message` | Supervisor | Persistent |

For each pattern, the article specifies a **When-to-use** and a **Limitations** statement (verbatim). The decomposition table below pins both, plus a definition citation, plus a **DevolaFlow-coupling note** (the L0..L3 layer the pattern most naturally interacts with):

### 3.1 — Pattern 1: Inline Tool

* **Verbatim definition** (article §1, paragraph 1): *"The simplest pattern. The main agent calls a tool that spawns a subagent and returns the result as the tool response. From the main agent's perspective, calling a subagent is identical to calling `read_file` or `run_command`."*
* **Sync vs. async** (article §1, paragraphs 5–7): *"Sync (above): The tool call blocks. The main agent's turn is paused until the subagent finishes. The result arrives as a normal tool response. Async: The tool returns immediately with an agent ID. The subagent's result is injected into the conversation as a notification message when it finishes. The main agent can do other tool calls before the result arrives."*
* **When to use** (verbatim): *"Self-contained work. Research lookups, code reviews, file analysis, test generation. Most subagent use cases start and stay here."*
* **Limitations** (verbatim): *"Works with any model that supports tool use, including smaller and cheaper ones. Results arrive as a single tool response (sync) or as an injected notification message (async). No way to send follow-up instructions, check progress, or cancel early. If the subagent misunderstands the task, you find out when the result comes back."*
* **DevolaFlow coupling**: L0 → single L3 dispatch via the `Task` tool (sync only — DevolaFlow's `Task` tool blocks until the subagent reports back). The async sub-variant is NOT supported by the current `Task` tool; v12.0.0+ may evaluate adding async-Task support but this is forecast-indicative-not-graduation-commitment per the v11.1.0 retrospective L-1 process improvement.

### 3.2 — Pattern 2: Fan-Out

* **Verbatim definition** (article §2, paragraph 1): *"The main agent spawns subagents and collects results using a `wait_agent` tool. Unlike the inline tool, spawning and collecting are separate steps. `spawn_agent` always returns immediately. The model decides what to do next: call `wait_agent` right away, do its own work first, or spawn more agents before waiting."*
* **Tools** (verbatim): *"Two tools: `spawn_agent` dispatches work and returns immediately with an ID. `wait_agent` blocks until one or more agents finish."*
* **When to use** (verbatim): *"Multiple independent tasks that can run concurrently. The main agent does not need intermediate results from one subagent to start another."*
* **Limitations** (verbatim): *"The model needs to correctly decide when to wait. A model that calls `wait_agent` immediately after every spawn gets no benefit over Pattern 1. The value depends on the model's ability to interleave its own work between spawn and wait. Results are collected in batch via `wait_agent`, which returns all completed agent outputs since the last call. Still fire-and-forget: no way to send follow-up instructions or course-correct mid-task to subagents."*
* **DevolaFlow coupling**: L2 wave dispatching N parallel L3 task agents (already a first-class DevolaFlow primitive — `references/agent-hierarchy.md` §5 "Constraints" caps `max tasks per wave = 5`; `references/execution-protocol.md` §13 documents the `dispatch_wave_tasks(...)` async dispatch executor with `asyncio.gather` + bounded `Semaphore`). The "model decides when to wait" interleaving is structurally absent in DevolaFlow today (the L2 wave agent always waits at the wave barrier per `wave_definition.sync_barrier.mode`); v12.0.0+ may evaluate model-controlled wait points but this is OUT OF SCOPE for v11.4.0.

### 3.3 — Pattern 3: Agent Pool

* **Verbatim definition** (article §3, paragraph 1): *"The main agent spawns long-lived subagents and communicates with them through messages. Agents persist across interactions. The main agent can send follow-up instructions, check status, and coordinate work between agents."*
* **Tool surface** (verbatim): *"This requires a richer tool surface: `spawn_agent`, `send_message`, `wait_agent`, `list_agents`, `kill_agent`."*
* **State semantics** (verbatim): *"Unlike Pattern 2, agents here are stateful and interactive. The main agent sends a message, gets a response, and sends another message to the same agent. The agent retains its full conversation history. This supports multi-step workflows where the main agent coordinates between specialists."*
* **When to use** (verbatim): *"Multi-step workflows where agents need to collaborate. The main agent routes information between specialists."*
* **Limitations** (verbatim): *"The main agent must track multiple agent states, decide when to send follow-ups vs wait, and route information correctly. Smaller models lose track of which agent has which context, or forget to call `kill_agent` when done. Frontier models might handle 2-4 agents okayish."*
* **DevolaFlow coupling**: NOT MODELLED in v11.x. P1 (dispatcher-not-implementer) + P5 (artifacts-as-contracts) + L3 fresh-context guarantee preclude persistent stateful workers — DevolaFlow's `change-driven` workflow (per `references/execution-protocol.md` §12) provides the closest analogue via the `apply ↔ verify` convergence loop, but each round dispatches a NEW L3 with fresh context (the persistent state lives in `.local/.agent/active/<id>/STATUS.yaml` artifacts, not in any agent's conversation history). v12.0.0+ Pattern 3 landing is **forward-compat only** in v11.4.0 (no API; reference-only documentation).

### 3.4 — Pattern 4: Teams

* **Verbatim definition** (article §4, paragraph 1): *"Agents message each other directly without going through the main agent. The main agent sets up the team, defines roles, and steps back. Agents coordinate among themselves using direct messaging or a shared mailbox."*
* **Cross-agent addressing** (verbatim): *"The tool surface includes cross-agent addressing. Each agent gets `send_message` in its own tool set and can address other agents by name or path."*
* **When to use** (verbatim): *"Large tasks where the coordination logic exceeds what a single agent can manage step-by-step."*
* **Limitations** (verbatim): *"Every agent in the team needs frontier-class model capabilities, not just the main agent. Each team member must independently decide when to message teammates, what to include, and when to report back. Models can message the wrong agent, forget to report completion, or get stuck in loops. Beyond model capability, there are infrastructure challenges: cycle detection (A waits on B, B waits on A), conflict resolution (two agents edit the same file), and shutdown coordination. Debugging is hard because message chains between agents are difficult to trace and failures cascade."*
* **DevolaFlow coupling**: **PERMANENTLY NOT SUPPORTED**. P5 (artifacts-as-contracts) explicitly forbids cross-agent shared state and direct messaging: per `repo-governance.mdc` §A-1 P5, *"Layers communicate through artifact files, not shared memory or conversation history. Each artifact has a defined schema. The producing layer writes; the consuming layer reads. No bidirectional shared state."* This is a Soul-level architectural commitment; reversing it requires a new SI-1 + ADR + W-21 2-cycle deliberation cadence per the W-21 Soul-set freeze governance contract. The article's own enumeration of Pattern 4's infrastructure challenges (cycle detection, conflict resolution, debugging difficulty) directly validates DevolaFlow's existing P5 stance.

### 3.5 — Cross-pattern principles (article §"Choosing a Pattern" — verbatim)

* **Start point** (verbatim): *"Start with Pattern 1. Most tasks that feel like they need a multi-agent system work fine with a well-prompted inline tool call."*
* **Model-capability ladder** (verbatim): *"Each step up requires a more capable model. Pattern 1 works with any model that can call tools. Pattern 2 needs a model that reasons about when to wait. Pattern 3 needs a model that tracks multi-agent state across turns. Pattern 4 needs frontier models for every agent. With a smaller or cheaper model, stay with Pattern 1 or 2."*
* **Result-collection delta** (verbatim): *"Result collection also changes across patterns. Pattern 1 returns results inline as a tool response. Pattern 2 batches results via `wait_agent`. Pattern 3 delivers results incrementally. Pattern 4 surfaces only what agents explicitly report back; everything else stays inside inter-agent conversations."*
* **Forward-looking principle** (verbatim, last paragraph): *"For patterns 2-4, `spawn_agent` always returns immediately and `wait_agent` collects results when the model decides to call it. The framework provides the tools. The model controls the orchestration. A task that takes 4 coordinated agents today may be solvable by a single agent with a better model tomorrow."*
