## §2 PV-02 — Predecessor summary delta-compression (hash-based dedup)

### §2.1 Problem statement

When a convergence round N>1 dispatches, the per-task `predecessor_artifacts[*].summary`
field often re-states content from round N-1's same predecessor. The receiver
reads identical text twice (once in round N-1's pred, once in round N's). The
LLM cache mostly absorbs this, but:

1. The dispatch payload is BIGGER than necessary, costing tokens at the L0
   prompt boundary.
2. Per-summary text duplication makes status-report diffing harder (the
   `delta` field gets noisy).

### §2.2 Mechanism

Add `dedup_predecessor_summaries(payload, round_num, prior_rounds) -> payload`
to `src/devolaflow/compressor/transforms.py`:

* **Round 1**: pass-through. No prior rounds means no dedup state. Returns
  the payload byte-identical to its input.
* **Round 2+**: for each `pred[i].summary`:
  - Compute `sha256(summary).hexdigest()[:12]` (12-char hash).
  - Look up in `prior_rounds[N-1].dedup_ledger` (if any).
  - If hit → replace summary with `"@round-N-1:pred-K"` reference.
  - If miss → keep verbatim AND emit a fresh ledger entry for round N.
* The ledger lives at top-level position 17 in `change_context`-adjacent
  layout: `predecessor_dedup_ledger: { round_num: int, entries: [...] }`.

### §2.3 Schema bump (lean-dispatch.yaml v5 → v6)

* `version: 5` → `version: 6`
* `canonical_order` length 16 → 17 (APPEND-ONLY per A-2.2)
* New position 17: `predecessor_dedup_ledger`
* Positions 1-12 (FROZEN PREFIX) UNTOUCHED.
* Positions 13-16 UNTOUCHED (`repos`, `behavioral_guidelines`, `acceptance_criteria_v2`, `change_context`).

### §2.4 Backward compatibility

* `predecessor_dedup_ledger` is OPTIONAL.
* Round 1 dispatches OMIT the field entirely (canonical absence-as-default).
* Round N>1 dispatches MAY omit when no dedup hit was found.
* Receiver-side: a payload WITHOUT `predecessor_dedup_ledger` continues to
  parse byte-identical to the v9.3.0 / v9.6.0 contract.

### §2.5 Expected gain (best-case)

* For convergence rounds 2-5, ~30-60% of pred summaries are exact duplicates
  of round N-1's same predecessor (empirical observation from v9.0.0 +
  v9.1.x reinforcement loops).
* Each dedup replaces a ~200-token summary block with a ~5-token reference.
* Estimated dispatch payload shrinkage: 4-12% per round-N≥2 dispatch.
* This does NOT directly affect any of the 4 measured `latency_harness`
  primitives (compressor latency stays the same; the gain is bytes-on-wire,
  not microseconds-on-CPU). It IS, however, a header-cache discipline gain.

## §3 PV-03 — Async wave dispatch auto-wire

### §3.1 Problem statement

v9.3.0 PV-05 shipped `AsyncDispatchExecutor` as a library — it has all the
asyncio.gather + Semaphore + per-task TaskOutcome capture machinery — but
NO call site in `src/devolaflow/feedback.py` actually invokes it. So when
a wave declares `mode: parallel`, the dispatcher still iterates tasks
serially (sequential `for task in tasks: dispatch(task)` shape).

### §3.2 Mechanism

In `src/devolaflow/feedback.py`'s wave dispatch path:

```python
# Pseudocode for the wire-in
if wave.mode == "parallel" and len(wave.tasks) > 1:
    from devolaflow.agent_workspace.dispatch_executor import AsyncDispatchExecutor
    executor = AsyncDispatchExecutor(max_concurrency=4)
    callables = [(task.id, lambda t=task: dispatch_one(t)) for task in wave.tasks]
    outcomes = executor.dispatch_parallel(callables)
    return [o.result for o in outcomes if o.succeeded]
else:
    return [dispatch_one(t) for t in wave.tasks]
```

### §3.3 P1 invariant preservation

Per S-1 / A-1 P1: dispatchers MUST NOT do work directly. The
`AsyncDispatchExecutor.dispatch_parallel` method only schedules
caller-provided callables. The L2 wave passes the per-task dispatch
prep callables in; the executor schedules them; the L3 Task agents
DO the work. P1 is preserved at every layer.

### §3.4 Expected gain

* Pre-wire: 4-task parallel wave pays `4 × 2 ms = 8 ms` of selector
  warmup + `4 × ~3 ms = 12 ms` of message compression + `4 × ~1 ms = 4 ms`
  of layout assertion = ~24 ms wall-clock per wave.
* Post-wire: with `max_concurrency=4` and `asyncio.gather`, the wall-clock
  collapses to `max(2, 3, 1) ≈ 3 ms` per primitive — a roughly **4× speedup**
  on a 4-task parallel wave. (Pre-LRU this saving was 800 ms; post-LRU it is
  ~21 ms, but the architectural pattern matters more than the absolute
  number — it unlocks future asyncio extension at every layer.)
* The cumulative dispatch latency improvement is small in absolute terms
  but >> 0 — and it's a correctness fix (the wave declared `mode: parallel`
  but executed sequentially, which violates the wave contract).

### §3.5 Risk surface

* `asyncio.run` cannot be called from within an already-running event loop.
  The wire-in MUST detect when called from inside an asyncio context and
  fall back to `dispatch_sequential` (matches the existing executor
  contract — `dispatch_parallel` already calls `asyncio.run` which raises
  if a loop is active).
* Sequential waves (mode != "parallel") are byte-identical to the v9.3.0
  / v9.6.0 path — no behaviour change.

## §4 PV-04 — Selector cache warmup (opt-in)

### §4.1 Problem statement

The v9.3.0 LRU cache on `load_profiles` / `load_skill_md` /
`estimate_tokens` is COLD on session start. A fresh `select_context(...)`
pays the full ~80 ms per cache miss for `load_profiles`. After 5 calls
the cache covers the steady-state pattern, but the first 5 dispatches
of a session experience a "warm-up tax."

### §4.2 Mechanism

Add `warmup_selector_cache()` to `src/devolaflow/task_adaptive_selector.py`:

```python
def warmup_selector_cache() -> None:
    """Pre-populate the LRU caches for the top-5 task_types × 3 round_nums.

    Runs once on first import-time call when DEVOLAFLOW_WARMUP=1 is set.
    Idempotent: the second call is a no-op (the LRU cache absorbs the
    repeats). Time budget: ≤ 500 ms wall-clock on a fresh import.
    """
    import os
    if os.environ.get("DEVOLAFLOW_WARMUP") != "1":
        return
    top_5_task_types = ("implement", "research", "design", "hotfix", "review")
    for task_type in top_5_task_types:
        for round_num in (1, 2, 3):
            try:
                select_context(task_type=task_type, round_num=round_num)
            except Exception:  # noqa: BLE001
                # warmup is best-effort — never block import on a transient failure
                continue
```

### §4.3 W-20 env-flag justification

Per `workflow-system/agent/references/env-flags.md` §7 W-20 checklist:

1. **Reuse-first**: does any existing `DEVOLAFLOW_*` flag activate the same
   surface? Surveyed 8 active flags (AGENT_WORKSPACE, RTK_PROXY, SI_CHIP_DEEP,
   etc.) — NONE activate selector cache warmup.
2. **R5 strict pattern**: yes — `os.environ.get("DEVOLAFLOW_WARMUP") != "1"`
   matches the v8.3.4 PV-04 RTK_PROXY pattern (env-var read EXACTLY `"1"`,
   no truthy-coercion).
3. **Behaviourally orthogonal**: yes — selector cache warmup has no overlap
   with workspace activation, command mapping, Si-Chip deep mode, etc.

→ **W-20 §3 orthogonality test: PASS. New flag justified.**

### §4.4 Expected gain

* Pre-warmup: first session dispatch pays 80 ms cold-cache miss for
  load_profiles + 5 ms for load_skill_md ≈ 85 ms cold-call cost.
* Post-warmup: the warmup runs once on session start (one-time 80-300 ms
  cost amortised across the entire session); first dispatch pays ~2 ms.
* Net: an N-dispatch session amortises the warmup over N calls; for N ≥ 4,
  warmup is a strict win (saves ~80 ms × (N-1) = ~240 ms on a 4-dispatch
  session, costs ~80 ms upfront).

### §4.5 Idempotency contract

* Calling `warmup_selector_cache()` a second time is a no-op (the LRU
  cache absorbs the repeated calls in O(1)).
* Calling without the env flag is a strict no-op (zero IO, zero CPU).
* Calling with the env flag in a stale Python process where the LRU
  cache is already populated is also a strict no-op (same hit path).
