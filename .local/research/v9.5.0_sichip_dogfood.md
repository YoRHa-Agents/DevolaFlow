## §3 — Why the per-file FAIL is NOT auto-actionable

Per the v9.5.0 user requirement ("genuinely effective ... tested gains BEFORE applying them"), an automated shrink based on Si-Chip's default budgets would be **premature**:

### 3.1 DevolaFlow already enforces a DIFFERENT budget regime (C-4 tiered line budgets)

DevolaFlow's canonical budget rule is **C-4 (Tiered Line Budget)** — measured in LINES, not tokens — with three tiers:

| Tier | Ceiling | Files | Si-Chip budget comparison |
|---|---|---|---|
| Default | < 500 lines | `SKILL.md` | Si-Chip: meta 100 + body 5000 tokens |
| Large | ≤ 1000 lines | `references/*.md` (10 files) | Si-Chip: meta 100 + body 5000 tokens |
| XL | ≤ 1600 lines | `examples/*.md` (3 files) | Si-Chip: meta 100 + body 5000 tokens |

The two budget regimes target **different skill profiles**:

* **Si-Chip's defaults** target lean BasicAbility skills (the typical Si-Chip-managed ability is ~100 tokens of frontmatter + ~5000 tokens of body — total ~5K tokens).
* **DevolaFlow's tiered budgets** target a 14-file workflow-orchestration meta-framework (total ~100K tokens spread across SKILL.md + 10 references + 3 examples). The size reflects the framework's complexity (4-layer agent hierarchy, 10 lifecycle hooks, 14 env flags, 5 SSOT registries, etc.).

A wholesale shrink to Si-Chip defaults would **delete operator-essential reference content** — every reference exists because some past PV's gap analysis identified an operator information gap. Per the user requirement, we MUST NOT auto-apply such cuts without operator review.

### 3.2 What WOULD be evidence-based action

The Si-Chip iteration_delta methodology (spec §23) is the right gate:

1. Capture a **with-ability baseline** — measure agent task success rates with the current SKILL corpus.
2. Propose a shrink (e.g. compress `env-flags.md` by 50%).
3. Capture a **post-change run** — measure agent task success rates with the shrunk corpus.
4. Compute `iteration_delta = after.composite - before.composite`.
5. Apply the change ONLY when `iteration_delta >= +0.10` (Si-Chip spec §23 default threshold, encoded in `devolaflow.si_chip_bridge.runner.DEFAULT_THRESHOLD`).

The PV-04 `post_skill_edit` lifecycle hook will perform exactly this gate when operators opt-in via `DEVOLAFLOW_SI_CHIP_DEEP=1`. The dogfood pass at PV-05 cut **cannot** complete the full cycle because:

* No real-LLM with-ability vs no-ability eval harness is available in the v9.5.0 CI environment (the v9.5.0 cycle deliberately stayed scoped to the bridge + lifecycle hook plumbing per the L0 dispatch).
* Generating the eval data is a multi-hour LLM-driven pipeline (per Si-Chip's `real_llm_runner_quickstart.md`) — out of scope for the cycle close.

The deferred-changes feedback doc (`.local/feedbacks/v9.5.0_sichip_deferred.md`) captures every Si-Chip per-file finding so operators can drive the eval cycle in a future iteration.
