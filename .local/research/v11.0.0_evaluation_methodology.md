# DevolaFlow v11.0.0 — Evaluation Methodology (small + large project benefit measurement)

> **Status:** L0 evaluation contract for v11.0.0 SI-1 planning gate
> **Author:** L0 Project Agent
> **Date:** 2026-05-04
> **Sister docs:** `v11.0.0_decomposition_plan.md`, `v11.0.0_admission_checklist.md`
> **Mandate:** every patch must demonstrate **measurable DF-internal benefit on BOTH small and large projects** before becoming a formal v11.0.0 patch (per user instruction 2026-05-04 "评测在大型项目和小型项目上都有明确收益才可以作为正式 patch 发布")

## §1 — Why two project sizes

DevolaFlow is a **workflow meta-framework** — its value depends on usefulness across project complexity tiers. A patch that benefits a 10K-line repo but harms a 100-line repo (or vice versa) is unsafe to ship as a default. The two-tier evaluation forces every patch to articulate its applicability bounds.

**Definition of project sizes** (DF-internal terminology, NOT external benchmarks):

| Tier | Size proxies | Test bed |
|----|----|----|
| **Small** | 1-3 source files, < 200 LOC, no plugins, no `.local/.agent/active/`, no rules.mdc | **synthetic_small_repo/** scaffolded by §3 harness |
| **Large** | 50+ source files, > 5K LOC, ≥ 4 plugins registered, complete `.cursor/rules/` + `AGENTS.md`, active research artifacts | **DevolaFlow itself** (this repo at v10.3.0) |

## §2 — Small project test bed: `synthetic_small_repo/`

Built by the harness `scripts/eval_v11/build_small_repo.py` (to be authored as part of v11.0.0 PV-01 if v11.0.0 cycle is approved). Layout:

```
synthetic_small_repo/
├── README.md           # 10 lines
├── pyproject.toml      # minimal Python pkg, version=0.1.0
├── src/synthetic/
│   ├── __init__.py     # __version__ = "0.1.0"
│   ├── core.py         # ~50 lines, 3 functions, 1 class
│   └── cli.py          # ~30 lines argparse
└── tests/
    └── test_core.py    # ~40 lines, 8 test functions
```

**Synthetic operations** (each evaluation runs a subset):

1. `init` — invoke `repo-init` workflow with `mode: core`
2. `feature` — invoke `feature-enhancement` workflow with 1-file scope
3. `bugfix` — invoke `hotfix` workflow with 1-line fix
4. `refactor` — invoke `refactoring` workflow with 1-method extraction
5. `docs` — invoke `documentation-only` workflow with README update

Each operation timed (wall clock) + measured (token count via `compressor` instrumentation; coverage via `pytest --cov`).

## §5 — Evaluation harness (per-direction)

Each L3 patch design (PDS §3 small_project_eval + §4 large_project_eval) MUST follow this template:

### Small project evaluation template

```markdown
**Synthetic test bed:** synthetic_small_repo (per `v11.0.0_evaluation_methodology.md` §2)
**Operations exercised:** [select from §2: init / feature / bugfix / refactor / docs]
**Metric collection:** [per §4.X bucket; list specific metric names]
**Expected delta (before → after):**
| Metric | Before | After | Δ | Direction |
|---|---:|---:|---:|:---:|
| <metric-1> | x | y | +/-z | improve/regress |

**Pass criterion:** [specific threshold, e.g., "Δ ≥ +10% on metric-1 OR Δ ≤ -5% with no regression on metric-2"]

**If no improvement on small project:** mark verdict = `CONDITIONAL_PASS` (large-only) or `FAIL`.
```

### Large project evaluation template

```markdown
**Test bed:** DevolaFlow self (this repo at v10.3.0 baseline)
**Metric collection:** [per §4.X bucket; specific metric names]
**Expected delta (v10.3.0 baseline → post-patch):**
| Metric | Baseline | Post-patch | Δ | Direction |
|---|---:|---:|---:|:---:|
| <metric-1> | x | y | +/-z | improve/regress |

**Pass criterion:** [specific threshold]

**Side-effect check:** [enumerate metrics that MUST NOT regress]
```

## §6 — Worked example (for L3 reference)

**Direction:** D-X-1 (Workflow template scaffold CLI)

**Small project evaluation:**
- **Operations exercised:** `init` (creates 1-file workflow `synthetic-test.yaml`)
- **Metric collection:** Steps-to-add-template (manual count)
- **Expected delta:**
  | Metric | Before | After | Δ |
  |---|---:|---:|---:|
  | Steps-to-add-template | 9 | 3 | -6 (66% reduction) |
  | Time to add 1 template | ~45 min | ~15 min | -30 min |
- **Pass criterion:** Δ ≥ -50% on Steps-to-add-template
- **Verdict if pass:** PASS small tier

**Large project evaluation:**
- **Test bed:** DevolaFlow self
- **Metric collection:** Steps-to-add-template + adapter build success
- **Expected delta:**
  | Metric | Baseline | Post-patch | Δ |
  |---|---:|---:|---:|
  | Steps-to-add-template | 9 | 3 | -6 |
  | `build-skill` success rate | 100% | 100% | 0 |
  | Test count delta (per use) | +6-8 | +6-8 | 0 |
- **Pass criterion:** Δ ≥ -50% on Steps-to-add-template AND no test count inflation per use
- **Side-effect check:** SKILL.md line count remains < 500
- **Verdict if pass:** PASS large tier

**Combined verdict:** PASS (both tiers) → admission verdict = PASS, tier = `core`

## §7 — Out-of-scope evaluations

Explicitly NOT measured for v11.0.0 admission:

- **EvoBench composite score / pass-rate / gap_score** — per user mandate
- **NineS overall composite delta** — informational only; NineS warnings (D-Q-1) tracked separately as a code-quality input not as a top-line evaluator
- **Si-Chip iteration_delta** — informational only; Si-Chip is one of the 4 plugins, not an admission gate
- **Wall-clock cycle duration** — too noisy across operator sessions
- **Subjective "developer happiness"** — replaced by quantitative steps-count + time-to metrics in §4.1

## §8 — Why this avoids the v9.5.0 OA-1 problem

The v9.5.0 cycle's "Si-Chip OA-1 blocker" was caused by relying on an **external eval pipeline** (with-ability/no-ability data) that DevolaFlow could not produce in-house. v11.0.0's evaluation methodology is **fully in-house**:

- Synthetic small repo built by DF (no external dependency)
- Large repo IS DF (no external dependency)
- All 30+ metrics in §4 are scriptable from current DF tooling (radon, pytest, ruff, grep, wc)
- Optional NineS / Si-Chip data treated as informational, not gating

This means v11.0.0 admission can run cleanly even if NineS / Si-Chip / RTK / ui-pro are all unreachable.
