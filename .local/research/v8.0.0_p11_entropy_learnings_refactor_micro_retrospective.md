## 3. What Was Deferred and Why

- **Out-of-scope file expansion: 14 files vs 6 owned — handled EXPLICITLY via 2-commit split (NOT silent).** The `f68710e coupling(P-11)` commit is the explicit, auditable record of the 7 invariant-pin files driven by AC5 + AC6. The commit body enumerates each file with the test name(s) that pin it, so a reviewer can audit "is this a strictly-necessary invariant tick, or is it scope-bleed?" for each one. **This is the cleanest scope-expansion pattern in the v8.0.0 cycle so far** — significantly cleaner than P-02's single-commit collapse (12 files, no separate coupling commit). P-03 / P-04 / future patches should default to this 2-commit pattern (`feat(...)` + `coupling(<patch-id>)`) when OOB files are forced by invariants.
- **`_parse_frontmatter` OSError edge — 3 uncovered lines (1% of `entropy_manager.py`).** Per coverage table footnote: *"`entropy_manager.py` — 99% (3 lines missing: `_parse_frontmatter` OSError)"*. Hitting these requires injecting an `OSError` mid-parse (e.g., a file deleted between `os.stat` and `open`); the deferral is intentional because (a) coverage is already 99% (well above the 80% floor), (b) the OSError path itself uses the same S-5 surfacing pattern as the rest of the module so we know it won't silently swallow, (c) writing the test would require either monkeypatching `pathlib.Path.read_text` or building a TOCTOU race fixture. **Action item for v8.x grooming**: add a single test using `pytest.MonkeyPatch.setattr(pathlib.Path, "read_text", raise_oserror)` to push coverage to 100% — low priority, no behavior change.
- **`learnings.py` legacy path stubs — coverage 92%, not 100%.** The remaining uncovered branches are pre-existing v7.x compatibility shims (e.g., the `if learnings_v1_format` legacy branch) that no current test exercises. Touching them would require either (a) adding a v1 fixture (tedious, low ROI), or (b) deleting the dead branches (out of scope for a refactor patch — would be a separate cleanup). **Deferred** to a future v8.x grooming patch; the 92% coverage is well above the CP-2 80% floor.
- **`check_drift.py` coverage 88%** — the missing 12% is the legacy CLI argument parsing that the new `entropy_manager.DeviationScanner` route bypasses. Same rationale as above — legacy entry point, not the new code path. Deferred.
- **CHANGELOG entry for P-11** — DEFERRED to **aggregate `[8.0.0]` rollup at S05 G1**, same pattern as P-01 / P-02 / P-13. The aggregate entry will reference P-11 by tag + 2-WARN closure + new template + new profile + 67-test addition.

The plan is for human invocation (or a higher-level orchestrator) to dispatch the template explicitly; auto-trigger is deferred to a future grooming patch (likely v8.1.0 candidate) that will add a `lifecycle/entropy_scan.py` periodic-trigger module.

## 4. Key Learnings

- **Two-commit `feat(...) + coupling(<patch-id>)` is the gold-standard pattern for OOB scope expansion.** P-11's `02d4ff8` + `f68710e` split made the 7 invariant-pin files completely auditable: each file in the coupling commit is justified by a named pre-existing invariant test. P-02 (which collapsed 12 files into 1 commit) is harder to bisect; P-03 / P-04 (with smaller OOB sets — 2 files each — collapsed into 1 commit each, acceptable for ≤2 OOB files but should still be considered for the 2-commit pattern). **Recommend codifying** in `.cursor/rules/devola-flow-rules.mdc` (or a new W-?? workflow rule): *"Any patch with ≥3 invariant-pin files outside its owned set MUST split into a `feat(...)` core commit + a `coupling(<patch-id>)` follow-up commit, with each coupling-commit file justified by a named test."*
- **2-for-1 closure (capability + cc-cleanup) is high-value when the surfaces overlap.** Pairing entropy gap 4.5 with the `learnings.py` cc-cleanup (Task A §7.2 决议 4) yielded 1 module + 2 cc closures + 1 template + 1 profile + 67 tests in a single 7-min merge cycle. The overlap was real because (a) `DeviationScanner` semantically supersedes `check_drift`, (b) `cleanup()` GC consumes the same `DocFreshnessReport` shape, (c) `entropy-cleanup` workflow needs a profile in the same `context_profiles.yaml` file. **Recommend** for v8.x: at SI-1 planning, look for "capability gap + cc-WARN in same module" pairs and merge them by default — saves merge-conflict surface and aligns the scope's intent.
- **`per-path errors surfaced, never silenced` is the right S-5 default for GC dispatchers.** `cleanup(dry_run=False)` returns `ApplyReport(errors=[...])` rather than swallowing or aborting on first error. This means a partial-success GC run (e.g., 18 of 20 files cleaned, 2 permission-denied) returns a structured report the orchestrator can act on, instead of a thrown exception that would obscure the partial progress. **Adopt** as the canonical pattern for v8.x cleanup / GC / batch APIs: *"return a structured report with per-item error surfacing; raise only on validation failure"*.
- **Pure-helper extraction with single-responsibility names beats multi-purpose helpers.** P-11's 7 extracted helpers (`_entry_ttl_valid`, `_entry_to_learning`, `_is_pinned_for_session`, `_merge_ranked_learnings`, `_resolve_last_accessed`, `_effective_half_life`, `_decay_formula`) each have a name that fully describes the predicate or transformation. This is the same `_resolve_X / _filter_Y / _apply_Z` triad pattern P-01's retro called out (`select_stages_for_runtime` 18→3) — applied here to a different shape (predicate / mapper / formula). **Reinforce** in v8.x cc-cleanup work: prefer 7 single-purpose helpers over 3 multi-purpose ones, because cc audits + future modifications both benefit from the smaller, named units.
- **SKILL.md headroom is precious — every patch must check before adding rows.** P-11 added 2 rows to SKILL.md (Quick Start row + Template Quick-Reference row), bringing it from 493 → 495 lines (under the SF-1 default 500 ceiling). Per patch plan §1 line 45: *"SKILL.md 仅 2 行 headroom (498/500, v7.5.0 P-03 cycle 释放 1 行); 凡触 SKILL.md 的 patch 必须 (a) 内嵌 lossless 压缩 OR (b) 把新内容下沉到 `references/`"* — P-11's +2 actually fits because the actual line count was lower than the patch plan's estimate (495 < 500), but every future SKILL-touching patch (P-08 ratchets +1 row per plan §S03) must do this same arithmetic check before claiming the headroom. **Action item for v8.x**: add a CI check `tests/test_skill_md_under_500_lines` (already exists per SF-1) emits the *delta* from 500 in its failure message so future planners see "you have N lines headroom" not just "≤500 OK".
- **Profile count `23 → 24` cascades to `workflow-system/human/demo/index.html` 3 times — codify the propagation list.** P-11 had to update the demo HTML in 3 places to reflect `profile_count` ticking. Each of those 3 edits is enforced by a single test (`test_doc_consistency.py::test_context_profiles_count`), so missing any one would have failed SI-10 step 1. **Recommend** authoring a `scripts/check_count_invariants.py` (future grooming patch, v8.1.0 candidate) that emits the full propagation list when any tracked count (template_count, profile_count, scenario_count, workflow_type_count) changes — would have replaced this patch's manual coupling enumeration with a single `python scripts/check_count_invariants.py --update template_count` invocation.
- **`context_profiles.yaml` line-range shift after a SKILL.md edit is a recurring pattern — formalize it.** P-11's coupling commit had to shift 17 `sections.lines` ranges in `context_profiles.yaml` because the SKILL.md row additions cascade into the line-anchored section extractions. This is exactly the kind of brittle line-anchor coupling that should eventually be replaced with section-anchor coupling (e.g., `section: "Quick Start — Workflow Selection"` instead of `lines: [137, 165]`). **Action item for v8.x architecture grooming**: replace `lines:` ranges with `section:` anchors in `context_profiles.yaml` to eliminate this entire class of forced re-shifts on every SKILL.md edit. Tracked as a candidate v8.2.0 SI-1 gap.
