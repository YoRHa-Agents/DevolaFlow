## Summary

- **decision:** **ACCEPT-WITH-CAVEATS**
- **confidence:** high
- **claimed perf gain (C-001):** 35–45% advisor *output* token reduction (advisor model responses, not L3 section)
- **measured/estimated perf gain:** plausible; advisor section *grows* +100 tokens (tiktoken) / +126 tokens (chars//4 fallback), but downstream advisor responses are expected to shrink ≥35% per the conciseness instruction (claim not directly measurable from this validation — requires EvoBench convergence-loop run with advisor calls instrumented)
- **claimed value (C-003):** "high signal for L3 agents" (no quantitative claim) — qualitatively addresses a real failure mode (silent advisor override)

The combined patch merges cleanly, preserves all existing tests, and is backward-compatible (opt-out via per-profile flags, defaults true). Two material caveats motivate the WITH-CAVEATS qualifier:
1. **Budget headroom is consumed.** All 4 advisor profiles run at 98.9–99.9% utilization after the patch, leaving ≤56 tokens of margin (tiktoken). Under the chars//4 fallback (when tiktoken is not installed — and it is *not* a `pyproject.toml` dependency), 3 of 4 profiles silently bump one `important`-priority section each.
2. **Dispatch metadata mismatches reality.** The dispatch and candidate-list refer to function `_build_advisor_section` (no such symbol exists; actual name is `_resolve_advisor_text`) and claim 6 advisor-enabled profiles (actual count: 4). These do not block the patch but should be corrected in the v7.2.0 PR-D description and in the candidate-list `integration_target` fields.

The recommended fix is a 4-line YAML budget bump in the same PR-D (Option A in `token_count.txt`).

## Evidence

### Token impact analysis (C-001 + C-003)

Three estimators evaluated; the selector uses `tiktoken` if available, `len(text)//4` otherwise. Exact counts in `.local/sandbox/v7.2.0/V01/token_count.txt`.

| Variant | tiktoken | chars//4 | Δ vs baseline (tiktoken) |
|---|---:|---:|---:|
| BASELINE | 33 | 33 | — |
| C-001 only | 55 | 59 | +22 (+67%) |
| C-003 only | 111 | 133 | +78 (+236%) |
| **C-001+C-003 combined** | **133** | **159** | **+100 (+303%)** |

**Critical reframing of the C-001 claim:** the candidate-list says "reduce advisor output tokens 35–45%". This refers to the advisor *model's response* (output tokens emitted by the advisor LLM when invoked), not the section's footprint inside the L3 prompt. The L3 prompt section actually *grows* +22 tokens for C-001 alone. Net cost-benefit at the system level:
- Cost: +22 tokens to every L3 prompt with advisor enabled (sustained).
- Benefit: ~35–45% reduction of each advisor *response*; for a typical 200–500-token advisor reply that is 70–225 tokens saved per call.
- Break-even: ≥1 advisor call per L3 dispatch session amortises the section growth several times over.

The claim is plausible but **must be reworded in the v7.2.0 release notes** to specify "advisor *response* tokens" not "advisor tokens" — otherwise readers will assume the L3 prompt shrinks (it does not).

**End-to-end simulation** (using the modified selector loaded from sandbox, against unmodified `context_profiles.yaml`):

| Profile | tiktoken-present: util%, sections, bumped | tiktoken-absent (chars//4): util%, sections, bumped |
|---|---|---|
| feature | 99.1%, 14/14, none | 100.0%, 14→14 (1 swap), `dispatch_report` bumped |
| refactor | 99.9%, 15/15, none | 100.0%, 15→14, `repo_mode` bumped |
| migration | 99.9%, 15/15, none | 100.0%, 15→14, `repo_mode` bumped |

`tiktoken` is **not** declared in `pyproject.toml` (`dependencies` or `dev`). It is used opportunistically inside `estimate_tokens()` via `try: import tiktoken; except: return len(text)//4`. ## Risks / Caveats

1. **Budget headroom risk under tiktoken-absent environments (HIGH).** Without tiktoken installed, the selector's `estimate_tokens` falls back to `len(text)//4 = 159 tokens` for the combined section, exceeding headroom in all 4 advisor profiles. Three profiles silently bump one `important`-priority section each (`dispatch_report` for `feature`, `repo_mode` for `refactor`/`migration`, `stage_primitives` for `security-audit`). `dispatch_report` in particular defines the L3 protocol contract — losing it from `feature` profile is a real degradation. **Mitigation:** bump `token_budget` by +200 for the 4 advisor profiles in the same PR-D (4-line YAML change; cost 1/5; fully reversible).

2. **Misleading framing of the C-001 perf claim (MEDIUM).** "35–45% advisor output token reduction" is true for the *advisor's response tokens*, but the L3 prompt section actually *grows* +22 tokens. The release notes and CHANGELOG must call this out precisely or readers will conclude the prompt shrinks (it does not). Net cost-benefit positive only if advisor is actually called.

3. **Function name discrepancy in dispatch / candidate-list (LOW).** The dispatch and candidate-list refer to `_build_advisor_section`; the actual symbol is `_resolve_advisor_text`. No code impact; a 1-line edit to the candidate-list `integration_target` for both C-001 and C-003 would close this.

4. **Profile name/count discrepancy in dispatch / candidate-list (LOW).** Claimed 6 advisor profiles vs actual 4. Names also mismatch (`refactoring` vs `refactor`, `security_audit` vs `security-audit`, `performance_optimization` vs `perf-optimization`, plus a non-existent `full_pipeline`). No code impact, but the v7.2.0 PR-D description should cite the correct list to avoid auditors looking for non-existent profiles.

5. **No new test coverage (MEDIUM).** The patch as-is does not add tests for the new conditional appends or the per-flag opt-out behaviour. CP-2 ("80% coverage floor") still met by existing tests (which still pass), but the new conditional branches are not exercised. The implementing PR-D agent should add at minimum:
   - `test_advisor_text_contains_conciseness_default` — flag default-on present.
   - `test_advisor_text_contains_timing_default` — flag default-on present.
   - `test_advisor_text_contains_reconcile_default` — flag default-on present.
   - `test_advisor_text_optout_per_flag` — each flag set false suppresses its block.
   - `test_advisor_section_token_growth_within_budget` — for each of 4 advisor profiles, post-patch `total_tokens <= budget`.

6. **Empirical advisor-response-reduction not measured here (LOW).** Validating the 35–45% claim requires running advisor calls under both wordings and counting response tokens. This validation only confirms the section text is emitted correctly; it cannot verify the downstream LLM response shrinks as claimed. EvoBench convergence-loop scenarios are the natural validation target — flagged for SI-4 benchmark gate at PR-D merge time.
