## 2. What Was Implemented

Single-commit patch (`7b4a75f`) modifying **5 files** (under the ≤6 owned-file ceiling per task contract): `+740 / -0` net diff (insert-only — same safest-possible-diff pattern as P-03). 5 owned files exactly per plan §3 P-04 lines 210-216.

**`gate/reinforcement.py::fence_to_instruction(fence_type, fence_payload, *, sequence=1, max_tokens=200, severity=None) -> ReinforcementRule`** NEW (verbatim from commit body):

- **Pure function, zero I/O.** Maps a single fence-check failure to a deterministic `ReinforcementRule`.
- **Deterministic id** format: `F-{type}-{seq:03d}` (e.g., `F-lint-001`, `F-test-002`, `F-build-001`). Same `(fence_type, sequence)` pair always renders the same id — the **defining contract** of "deterministic" expansion.
- **Severity table** `FENCE_DEFAULT_SEVERITY`:
  - `lint` → major
  - `format` → major
  - `typecheck` → critical
  - `test` → critical
  - `build` → critical
  (Caller can override via the `severity=` kwarg.)
- **Mandate format**: `"MUST fix {fence_type} error at {file}:{line}: {msg}"` (verbatim from PR #64 AC #1).
- **`max_tokens=200` truncation** — the mandate string is bounded so the W-8 / SI-9 5-rules-per-round cap stays under the lean-dispatch budget.
- **S-5 honored** — invalid inputs (missing file/line/msg, non-string fence_type, negative sequence) raise `ValueError` / `TypeError` rather than silently returning malformed rules.

**`gate/scorer.py::_evaluate_checks(gate_input, *, round_num, prior_score, target_score, severity_floor='major', extra_checks=None, max_tokens_per_rule=200) -> ReinforcementBlock | None`** NEW (verbatim from commit body):

- Walks the failing built-in checks (`build` / `test` / `lint`) and any caller-supplied extras (`format` / `typecheck` / ...).
- Returns `None` when nothing failed — **byte-identical pre-P-04 behaviour for callers that don't opt in** (AC #2 wording verbatim from patch_plan §3 P-04). This is the same `breaker=None` byte-identicality discipline P-03 codified, applied here to a different opt-in.
- Honours the **W-8 / SI-9 cap of ≤5 reinforcement rules per round** (the existing `MAX_REINFORCEMENT_RULES` constant is reused).
- Severity-floor filtering: rules below the `severity_floor` are dropped before the cap is applied — so a `format` failure (major) won't crowd out a `test` failure (critical) when both fire.
- Round-trip integration: rules emitted by `_evaluate_checks` flow through the existing `merge_reinforcement_into_dispatch()` pipeline → land under `dispatch.context.applicable_rules.reinforcement.rules[*]` in the round N+1 L3 dispatch (no new pipeline plumbing needed — just the existing reinforcement schema).

## 4. Key Learnings

- **Deterministic id format `F-{type}-{seq:03d}` is the linchpin of round-over-round reinforcement.** The same `(fence_type, sequence)` pair MUST always render the same id — this is what lets round N+1 deduplicate ("we already saw `F-lint-001`, drop the duplicate"), what lets the audit trail trace a single failure across multiple rounds, and what lets the W-8 / SI-9 5-rule cap deterministically prune. The `:03d` zero-pad is intentional so lex-sort matches numeric-sort up to 999 occurrences. **Adopt** as the canonical format for any future deterministic-instruction generator: `cycle_to_instruction` (P-06), `complexity_to_instruction` (P-09), `auto_ac_to_instruction` (P-10) should all use the `<prefix>-{type}-{seq:03d}` shape.
- **`pure function + zero I/O` is the correct shape for instruction generators.** `fence_to_instruction` reads no files, writes no files, calls no LLM, has no global state. This makes it (a) trivially unit-testable (40 tests, all pure-input → pure-output), (b) deterministic at the function level (same input always → same output), (c) cheap (no I/O latency in the hot reinforcement loop). **Reinforce** for v8.x: every `*_to_instruction` helper must be pure + zero-I/O; any I/O (e.g., reading the failing file's source line for context) must happen in the *caller* (`_evaluate_checks`), not the generator.
- **Returning `None` for "nothing to add" is the cleanest opt-in shape.** `_evaluate_checks` returns `ReinforcementBlock | None` — when nothing failed, it returns `None`, and the calling code at `evaluate_gate()` simply doesn't merge anything into the verdict. This is byte-identical pre-P-04 behavior for callers that don't opt in — the same `breaker=None` discipline P-03 used, applied here to a return value rather than a parameter. **Adopt** as the v8.x canonical pattern for opt-in gate features: parameters default to `None` (P-03), return values use `Block | None` for the empty case (P-04). Both produce byte-identical pre-existing behavior for non-opt-in callers.
- **Severity floor + cap = 2-stage deterministic pruning.** When fence failures fire, the W-8 / SI-9 cap (≤5 rules per round) needs deterministic pruning. P-04's two-stage approach: (1) drop everything below `severity_floor` (default `major`), (2) cap remaining at `MAX_REINFORCEMENT_RULES`. This guarantees critical findings (test/build/typecheck) are never crowded out by major findings (lint/format) — a desirable property for a circuit breaker. **Codify** in `references/execution-protocol.md` §9 (already done) and **reinforce**: any future reinforcement-emitter (cycle, complexity, auto-AC) must use the same severity-floor + cap pruning so the dispatch payload size stays bounded under realistic worst-case load.
- **Reference doc growth must be checked against tier ceiling.** P-04 added 29 lines to `references/execution-protocol.md` (now 578 / 1000 ≤ SF-1 Large tier ceiling). The patch_plan §3 P-04 line 216 had pre-computed this: *"≤30 行新增, 当前 478 行 + ≤30 = ≤508, 远低于 SF-1 Large tier 1000 行天花板"*. The actual post-patch count (578) exceeded the patch_plan estimate (508) by ~70 lines — meaning the file had grown by ~70 lines between when the plan was written and when P-04 was authored. **Action item**: pre-flight `wc -l` on every reference file mentioned in a patch plan, both at plan-write time AND at patch-author time, to detect intervening growth that could push a patch over its tier ceiling.
- **5 owned files vs ceiling 6 = the cleanest scope-discipline pattern.** P-04 is the most disciplined patch in the v8.0.0 W01-W03 cohort: no schema changes, no template count changes, no profile count changes, no public symbol exports, no allowlist additions, no demo HTML edits. The result is a ~11-min commit-to-merge cycle with zero coupling-commit overhead. **Recommend** as the v8.x gold-standard discipline: every patch should aim to confine itself to internal helpers + private integration functions where possible, escalating to schema / count / public-symbol changes only when strictly necessary. Patches in this shape are easier to review, easier to bisect, and easier to revert if a downstream regression is traced to them.
- **P-03 → P-04 sub-wave ordering worked perfectly.** Per plan §5 line 558, `gate/scorer.py` was a 3-way concurrent write target (P-03 adds `breaker` param + `evaluate_gate` integration; P-04 adds `_evaluate_checks` private function). The wave-internal sub-ordering (P-03 first, P-04 second) was strictly necessary to avoid same-file merge conflict. Both patches honored the discipline: P-03 only modified `evaluate_gate`; P-04 only added `_evaluate_checks` (a new private function). The ≈17 minutes between P-03 merge (17:02:28Z) and P-04 commit (17:19:10Z) is the wave-internal sequencing window. **Validate** the *"Wave-internal parallel + wave-between stack with sub-wave ordering for hot files"* topology design (plan §Overview line 43) — P-03 → P-04 within W2 is the proof point that disjoint-function-within-shared-file ownership genuinely enables sequential-but-fast merge.
- **97.47% project total coverage ≥ 80% floor with significant headroom.** The CP-2 floor is 80%; P-04 lands the project at 97.47%. The headroom matters because future patches (P-05 ladder, P-06 cycle, P-07 ratchet, P-08 behavioral, P-09 complexity, P-10 AC) will add more code, and starting each from a 97%+ baseline gives them room to add features without hitting the floor. **Reinforce**: every patch in v8.x should publish its post-patch `--cov-report=term-missing` summary in the commit body (P-04 did), so the cycle-end retrospective can track coverage trajectory across the 13 patches.
