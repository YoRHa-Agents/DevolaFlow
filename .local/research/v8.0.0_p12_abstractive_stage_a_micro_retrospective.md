## 1. Gaps Identified

`.local/research/tweet_analysis_harness_engineering_v7.8.md` §4.6 + `.local/research/v8.0.0_patch_plan.md` §1 capability table (line 62) jointly flagged **Abstractive Summarization Engine (Stage A)** as a **P2** gap — the 2-stage split into "heuristic Stage A" (this patch) + "LLM-assisted Stage B" (deferred to v8.2.0 PV-01) is itself a key architectural decision Task A made during the patch_plan phase. Per patch_plan §3 P-12 (line 457):

- Gap **4.6** (Abstractive Summarization Engine) — *"`summarise_predecessor(mode='abstractive')` 抛 `NotImplementedError` (compressor.py:1231)"* — at the v7.8.0 baseline, the compressor's predecessor-artifact summariser had a defined `mode='abstractive'` parameter slot but **no implementation**. Calling `summarise_predecessor(artifact_path, mode='abstractive')` raised `NotImplementedError`. The only working mode was `'extractive'` (line-by-line truncation to N chars). For long-context complex-feature artifacts (e.g., the 1200-line `tweet_analysis_harness_engineering_v7.8.md`), extractive mode burned predecessor budget on irrelevant lines and left no room for high-density entity preservation.
- Verbatim from `tweet_analysis_harness_engineering_v7.8.md` §4.6 (per patch_plan §3 P-12 line 459): the requirement is a **2-stage** abstractive engine: (Stage A) deterministic information-density routing — sections with low entity density collapse to ≤2-line key-phrase summaries; sections with high entity density preserve up to 5 lines with named entities (file paths, version strings, commit hashes, task IDs) intact; (Stage B) LLM-assisted full-rewrite with prompt template + 7 fallback modes — out of scope for v8.0.0, deferred to v8.2.0 PV-01.
- Stage A vs Stage B split rationale (per patch_plan §3 P-12 line 459 *"Stage A only — Stage B LLM-assisted 延后到 v8.2.0"*): Stage A is **deterministic** (zero I/O, zero LLM calls, zero cost) and can ship as a pure heuristic. Stage B requires LLM calls (latency + cost + non-determinism) and a fallback chain — too risky for the v8.0.0 cycle. Splitting them into two separate patches lets Stage A land in v8.0.0 immediately and Stage B accumulate operational data for v8.2.0.
- NineS finding delta: **0** for this patch (per patch_plan §3 P-12 line 473) — *"P-02 已清理 compressor cc 热点"* — P-02 (layered directed compaction, S01 W02 T01) had already refactored `summarise_predecessor` and split out helpers, so P-12 is purely additive on top of P-02's clean baseline. No NineS cc warning was ever attached to the abstractive code path.
- Critical-path role: P-12 is **not on the v8.0.0 critical path** (per patch_plan §5 line 547 *"反向 DFS 从 P-12: P-12 ← P-02 ← P-01 (链长 3)"* — chain length 3 vs critical path length 4). P-12's strategic value is **opening up long-context budget headroom** for downstream patches (and for v8.0.x users running L3 task agents on large predecessor artifacts).

## 4. Key Learnings

- **Stage A / Stage B split is the canonical pattern for "deterministic + LLM-assisted" features.** P-12 demonstrates this pattern: Stage A is **pure deterministic** (zero LLM calls, zero I/O, fully reproducible, fully unit-testable) and Stage B is **LLM-assisted** (latency + cost + non-determinism + fallback chain). Splitting them lets Stage A land **immediately** with full test coverage, while Stage B accumulates operational data and design refinement before its own dedicated cycle. **Adopt** for v8.x: any future feature that combines deterministic + LLM-assisted paths must split Stage A (deterministic) into a v8.0.x patch and Stage B (LLM) into a later v8.x patch with its own design doc in `.local/research/`. Do not ship combined Stage A+B in a single patch — the LLM call discipline (fallback, retry, cost ceiling) needs its own design + benchmark phase.
- **`_compute_information_density()` returning `[0.0, 1.0]` makes the routing decision trivially testable.** The 11 `TestComputeInformationDensity` unit tests cover the contract: empty text → 0.0, all-unique tokens → high, all-repeated tokens → low, all-entity → 1.0. The downstream `_summarise_low_density_section` / `_summarise_high_density_section` routing is then a single threshold compare (`density < 0.30`). **Codify** for v8.x: any "smart routing" decision must be backed by a pure scalar score (return type `float` in `[0.0, 1.0]`) so the threshold is empirically tunable and the routing test set is finite.
- **Defensive fallback to extractive preserves v7.x byte-stable behaviour for blank artifacts.** Verbatim from PR #67: *"Defensive fallback: empty Stage A output → automatic fallback to extractive (preserves v7.x byte-stable behaviour for blank artifacts)"*. This is the same `breaker=None` byte-identicality discipline P-03 / P-04 / P-05 / P-06 codified, applied here to the **output domain** (when Stage A produces empty output, fall back to extractive instead of returning empty). **Adopt**: every new optimization path must have a documented fallback to the legacy path; the fallback trigger must be a measurable condition (here: empty Stage A output) not a vague "if it doesn't work".
- **Top-level section in `context_profiles.yaml` keeps profile count at 24.** P-12 added the new `complex_feature` configuration as a **sibling** to `meta:` / `sections:` / `profiles:` rather than a new entry under `profiles:`. This preserves the profile count invariant (`tests/test_doc_consistency.py` checks count = 24) and keeps the existing 24 profiles' byte-stable shape. **Adopt** for v8.x: feature-flag-style configuration that doesn't cleanly fit a single profile should be added as a top-level sibling section, not as a 25th profile. The profile count invariant is a load-bearing test that prevents accidental profile additions during refactors.
- **Gitignored design doc in `.local/research/` is the v8.x convention for deferred-feature artifacts.** P-12 ships a 260-line Stage B design doc that is **gitignored** (`.local/` is gitignored) but **referenced** in the patch commit body. The v8.2.0 SI-1 planning gate will consume this artifact. **Codify**: future "split-feature" patches (v8.0.x P-XX with Stage B deferred) must include the deferred-stage design doc in `.local/research/` with a known filename pattern (`v<X.Y.Z>_p<NN>_<feature>_stage_<letter>_design.md`); the patch commit body must cite the doc path so future SI-1 gates can find it. Do not put deferred designs in the tracked `workflow-system/` or `src/` trees — they're research artifacts, not contracts.
- **+0.59pp on `long_context_repo_qa` is "no regression" not "the +3-5pp target hit".** The patch_plan §3 P-12 line 470 projected +3-5pp on `long_context_repo_qa`. Actual is +0.59pp. The patch correctly classifies AC #6 as PARTIAL-PASS rather than PASS because the dedicated `abstractive_vs_extractive.yaml` scenario (which targets the +3-5pp lift) is OUT of owned scope. **Document** this discipline for future patches: if a benchmark target requires a new scenario file, that scenario file must be in the owned scope OR the target must be classified as PARTIAL with a follow-up patch recommendation. Do not silently downgrade targets — make the deferral explicit in commit body / PR / retro.
- **Stage A Disjoint from P-08 within the same `compressor.py` file.** Per patch_plan §5 line 559: *"`compressor.py` 二方共写 (P-08 + P-12): P-08 仅 `assert_dispatch_layout()` 更新 (单函数), P-12 仅 `summarise_predecessor()` abstractive 分支 (单函数), 不同函数无冲突, 可并行"*. P-08 touched ONLY `assert_dispatch_layout` + `DEFAULT_DISPATCH_LAYOUT` (lines ~10 + ~5); P-12 touched ONLY `summarise_predecessor` + 4 new helpers (lines +309 / -17). Function-level disjoint ownership made the wave-internal sequencing trivial — same pattern as W2's P-03 → P-04 `gate/scorer.py` 3-way co-write. **Validate**: function-level disjoint ownership is the v8.x recipe for "same-file co-write within the same wave" — patches must explicitly partition the file by function, document the partition in the patch_plan §5 owned-files ledger, and verify the partition holds at commit time (no overlap of touched function names).
- **9-min commit-to-merge wall on a +743 LOC patch with new helpers + 37 tests + design doc is achievable.** P-12 matches P-05's 9-min cycle despite adding a brand-new feature (Stage A heuristic) plus a 260-line design doc for the deferred Stage B. The discipline that makes this work: (a) the patch_plan §3 P-12 pre-locked the 7 ACs (line 474-481), (b) the 4-helper architecture was pre-decided in patch_plan §3 P-12 line 461, (c) the Stage B design doc was the LAST artifact written (so it captures the lessons learned during Stage A authoring), (d) the EvoBench drift target was pre-classified as PARTIAL (so AC #6 didn't block merge). **Reinforce**: front-loading the contract + pre-classifying ambiguous ACs as PARTIAL with documented follow-up is what makes ≈10-min cycles achievable on substantive feature patches.
