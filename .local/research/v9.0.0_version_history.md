## Executive Summary

This retrospective documents **82 versions / pre-release variants (PVs)** spanning DevolaFlow v2.1.0 (2026-04-07) through v8.4.0 (2026-04-23) — roughly 17 calendar days of intense iteration aggregated from 5 era manifests authored in parallel by S01-T01..T05. The git ledger holds **77 annotated tags** starting at `v4.3.0` (the v2.x and most of the v3.x eras are CHANGELOG-only). The cycle delivered five named architectural inflection points: **v6.0.0 → v6.2.0** cemented the 4-layer agent hierarchy enforcement and the YAML-driven adapter registry (4 → 11 platforms); **v7.0.0** shipped the cache-layout invariant (`schemas/lean-dispatch.yaml#layout_invariant`) which became the load-bearing contract for all subsequent dispatch-schema additions; **v8.0.0** absorbed all 14 Karpathy "ChatGPT Vibes Engineering" primitives in a single 13-patch cycle; **v8.3.0** introduced the `.local/.agent/{active,handoff,archive}/` workspace primitive plus 4 new Soul/Architecture/Conventions rules (S-8, S-9, A-4, C-9); and **v8.4.0** capped the era with the RTK + fast-path memory router + shell-proxy quartet validating the single-source-of-truth registry pattern.

The headline metric trajectory shows **test count growth 254 (v3.0.0) → 822 (v5.4.0) → 1009 (v6.2.0) → 1525 (v7.7.0) → 3216 (v8.4.0)** (12.7× expansion across the documented window); **NineS composite plateaued at 0.7405 across v5.4.2 → v6.1.0 (7 versions, zero source changes), then jumped to 0.8805 at v6.1.1 via tool-config alone (+18.9% with no `src/` edits), and stabilised at 0.9050 across 6 byte-stable measurements during the v8.4.0 cycle**; **EvoBench scenarios grew 3 (v3.0.0 origin) → 17 (v3.3.0) → 25 (v4.2.0) → 30 (v5.4.0) → 39 (v7.3.0) → 48 (v8.4.0)**, with the >5% regression guard (W-4 / SI-4) operationally proven across more than 30 patch cycles before being lifted to a Soul-tier rule. The patch accept rate reached **49 / 49 = 100% lifetime** by the v8.4.0 rollup, sustained by the SI-1 8-mandatory-field-per-patch decomposition discipline that v9.0.0 must preserve.

### Era v2.x — Anomalies for S02 attention

- **Version-numbering jump (0.1.0 → 2.1.0)**: skips both v1.x and v2.0.0 in a single release. The `.local/feedbacks/feedback_for_v2.0.0.md` file asks for a release labelled v2.1.0 explicitly. Worth noting in the multi-version retrospective as the project's first non-monotonic version step.
- **EvoBench is born inside v2.x**: v2.2.0 introduces `/benchmarks/devolaflow_context/` and the W-4 / SI-4 benchmark regression guard's substrate. This is the cradle of every later regression baseline; downstream eras' "no regression vs. baseline" claims trace back to this release.
- **Acceptance Readiness Gate cradle**: v2.2.0 introduces `acceptance_readiness` gate type plus `acceptance_readiness_criteria` and `acceptance_readiness_threshold` on `GateInput` / `GateProfile`. Any later gate-module changes (W-11 / CP-4) build on this v2.2.0 surface.
- **SKILL.md compression milestone**: v2.2.0 records a 449 → 293 line reduction with "Zero degradation verified across 7 output types" and "254/254 tests pass, all 4 adapters verified". This is the earliest documented enforcement of the < 500-line tier ceiling that later becomes Rule C-4 / SF-1.
- **Lean message format origin**: v2.2.0's "Lean Message Templates" is the seed for what becomes Rule C-2 (`schemas/lean-dispatch.yaml`, `schemas/lean-report.yaml`) and the P6 cached-prefix invariant (Rule A-2). Worth tagging at S02 as the genesis of the inter-layer-protocol lineage.
- **Feedback-driven release loop**: v2.1.0 is documentary evidence that the feedback-file → release pipeline existed before any formal SI-1 planning gate. The feedback file is dated against v2.0.0 but explicitly names v2.1.0 as the implementation target — a one-cycle lead between user ask and release.

### Era v3.x → v5.x — v9.0.0-relevant Patterns

Five patterns observed in v3.x–v5.x that remain load-bearing in v8.x and should
inform v9.0.0 planning:

1. **Plan-mode hierarchy enforcement is a recurring failure mode** — first
   addressed in v3.2.0/v3.3.0 ("Plan Mode Hardening: rigid hierarchy
   constraints"), regressed and re-fixed in v3.6.0 ("P1 Dispatcher-Not-
   Implementer not enforced — root cause: 5 gaps in SKILL.md"), and reinforced
   again in v3.7.0 ("Plan template now embeds the 4-layer delegation model
   explicitly"). Even after v3.8.0 lifecycle hooks made enforcement
   "deterministic", the same drift was observed in v4.0.1's "L2 now reads
   `model_hint`" SKILL fix. v9.0.0 should expect this drift to recur and design
   regression tests that catch SKILL-level enforcement decay, not just runtime
   hook compliance — current Soul Rule **S-1** descends directly from this
   lineage.

2. **Verbatim / lean compression is a layered design, not a single feature** —
   the design accreted across 4 versions: v3.9.0 introduced declarative rules
   (`preserve_list`/`drop_list`, 3 intensity tiers in `lean-dispatch.yaml` /
   `lean-report.yaml`), v4.0.0 added `compression_intensity` dispatch field +
   `compression_defaults` per layer boundary, v4.1.0 added the runtime
   `compressor.py` validator + `format_compliance` EvoBench dimension, and
   v4.1.1 hardened it with edge-case tests. The lesson — schema → boundary
   defaults → runtime validator → benchmark dimension → robustness sweep — is
   the template currently encoded in **C-2** (Lean Message Format) and **C-3**
   (Verbatim Extraction). v9.0.0 should follow the same 5-step expansion when
   adding new compression-adjacent fields.

3. **Self-improving feedback loop has been the central engine of every
   convergence cycle since v3.9.0** — `feedback.py`
   (`FeedbackCollector`/`FeedbackAnalyzer`/`ProposalGenerator`) shipped with
   "max 3 proposals/workflow, confidence floor 0.7, scope lock, cooldown"
   guardrails, was bridged to the gate in v5.3.0 via
   `ProposalGenerator.generate_reinforcement()`, and the `gate/reinforcement.py`
   module from v5.1.0-pre then became the canonical injection point
   (`applicable_rules.reinforcement`, capped at 5 rules/round, severity-
   filtered). This is the runtime backbone of current rules **W-8** (Convergence
   Round Reinforcement) and **SI-9**. v9.0.0 should treat the
   feedback→reinforcement bridge as a load-bearing primitive, not an
   optional plugin.

4. **NineS belongs in research/iteration, not gate scoring** — v4.3.0
   explicitly corrected this: "NineS role correction: NineS repositioned from
   gate scoring tool to research/iteration tool. Removed `nines_provider` from
   gate advisor configs". v5.0.0 then completed the v2.0.0 CLI migration and
   added `run_self_improve_loop()`; v5.2.0 codified it as the SI-2 rule. The
   anti-pattern of routing NineS findings into the quality gate has been
   eliminated; v9.0.0 must keep this boundary intact (current rule **W-2** /
   **SI-2** explicitly scopes NineS to analysis + self-eval, never to gate
   composite). EvoBench (in this repo) remains the gate authority.

5. **EvoBench-driven release gating predates SI-4 by 5 minor versions** —
   established in v3.0.0 ("EvoBench Benchmark Suite ... baseline storage and
   regression detection"), expanded to 17 scenarios in v3.3.0 with hardened
   thresholds ("min_composite >= 80.0, max_noise_ratio <= 0.1, min_relevance >=
   0.8"), to 25 by v4.2.0, and to 30 by v5.4.0. The "no regression > 5%"
   discipline that v9.0.0 inherits as **W-4** / **SI-4** ("composite score must
   not drop >5% below baseline per scenario") was operationally proven across
   more than a dozen v3/v4 iterations before being lifted into a Soul-tier
   rule. v9.0.0 expansions of the benchmark suite should reuse the same
   3-step pattern: scenarios → recalibrate to ≤0% structural noise → tighten
   `min_composite` once converged.

## v9.0.0-Relevant Patterns (cross-era synthesis)

### 1. Single-source-of-truth registry pattern (RTK-mirrored — A-5 candidate)

**Lineage**: Born in v6.0.4 with `AdapterRegistry` + `DataDrivenAdapter` (4 → 11 platforms via YAML), matured in v6.1.2 with the `keep_sections` transform proving the "registry owns the data, all consumers delegate" shape, formalised in v8.4.0 PV-02/03/04 across `shell_proxy/registry.py::WHITELIST` + `memory_router/cache.py::MemoryCase` + `shell_proxy/commands.py::CommandMapping`. Per v8.4.0 retro §4.1 #5: *"consider documenting it as a 5th canonical Architecture Rule in v8.5.0 (provisionally A-5)"*. **v9.0.0 should formalize as Architecture Rule A-5** with a CI test that fails when a new whitelist/recipe surface is introduced without a single-owner module.

### 2. R5 strict zero-overhead env-flag opt-in (default discipline for v9.0.0+)

**Lineage**: Implicit since v3.9.0's "Lean Compression Rules" 3-intensity tiers (opt-in by intensity setting); explicit since v6.1.5 plan-mode `DEVOLAFLOW_PLAN_MODE` env var + marker file; matured in v7.0.0..v7.0.3 cycle's "opt-in → default-on after 3 versions of benchmark evidence"; reached its final form in v8.4.0 PV-02..PV-04 with **triple-layer codification** (unit `monkeypatch.setattr(Path, "read_text", watcher)` + integration full pytest pass byte-identical when env-flag off + EvoBench `*_disabled.yaml` scenario above floor 90). Per v8.4.0 retro §4.1 #4: *"make this the default for all opt-in features in v8.5.0+"*. **v9.0.0 should adopt as the default discipline for ALL new features** — no feature ships without (a) env-flag, (b) zero-IO when off, (c) byte-identical pre-PV tests, (d) EvoBench `disabled` scenario.

### 3. P6 cache-layout invariant additivity (v7.0.0 → v8.4.0 baseline-stable)

**Lineage**: Originated in v7.0.0 (`schemas/lean-dispatch.yaml#layout_invariant` 12-key canonical + `assert_dispatch_layout()` runtime validator + Rule 6 P6); proven additive across 5 successive schema generations (12 → 13 v7.2.6 `repos:` → 14 v8.0.0 P-08 `behavioral_guidelines` → 15 v8.0.0 P-10 `acceptance_criteria_v2` → 16 v8.3.0 PV-05 `change_context`); v7.0.0 + v7.3.0 byte-baselines STILL PASS at v8.4.0.
