## v9.0.0-relevant Patterns

Five patterns observed in v3.x–v5.x that remain load-bearing in v8.x and should
inform v9.0.0 planning:

1. **Plan-mode hierarchy enforcement is a recurring failure mode** — first
   addressed in v3.2.0/v3.3.0 ("Plan Mode Hardening: rigid hierarchy
   constraints"), regressed and re-fixed in v3.6.0 ("P1 Dispatcher-Not-
   Implementer not enforced — root cause: 5 gaps in SKILL.md"), and reinforced
   again in v3.7.0 ("Plan template now embeds the 4-layer delegation model
   explicitly"). Even after v3.8.0 lifecycle hooks made enforcement
   "deterministic", the same drift was observed in v4.0.1's "L2 now reads
   `model_hint`" SKILL fix. v9.0.0 should expect this drift to recur and design
   regression tests that catch SKILL-level enforcement decay, not just runtime
   hook compliance — current Soul Rule **S-1** descends directly from this
   lineage.

2. **Verbatim / lean compression is a layered design, not a single feature** —
   the design accreted across 4 versions: v3.9.0 introduced declarative rules
   (`preserve_list`/`drop_list`, 3 intensity tiers in `lean-dispatch.yaml` /
   `lean-report.yaml`), v4.0.0 added `compression_intensity` dispatch field +
   `compression_defaults` per layer boundary, v4.1.0 added the runtime
   `compressor.py` validator + `format_compliance` EvoBench dimension, and
   v4.1.1 hardened it with edge-case tests. The lesson — schema → boundary
   defaults → runtime validator → benchmark dimension → robustness sweep — is
   the template currently encoded in **C-2** (Lean Message Format) and **C-3**
   (Verbatim Extraction). v9.0.0 should follow the same 5-step expansion when
   adding new compression-adjacent fields.

3. **Self-improving feedback loop has been the central engine of every
   convergence cycle since v3.9.0** — `feedback.py`
   (`FeedbackCollector`/`FeedbackAnalyzer`/`ProposalGenerator`) shipped with
   "max 3 proposals/workflow, confidence floor 0.7, scope lock, cooldown"
   guardrails, was bridged to the gate in v5.3.0 via
   `ProposalGenerator.generate_reinforcement()`, and the `gate/reinforcement.py`
   module from v5.1.0-pre then became the canonical injection point
   (`applicable_rules.reinforcement`, capped at 5 rules/round, severity-
   filtered). This is the runtime backbone of current rules **W-8** (Convergence
   Round Reinforcement) and **SI-9**. v9.0.0 should treat the
   feedback→reinforcement bridge as a load-bearing primitive, not an
   optional plugin.

4. **NineS belongs in research/iteration, not gate scoring** — v4.3.0
   explicitly corrected this: "NineS role correction: NineS repositioned from
   gate scoring tool to research/iteration tool. Removed `nines_provider` from
   gate advisor configs". v5.0.0 then completed the v2.0.0 CLI migration and
   added `run_self_improve_loop()`; v5.2.0 codified it as the SI-2 rule. The
   anti-pattern of routing NineS findings into the quality gate has been
   eliminated; v9.0.0 must keep this boundary intact (current rule **W-2** /
   **SI-2** explicitly scopes NineS to analysis + self-eval, never to gate
   composite). EvoBench (in this repo) remains the gate authority.

5. **EvoBench-driven release gating predates SI-4 by 5 minor versions** —
   established in v3.0.0 ("EvoBench Benchmark Suite ... baseline storage and
   regression detection"), expanded to 17 scenarios in v3.3.0 with hardened
   thresholds ("min_composite >= 80.0, max_noise_ratio <= 0.1, min_relevance >=
   0.8"), to 25 by v4.2.0, and to 30 by v5.4.0. The "no regression > 5%"
   discipline that v9.0.0 inherits as **W-4** / **SI-4** ("composite score must
   not drop >5% below baseline per scenario") was operationally proven across
   more than a dozen v3/v4 iterations before being lifted into a Soul-tier
   rule. v9.0.0 expansions of the benchmark suite should reuse the same
   3-step pattern: scenarios → recalibrate to ≤0% structural noise → tighten
   `min_composite` once converged.
