## §1 — Parallelization principles

**P1 P3 P5 contract** (per SKILL.md §"4-Layer Agent Hierarchy"):

1. **Disjoint file ownership per wave** — every L3 task agent in a wave writes to a unique file in `.local/research/v11.0.0_patches/<dir-id>.md`; zero file overlaps. Read-only access to source code (`src/`, `workflow-system/`, `tests/`, `.local/research/`) is unrestricted.
2. **Each L3 produces a typed artifact** — Patch Design Specification (PDS) document conforming to §3 schema below. The L0 (this conversation) reads ONLY the PDS summary, never the full source the L3 inspected.
3. **No inter-wave dependencies for the audit phase** — all 5 waves dispatch simultaneously. Synthesis (admission verdicts + v11.0.0 composition) is the only post-wave L0 work.

## §3 — Patch Design Specification (PDS) schema

Each L3 agent produces ONE markdown file per direction at `.local/research/v11.0.0_patches/<dir-id>.md`. Every file MUST contain the following 9 sections (in order). The synthesizer (L0) parses this exact schema.

```yaml
# PDS schema v1
sections:
  1. current_state:        # 50-150 words; what exists today + verbatim file path evidence
  2. patch_design:         # algorithm + files-touched list + API/CLI surface; 100-300 words
  3. small_project_eval:   # synthetic minimal repo simulation; method + expected metric delta
  4. large_project_eval:   # DevolaFlow self-evaluation; method + expected metric delta
  5. benefit_metrics:      # quantified before/after table (≥3 metrics); MUST be DF-internal (not EvoBench)
  6. admission_verdict:    # one of {PASS, CONDITIONAL_PASS, FAIL, DEFER}
                           # PASS = clear benefit on both small + large
                           # CONDITIONAL_PASS = benefit on one tier; needs follow-up
                           # FAIL = no measurable benefit OR negative side-effects
                           # DEFER = needs more data; recommend audit-only this cycle
  7. effort_estimate:      # S (≤0.5 PV) | M (1 PV) | L (2-7 PV); confirm/revise §3 estimate
  8. dependencies:         # list of <dir-id> this patch depends on; empty if standalone
  9. risk_register:        # 1-3 risks + mitigation; tag each with severity {minor, major, blocker}
```

The PDS file MUST end with a one-line **admission summary**:

```
ADMISSION: <verdict> | EFFORT: <S|M|L> | DEPS: <list-or-none> | TIER: <core|standard|stretch|defer>
```

Where TIER = recommended v11.0.0 inclusion tier:
- `core` = MUST be in v11.0.0 (clear cross-tier benefit + standalone)
- `standard` = SHOULD be in v11.0.0 (single-tier benefit OR shared deps)
- `stretch` = COULD be in v11.0.0 (lower priority; ship if cycle budget allows)
- `defer` = NOT in v11.0.0; revisit in v11.1.0+

## §7 — Why these 5 waves (not 17 single-direction L3 tasks)

**Tradeoff:** 17 single-direction L3 spawns gives perfect file isolation but multiplies codebase-reading overhead 5x (each L3 reads SKILL.md + relevant references; the read cost dominates in audit-heavy work).

**5-wave design** allows each L3 to amortize codebase reading across 3-4 thematically-related directions. Wave themes are designed so the SAME source files (e.g., Wave 1 reads `scripts/sync_cursor_skill.py` for D-X-1 + D-X-2; Wave 5 reads `lifecycle/__init__.py` for D-Q-3 + D-C-3) get re-used.

**Risk** — bigger L3 prompts means each agent must hold more context. Mitigation: PDS schema is uniform; each direction's analysis is independent (L3 just authors 3-4 sequential PDS files within its wave).
